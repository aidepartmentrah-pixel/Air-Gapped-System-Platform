# 1. Introduction

## 1.1 Purpose of this Standard

The RAH Infrastructure Architecture defines the infrastructure model that supports software engineering, validation, deployment, and long-term operation within Al-Rassoul Al-Aazam Hospital (RAH).

It establishes the architectural boundaries, infrastructure roles, network environments, platform technologies, shared services, and operational infrastructure conventions used across RAH Lab.

Its purpose is to provide a stable infrastructure foundation that allows software and infrastructure systems to evolve without requiring each application or engineering team to redefine the environment in which it operates.

The architecture supports both Internet-connected engineering activities and the hospital's air-gapped production environment while preserving clear separation between development, validation, and production responsibilities.

This document serves as the primary architectural reference for infrastructure decisions within RAH Lab.

---

## 1.2 Scope

This architecture applies to computing infrastructure owned, managed, or used by RAH Lab.

It defines the architectural model governing:

- Online and Offline infrastructure environments.
- Physical and virtual infrastructure roles.
- Server and virtualization platforms.
- Network separation and connectivity boundaries.
- Debian-based server infrastructure.
- Docker runtime infrastructure.
- Approved database infrastructure.
- Shared infrastructure services.
- Engineering and offline validation environments.
- Operational application hosting.
- Standard operational filesystem namespaces.
- Infrastructure tooling used across deployed applications.
- The infrastructure foundation supporting the RAH Offline Infrastructure Platform (RAH-OIP).

This document defines **where systems operate and what infrastructure capabilities are available**.

It does not define:

- Application software architecture.
- Application engineering requirements.
- Application Release construction.
- Installation or update behavior of Application Releases.
- Detailed RAH-OIP release engineering.
- Routine operator procedures.
- Current machine-specific configuration.

These responsibilities are defined by their corresponding RAH standards, playbooks, operator documentation, and environment references.

---

## 1.3 Objectives

The objectives of the RAH Infrastructure Architecture are to:

- Establish a stable infrastructure model for RAH Lab.
- Maintain clear separation between engineering, validation, and production environments.
- Support secure operation within air-gapped hospital infrastructure.
- Standardize core server, virtualization, and container platforms.
- Provide predictable infrastructure for Docker-based applications.
- Define reusable infrastructure services shared across applications.
- Provide stable infrastructure roles independent of individual physical machines.
- Establish common operational locations and tooling used by deployed applications.
- Support independent Application Release and Infrastructure Release lifecycles.
- Simplify infrastructure maintenance and future expansion.
- Promote reliability, maintainability, reproducibility, and operational stability.
- Support long-term ownership of hospital systems without dependence on individual engineers or machines.

---

# 2. Infrastructure Philosophy

RAH Lab treats infrastructure as a coordinated engineering and operational platform rather than a collection of unrelated computers and servers.

The infrastructure exists to provide stable environments in which applications and supporting services can be engineered, validated, transferred, deployed, and maintained predictably.

The central architectural principle is the separation of **engineering activity** from **production operation**.

Software and infrastructure are prepared and validated within controlled engineering environments before approved release artifacts cross into the air-gapped production environment.

The Offline Production Environment hosts real hospital workloads and persistent operational information. It shall therefore not depend upon Internet connectivity, developer workstations, temporary release directories, or undocumented engineering state.

The infrastructure architecture should remain stable even when individual machines, software versions, or application implementations change.

---

## 2.1 Architectural Principles

RAH infrastructure follows these principles:

- Separate engineering, validation, and production responsibilities.
- Maintain physical or effective network isolation between Online and Offline environments.
- Treat production infrastructure as operational infrastructure rather than a development environment.
- Standardize common infrastructure capabilities wherever practical.
- Prefer reusable shared infrastructure services over unnecessary duplication.
- Keep application-specific engineering independent from infrastructure implementation where possible.
- Provide stable infrastructure identities and locations for long-lived operational state.
- Preserve persistent production information across application and infrastructure updates.
- Avoid dependence on temporary release locations or developer-machine configuration.
- Design infrastructure for long-term maintainability and controlled evolution.
- Allow infrastructure implementations to change without redefining the architectural roles they fulfill.

---

## 2.2 Infrastructure Layers

RAH infrastructure is organized into cooperating architectural layers.

### Physical Infrastructure

Provides the underlying:

- Workstations.
- Servers.
- Networking equipment.
- Storage resources.
- GPU resources.
- Other physical computing platforms.

Physical devices may be replaced or upgraded without changing the infrastructure role they perform.

---

### Virtual Infrastructure

Provides isolated execution environments used for:

- Infrastructure engineering.
- Offline validation.
- Application hosting.
- Database hosting.
- Shared infrastructure services.
- Other controlled workloads.

The current virtualization implementation is documented separately from the architectural role itself.

---

### Platform Infrastructure

Provides the standardized software foundation required by higher infrastructure layers.

Core platform technologies include:

- Debian Linux.
- Docker.
- Docker Compose.
- Approved database platforms.
- Virtualization infrastructure.

These technologies establish the common runtime environment used by applications and infrastructure services.

---

### Shared Infrastructure Services

Provides reusable capabilities that may be consumed by multiple applications.

Examples include:

- Database infrastructure.
- Speech-to-Text services.
- AI inference services.
- Shared GPU resources.
- Future authentication or other common infrastructure services.

Shared services should expose stable interfaces and remain operationally independent from individual applications where practical.

---

### Application Runtime Layer

Hosts persistent live application deployments.

RAH standardizes the operational application namespace as:

```text
/opt/rah/apps/
```

Each deployed application receives its own stable operational location:

```text
/opt/rah/apps/<app-slug>/
```

This location represents the live deployment state of the application and is independent of the versioned Release Package from which the application was installed or updated.

Application-specific persistent configuration and deployment state shall not depend upon retaining incoming release directories.

---

### Operational Documentation Layer

Human-facing operational knowledge is maintained separately from machine/runtime state.

The standard documentation root is:

```text
/opt/rah/documentation/
```

This directory exists in parallel with `/opt/rah/apps/` and serves as the operational Obsidian Vault for RAH Lab.

Conceptually:

```text
/opt/rah/
│
├── apps/
│   ├── application-a/
│   ├── application-b/
│   └── ...
│
└── documentation/
    ├── Applications/
    ├── Infrastructure/
    └── Operations/
```

The distinction is intentional:

```text
/opt/rah/apps/
    → machine-facing operational state

/opt/rah/documentation/
    → human-facing operational knowledge
```

The Application Release & Deployment Standard defines how deployment processes populate and maintain these locations.

---

### Operational Tooling Layer

RAH Lab uses standardized human-facing tools to inspect and operate deployed systems.

Current architectural tooling includes:

- **Obsidian** for operational deployment documentation.
- **DBeaver** for supported database inspection and administration.

Applications and release processes should integrate with these common tools where applicable so that operators do not need to rediscover deployment information independently for each project.

The exact implementation used to configure these tools belongs to release engineering rather than this architecture document.

---

## 2.3 Online and Offline Environment Model

RAH Lab uses two primary network environments:

### Online Engineering Environment

Supports activities requiring Internet access, including:

- Application engineering.
- Infrastructure engineering.
- Dependency acquisition.
- Source control access.
- Docker image construction.
- Technical research.
- Validation.
- Release preparation.

Development, test, synthetic, or other approved non-production databases may exist within this environment where required.

The architecture does **not** require an online replica of every production database in order to construct or validate an Application Release.

---

### Offline Production Environment

Hosts official hospital systems and persistent production information.

This environment:

- Remains isolated from the public Internet.
- Hosts approved application and infrastructure services.
- Hosts production databases and persistent application state.
- Provides internal network communication required by hospital systems.
- Receives only approved release artifacts through controlled offline transfer procedures.

Production applications shall remain functional without runtime dependence on public Internet resources.

---

### Offline Validation Environment

RAH Lab also maintains an air-gapped validation role used to reproduce relevant Offline Production conditions before release introduction.

Its purpose is to validate, where applicable:

- Offline installation.
- Offline updates.
- Infrastructure Releases.
- Application Releases.
- Package availability.
- Docker deployment.
- Runtime independence from the Internet.
- Operational access through representative network paths.

The current physical or virtual machine implementing this role is recorded in the RAH-OIP Lab Environment Reference.

---

## 2.4 Infrastructure Evolution

RAH infrastructure is designed to evolve incrementally.

Architectural roles should remain stable even when their current implementations change.

For example:

```text
Infrastructure Builder
```

may initially be implemented as a virtual machine and later move to a dedicated engineering server without changing its architectural responsibility.

Likewise, shared services may move between hosts as capacity and operational requirements evolve.

Infrastructure changes should preserve:

- Environment separation.
- Stable operational interfaces.
- Application compatibility.
- Persistent operational state.
- Release reproducibility.
- Maintainability.
- Recovery capability.

Future infrastructure capabilities may be introduced when operational requirements justify them, but speculative future systems should be maintained in planning or roadmap documentation rather than treated as part of the current authoritative architecture.

The purpose of this architecture is therefore to define a stable organizational model within which RAH infrastructure can evolve without requiring repeated redesign of the application and operational lifecycle.

# 3. Network and Environment Architecture

RAH infrastructure uses intentionally separated network environments to support engineering activities while protecting production systems and hospital operational data.

The architecture distinguishes between:

- the **Online Engineering Environment**;
- the **Offline Validation Environment**; and
- the **Offline Production Environment**.

These environments perform different roles and shall not be treated as interchangeable.

The Online Engineering Environment supports software and infrastructure engineering activities requiring external resources. The Offline Validation Environment reproduces relevant air-gapped conditions before production introduction. The Offline Production Environment hosts official hospital workloads and persistent production information.

---

## 3.1 Environment Overview

The infrastructure is organized around the following network roles:

```text
Online Engineering Environment
        │
        │ Approved release artifacts
        ▼
Offline Validation Environment
        │
        │ Approved offline transfer
        ▼
Offline Production Environment
```

This diagram represents the architectural progression of approved artifacts rather than direct network connectivity.

The Online and Offline environments do not communicate directly over the network.

Application Releases and Infrastructure Releases maintain their own engineering and validation lifecycles, but both cross into production only through approved offline transfer procedures.

---

## 3.2 Online Engineering Environment

The Online Engineering Environment supports activities that require Internet connectivity or access to external engineering resources.

Typical activities include:

- Application engineering.
- Infrastructure engineering.
- Source-control access.
- Dependency acquisition.
- Docker image construction.
- Development and functional testing.
- Customer or stakeholder validation.
- Database engineering using approved non-production data.
- Application Release preparation.
- Infrastructure Release preparation.
- Technical research and documentation.

The environment may contain:

- Engineering workstations.
- Online engineering virtual machines.
- Development databases.
- Application-validation services.
- Docker engineering environments.
- Other approved non-production services.

Development databases may be created or shared where useful, but the architecture does **not** require an online replica of every production database.

The required condition for release engineering is reproducible database initialization and migration, not duplication of production state into the Online Environment.

Real production patient information shall not be introduced into the Online Engineering Environment except through an explicitly authorized procedure.

---

## 3.3 Offline Validation Environment

The Offline Validation Environment provides an air-gapped environment for testing behavior that cannot be reliably validated while Internet access is available.

Its purpose is to reproduce relevant characteristics of the production environment before approved artifacts are introduced into production.

Validation may include:

- Offline package installation.
- Infrastructure Release installation.
- Application Release installation.
- Application update procedures.
- Docker image loading and startup.
- Database initialization and migration.
- Offline frontend asset behavior.
- Production-like network access paths.
- HTTPS and certificate behavior.
- Browser-dependent functionality.
- Verification scripts.
- Recovery procedures where applicable.

The environment should remain sufficiently representative of production conditions for the behavior being tested.

It is a validation environment, not the authoritative production environment, and shall not contain production operational state unless an explicitly approved validation procedure requires it.

---

## 3.4 Offline Production Environment

The Offline Production Environment hosts the official systems used for hospital operation.

It may contain:

- Application servers.
- Production Docker services.
- Production databases.
- Shared infrastructure services.
- Hospital workstations.
- GPU and AI services.
- Persistent application state.
- Operational documentation and administration tooling.

The Offline Production Environment:

- does not depend upon public Internet connectivity;
- processes real hospital operational data;
- receives only approved application, infrastructure, and supporting artifacts;
- maintains persistent production state;
- supports internal communication required by hospital systems.

Production systems shall not be used as general engineering environments.

Changes to production applications and infrastructure shall originate from the appropriate controlled release and deployment processes.

---

## 3.5 Environment Isolation and Transfer Boundary

The Online Engineering Environment and the hospital's offline environments are intentionally isolated.

There is no direct network path through which software, packages, configuration, or data automatically synchronize between them.

Approved artifacts cross the boundary using the hospital-approved offline transfer procedure and approved physical media.

Conceptually:

```text
Online Engineering
        │
        │  Application Release
        │  Infrastructure Release
        │  Approved supporting artifacts
        ▼
════════════════════════════════════
     Controlled Offline Boundary
════════════════════════════════════
        │
        ▼
Offline Validation / Production
```

The specific physical transfer medium may evolve over time and should be recorded in the current environment or operational reference rather than treated as a permanent architectural requirement.

The controlled boundary is the architectural requirement.

---

## 3.6 Internal Network Communication

Isolation from the public Internet does not mean that offline hospital systems operate independently from one another.

Devices and services within an approved environment may communicate through normal internal TCP/IP networking according to the hospital network architecture.

Typical internal communication may include:

```text
Hospital Workstation
        │
        ▼
Application Endpoint
        │
        ├────────► Application Backend
        │
        ├────────► Database Service
        │
        └────────► Shared AI / STT Service
```

Applications should communicate with required services through stable and documented service interfaces.

Environment-specific addresses, ports, and hostnames are configuration values and should not be treated as immutable architectural identities.

The current network addresses and machine-specific connectivity information belong to the RAH-OIP Lab Environment Reference or other controlled environment documentation.

---

## 3.7 Application and Infrastructure Release Paths

RAH distinguishes between two independently versioned artifact paths.

### Application Release Path

```text
Application Engineering
        │
Application Validation
        │
Application Release
        │
Offline Validation
        │
Approved Transfer
        │
Persistent Production Deployment
```

An Application Release installs or updates an application and ultimately establishes or modifies its live deployment under the standardized application runtime hierarchy.

### Infrastructure Release Path

```text
Infrastructure Engineering
        │
Infrastructure Release
        │
Offline Infrastructure Validation
        │
Publication / Approval
        │
Approved Transfer
        │
Offline Platform Installation or Update
```

An Infrastructure Release installs or updates capabilities of the RAH Offline Infrastructure Platform.

The two release types may interact through declared infrastructure prerequisites but remain independently versioned engineering artifacts.

Detailed release construction and operational deployment behavior are defined by their respective standards rather than by the network architecture.

---

## 3.8 Network Architectural Principles

RAH network and environment architecture follows these principles:

- Engineering and production environments remain separated.
- Offline production remains isolated from the public Internet.
- Offline validation reproduces relevant production constraints before deployment.
- Production data does not flow into online engineering environments without explicit authorization.
- Application Releases and Infrastructure Releases cross the environment boundary through controlled offline transfer.
- Internal hospital services may communicate normally within approved offline networks.
- Applications depend on configurable service locations rather than fixed machine identities.
- The architecture does not require an online production-database replica.
- Current IP addresses, hostnames, and hardware assignments remain reference information rather than permanent architecture.
- Network architecture supports infrastructure evolution without changing the fundamental security and operational boundaries.

# 4. Infrastructure Roles

RAH infrastructure is organized around stable functional roles rather than permanent assignments to individual physical machines or virtual machines.

A physical workstation, server, or virtual machine may be replaced, upgraded, consolidated, or divided into multiple systems while the architectural responsibility of its role remains unchanged.

This separation allows the laboratory to evolve its hardware without repeatedly redefining the infrastructure architecture.

Current machines, operating-system versions, IP addresses, hardware specifications, and role assignments are maintained in the **RAH-OIP Lab Environment Reference**.

---

## 4.1 General Engineering Workstation

### Purpose

Supports general engineering, documentation, planning, communication, and administrative work.

Typical responsibilities include:

- Technical documentation.
- Engineering planning.
- Project administration.
- Communication.
- General technical work.
- Light software engineering where appropriate.

This role does not define the authoritative application build or infrastructure-release environment.

---

## 4.2 Application Engineering Workstation

### Purpose

Provides the primary environment for software engineering and application release preparation.

Typical responsibilities include:

- Source-code engineering.
- Git operations.
- Local application development.
- Docker image construction.
- Docker Compose testing.
- Application integration testing.
- Database engineering.
- Offline-readiness engineering.
- AI-assisted development.
- Application Release preparation.
- Hosting engineering virtual machines where appropriate.

This role represents the primary application-engineering environment rather than a specific laptop or workstation.

---

## 4.3 Infrastructure Builder

### Purpose

Provides the Internet-connected Debian engineering environment used to build and maintain the RAH Offline Infrastructure Platform.

Typical responsibilities include:

- Collecting approved Debian packages and dependencies.
- Building and maintaining the offline APT repository.
- Preparing required infrastructure container images.
- Preparing installation and update tooling.
- Preparing verification tooling.
- Generating infrastructure-release documentation.
- Assembling Infrastructure Releases.

The Infrastructure Builder is an engineering environment and shall not become the authoritative offline production platform.

---

## 4.4 Air-Gapped Validation Environment

### Purpose

Provides a controlled offline environment in which Application Releases and Infrastructure Releases can be tested against relevant air-gapped conditions before production introduction.

Typical responsibilities include:

- Testing offline installation.
- Testing application updates.
- Validating Infrastructure Releases.
- Validating Application Releases where required.
- Loading and verifying container images.
- Validating database installation and migration.
- Testing offline runtime dependencies.
- Testing production-like network access.
- Executing verification procedures.
- Testing recovery behavior where appropriate.

This environment should remain isolated from the public Internet during offline validation.

---

## 4.5 Offline Production Platform

### Purpose

Hosts official hospital production workloads.

Typical responsibilities include:

- Production application hosting.
- Docker runtime services.
- Persistent application deployments.
- Production database services.
- Shared production infrastructure services.
- Internal application networking.
- Operational application state.

Only approved artifacts and controlled operational changes shall be introduced into this role.

The production platform shall not be used as a general development or release-construction environment.

---

## 4.6 Shared Database Platform

### Purpose

Provides relational database services that may be reused by multiple applications where the approved architecture calls for shared database infrastructure.

Responsibilities may include:

- Hosting independent application databases.
- Providing approved database connectivity.
- Supporting backup and recovery.
- Supporting database administration.
- Providing stable database infrastructure independent from individual application containers.

Applications may instead use approved project-specific database services where required.

The architecture therefore defines the **database-service role**, not a mandatory rule that every application must use one shared database server.

---

## 4.7 Shared AI and GPU Platform

### Purpose

Provides centralized computational resources and reusable AI services that would be inefficient or difficult to duplicate within individual application deployments.

Potential responsibilities include:

- Speech-to-Text.
- AI inference.
- Language-model inference.
- Medical image processing.
- Other approved GPU workloads.
- Shared AI APIs.

Applications should consume shared AI capabilities through documented interfaces rather than relying on the physical identity of the machine providing them.

---

## 4.8 Operator Workstation Role

### Purpose

Provides human-facing tools used to inspect, administer, document, and troubleshoot deployed systems.

Typical tooling may include:

- Obsidian.
- DBeaver.
- Browser access to hospital applications.
- Approved terminal or administration utilities.
- Other controlled operational tools.

This role is distinct from application engineering.

The operator should be able to use the standardized operational documentation and administration tooling without requiring the original developer's workstation or engineering environment.

---

## 4.9 Role Independence

Infrastructure roles define responsibilities; they do not permanently prescribe one machine per responsibility.

A single machine may temporarily implement multiple compatible roles, and a role may later move to dedicated infrastructure when scale or operational requirements justify it.

For example:

```text
Today:
Infrastructure Builder → Virtual Machine

Future:
Infrastructure Builder → Dedicated Server
```

The architecture remains unchanged because the responsibility remains the same.

Likewise:

```text
Today:
Shared AI Platform → One GPU Workstation

Future:
Shared AI Platform → Multiple GPU Servers
```

Applications should therefore depend upon documented service interfaces and infrastructure roles rather than current hardware assignments.

---

## 4.10 Role Reference

The stable infrastructure roles defined by RAH are:

|Infrastructure Role|Architectural Responsibility|
|---|---|
|General Engineering Workstation|Documentation, planning, administration|
|Application Engineering Workstation|Application engineering and release preparation|
|Infrastructure Builder|RAH-OIP and Infrastructure Release engineering|
|Air-Gapped Validation Environment|Offline application and infrastructure validation|
|Offline Production Platform|Official production application hosting|
|Shared Database Platform|Reusable database infrastructure where applicable|
|Shared AI / GPU Platform|Centralized AI and accelerated compute services|
|Operator Workstation|Human-facing administration and operational tooling|

The current system implementing each role shall be recorded separately in the RAH-OIP Lab Environment Reference.

# 6. Shared Infrastructure Services

RAH infrastructure may provide common capabilities as shared services when centralization improves maintainability, resource utilization, operational consistency, or long-term support.

Shared infrastructure services are distinct from individual application deployments.

Applications consume these services through documented and configurable interfaces rather than depending upon the physical machine, container, or internal implementation currently providing the capability.

The purpose of this chapter is to define the major categories of shared infrastructure available within the RAH architecture. Application-specific integration requirements remain the responsibility of the corresponding software and release documentation.

---

## 6.1 Database Infrastructure

RAH infrastructure supports relational database services required by hospital applications.

Microsoft SQL Server is the preferred relational database platform for internally developed applications, while approved applications may use other engines such as PostgreSQL when required by their architecture.

Database infrastructure may be provided through:

- a shared database server hosting logically independent application databases;
- a dedicated database service for a specific application;
- a project-specific database container;
- another approved database architecture.

The architectural requirement is not that every application use the same database engine or physical server.

Instead:

- each application shall clearly identify the database state it owns;
- database state shall remain persistent across application updates;
- database services shall support backup and recovery;
- database connectivity shall remain externally configurable;
- operator access shall be supported through approved database administration tooling.

An online replica of the production database is not required by the Application Release lifecycle.

---

## 6.2 Container Runtime Infrastructure

Docker is the standard container runtime used for application deployment within RAH infrastructure.

Docker infrastructure provides a common execution model for:

- application services;
- supporting services;
- validation environments;
- production deployments.

Docker Compose is used to describe and coordinate multi-service application deployments.

The infrastructure provides the runtime capability required by applications, while the application's own Docker architecture is defined by the Software Engineering Standard and its Application Release.

RAH infrastructure shall support stable application deployments under the standardized operational hierarchy:

```text
/opt/rah/apps/<app-slug>/
```

Container runtime infrastructure shall preserve the distinction between:

- replaceable application containers;
- persistent application state;
- shared infrastructure services.

The exact installation and update mechanisms used by Application Releases are defined outside this architecture document.

---

## 6.3 Shared Speech-to-Text Service

Speech-to-Text functionality may be provided as a centralized RAH infrastructure service rather than independently embedded into every application.

Applications consume the service through a documented interface.

A shared STT architecture can provide:

- centralized model management;
- consistent transcription behavior;
- reduced GPU duplication;
- independent model and infrastructure updates;
- simplified application integration;
- reusable access for multiple hospital systems.

Applications shall depend upon the service interface rather than upon the physical identity of the machine or GPU currently hosting it.

---

## 6.4 Shared AI and Accelerated Compute Services

AI capabilities that require substantial shared computational resources may be centralized within the Shared AI / GPU Platform.

Such capabilities may include approved workloads such as:

- AI inference;
- language-model inference;
- document processing;
- image processing;
- classification;
- other GPU-accelerated services.

Not every AI capability must become a shared infrastructure service.

Centralization should be used when it provides a clear architectural or operational advantage over application-local deployment.

Shared AI services should expose documented interfaces that allow their internal models, hardware, or implementation to evolve independently from consuming applications where practical.

---

## 6.5 Operational Documentation Service

RAH maintains a standardized human-facing operational documentation layer under:

```text
/opt/rah/documentation/
```

This directory serves as the operational **Obsidian Vault**.

Its purpose is to provide authorized engineers with a consistent location for understanding deployed applications and infrastructure without reconstructing information from:

- source code;
- Docker internals;
- old Release Packages;
- individual developer workstations;
- previous engineering conversations.

Application-specific operational documentation may include:

- deployed version information;
- deployment dates;
- application access details;
- database connection information;
- operational credentials;
- release history;
- backup information;
- deployment verification results;
- other information required for maintenance.

Because the Vault may contain sensitive operational information, it shall be treated as controlled infrastructure data.

The Application Release & Deployment Standard defines how application installation and update procedures populate and maintain this documentation.

---

## 6.6 Database Administration Tooling

DBeaver is the standard operator-facing database administration and inspection tool for supported application databases within the RAH environment.

Its architectural purpose is to provide a consistent interface for authorized engineers to:

- inspect databases;
- verify connectivity;
- perform approved database administration;
- troubleshoot application/database integration;
- access multiple supported database engines through a common tool.

Application deployments should integrate with the standardized DBeaver environment where applicable.

The architecture requires that relevant databases be operationally accessible through the approved tooling; the exact mechanism used by Application Release scripts to create, repair, or maintain DBeaver connections belongs to release engineering.

---

## 6.7 Backup and Recovery Infrastructure

RAH infrastructure shall support the protection and recovery of persistent operational state.

Backup targets may include:

- production databases;
- persistent application configuration;
- persistent application files;
- deployment configuration;
- operational documentation;
- infrastructure configuration;
- other state required for recovery.

Backup mechanisms may differ according to the service and database technology.

The architecture shall therefore ensure that persistent state is identifiable and recoverable rather than prescribing one universal backup mechanism for all systems.

Application and infrastructure updates that may affect persistent state shall operate with an appropriate recovery strategy.

---

## 6.8 RAH Offline Infrastructure Platform

The **RAH Offline Infrastructure Platform (RAH-OIP)** provides the standardized engineering and delivery mechanism used to establish and maintain Debian-based air-gapped infrastructure.

RAH-OIP may provide capabilities such as:

- curated offline Debian package repositories;
- approved infrastructure container images;
- infrastructure installation tooling;
- infrastructure update tooling;
- verification procedures;
- supporting infrastructure documentation;
- versioned Infrastructure Releases.

RAH-OIP is an infrastructure platform, not an Application Release.

Applications rely upon the infrastructure capabilities established by RAH-OIP but maintain their own independently versioned Application Releases.

The detailed engineering and lifecycle of RAH-OIP are defined by the **RAH Offline Infrastructure Platform Standard**.

---

## 6.9 Shared Service Design Principles

Shared infrastructure services should follow these architectural principles:

- Centralize functionality only where centralization provides a clear operational benefit.
- Keep shared services independent from individual application deployments where practical.
- Expose stable and documented interfaces.
- Keep application configuration independent from the physical machine hosting the service.
- Allow service implementations to evolve without unnecessary application changes.
- Preserve persistent state through appropriate storage and recovery mechanisms.
- Avoid introducing shared services solely because future reuse is theoretically possible.
- Document dependencies so applications can determine which infrastructure services must exist before deployment.

This approach allows RAH to gain the benefits of shared infrastructure without turning every application dependency into a centralized platform.

---

## 6.10 Service Evolution

Shared infrastructure shall evolve according to demonstrated operational requirements.

New services may be introduced when they provide measurable improvements in areas such as:

- maintainability;
- reliability;
- resource utilization;
- security;
- operational simplicity;
- reuse across applications.

Potential future services should remain in planning or roadmap documentation until they become approved architectural components.

Once a service becomes part of the implemented RAH infrastructure, its role and interfaces should be incorporated into the appropriate canonical architecture and operational documentation.

# 7. Infrastructure Technology Standards

This chapter defines the standard infrastructure technologies adopted by RAH Lab.

The purpose of these standards is to provide a common technological foundation across engineering, validation, and production environments while preventing individual applications from independently redefining laboratory-wide infrastructure choices.

The architectural roles and responsibilities of these technologies are defined in the preceding chapters. This chapter identifies the current standard technology associated with each infrastructure capability.

Technology standards may evolve through controlled architectural decisions when operational requirements justify a change.

---

## 7.1 Current Technology Baseline

|Infrastructure Capability|RAH Standard|
|---|---|
|Server Operating System|Debian Linux|
|Virtualization|Hyper-V|
|Application Container Runtime|Docker|
|Multi-Service Deployment|Docker Compose|
|Preferred Relational Database|Microsoft SQL Server|
|Approved Alternative Databases|Project-dependent when technically justified|
|Source Control|Git|
|Primary Source Collaboration Platform|GitHub|
|Operational Database Administration|DBeaver|
|Operational Documentation|Obsidian|
|Offline Infrastructure Platform|RAH-OIP|
|Offline Transfer|Hospital-approved physical transfer mechanism|

The exact installed versions, host assignments, IP addresses, and environment-specific configurations are maintained in the **RAH-OIP Lab Environment Reference** rather than in this architecture document.

---

## 7.2 Server Operating System

Debian Linux is the standard server operating system for RAH application and infrastructure workloads where technically appropriate.

Debian provides the common Linux foundation for:

- Docker hosts;
- application servers;
- infrastructure engineering environments;
- offline validation environments;
- shared infrastructure services.

Applications intended for RAH production should remain compatible with the Debian-based deployment environment unless an approved architecture explicitly requires another platform.

---

## 7.3 Virtualization

Hyper-V is the current standard virtualization platform used by RAH Lab.

Virtualization may provide isolated environments for:

- infrastructure engineering;
- offline validation;
- application hosting;
- database services;
- shared infrastructure services.

The architecture depends upon the **virtualization capability**, not permanently upon Hyper-V-specific implementation details.

A future change in virtualization technology may therefore be introduced through an approved infrastructure decision without redefining the roles described by this architecture.

---

## 7.4 Container Platform

Docker is the standard application container runtime.

Docker Compose is the standard mechanism for describing and coordinating multi-service application deployments.

Application container engineering requirements are defined by the **RAH Software Engineering Standard**.

Installation, update, persistent deployment behavior, and Application Release guarantees are defined by the **RAH Application Release & Deployment Standard**.

This architecture document therefore establishes Docker as the infrastructure platform without duplicating the application's container-engineering or release procedures.

---

## 7.5 Database Platform

Microsoft SQL Server is the preferred relational database platform for internally developed RAH applications.

Alternative database technologies, including PostgreSQL, may be used when:

- required by an existing application;
- technically justified;
- or approved as part of the application's architecture.

The infrastructure standard does not require an application to migrate databases solely to achieve technology uniformity.

Supported database platforms shall be capable of being:

- deployed within the approved RAH environment;
- backed up and restored;
- migrated safely;
- administered using approved tooling;
- maintained without public Internet dependencies.

DBeaver is the standard operator-facing database administration tool for supported database platforms.

---

## 7.6 Operational Documentation Standard

Obsidian is the standard human-facing operational documentation tool used by RAH Lab.

The standard Vault location is:

```text
/opt/rah/documentation/
```

This location contains controlled operational knowledge relating to deployed applications and infrastructure.

The architectural requirement is the existence of a standardized, discoverable, human-readable operational documentation system.

The exact Markdown organization and automatic generation mechanisms are governed by the Application Release & Deployment Standard and its engineering implementation.

---

## 7.7 Source Control Platform

Git is the standard version-control system used by RAH Lab.

GitHub is the primary online platform for source-code collaboration and repository hosting during application and infrastructure engineering.

Every production software project shall have an authoritative repository under RAH control or governance.

Detailed source-control practices belong to the RAH Software Engineering Standard rather than this architecture document.

Offline production systems do not depend upon GitHub connectivity during normal operation.

---

## 7.8 Offline Infrastructure Platform

RAH-OIP is the standardized platform used to establish and maintain Debian-based air-gapped infrastructure.

Its responsibilities include providing the offline infrastructure capabilities required for systems that cannot access public software repositories or container registries during operation.

Infrastructure Releases produced through RAH-OIP are independently versioned from Application Releases.

The detailed structure, engineering process, validation requirements, and lifecycle of Infrastructure Releases are defined by the **RAH Offline Infrastructure Platform Standard**.

---

## 7.9 Infrastructure Security Principles

Infrastructure technology shall be implemented in a manner consistent with the hospital's security and operational requirements.

Core principles include:

- separation of Online Engineering and Offline Production environments;
- protection of production data;
- controlled introduction of software and infrastructure changes;
- appropriate access control;
- controlled management of credentials and sensitive operational documentation;
- minimization of unnecessary external network dependencies;
- preservation of recovery capability.

Technology selection alone does not provide these guarantees. They must be maintained through the architecture, deployment standards, and operational procedures governing each system.

---

## 7.10 Technology Exceptions

Individual applications shall not redefine laboratory-wide infrastructure standards solely for developer convenience.

A project may use an alternative technology when:

- the existing application already depends upon it;
- migration would introduce disproportionate risk or engineering effort;
- the alternative provides a clear technical advantage;
- or another justified architectural requirement exists.

An exception should identify:

- the technology being substituted;
- the reason for the exception;
- operational consequences;
- deployment requirements;
- maintenance implications.

An approved exception becomes part of the application's architecture without automatically changing the laboratory-wide standard.

---

## 7.11 Infrastructure Evolution

Infrastructure technologies shall evolve through controlled architectural decisions rather than ad hoc project-level changes.

A standard technology may be reconsidered when another option provides meaningful improvement in:

- reliability;
- maintainability;
- security;
- compatibility;
- performance;
- operational simplicity;
- offline support;
- long-term sustainability.

When a standard changes, migration should preserve the stable architectural roles, operational interfaces, persistent state, and deployment compatibility defined by this document.

The objective is to allow RAH infrastructure to evolve technologically without repeatedly redesigning its operating model.
