#### The RAH Application Deployment Pipeline Uses

```text
1. Engineering Model
   - Treat database engineering, Dockerization, release engineering,
     and offline qualification as separate stages.
   - Preserve existing application behavior unless deployment requirements
     require a change.
   - Use the database platform already used by the application unless
     migration is explicitly requested.

2. Database Deployment
   - Reproducible fresh installation.
   - Version-controlled migration.
   - Safe lookup/reference/bootstrap handling.
   - Production-data preservation.
   - Validation, backup, and tested recovery.
   - Callable install / migrate / verify / backup / restore operations.

3. Application Dockerization
   - Debian/Linux-compatible application containers.
   - Production backend/frontend execution.
   - Docker Compose orchestration.
   - Externalized deployment configuration.
   - Stable application / Compose identity.
   - Explicit persistent-state handling.
   - Configurable internal hospital-service endpoints.
   - No required public Internet runtime dependency.

4. Application Release Engineering
   - Build one versioned RAH Application Release.
   - Package exact application Docker images and required offline assets.
   - Maintain a stable live deployment under:
     /opt/rah/apps/<app-slug>/
   - Keep release/staging material separate from live deployment state.
   - Provide one-command installation and update.
   - Preserve production configuration, credentials, certificates,
     databases, files, volumes, and deployment history during updates.
   - Integrate database initialization, migration, backup, and recovery.
   - Maintain operational documentation and operator access.
   - Produce manifest and checksums.
   - Freeze the artifact before qualification.

5. Offline Release Qualification
   - Test the exact frozen release in the Offline Debian Validation Environment.
   - Perform genuine clean installation.
   - Perform genuine Release N → Release N+1 update.
   - Verify persistent-state preservation.
   - Verify database migration and recovery.
   - Verify offline runtime behavior.
   - Verify LAN / HTTPS / browser capabilities where applicable.
   - Verify restart and release-folder independence.
   - Record evidence and return:
     QUALIFIED
     or
     FAILED QUALIFICATION

6. Core Deployment Rules
   - Never hardcode deployment-specific IPs, passwords, or machine paths.
   - Never recreate an operational database merely to perform an update.
   - Never treat production/business data as installation seed data.
   - Replace version-owned state; preserve deployment-owned state.
   - Do not make the live application depend on the incoming release folder.
   - Do not silently repair a frozen artifact during qualification.
   - Do not depend on public Internet access in the offline environment.
```

**§13a — Lifecycle Scripts Must Read the Configuration Template From Where the RAH Packaging Engine Actually Puts It, Not From Its Source-Tree Location**

The RAH Packaging Engine relocates a declared configuration template into the finalized Release's own `configuration/` directory as a fixed, universal rule — regardless of which subdirectory the template file lived in inside the application's own source tree (for example, a template kept alongside `compose/docker-compose.yml` in source is still packaged at `configuration/<template-filename>`, never at `compose/<template-filename>`). The Release manifest declares this real, actual path.

Do not write `install_offline.sh`/`update_offline.sh` (or an equivalent lifecycle script) to read the configuration template from a hardcoded path that merely mirrors its convenient location in the source repository. A script that assumes the template stays wherever it was authored — e.g. `$RELEASE_DIR/compose/.env.offline.template` — will fail the moment it runs against a Release actually produced by the Packaging Engine, with an error resembling `No such file or directory` for a file that is real, present, and correctly declared in the manifest, just under `configuration/` instead.

Read the configuration template from `$RELEASE_DIR/configuration/<template-filename>`, matching the manifest's own `configuration.template` field, not from an assumed source-tree-relative path. This rule applies only to applications whose Release is actually built by the shared RAH Packaging Engine (i.e., the application has a `.rah/` engineering-answers directory and is packaged via `rah package`/`rah construct`) — an application with its own independent, self-built release pipeline defines and is free to keep its own internally consistent convention, and forcing this rule onto it would be a regression, not a fix.

**§22a — Already-Installed Detection Must Survive Orchestrator-Rendered Configuration**

The RAH Offline Installation Platform, not only a human operator, may invoke this script. Per the RAH Offline Platform Specification, the Platform renders the production configuration file (`.env` or equivalent) into the canonical deployment path as a preparation step immediately before invoking `install_offline.sh` — for a fresh installation, not only for an update. The file existing on disk at the moment the script runs is therefore not evidence that a previous installation ever completed.

Do not use the mere presence of the rendered production configuration file as the "already installed" signal for this idempotency check.

Instead, base "already installed" detection on a dedicated completion marker written only at the end of a fully successful install or update — for example, an `INSTALLED_VERSION` file (already a documented persistent-state resource) written as the last step of a successful deployment. A configuration file existing without a corresponding completion marker indicates an interrupted or orchestrator-prepared deployment, not a completed one, and shall not cause the script to refuse execution.

Do not manually copy certificates.

Do not manually migrate the database unless the documented release workflow explicitly requires an unavoidable operator action.

Observe and record the complete update process.

---

# 30. Verify Update Targets Existing Deployment

Confirm that the update recognizes the existing application.

Verify that it does not create:

* another `/opt/rah/apps/...` version directory;
* a second unintended Compose project;
* duplicate application containers;
* duplicate database services;
* duplicate DBeaver connections.

The result must remain one continuously maintained application deployment.

---

# 31. Verify Persistent Configuration Preservation

After update, compare the deployment configuration with the pre-update state.

Confirm:

* production `.env` remains;
* existing values remain unless intentionally migrated;
* existing machine/service credentials remain;
* existing application secrets remain;
* newly required variables were introduced correctly where applicable.

Routine update must not behave like a new installation.

---

# 32. Verify Credential Preservation

Verify that update did not unintentionally regenerate:

* database passwords;
* application secret keys;
* internal service credentials;
* other persistent machine secrets.

Verify existing credentials still function.

Intentional credential rotation must be explicitly documented.

Unexpected rotation is a qualification failure.

---

# 33. Verify Database Migration

Record the database version/state before update.

Run the update.

Verify:

* correct migrations were applied;
* target database version is reached;
* existing representative data remains;
* intended data transformations are correct;
* lookup/reference changes are correct;
* relationships remain valid;
* backend operates against the resulting database.

Do not accept a database that was silently deleted and recreated.

---

# 34. Verify Persistent Business Data

Re-check every representative record created before update.

Confirm it still exists and is correct.

Verify application access to that data through normal application workflows where possible.

Database schema success alone does not prove data preservation.

---

# 35. Verify Persistent Files and Volumes

Where the application uses:

* uploaded files;
* attachments;
* generated reports;
* persistent local assets;
* other volume-backed state,

confirm that the pre-update test state remains intact.

---

# 36. Verify Container Reconciliation

Inspect Docker after update.

Confirm:

* target release image versions are running;
* stale old application containers do not remain unintentionally;
* failed containers from earlier attempts are not still controlling the deployment;
* removed services are gone;
* new services exist;
* persistent data volumes remain intact.

The final running service set must represent the intended target release.

---

# 37. Verify Certificate Persistence

Where HTTPS is applicable, compare the deployment certificate before and after update.

Confirm that a normal application update did not unnecessarily generate a new certificate.

Verify:

* same valid certificate identity/fingerprint remains;
* workstation trust remains valid;
* browser still accepts the origin.

If the release explicitly requires certificate rotation, validate the documented rotation behavior instead.

---

# 38. Verify DBeaver After Update

Open DBeaver after update.

Verify:

* connection remains available;
* connection works;
* no unnecessary duplicate connection was created;
* changed connection information was repaired where required.

If the older deployment intentionally lacked DBeaver registration, verify that the update brings it into compliance.

---

# 39. Verify Operational Documentation After Update

Open the application's operational documentation.

Verify:

* current release changed to the new version;
* update date is correct;
* database migration information is updated;
* current deployment information remains correct;
* credentials remain discoverable;
* certificate information remains correct;
* DBeaver information remains correct.

Most importantly:

**previous deployment history must still exist.**

The update must append history rather than replace it.

---

# 40. Verify Deployment History

Confirm a new history entry exists containing, as applicable:

* previous version;
* new version;
* update date;
* database migration;
* result;
* backup information;
* verification result.

Confirm initial-installation history remains present.

---

# 41. Verify Application Functionality After Update

Repeat representative smoke tests.

Verify that the new release:

* opens;
* authenticates;
* communicates with the backend;
* reads preserved data;
* writes new data;
* performs major workflows;
* communicates with internal services;
* supports required STT/AI functions;
* supports browser capabilities.

The update is not qualified if infrastructure updates correctly but the application is functionally broken.

---

# 42. Verify Offline Operation After Update

Repeat the offline-runtime checks.

A new release may accidentally reintroduce:

* CDN dependencies;
* public fonts;
* online model downloads;
* Internet package requirements.

Confirm the updated application remains fully usable under air-gapped conditions.

---

# 43. Verify Release-Folder Independence After Update

Make the new incoming update release directory unavailable after the update.

Then verify the updated live deployment remains operational.

This proves that the new release did not reintroduce a staging-directory dependency.

---

# 44. Verify Restart After Update

Restart the updated application.

Where appropriate, reboot the validation server.

Verify:

* updated application returns;
* database returns;
* preserved data remains;
* configuration remains;
* credentials remain;
* certificate remains;
* application features work.

---

# 45. Backup and Recovery Qualification

Where the release includes backup/recovery behavior, qualify it using non-sensitive validation data.

Test:

* database backup creation;
* backup location;
* backup artifact existence;
* restoration in a safe validation state;
* database usability after restoration.

Where application-level persistent files require backup, test the documented mechanism where applicable.

Do not claim recovery readiness merely because a backup script exits successfully.

---

# 46. Rollback Qualification Where Applicable

Determine the documented rollback strategy for this release.

Do not assume rollback means only loading old Docker images.

Where practical and safe, test the applicable recovery sequence.

Depending on the release, this may involve:

* restoring previous images;
* restoring previous Compose definition;
* restoring database backup;
* applying reverse migration;
* restoring persistent files;
* restarting the previous application version.

Verify that application and database versions become compatible again.

Where rollback cannot safely be executed automatically, verify that the documented recovery procedure is technically coherent.

---

# 47. Failure Injection Where Practical

Where safe, test selected predictable failure conditions.

Examples:

* stop the database temporarily;
* make a required internal service unavailable;
* simulate failed migration in a test copy;
* interrupt a non-destructive deployment step;
* leave a failed/stale application container.

Observe whether:

* scripts fail clearly;
* false success is avoided;
* diagnostics are understandable;
* retry/recovery behavior is sensible.

Do not perform destructive failure injection against valuable data.

# 49. Failure Classification

When a test fails, classify the failure.

Use categories such as:

## Release Defect

Examples:

* missing file;
* broken deployment script;
* wrong path;
* missing Docker image;
* broken update behavior;
* lost configuration;
* missing documentation.

## Application Defect

Example:

* application business functionality fails independently of deployment.

## Infrastructure Defect

Example:

* approved RAH-OIP component is broken.

## Environment Mismatch

Example:

* Validation VM does not represent the documented target environment.

## Test Limitation

Example:

* required external hospital shared service cannot currently be reproduced.

Explain the classification.

Do not repair a release defect and continue pretending the original artifact passed.

# 50. Qualification Failure Criteria

The release shall fail qualification if any mandatory requirement fails.

Examples include:

* release integrity/checksum failure;
* installation requires undocumented repair;
* canonical live deployment is not established;
* Compose identity changes with release folder;
* generated credentials do not work;
* persistent credentials are lost on update;
* production-style database data is lost;
* database is recreated during update;
* migration fails;
* stale containers survive incorrectly;
* DBeaver requirement fails;
* operational documentation is missing or wrong;
* history is destroyed;
* application requires public Internet access;
* required model is unavailable offline;
* HTTPS does not work where required;
* certificate trust is missing;
* microphone does not work where required;
* application functionality fails;
* restart destroys required state;
* recovery requirement cannot be satisfied.

A single critical mandatory failure is enough to prevent qualification.

---

# 51. Do Not Fix the Frozen Release In Place

If qualification discovers a release defect:

Do not change:

```text
<App>_Release_<version>/
```

and continue as though the original artifact passed.

Instead:

```text
Qualification Failure
        │
Document Defect
        │
Return to Application Release Engineering
        │
Correct Source/Release Engineering
        │
Produce New Corrected Artifact
        │
Reset Qualification Environment
        │
Qualify Again
```

Preserve the integrity of the qualification process.

---

# 52. Reset Between Qualification Cycles

When qualification must be repeated after a corrected release:

* restore the appropriate clean validation baseline;
* remove artifacts from the failed test where required;
* do not let previous manual repairs hide defects in the corrected release;
* re-run all affected tests.

Use the Golden Snapshot or other approved environment-reset mechanism where appropriate.

# 55. Definition of Qualified

An Application Release is qualified only when the finalized artifact has demonstrated, inside the Offline Validation Environment, that it can:

* install from a clean state;
* establish the canonical live deployment;
* operate independently of its release folder;
* operate without public Internet access;
* initialize its required database correctly;
* provide a functioning application;
* provide required operational documentation;
* provide required DBeaver access;
* operate through the intended LAN path;
* provide secure-browser functionality where required;
* survive normal restart;
* preserve persistent state;
* update a previous deployment using a separate release artifact;
* migrate the existing database without losing representative operational data;
* preserve production configuration and credentials;
* preserve certificates where applicable;
* update operational documentation and deployment history;
* reconcile application containers correctly;
* and provide a technically valid recovery path.

The final outcome of this prompt is:

> **Evidence that the frozen Application Release behaves correctly as a real offline installation and update artifact under production-like conditions—not merely that its source code, Docker images, or deployment scripts appear correct.**
