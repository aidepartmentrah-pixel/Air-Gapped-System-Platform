# Part 1 — Introduction

## 1.1 Background

The **RAH Offline Infrastructure Platform (RAH-OIP)** was established to provide a standardized methodology for engineering, validating, publishing, deploying, and maintaining infrastructure within the air-gapped environment of Al-Rassoul Al-Aazam Hospital (RAH).

The hospital operates two completely independent computing environments:

- **Online Engineering Environment**, where software and infrastructure are developed, tested, and prepared.
- **Offline (Air-Gapped) Production Environment**, where approved software systems operate without Internet connectivity.

While application development can be performed normally within the Online Engineering Environment, deployment to the Offline Environment introduces additional engineering challenges. Production systems cannot download operating system packages, install software from public repositories, or retrieve Docker images from online registries. Every required component must therefore be prepared, validated, versioned, and transferred through approved physical media before deployment.

Docker successfully solved one important part of the deployment problem by packaging applications together with their runtime dependencies into portable containers. However, Docker alone was insufficient for maintaining completely air-gapped systems. Offline environments also require operating system packages, infrastructure software, administrative utilities, installation procedures, verification scripts, and operational documentation that remain available without Internet access.

The RAH Offline Infrastructure Platform addresses these challenges by treating infrastructure as a versioned engineering product. Rather than manually preparing individual servers, RAH-OIP produces standardized infrastructure releases that can be repeatedly deployed, validated, updated, and maintained across multiple offline systems while ensuring consistency, reproducibility, and long-term maintainability.

---

## 1.2 Purpose

The purpose of this standard is to define the engineering methodology used to create, validate, publish, deploy, and maintain the **RAH Offline Infrastructure Platform (RAH-OIP).**

Specifically, this document defines:

- The architecture of the Offline Infrastructure Platform.
- The responsibilities of each engineering and production environment.
- The lifecycle of infrastructure releases.
- The validation workflow performed before publication.
- The deployment methodology for air-gapped systems.
- The preparation of offline operating system packages, Docker images, installation scripts, and supporting resources.
- Infrastructure versioning and release management.
- Long-term maintenance strategies for multiple offline systems.

The objective is to ensure that every infrastructure release can be reproduced, validated, deployed, and maintained consistently throughout its lifecycle while minimizing operational risk and eliminating dependence on external network connectivity.

---

## 1.3 Scope

The RAH Offline Infrastructure Platform provides a standardized infrastructure release containing all resources required to prepare and maintain Debian-based production systems operating within the hospital's air-gapped environment.

Each infrastructure release may include, but is not limited to, the following categories of components.

### Operating System Components

- Curated local Debian package repository.
- Infrastructure package dependencies.
- Approved operating system utilities.

### Container Platform

- Docker Engine.
- Docker Compose.
- Supporting container runtime packages.

### Infrastructure Services

- Remote administration tools.
- SSH utilities.
- System management utilities.

### Database Platform

- Database initialization resources.

### Development and Administration Tools

- DBeaver.

- wget.
- rsync.

### Application Platform

- Versioned Docker images for approved hospital applications.

### Validation and Deployment Resources

- Installation scripts.

The scope of this standard is limited to the engineering, validation, publication, deployment, and maintenance of the infrastructure platform itself. Application-specific software development, business logic, and individual software projects are documented separately and are considered consumers of the platform rather than components of this standard.

### Relationship to Application Releases

RAH-OIP provides the standardized offline infrastructure required to host and operate hospital applications. Individual hospital applications are distributed separately through versioned **Application Releases** and are not components of the Infrastructure Release itself.

An Infrastructure Release may provide shared platform components required by applications, including Docker, operating system packages, approved infrastructure services, administrative utilities, and shared infrastructure images. Application-specific Docker images, database migrations, deployment scripts, and application configuration belong to the corresponding Application Release.

Infrastructure Releases and Application Releases are therefore independently versioned engineering artifacts that may be transferred and deployed together when operationally required.

# Part 2 — Overall Architecture

## 2.1 Engineering Philosophy

The RAH Offline Infrastructure Platform is based on a single engineering principle:

> **Every infrastructure release should be reproducible, versioned, validated, and deployable without requiring Internet access.**

Achieving this objective requires treating infrastructure as an engineering product rather than as a collection of manually installed software components. Every infrastructure release is therefore engineered, validated, versioned, documented, and maintained using the same disciplined lifecycle applied to application software.

RAH-OIP extends the role of Docker by providing the remaining infrastructure required for air-gapped environments. In addition to application container images, every infrastructure release contains the operating system packages, infrastructure software, installation scripts, verification procedures, administrative utilities, and documentation necessary to prepare an offline Debian system without accessing external repositories.

Another fundamental principle of the platform is **validation before publication**. Every infrastructure release must first be installed and verified within a controlled Offline Validation Environment that accurately reproduces the hospital's air-gapped infrastructure. Only after successful validation may the release be approved for production deployment.

This engineering methodology transforms infrastructure deployment from a manual installation activity into a standardized release engineering process, enabling reliable deployment, controlled updates, simplified maintenance, and long-term sustainability across multiple offline systems.

RAH-OIP is responsible for the **platform required to operate applications**, not for the lifecycle of individual applications themselves. Application software is delivered through independently versioned Application Releases. This separation allows the infrastructure platform to evolve independently from the hospital applications that consume it.

## 2.2 System Architecture

The RAH Offline Infrastructure Platform separates development, release engineering, validation, and production into independent environments. Each environment has a single well-defined responsibility, ensuring that infrastructure releases are created, validated, and deployed in a controlled and reproducible manner.

The validation environment represents a faithful simulation of the hospital's production infrastructure. Every infrastructure release must successfully complete the validation workflow before being published. Failed validation requires the release to return to the release engineering environment for correction and re-validation.

# Part 3 — Release Engineering

## 3.1 Infrastructure Release

The **Infrastructure Release** is the fundamental deployment artifact of the RAH Offline Infrastructure Platform.

An Infrastructure Release represents a complete, versioned, and validated distribution containing every component required to deploy or update approved Debian-based infrastructure within the hospital's air-gapped environment.

Unlike individual installation scripts or software packages, an Infrastructure Release is treated as a single engineering product. Every release is built, validated, archived, and published as one immutable unit.

Each published release shall contain:

- Infrastructure software packages
- Curated local Debian repository
- Docker container runtime
- Approved infrastructure and shared-service Docker images, when required
- Installation and verification scripts
- Documentation
- Release metadata
- Validation artifacts

An Infrastructure Release is first created within the Release Engineering Machine (Online Debian VM), validated using the Offline Validation VM, and only after successful validation is it approved for publication and deployment to the hospital environment.

# Part 5 — Validation Standard

## 5.1 Offline Validation VM

The **Offline Validation VM** is the controlled testing environment used to validate every candidate RAH Offline Infrastructure Platform release before it is published.

Its purpose is to imitate the real hospital air-gapped Debian environment as closely as possible while remaining inside the Lenovo engineering laboratory. It exists to reduce the time, risk, and manual effort required to test infrastructure releases before transferring them to the real offline hospital environment.

The Offline Validation VM must operate without Internet access. It must not be able to run `apt update` from public repositories, download files from GitHub, pull Docker images from Docker Hub, or access external package sources.

The Offline Validation VM is allowed to receive files only from the Release Engineering Machine using controlled local transfer methods such as SSH and SCP.

The Offline Validation VM represents the final technical gate before publication. If a release fails in the Offline Validation VM, it must be corrected in the Release Engineering Machine and tested again. A release that does not pass validation in the Offline Validation VM must not be copied to DVD or deployed to the hospital environment.

---

## 5.2 Snapshot Policy

Every validation cycle shall begin from a clean baseline snapshot of the Offline Validation VM.

This baseline snapshot is called the **Golden Snapshot**.

The Golden Snapshot represents the expected starting condition of a clean offline Debian server before the RAH Offline Infrastructure Platform is installed.

The Golden Snapshot should include only:

- Clean Debian installation
- Required user account
- SSH access from the Release Engineering Machine
- No Internet access
- No Docker installation, unless explicitly documented as part of the baseline
- No previously installed RAH-OIP components

Before every validation run, the Offline Validation VM must be restored to the Golden Snapshot.

This policy is mandatory.

The purpose of this rule is to ensure that every validation run starts from the same known system state. This prevents false success caused by files, packages, services, or configuration left over from previous tests.

A release is not considered properly validated if it was tested on a dirty or previously modified validation VM.

---

## 5.3 Automatic Testing Procedure

The validation procedure should be executed from the Release Engineering Machine against the Offline Validation VM.

The testing process shall follow this sequence:

```
Restore Offline Validation VM to Golden Snapshot
        │
        ▼
Boot Offline Validation VM
        │
        ▼
Confirm SSH access
        │
        ▼
Copy candidate release using SCP
        │
        ▼
Extract release package
        │
        ▼
Run installation procedure
        │
        ▼
Run verification procedure
        │
        ▼
Collect logs
        │
        ▼
Generate validation report
        │
        ▼
PASS / FAIL decision
```

The candidate release shall be transferred using SSH/SCP from the Release Engineering Machine to the Offline Validation VM.

The installation procedure must run using only files contained inside the candidate release. The Offline Validation VM must not download anything from the Internet during validation.

The validation procedure shall collect logs for:

- File transfer
- Archive extraction
- APT repository configuration
- Package installation
- Docker installation
- Docker Compose installation
- Docker image loading
- Infrastructure service installation
- Verification script execution
- System service status
- Error output

At the end of each validation run, a validation report shall be produced.

The report should identify:

- Release version
- Target Debian version
- Validation date
- Offline Validation VM name
- Installation result
- Verification result
- Failed step, if any
- Relevant error logs
- Final PASS or FAIL status

If validation fails, Claude or the release engineer must inspect the logs, correct the release in the Release Engineering Machine, restore the Offline Validation VM to the Golden Snapshot, and repeat the validation cycle.

---

## 5.4 Acceptance Criteria

A candidate Infrastructure Release is accepted only when all validation checks pass successfully inside the Offline Validation VM.

The release must satisfy the following acceptance criteria:

- The release transfers successfully to the Offline Validation VM.
- The release extracts successfully.
- The local APT repository is recognized by the offline system.
- Required package dependencies resolve without Internet access.
- Docker Engine installs successfully.
- Docker Compose installs successfully.
- Required utilities install successfully.
- Required infrastructure services install successfully.
- All required Docker images load successfully.
- Installation scripts complete without error.
- Verification scripts complete without error.
- Required system services start correctly.
- No installation step attempts to access the Internet.
- Logs and validation report are generated successfully.

A release is rejected if:

- Any installation script fails.
- Any verification script fails.
- Any dependency is missing.
- Any required Docker image is missing or fails to load.
- Docker is not operational after installation.
- The system requires Internet access to complete installation.
- The Offline Validation VM was not restored to the Golden Snapshot before testing.

The release may be published only after the validation report shows a final status of:

```
PASSED
```

Final principle:

> A release is not trusted because it was generated. A release is trusted only because it successfully installed and verified itself in the Offline Validation VM without Internet access.

## 6.3 Update Procedure

One of the primary objectives of the RAH Offline Infrastructure Platform is to enable long-term maintenance of air-gapped systems without requiring Internet connectivity.

This is achieved through the use of a **Curated Local APT Repository**, distributed as part of every Infrastructure Release.

Rather than downloading Debian packages directly from public repositories, the Release Engineering Machine collects and validates all required packages during the release engineering process.

These packages are then assembled into a curated local repository that becomes part of the Infrastructure Release.

During deployment, the offline system is temporarily configured to use this local repository as its package source.

Conceptually, the update process becomes:

```
Internet
        │
        ▼
Release Engineering Machine
        │
Collect Approved Packages
        │
Create Curated Local Repository
        │
Build Infrastructure Release
        │
Publish ZIP
        │
DVD
        │
Offline Production VM
        │
APT installs packages
from the local repository
instead of the Internet
```

From the perspective of the offline Debian system, package installation proceeds using the normal `apt` workflow.

The difference is that the package source is no longer an Internet repository but the curated repository contained within the Infrastructure Release.

This approach provides several engineering advantages:

- Automatic dependency resolution using APT.
- Consistent package versions across all production systems.
- Elimination of manual dependency tracking.
- Fully reproducible infrastructure installations.
- Version-controlled operating system packages.
- Repeatable updates for multiple offline virtual machines.

Every new Infrastructure Release contains an updated version of the curated repository appropriate for that release.

As newer platform versions are published, the curated repository evolves together with the platform, ensuring that infrastructure software, supporting utilities, and approved package dependencies remain synchronized across all hospital systems.

---

## Engineering Principle

The Curated Local APT Repository is not intended to replace the official Debian repositories.

Its purpose is to provide a controlled, versioned subset of Debian packages required by the approved RAH infrastructure platform.

This design ensures that every offline production system installs and updates from the same validated software source, making infrastructure deployment reproducible, auditable, and independent of Internet connectivity.

### Policy statement capturing the philosophy of the entire platform

> **Infrastructure updates are performed by publishing a new RAH Offline Infrastructure Release, not by manually copying individual packages or installation files.**

That single sentence establishes a very important engineering rule: **the release becomes the unit of deployment and maintenance**. From that point forward, the platform evolves through versioned releases rather than ad hoc fixes, which aligns perfectly with the release engineering model used throughout this document.

# Part 7 — APT Repository Philosophy

## 7.1 Introduction

One of the fundamental challenges of operating an air-gapped infrastructure is the inability to install or update software directly from Internet repositories.

In a standard Debian installation, software is installed using the Advanced Package Tool (APT). APT automatically locates software packages, resolves dependencies, downloads required files, and performs installation using repositories configured within the operating system.

This process assumes permanent Internet connectivity.

Within the hospital's air-gapped environment, this assumption is no longer valid. Production systems cannot communicate with public Debian repositories and therefore cannot install new software or resolve package dependencies after deployment.

The RAH Offline Infrastructure Platform addresses this challenge by replacing the Internet package source with a **Curated Local APT Repository** that is distributed as part of every Infrastructure Release.

---

## 7.2 What is APT?

APT (Advanced Package Tool) is Debian's package management system.

Its primary responsibilities are:

- Installing software packages.
- Removing software packages.
- Resolving software dependencies.
- Managing package versions.
- Performing software updates.

APT itself does not contain software.

Instead, it acts as a client that retrieves packages from one or more configured software repositories.

---

## 7.3 What is a Repository?

A repository is a structured collection of software packages together with metadata describing:

- Package versions.
- Dependencies.
- Compatibility.
- Installation information.

When a user executes:

```
apt install docker
```

APT searches the configured repositories, identifies all required dependencies, downloads the necessary packages, and performs the installation automatically.

The repository therefore serves as the software source from which APT retrieves packages.

---

## 7.4 Curated Local Repository

The RAH Offline Infrastructure Platform does not attempt to replicate the complete Debian repository.

Instead, every Infrastructure Release contains a **Curated Local Repository**.

The curated repository contains only the Debian packages required to deploy and maintain the approved RAH infrastructure platform.

Typical package categories include:

- Docker Engine
- Docker Compose
- Container runtime dependencies
- XRDP
- SSH utilities
- Git
- curl
- wget
- rsync
- tmux
- Database-related packages
- Other approved infrastructure utilities

Restricting the repository to approved packages provides several advantages:

- Smaller release size.
- Faster validation.
- Easier maintenance.
- Improved reproducibility.
- Controlled software versions.
- Reduced operational risk.

---

## 7.5 Bridging the Online and Offline Environments

The Curated Local Repository provides the missing bridge between the online engineering environment and the hospital's offline production environment.

The engineering workflow becomes:

```
Internet
        │
        ▼
Release Engineering Machine
        │
Collect Approved Debian Packages
        │
Build Curated Local Repository
        │
Package Infrastructure Release
        │
Validate Release
        │
Publish Release
        │
DVD / Approved Transfer Media
        │
Offline Hospital VM
        │
APT installs packages
from the Local Repository
```

From the perspective of the offline Debian system, software installation proceeds exactly as it would on an Internet-connected system.

The only difference is that package retrieval occurs from the Curated Local Repository contained within the Infrastructure Release rather than from public Debian servers.

This design allows infrastructure software to be installed, upgraded, and maintained using standard Debian tools while remaining completely independent of Internet connectivity.

# Part 8 — Release Governance

## 8.1 Introduction

Release Governance defines the engineering controls that ensure every Infrastructure Release is reproducible, traceable, and suitable for deployment into the hospital's production environment.

Every published release represents an immutable engineering artifact.

Once published, a release shall never be modified.

Any correction or enhancement requires publication of a new Infrastructure Release.

---

## 8.2 Validation Reports

Every validation cycle shall generate a Validation Report containing:

- Release version.
- Validation date.
- Target Debian version.
- Validation environment.
- Installation results.
- Verification results.
- Errors encountered.
- Final PASS or FAIL decision.

The Validation Report provides objective evidence that the release was successfully tested prior to publication.

---

## 8.3 Release Manifest

Every Infrastructure Release shall contain a machine-readable Release Manifest describing:

- Release identity.
- Component versions.
- Included packages.
- Docker images.
- Infrastructure services.
- Compatibility information.
- Validation status.

The Release Manifest acts as the authoritative description of the release.

---

## 8.4 Compatibility Matrix

Each release shall document the environments for which it has been validated.

The Compatibility Matrix should include:

- Supported Debian version.
- Docker version.
- Docker Compose version.
- PostgreSQL version.
- SQL Server container version.
- XRDP version.
- Target hardware architecture.

This information allows engineers to determine whether a release is compatible with a particular deployment environment.

---

## 8.5 Checksums

Every published Infrastructure Release shall include cryptographic checksums for all release artifacts.

Checksums provide assurance that:

- Files have not been modified.
- Transfer completed successfully.
- Deployment media has not been corrupted.

Checksum verification should be performed before deployment whenever practical.

---

## 8.6 Release Archive

All published releases shall be permanently archived.

The Release Archive provides:

- Historical record.
- Rollback capability.
- Engineering traceability.
- Regulatory evidence.
- Disaster recovery support.

Published releases shall remain immutable within the archive.

---

## 8.7 Naming Convention

Every release shall follow the standardized naming convention defined in this standard.

Consistent naming ensures:

- Unambiguous identification.
- Easier release tracking.
- Automated processing.
- Historical organization.

---

## 8.8 Immutability

An Infrastructure Release is immutable after publication.

No published release shall be edited, updated, or partially modified.

Any change, regardless of size, requires publication of a new version.

This guarantees that every release can always be reproduced exactly as originally validated.

# Final Engineering Principle

The RAH Offline Infrastructure Platform is not simply a collection of installation scripts, Docker images, or software packages.

It is a standardized, versioned, validated, and reproducible engineering platform for building, testing, publishing, deploying, and maintaining Debian-based infrastructure within completely air-gapped environments.

Every Infrastructure Release represents a complete, self-contained deployment artifact that includes the operating system packages, container platform, application images, installation procedures, verification procedures, and supporting documentation required to deploy and maintain approved hospital infrastructure without Internet connectivity.

By treating infrastructure as a version-controlled engineering product, RAH Lab establishes a reliable and repeatable methodology that supports long-term maintenance, controlled evolution, and consistent deployment across multiple air-gapped systems.

# One chapter worth keeping in mind

### 2.2.1 Engineering Laboratory

The Engineering Laboratory is the controlled development environment used to engineer, validate, and publish the RAH Offline Infrastructure Platform.

The Engineering Laboratory is intentionally isolated from the hospital production environment and provides the resources required to build and validate Infrastructure Releases before deployment.

Within the current implementation, the Engineering Laboratory consists of:

- Windows 11 Engineering Workstation
- Docker Desktop
- VS Code
- Git
- Online Debian VM (Release Engineering Machine)
- Offline Debian VM (Validation Environment)

The laboratory separates infrastructure engineering into independent environments with clearly defined responsibilities:

- The Windows Engineering Workstation develops hospital applications and builds Docker images.
- The Online Debian VM prepares Infrastructure Releases.
- The Offline Validation VM validates candidate releases under simulated air-gapped conditions.

No Infrastructure Release may be deployed to the hospital without first passing through the Engineering Laboratory validation process.

The exact hardware used to host the Engineering Laboratory may evolve over time; however, the engineering workflow and responsibilities defined by this standard remain unchanged.
