# 1. Introduction

## 1.1 Purpose of this Standard

The RAH Lab Software Development Standard defines the engineering principles and technical requirements that software systems must satisfy when they are developed, maintained, or prepared for deployment within Al-Rassoul Al-Aazam Hospital (RAH).

Its purpose is to establish a common engineering model that allows software developed by different developers, at different times, to remain compatible with the RAH Lab development, release, deployment, and operational environment.

The standard defines how applications should be engineered so that they can be built reproducibly, containerized, configured externally, deployed through standardized mechanisms, updated without reconstructing their operational state, and maintained independently of their original developers.

This standard serves as the primary technical reference for **application engineering within RAH Lab**.

---

## 1.2 Scope

This standard applies to all software projects developed, received, maintained, or prepared for deployment by RAH Lab, regardless of whether they originate from internal engineers or external developers.

It defines the engineering requirements applicable to:

- Development environments.
- Source code management.
- Application architecture.
- Docker containerization.
- Environment and deployment configuration.
- Database engineering.
- Release engineering readiness.
- Project delivery and technical handover.

This document defines **how software must be engineered to support the RAH deployment model**. It does not define the complete operational behavior of an Application Release after publication.

Application installation, update behavior, live deployment structure, deployment history, operational documentation, and production release guarantees are governed by the **RAH Application Release & Deployment Standard**.

Project-specific business logic and user interface design remain the responsibility of the corresponding development team unless additional RAH requirements explicitly apply.

---

## 1.3 Engineering Philosophy

RAH Lab adopts a software engineering philosophy based on standardization, reproducibility, maintainability, automation, and long-term institutional ownership.

Software shall be engineered with the assumption that it will continue to evolve after its original developer is no longer involved.

Engineering decisions should therefore reduce dependence on:

- Individual developers.
- Undocumented configuration.
- Machine-specific assumptions.
- Manual deployment knowledge.
- Environment-specific source-code modifications.
- Interactive deployment procedures that must be rediscovered for every installation.

Applications should be portable across environments, deployable through standardized Docker-based infrastructure, configurable through external configuration, and compatible with the release and operational workflows adopted by RAH Lab.

The same application artifacts should progress from engineering to validation and production without requiring source-code modification or rebuilding for the target environment.

The laboratory follows the engineering principle:

> **Build Once. Validate Carefully. Deploy Repeatedly. Maintain Continuously.**

The application should not merely be capable of running inside Docker. It should be engineered so that installation, configuration, update, database evolution, verification, and operational maintenance can be performed through standardized and increasingly automated deployment mechanisms.

This philosophy enables RAH Lab to maintain sustainable software systems rather than isolated software projects.

---

## 1.4 Engineering Objectives

The primary objectives of this standard are to:

- Establish a common engineering methodology across RAH Lab software projects.
- Standardize Docker-based application deployment.
- Ensure compatibility with Debian Linux production environments.
- Maintain reproducible application and database deployments.
- Externalize deployment-specific configuration.
- Eliminate runtime dependence on public Internet resources.
- Support automated installation and update procedures.
- Support controlled database initialization and migration.
- Encourage modular and maintainable application architecture.
- Reduce manual deployment work and configuration discovery.
- Enable reliable software updates and rollback.
- Maintain technical ownership within RAH Lab.
- Facilitate knowledge transfer between engineers.

These objectives establish the application-engineering foundation required by the RAH release and operational environment.

---

## 1.5 Developer Responsibilities

Every developer contributing software to RAH Lab is responsible for ensuring that the application satisfies the engineering requirements defined by this standard.

Developers are expected to:

- Design software for long-term maintainability.
- Maintain understandable project organization.
- Develop for Linux-compatible production environments.
- Provide reproducible Docker-based deployment.
- Externalize environment-specific configuration.
- Declare and package all required runtime dependencies.
- Eliminate required Internet dependencies from production operation.
- Provide reproducible database initialization and migration mechanisms.
- Maintain version-controlled source code and deployment resources.
- Maintain compatibility between application and database evolution.
- Provide the technical resources required to construct compliant Application Releases.
- Provide sufficient technical documentation for future engineering and maintenance.
- Participate in technical knowledge transfer when required.

A project should not require the original developer to manually reconstruct undocumented deployment knowledge before another engineer can build, release, deploy, or maintain it.

---

The RAH Lab Software Development Standard is one component of the laboratory's engineering documentation framework.

Its primary responsibility is **application engineering**.

Related documents provide the surrounding infrastructure and operational standards:

# 2. Development Environment Standard

This chapter defines the development-environment requirements adopted by RAH Lab.

The objective is to ensure that applications developed by different engineers remain compatible with the laboratory's deployment infrastructure and can progress from development to the Online Engineering Environment and ultimately to the air-gapped Offline Production Environment without redesigning or rebuilding the application for each environment.

Developers may choose their preferred local development workflow provided that the resulting project satisfies the engineering and deployment requirements defined by this standard.

---

## 2.1 Target Deployment Environment

All software developed for RAH Lab shall target Linux-based production environments.

Development may take place on Windows, Linux, or macOS; however, production application services are expected to execute as Docker containers on Debian Linux unless an approved architecture specifies otherwise.

Depending on the application architecture, supporting services such as databases may be deployed as project-specific containers or consumed through approved shared infrastructure services.

Developers shall avoid operating-system-specific assumptions that prevent reproducible Linux deployment.

Examples include:

- Windows-only file paths.
- Hardcoded drive letters.
- Case-insensitive filename assumptions.
- Platform-specific runtime dependencies.
- Host-specific filesystem locations.
- Platform-dependent scripts without an equivalent supported deployment mechanism.

Application behavior shall not depend upon the operating system used by the original developer.

---

## 2.2 Recommended Development Platform

RAH Lab currently recommends the following engineering environment.

### Operating Systems

- Windows 11 Professional — recommended engineering workstation platform.
- Linux — supported.
- macOS — supported when the resulting project remains compatible with the target deployment environment.

### Development Tools

Typical engineering tools include:

- Visual Studio Code.
- Git.
- GitHub.
- Docker Desktop or Docker Engine.
- Docker Compose.
- Debian engineering and validation environments.
- Appropriate database administration tools.

The exact development workstation tooling may evolve without changing the deployment requirements defined by this standard.

### Backend Technologies

Preferred technologies currently include:

- Python.
- FastAPI.

Alternative backend technologies may be used when technically justified and compatible with the RAH deployment environment.

### Frontend Technologies

Preferred technologies currently include:

- React.
- Modern JavaScript or TypeScript.

Alternative frontend technologies may be used provided that they satisfy the deployment, offline-operation, and maintainability requirements defined by RAH Lab.

---

## 2.3 Development Database

Application development shall use approved development databases rather than production databases.

Development databases provide controlled environments in which engineers can:

- Develop application functionality.
- Perform functional testing.
- Validate customer requirements.
- Test database initialization.
- Test database migrations.
- Verify application/database compatibility.
- Reproduce deployment scenarios before production release.

The Offline Production Database shall never be used for routine software development or engineering testing.

Each application shall maintain logically independent application data regardless of whether its database is implemented as:

- a dedicated database within shared database infrastructure;
- a project-specific database container; or
- another approved architecture.

An online replica of the production database is **not required** for constructing an Application Release. What is required is a reproducible database installation and migration mechanism that can be validated independently of production data.

---

## 2.4 Local Development

Developers should perform application engineering and initial validation locally before introducing changes into shared engineering environments.

Local development typically includes:

- Running backend services.
- Running frontend services.
- Running or connecting to appropriate development databases.
- Building Docker images.
- Starting the application through Docker Compose.
- Performing functional testing.
- Testing environment configuration.
- Correcting implementation defects.

Where practical, developers should regularly test the containerized form of the application during development rather than postponing containerization until release preparation.

Local development should produce artifacts and configuration that can progress into shared validation without requiring structural changes to the application.

---

## 2.5 Online Development and Validation Environment

After local engineering reaches a stable state, the application should be validated within the shared Online Engineering Environment.

This environment supports activities such as:

- Shared application testing.
- Development database integration.
- Multi-user testing.
- Customer validation.
- Integration testing.
- External service integration.
- Release preparation.

Successful operation in the Online Engineering Environment demonstrates that the application can operate outside the original developer's workstation.

An application should become a Release Candidate only after its relevant application, database, configuration, and deployment behavior have been successfully validated.

---

## 2.6 Container-Oriented Development

RAH Lab follows a container-oriented application engineering model.

Docker shall be treated as part of normal software development rather than as a packaging exercise performed only after application development is complete.

Throughout development, engineers should verify that:

- Required Docker images build successfully.
- Docker Compose starts the intended deployment architecture.
- Application services communicate correctly.
- Database connectivity functions correctly.
- Environment configuration is supplied externally.
- Persistent data remains outside replaceable application containers.
- The application starts correctly from a clean deployment state.
- Containers can be replaced or recreated without reconstructing application source code.
- The deployment does not depend upon the name or location of a developer's project directory.

Projects should remain deployable throughout their development lifecycle.

This requirement is important because the final Application Release will be responsible for installing and updating the application through standardized deployment automation. Application engineering shall therefore avoid assumptions that make automated installation, update, or recreation unreliable.

---

## 2.7 Environment Independence

Applications shall remain independent of the environment in which they execute.

Deployment-specific configuration shall be supplied externally through environment variables, configuration files, or other approved deployment mechanisms.

Typical configurable values include:

- Database connection information.
- Database credentials.
- API endpoints.
- Shared service endpoints.
- Authentication configuration.
- Application secrets.
- Logging configuration.
- Application mode.
- Network ports.
- External service URLs.

Infrastructure-specific values shall not be hardcoded into application source code or Docker images.

The same versioned application artifacts should be capable of operating in:

- Local Development.
- Online Engineering and Validation.
- Offline Production.

Environment transitions should require configuration changes rather than source-code modification or rebuilding of application artifacts.

Applications shall also avoid deriving persistent operational identity from temporary engineering or release paths. Deployment automation must be capable of placing the application into its standardized live environment without application behavior depending upon the name of the incoming release directory.

---

## 2.8 Offline Frontend Asset Standard

Applications developed for RAH Lab shall remain fully functional within the hospital's air-gapped production environment without requiring public Internet access during normal operation.

All frontend runtime dependencies required by the application shall therefore be packaged with the application or provided by approved internal infrastructure.

Production applications shall not require public resources such as:

- Content Delivery Networks (CDNs).
- Externally hosted JavaScript libraries.
- Externally hosted CSS frameworks.
- Public web fonts.
- Public icon libraries.
- Externally hosted images.
- Internet-hosted analytics services.
- Other runtime assets requiring access to the public Internet.

Whenever practical, frontend dependencies should be managed through the project's package-management and build process and incorporated into the production artifacts.

Assets that cannot be bundled shall be stored locally or supplied through approved internal services.

Before release preparation, the application shall be tested without Internet access to verify that relevant functionality continues to operate correctly, including:

- User interface components.
- Fonts and icons.
- Charts and visualizations.
- Images.
- Reports.
- Document generation.
- Browser-side libraries.
- Other required static or runtime assets.

Successful online operation does not demonstrate compliance with this requirement. Offline behavior must be explicitly validated.

---

## 2.9 Engineering Principles

Software developed for RAH Lab shall follow these development-environment principles:

- Target Debian/Linux-compatible production execution.
- Build application artifacts once and deploy them repeatedly.
- Treat Docker as part of application engineering.
- Keep deployment configuration external to application source code.
- Keep operational data independent from replaceable application containers.
- Maintain reproducible application and database deployment mechanisms.
- Avoid dependence on temporary directories, developer machines, or release-folder names.
- Package all required offline runtime assets.
- Validate air-gapped behavior before production release.
- Design deployment resources for automated installation and update.
- Maintain software for long-term institutional ownership rather than one-time delivery.

These principles establish the engineering conditions required for applications to participate reliably in the RAH Application Release and deployment lifecycle.

# 3. Source Control Standard

Source control provides the authoritative engineering history of every software project maintained by RAH Lab.

Every project shall be maintained under a controlled version-management process that preserves source-code ownership, development history, release traceability, and the laboratory's ability to maintain the software independently of its original developer.

The source repository represents the authoritative engineering state of the application. Production runtime state, deployment credentials, and machine-specific operational information are maintained separately through the corresponding deployment and operational mechanisms.

---

## 3.1 Source Control Philosophy

RAH Lab treats the source repository as a long-term engineering asset rather than simply a storage location for source code.

The repository should preserve:

- Application source code.
- Engineering history.
- Version history.
- Release-related source history.
- Deployment resources maintained with the project.
- Database engineering resources.
- Traceability of significant software changes.

A project should remain understandable and maintainable after its original developer is no longer involved.

Source control shall therefore support the complete engineering lifetime of the application rather than only its initial development.

---

## 3.2 Repository Ownership

Every software project accepted into RAH Lab shall have an authoritative repository managed by or under the control of the laboratory.

When software is received from an external developer, RAH Lab should establish its own managed repository through an appropriate mechanism such as:

- forking the original repository;
- importing the repository while preserving its history; or
- transferring ownership into an approved RAH-managed repository.

The RAH-managed repository becomes the authoritative engineering source for:

- Future development.
- Bug fixes.
- Feature implementation.
- Deployment engineering.
- Database evolution.
- Release preparation.
- Long-term maintenance.

An external developer's repository may remain an upstream source of future improvements, but it shall not independently determine the state of RAH production software.

---

## 3.3 Receiving External Projects

When RAH Lab assumes responsibility for an externally developed project, the engineering handover should establish a controlled source baseline.

A typical process is:

1. Obtain access to the original source repository.
2. Establish the authoritative RAH-managed repository.
3. Preserve the available project history whenever practical.
4. Clone the RAH repository into the Engineering Laboratory.
5. Review the project architecture and documentation.
6. Verify that the application can be built from the documented source.
7. Evaluate the project against the RAH Software Development Standard.
8. Identify engineering work required before the project can enter the standardized release and deployment lifecycle.

Future changes from the original developer shall be reviewed and validated before incorporation into the authoritative RAH codebase.

External repositories shall not automatically synchronize changes into production-controlled branches.

---

## 3.4 Branching Strategy

Repositories should use a branching model appropriate to the size and complexity of the project while keeping stable software states clearly identifiable.

A typical RAH branching model is:

```text
main
│
├── development
│
├── feature/<feature-name>
├── bugfix/<bug-name>
└── release/<version>
```

### Main Branch

The `main` branch represents stable application source suitable for release preparation.

Changes entering `main` should have completed the validation appropriate to the project.

### Development Branch

The `development` branch may be used as the primary integration branch for ongoing engineering work.

Features and corrections can be combined and validated here before promotion to `main`.

### Feature Branches

Significant functionality may be developed in dedicated branches such as:

```text
feature/docker-support
feature/stt-service
feature/report-redesign
```

### Bug-Fix Branches

Software defects may be corrected through dedicated branches such as:

```text
bugfix/login-error
bugfix/database-timeout
```

### Release Branches

A `release/<version>` branch may be used when a project requires a stabilization period before publication.

Not every project requires every branch type. Smaller projects may use a simpler workflow provided that development work remains controlled and released source states remain clearly identifiable.

---

## 3.5 Commit Standards

Commits should represent understandable engineering changes.

Commit messages should describe the purpose of the modification rather than merely identifying the files that changed.

Examples include:

- `Add Docker support for backend service`
- `Fix SQL migration for complaint categories`
- `Refactor report generation module`
- `Remove external CDN dependency`
- `Add offline certificate configuration support`

Unrelated engineering changes should not normally be combined into a single commit.

A disciplined commit history improves troubleshooting, code review, rollback of engineering changes, and understanding of how the application evolved.

---

## 3.6 Merge and Integration Policy

Changes entering stable project branches shall be validated to the degree appropriate to their impact.

Relevant checks may include:

- Successful application build.
- Successful Docker image build.
- Automated tests where available.
- Functional testing.
- Database compatibility.
- Migration testing where applicable.
- Offline-runtime compatibility.
- Review of configuration changes.
- Review of deployment-impacting changes.
- Resolution of merge conflicts.

External contributions shall not enter production-controlled source states without technical review and validation.

Changes affecting deployment behavior should also be evaluated for compatibility with the RAH Application Release & Deployment Standard.

---

## 3.7 Version Tags

Every published Application Release should be traceable to an identifiable source state.

Git tags are the preferred mechanism for identifying the source associated with a published release.

Example:

```text
v1.0.0
v1.1.0
v2.0.0
```

A release tag identifies the authoritative source state from which the corresponding Application Release was engineered.

The Application Release may contain multiple artifacts with their own internal versions. These artifacts do not need to duplicate the Git tag mechanically; instead, the published release shall define the compatible set of artifacts associated with that source state.

Published release tags shall not be silently moved to unrelated source states.

---

## 3.8 Repository Documentation

Every authoritative repository shall contain sufficient engineering documentation for another engineer to understand, build, modify, and prepare the application for release.

Depending on the project, repository documentation may include:

- README.
- Project purpose and architecture.
- Technology stack.
- Project structure.
- Development setup.
- Dependency information.
- Build instructions.
- Docker engineering information.
- Database schema and migration information.
- Configuration requirements.
- External-service dependencies.
- Testing procedures.
- Release-engineering requirements.
- Known engineering limitations.

Repository documentation is **engineering documentation**.

Production credentials, machine-specific deployment information, current production state, DBeaver connection information, and deployment history belong to the protected operational documentation system and shall not be duplicated into the source repository merely for convenience.

---

## 3.9 Long-Term Ownership

The primary objective of RAH Lab source-control practice is institutional software ownership.

RAH Lab should be able to determine:

- what source produced a released application;
- how the application changed;
- why significant engineering changes were introduced;
- what deployment and database resources belong to the project;
- and how another engineer can continue development without depending upon the original developer.

Authoritative repositories, controlled integration, identifiable release source states, and maintained engineering documentation ensure that applications remain RAH institutional assets throughout their operational lifetime.

# 4. Application Engineering Standard

This chapter defines the engineering requirements governing the design, structure, behavior, and maintainability of software applications developed or maintained by RAH Lab.

The objective is to ensure that applications remain understandable, maintainable, extensible, diagnosable, and compatible with the standardized RAH release and deployment lifecycle.

The application should remain logically independent from the infrastructure on which it is deployed while exposing the configuration, startup behavior, dependencies, persistence model, and operational interfaces required for deterministic deployment and maintenance.

---

## 4.1 Application Architecture

Applications should be organized into clearly defined functional components.

The architecture should promote:

- Separation of concerns.
- Clear component responsibilities.
- Modular design.
- Controlled dependencies.
- Low coupling.
- Maintainability.
- Testability where practical.

Business logic, user-interface logic, data access, integration logic, and infrastructure-facing concerns should remain logically separated where practical.

Architectural decisions should support continued feature development without requiring unnecessary structural redesign.

The objective is not to enforce a single application architecture across every RAH project, but to ensure that application boundaries remain understandable to future engineers.

---

## 4.2 Project Organization

Every application shall maintain a clear and consistent project structure.

Where applicable, the repository should make areas such as the following identifiable:

```text
project/
├── backend/
├── frontend/
├── database/
├── deployment/
├── documentation/
├── tests/
└── README.md
```

The exact directory names are project-specific and need not follow this example literally.

What matters is that another engineer can readily identify:

- Application source code.
- Frontend and backend boundaries where applicable.
- Database engineering resources.
- Docker resources.
- Deployment-engineering resources.
- Configuration templates.
- Static assets.
- Tests where available.
- Engineering documentation.

Files required to construct or automate an Application Release shall be maintained as intentional project resources rather than scattered across developer workstations or undocumented external locations.

---

## 4.3 Maintainability

Applications shall be engineered for continued maintenance rather than one-time delivery.

Software should be:

- Readable.
- Modular.
- Understandable.
- Diagnosable.
- Documented appropriately.
- Reasonably testable.
- Easy to modify.
- Compatible with controlled deployment and update.

Engineering decisions should favor predictable long-term behavior over short-term implementation convenience.

Routine maintenance should not require reverse engineering basic application configuration, dependencies, startup behavior, database requirements, or deployment assumptions.

---

## 4.4 Configuration Interface

Applications shall expose deployment-specific configuration through defined external interfaces rather than embedding environment-specific values in application source code.

Configurable information may include:

- Database connection parameters.
- Service endpoints.
- Authentication settings.
- Application secrets.
- Shared AI or STT endpoints.
- Network ports.
- Application mode.
- Logging configuration.
- Feature-specific deployment settings.

Configuration may be supplied through:

- Environment variables.
- Approved external configuration files.
- Docker Compose configuration.
- Other documented deployment mechanisms.

Application code shall define and validate the configuration it requires.

Missing mandatory configuration should produce a clear diagnostic failure rather than unpredictable behavior.

Default values may be used where they are safe and intentional, but production-specific infrastructure information shall not be silently embedded into application images.

This configuration interface becomes the contract used by Application Release tooling to configure the application without modifying its source code.

---

## 4.5 Startup and Failure Behavior

Applications shall behave predictably during startup and when required dependencies are unavailable.

Expected failure conditions may include:

- Missing required configuration.
- Database unavailability.
- Invalid database credentials.
- Shared service unavailability.
- External API failure.
- Invalid user input.
- File or storage failure.
- Internal application exceptions.

Where appropriate, startup failures should identify the missing or unavailable dependency clearly enough for engineering diagnosis.

Applications should avoid entering an apparently successful state when a mandatory dependency has failed.

User-facing errors should remain understandable without unnecessarily exposing sensitive implementation details.

Engineering logs may contain the additional diagnostic information required for troubleshooting.

---

## 4.6 Logging and Operational Diagnostics

Applications shall provide sufficient diagnostic information to support engineering and operational troubleshooting.

Relevant events may include:

- Application startup.
- Application shutdown.
- Configuration failures.
- Database connection failures.
- External service failures.
- Authentication failures.
- Background-worker failures.
- Unexpected exceptions.
- Other application-specific critical events.

Logs should identify the responsible application or service and provide enough context to understand the failure.

Applications should emit logs through mechanisms compatible with their containerized deployment so that engineers can inspect application behavior without modifying or rebuilding the software.

Sensitive values such as passwords, secrets, tokens, or unnecessary patient information shall not be written to logs.

Where practical, applications should expose a lightweight health mechanism that deployment tooling can use to determine whether the service has started successfully.

---

## 4.7 Dependencies and Offline Runtime

Applications shall explicitly declare the dependencies required for successful build and execution.

Depending on the project, these may include:

- Programming-language versions.
- Framework versions.
- Backend packages.
- Frontend packages.
- Native libraries.
- Runtime requirements.
- Browser-side assets.
- Required external infrastructure services.

Dependencies required to build the application shall be reproducible through the project's engineering process.

Dependencies required during normal production runtime shall either:

- be packaged with the application;
- be included in its container images; or
- be provided through explicitly approved internal infrastructure services.

An application shall not depend unknowingly on resources available only on the original developer's workstation or through public Internet connectivity.

The offline frontend requirements defined in Chapter 2 apply to all browser-side application dependencies.

---

## 4.8 External and Shared Services

Applications may consume shared infrastructure capabilities through clearly defined interfaces.

Examples include:

- Database services.
- Shared Speech-to-Text services.
- AI inference services.
- Authentication services.
- File-storage services.
- Other approved internal APIs.

Service locations and environment-specific connection information shall remain externally configurable.

Applications shall document:

- which external services are mandatory;
- which services are optional;
- the interface or protocol used;
- the configuration required to locate them;
- and expected behavior when those services are unavailable.

Where a shared service can be updated independently, applications should depend upon its documented interface rather than unnecessary assumptions about its internal implementation.

---

## 4.9 Persistence Boundaries

Applications shall clearly identify information that must survive container replacement, service recreation, or application updates.

Persistent state may include:

- Database information.
- Uploaded files.
- Generated documents.
- Application-specific persistent storage.
- Required configuration.
- Other operational state.

Persistent production information shall not exist exclusively inside replaceable application container filesystems.

The application architecture and deployment resources shall identify the required persistence mechanisms so that Application Release tooling can update or recreate application services without unintentionally destroying operational state.

Temporary caches, generated intermediate data, and disposable runtime state should be distinguished from persistent operational information.

---

## 4.10 Deployment Automation Readiness

Applications shall be engineered so that routine installation and update operations can be performed through deterministic deployment tooling.

The application project shall therefore expose or provide sufficient information for release engineering to determine:

- required application services;
- required container images;
- required configuration values;
- persistent configuration;
- persistent storage;
- database initialization requirements;
- database migration requirements;
- service dependencies;
- expected network ports;
- startup ordering where relevant;
- health or verification mechanisms;
- required shared infrastructure services.

Application startup shall not normally depend upon undocumented interactive configuration performed manually after container creation.

Where unavoidable manual actions exist, they shall be explicitly documented and minimized.

The objective is that Application Release tooling can establish or update the application predictably without requiring the deploying engineer to rediscover how the application works.

---

## 4.11 Engineering Documentation

Every application repository shall contain sufficient technical documentation to support future engineering and release preparation.

Documentation should cover, where applicable:

- Project purpose.
- Architecture.
- Technology stack.
- Development setup.
- Project structure.
- Configuration contract.
- Dependency requirements.
- Database architecture.
- Database initialization and migration.
- Docker architecture.
- Persistent-state requirements.
- External and shared services.
- Build and testing procedures.
- Release-engineering considerations.
- Known technical limitations.

Documentation shall describe the application as an engineering system.

Production-specific credentials, current deployed versions, installation dates, machine-specific connection information, and operational release history belong to the operational documentation system rather than the source repository.

---

## 4.12 Application Engineering Principles

Applications maintained by RAH Lab shall be engineered to be:

- Maintainable over the long term.
- Understandable by engineers other than their original developers.
- Modular where appropriate.
- Linux-compatible.
- Container-compatible.
- Externally configurable.
- Explicit about dependencies.
- Explicit about persistent state.
- Diagnosable through meaningful logging.
- Predictable during startup and dependency failure.
- Compatible with offline production operation.
- Compatible with controlled database evolution.
- Suitable for deterministic installation and update automation.
- Compatible with the RAH Application Release & Deployment Standard.

The purpose of these requirements is to ensure that an application is not merely functional, but **engineerable, releasable, deployable, and maintainable as a long-term RAH software asset**.

# 5. Docker Engineering Standard

Docker is the standard application deployment platform adopted by RAH Lab.

Every application intended for production deployment shall provide a complete and reproducible containerized architecture compatible with the RAH engineering, validation, release, and offline production environments.

The purpose of this chapter is to define the **Docker engineering contract of the application project**. It specifies what the project must expose so that a compliant Application Release can later install, update, recreate, verify, and maintain the application deterministically.

The detailed construction and execution of offline release tooling is defined by the RAH Application Release & Deployment Standard and the corresponding engineering playbook.

---

## 5.1 Docker Engineering Philosophy

RAH Lab follows the principle:

> **Build Once. Validate Carefully. Deploy Repeatedly.**

Production application images are built within the Engineering Environment and validated before publication.

The same immutable application images should progress through validation and production deployment without rebuilding them for the target machine.

Differences between environments shall be supplied through external configuration rather than by modifying:

- application source code;
- Dockerfiles;
- built application images; or
- packaged application artifacts.

Containerization shall be treated as part of application engineering rather than an installation procedure added after development is complete.

A compliant Docker implementation must support not only first deployment, but also predictable update, service recreation, persistence, troubleshooting, and long-term maintenance.

---

## 5.2 Deployment Architecture

Every project shall define its complete deployment architecture.

The architecture shall identify all services and dependencies required to operate the application.

Depending on the project, these may include:

- Backend services.
- Frontend services.
- Reverse proxy.
- Database service.
- Background workers.
- Scheduled services.
- AI integration services.
- Shared infrastructure dependencies.
- Other application-specific services.

The deployment architecture shall also identify:

- service relationships;
- exposed ports;
- internal service communication;
- persistent storage;
- required configuration;
- startup dependencies;
- shared infrastructure dependencies;
- health or verification mechanisms where applicable.

The architecture shall remain reproducible independently of the original developer's workstation.

---

## 5.3 Container Architecture

Containers should be separated according to clear operational responsibilities.

Typical containers may include:

```text
Application
│
├── Reverse Proxy
├── Frontend
├── Backend
├── Worker
└── Database
```

Not every application requires every service shown above.

Where functionality is provided by a shared RAH infrastructure service, the application should consume that service through its documented interface rather than unnecessarily duplicating the capability inside the project.

Containers shall communicate through defined Docker networks and configurable service identities rather than relying on development-machine assumptions.

Replaceable application containers shall not contain the sole authoritative copy of persistent operational state.

---

## 5.4 Required Docker Engineering Artifacts

Every project shall maintain the Docker and deployment-engineering resources required to reproduce its approved architecture.

Typical resources include:

### Application Images

- Backend `Dockerfile`.
- Frontend `Dockerfile` or equivalent production web configuration.
- Dockerfiles for project-specific workers or supporting services where required.

### Deployment Definition

- `docker-compose.yml` or the approved Compose source used to construct the production deployment.

### Configuration Contract

- `.env.example` or equivalent configuration reference documenting required variables.
- Supporting configuration templates where required.

### Supporting Engineering Resources

Where applicable:

- Reverse-proxy configuration.
- Health-check configuration.
- Database initialization resources.
- Database migration resources.
- Persistent-storage definitions.
- Certificate/TLS configuration inputs.
- Deployment verification resources.

Release automation scripts themselves may be generated or maintained through the release-engineering process rather than being part of the core application source architecture.

The application project shall nevertheless expose everything required for those scripts to operate deterministically.

---

## 5.5 Docker Compose Standard

Docker Compose is the standard deployment description used by RAH Lab for application deployments.

The Compose definition shall describe the complete project-specific container architecture, including where applicable:

- Services.
- Image identities.
- Networks.
- Persistent volumes.
- Environment variables.
- Port mappings.
- Restart policies.
- Health checks.
- Service dependencies.

Each application shall define an explicit and stable Compose project identity.

The identity of a deployed application shall not depend upon:

- the name of the developer's source directory;
- the name of a versioned Release Package;
- the location from which an installer was executed.

For example, an application may explicitly define:

```yaml
name: stt-schedule
```

This allows successive Application Releases to operate against the same intended deployment rather than accidentally creating version-specific Compose projects.

The exact deployment-path and Compose invocation conventions are defined by the Application Release & Deployment Standard.

---

## 5.6 Environment and Persistent Configuration

Infrastructure-specific configuration shall remain external to immutable application images.

Typical configuration includes:

- Database connection information.
- Database credentials.
- Application secrets.
- Backend and frontend URLs.
- Network ports.
- Shared service endpoints.
- Authentication configuration.
- Logging configuration.
- Application mode.
- API or AI service configuration.

Every required configuration parameter shall be documented through the project's configuration contract.

The application shall distinguish between:

**release-provided configuration structure**

and

**persistent deployment-specific configuration values**.

The final live deployment maintains persistent configuration independently of the incoming versioned Release Package.

Application engineering shall therefore not assume that `.env` or equivalent operational configuration lives permanently beside the release files used to transport a particular version.

A new software version shall be capable of operating with the existing persistent deployment configuration unless the release explicitly introduces a controlled configuration migration.

---

## 5.7 Persistent Storage

Application containers shall be replaceable without destroying persistent operational information.

Persistent state may include:

- Database data.
- Uploaded files.
- Generated documents.
- Application-specific files.
- Persistent configuration.
- Other operational information identified by the application architecture.

Persistent state shall be stored using approved mechanisms such as:

- External database services.
- Docker volumes.
- Named persistent volumes.
- Approved host directories.
- Other documented persistent infrastructure.

The project shall clearly distinguish:

```text
replaceable application state
        vs.
persistent operational state
```

Container recreation shall not reset or destroy persistent production information.

---

## 5.8 Service Communication

Applications and containers shall communicate using configurable service endpoints.

They shall not depend upon development-specific assumptions such as:

- Fixed developer-machine IP addresses.
- Machine-specific hostnames.
- Hardcoded infrastructure addresses.
- Unnecessary `localhost` assumptions.
- Release-directory paths.
- Developer-specific network configuration.

Internal container communication should use stable Docker service identities where appropriate.

External services shall be configured through the application's defined configuration interface.

The application shall document which services are:

- internal to its Compose deployment;
- supplied by shared RAH infrastructure; or
- external dependencies that must exist before deployment.

---

## 5.9 Shared Infrastructure Services

Applications should consume approved shared RAH capabilities where doing so is appropriate to the system architecture.

Examples may include:

- Speech-to-Text services.
- AI inference services.
- Shared database infrastructure.
- Authentication services.
- Other approved infrastructure APIs.

Applications shall communicate with shared services through documented and configurable interfaces.

The application should not depend upon undocumented implementation details of the shared service.

A shared service may evolve independently provided that its supported interface remains compatible with the consuming application.

---

## 5.10 Resource and Lifecycle Behavior

Applications shall be engineered for predictable container lifecycle behavior.

Developers should consider:

- CPU requirements.
- Memory requirements.
- Disk usage.
- Startup time.
- Graceful shutdown.
- Restart behavior.
- Resource cleanup.
- Persistent-volume usage.

Projects with significant infrastructure requirements shall document those requirements.

Application containers shall tolerate controlled recreation during deployment or update.

Services shall not rely upon undocumented container-local changes that disappear when the container is recreated.

Persistent database or infrastructure services may require different lifecycle handling from replaceable application services and shall be identified accordingly.

---

## 5.11 Health and Operational Diagnostics

Dockerized services shall expose sufficient information for deployment tooling and engineers to determine whether startup succeeded.

Where practical, long-running services should provide an appropriate health mechanism.

This may include:

- HTTP health endpoint.
- Container health check.
- Database readiness check.
- Process-level verification.
- Application-specific verification mechanism.

Health checks should verify meaningful service readiness rather than merely confirming that a process exists.

Application logs shall also make relevant failures diagnosable, including:

- Startup failures.
- Missing configuration.
- Database connectivity failures.
- Shared service failures.
- Authentication failures.
- Unexpected exceptions.

The Docker implementation shall support troubleshooting without modifying or rebuilding production containers.

---

## 5.12 Update and Recreation Readiness

Docker deployments shall be engineered so that application services can be recreated predictably during controlled updates.

The application architecture shall not depend upon the continued existence of a specific container object.

Where required, release tooling may recreate application services to eliminate stale state from previous failed deployments.

The engineering requirement is therefore:

> **Replacing or recreating application containers shall restore the intended application state without destroying persistent production information.**

Database and other persistent infrastructure services shall follow their own defined lifecycle rather than automatically being treated as disposable application containers.

The exact use of mechanisms such as `--force-recreate` belongs to the Application Release engineering implementation rather than this standard.

---

## 5.13 Docker Quality Standard

Before an application is considered ready for release engineering, its Docker implementation shall satisfy the applicable requirements:

- Required Docker images build successfully.
- The deployment architecture is documented.
- Docker Compose describes the intended application deployment.
- Compose project identity is stable and explicit.
- Linux compatibility has been verified.
- Required configuration is documented and externalized.
- Production runtime does not depend upon the developer's directory structure.
- Persistent state has been identified and protected.
- Application containers can be recreated without losing persistent state.
- Service communication is configurable.
- Required shared services are documented.
- Health or verification mechanisms exist where appropriate.
- Operational logs provide useful diagnostics.
- Required frontend runtime assets operate without public Internet access.
- The Docker architecture provides the inputs required for deterministic Application Release automation.

Compliance with these requirements allows release engineering to concentrate on **automating deployment** rather than reverse engineering the application's container architecture.

# 6. Database Engineering Standard

Databases represent persistent application state and, in production, may contain critical hospital information that must survive application updates, container recreation, database schema evolution, and long-term software maintenance.

This chapter defines the database-engineering requirements that applications must satisfy before they can participate reliably in the RAH release and deployment lifecycle.

The objective is to ensure that every supported database can be initialized reproducibly, migrated safely, backed up and restored, operated independently of the original developer, and integrated into automated Application Release procedures.

---

## 6.1 Database Engineering Philosophy

RAH Lab treats application software and production databases as related but independently persistent engineering assets.

Application containers are replaceable.

Production database state is not.

Software releases shall therefore **evolve** an existing production database rather than recreate it as a normal update mechanism.

Database engineering shall follow these principles:

- Preserve production data.
- Support reproducible first-time installation.
- Support controlled schema evolution.
- Avoid manual production schema editing.
- Keep database credentials and environment configuration external to application source code.
- Maintain traceability between database changes and the Application Release that introduced them.
- Support backup and recovery.
- Allow another RAH engineer to understand and maintain the database without undocumented developer knowledge.

---

## 6.2 Supported Database Engines

Microsoft SQL Server is the preferred relational database platform for internally developed RAH applications.

Projects may use another database engine, including PostgreSQL, when:

- required by an existing application architecture;
- technically justified;
- or otherwise approved for the project.

The selected database engine becomes part of the application's documented deployment architecture.

The database platform shall be capable of operating within the approved RAH offline environment.

A database does not need to be migrated to Microsoft SQL Server solely for standardization if its existing platform can be deployed, backed up, restored, migrated, inspected, and maintained reliably.

---

## 6.3 Database Architecture

Each application shall clearly identify the persistent database state it owns.

Depending on the approved architecture, the application may use:

- a dedicated database within a shared database server;
- a dedicated PostgreSQL container;
- a dedicated Microsoft SQL Server container;
- another approved database deployment model.

Application databases shall remain logically separated unless a shared schema or database is an intentional documented part of the application architecture.

The database architecture shall document:

- database engine;
- database identity;
- hosting model;
- required users or roles;
- initialization method;
- migration mechanism;
- backup requirements;
- operational dependencies.

An online replica of the production database is not required for Application Release engineering.

Development and validation may use development, test, synthetic, or otherwise approved non-production databases.

---

## 6.4 Initial Database Installation

Every application requiring a database shall provide a reproducible mechanism for establishing a new empty production database.

The initialization mechanism shall produce the database state required by the initial supported application version.

Depending on the database architecture, initialization may include:

- Database schema.
- Tables.
- Indexes.
- Constraints.
- Views.
- Stored procedures.
- Functions.
- Lookup or seed data.
- Database users.
- Required roles and permissions.
- Initial schema/version metadata.

Initial installation resources shall not depend upon:

- Production hospital data.
- Developer test data.
- Temporary developer accounts.
- Developer-specific credentials.
- Manual schema creation.
- Undocumented environment-specific values.

Where the database is containerized, the application shall provide the Docker resources required to initialize and persist the database correctly.

The initialization mechanism shall be suitable for invocation by automated Application Release installation tooling.

---

## 6.5 Lookup and Seed Data

Applications may depend upon reference information required for correct application behavior.

Examples may include:

- Departments.
- Sections.
- User roles.
- Permissions.
- Classifications.
- Status definitions.
- Application reference values.

Required initial reference information shall be installable reproducibly.

Lookup and seed data shall be distinguished from operational production information.

Initialization and migration procedures should be designed so that required reference data can be created or updated without destroying valid production information.

Where repeated execution is possible, seed operations should avoid unintentionally creating duplicate records.

---

## 6.6 Database Evolution

Production databases shall evolve through controlled migrations.

A routine software update shall not require deletion and recreation of the production database.

Database evolution may include:

- Creating tables.
- Adding or modifying columns.
- Creating or modifying indexes.
- Updating lookup data.
- Adding constraints.
- Updating views.
- Updating stored procedures.
- Performing controlled data transformations.
- Correcting schema defects.

Database changes shall preserve existing production information unless the change explicitly and intentionally transforms that information as part of the approved migration.

Schema changes shall not be performed manually in production as the authoritative migration method.

---

## 6.7 Migration Standard

Every database change required by a new application version shall be delivered through a version-controlled migration mechanism.

Depending on the technology, acceptable mechanisms may include:

- SQL migration scripts.
- DACPAC deployment.
- Alembic or another approved migration framework.
- Database-engine-specific migration tooling.

A migration should:

- have an identifiable source state where relevant;
- produce a defined target state;
- be repeatable or safely detectable as already applied;
- preserve production data;
- fail clearly when prerequisites are not satisfied;
- be testable before production deployment;
- support recovery or rollback where practical;
- be associated with the Application Release that requires it.

Migration procedures shall operate regardless of whether the database is hosted as a dedicated container or through approved shared database infrastructure, provided the required privileges and connectivity exist.

Release tooling shall be able to invoke migrations without requiring the operator to manually reproduce schema changes.

---

## 6.8 Database Version and Compatibility

Database state shall be identifiable so that the currently deployed schema can be related to the application version that expects it.

The database may use:

- migration revision identifiers;
- schema-version records;
- framework-managed migration history;
- another documented mechanism appropriate to the technology.

Backend, frontend, database, migration, and documentation artifacts do **not** need to share identical numeric version strings.

Instead, the versioned **Application Release defines the compatible set of application artifacts and required database state**.

For example:

```text
Application Release 2.4.0

Includes:
- Backend image: api-build-184
- Frontend image: web-build-73
- Required DB migration: rev_018
```

What matters is that the Application Release unambiguously defines a compatible combination.

Release engineering shall not rely upon manually guessing compatibility from unrelated artifact version numbers.

---

## 6.9 Database Credentials and Authentication

Applications shall not depend upon developer-specific database credentials.

The project shall document the authentication structure required by the application, including where applicable:

- Database users.
- Database roles.
- Required permissions.
- Administrative requirements.
- Application service accounts.

Credentials shall not be hardcoded into application source code or immutable Docker images.

The application shall accept required credentials through its external configuration interface.

Production machine/service credentials may be generated by Application Release installation tooling.

The database architecture shall therefore support credential assignment without requiring source-code changes.

Generated values shall use a format compatible with the selected database engine, driver, connection mechanism, and application configuration.

The engineering standard does not require operators to manually invent service credentials during installation.

---

## 6.10 Database Connection Construction

Applications shall handle database credentials safely and predictably when constructing database connections.

Connection logic shall not depend upon naïve string interpolation that causes valid credential characters to be misinterpreted as connection-URL syntax.

Where applicable, applications should use:

- driver-supported connection parameters;
- properly encoded connection URLs;
- structured connection objects;
- or another mechanism appropriate to the database library.

Release tooling may generate credentials using a compatibility-safe character set, but application engineering should not unnecessarily depend upon undocumented password-character assumptions.

Connection failures shall provide diagnostic information sufficient to distinguish configuration, authentication, hostname, port, and database-availability problems where practical.

---

## 6.11 Database Administration Readiness

Every supported application database shall expose enough documented connection information for RAH operational tooling to register and access it.

Application engineering shall make the following information determinable where applicable:

- Database engine.
- Host or service identity.
- Port.
- Database name.
- Database user.
- Authentication method.
- Required driver.
- TLS or other connection requirements.

This information provides the engineering contract used by Application Release tooling to establish or repair the application's DBeaver registration during installation and update.

The exact mechanism used to modify DBeaver configuration is an implementation responsibility of the Application Release engineering process, not of the database application code.

---

## 6.12 Backup and Recovery Compatibility

Database architecture shall support documented backup and restoration procedures appropriate to the selected database platform.

Engineering decisions should allow production operators to:

- Create backups.
- Restore backups.
- Verify recovery.
- Apply database migrations.
- Recover from failed migrations where possible.

Applications shall avoid unnecessary database-design choices that make routine backup or recovery impractical.

Where database state is stored in Docker volumes, the persistence and backup model shall be explicitly documented rather than assuming that container recreation preserves all required information automatically.

---

## 6.13 Database Documentation

Every project shall maintain database engineering documentation sufficient for another engineer to understand and maintain the database.

Documentation should identify where applicable:

- Database engine.
- Deployment architecture.
- Schema or entity model.
- Initialization mechanism.
- Lookup and seed data.
- Migration mechanism.
- Current versioning/revision strategy.
- Required roles and permissions.
- Application connection requirements.
- Backup and restoration considerations.
- Container persistence where applicable.
- Operational dependencies.

Repository documentation describes the **engineering model** of the database.

Current production credentials, deployed database host information, DBeaver connection names, deployment dates, and production release history belong to the protected RAH operational documentation system rather than the source repository.

---

## 6.14 Database Quality Standard

Before an application is considered ready for release engineering, its database implementation shall satisfy the applicable requirements:

- Database engine is declared.
- Database architecture is documented.
- A reproducible initial installation mechanism exists.
- Required lookup and seed data are reproducible.
- Production data is separated from initial seed/test data.
- A controlled migration mechanism exists.
- Database migrations preserve production information.
- Applied database state can be identified.
- Required users, roles, and permissions are documented.
- Credentials are externally configurable.
- Connection handling is compatible with generated deployment credentials.
- Database connection information can be supplied to operational administration tooling.
- Backup and restoration requirements are documented.
- Containerized database persistence is explicitly configured where applicable.
- Database deployment does not require an online production replica.
- Release tooling can initialize and migrate the database without manual schema editing.

Compliance with these requirements allows the database to evolve safely as part of the Application Release lifecycle while remaining persistent, traceable, and independently maintainable.

# 7. Release Engineering Readiness

This chapter defines the engineering requirements that a software project shall satisfy before a compliant RAH Application Release can be constructed from it.

The objective is not to define the structure or operational behavior of the Application Release itself. Those requirements are defined by the **RAH Application Release & Deployment Standard**.

Instead, this chapter defines the responsibilities of the application project: the source code, Docker architecture, database resources, configuration contract, dependencies, documentation, and verification mechanisms that release engineering requires in order to construct, validate, and maintain versioned Application Releases.

A project is release-ready when a new Application Release can be engineered from its controlled source state without rediscovering undocumented application behavior or manually reconstructing deployment knowledge.

---

## 7.1 Release Engineering Philosophy

RAH Lab treats release readiness as an engineering property of the software project.

A functioning application is not automatically a release-ready application.

Before release engineering begins, the project should provide a stable and understood source state that has been:

- Implemented.
- Technically validated.
- Containerized.
- Configured externally.
- Tested with its required dependencies.
- Prepared for reproducible database initialization and migration.
- Verified for offline runtime compatibility.
- Documented sufficiently for release construction.

Release engineering should transform an already well-engineered application into a compliant Application Release.

It should not become the stage at which fundamental application architecture, database behavior, configuration requirements, or deployment dependencies are discovered for the first time.

---

## 7.2 Release Source State

Every Application Release shall originate from an identifiable and controlled project source state.

The source state should identify the exact application code and engineering resources used to construct the release.

Git tags are the preferred mechanism for identifying published release source states.

Example:

```text
v1.0.0
v1.1.0
v2.0.0
```

A release source state should include the applicable:

- Application source code.
- Dockerfiles.
- Docker Compose source.
- Database engineering resources.
- Configuration templates.
- Dependency declarations.
- Deployment-engineering resources maintained with the project.
- Technical documentation.

Once used to construct a published Application Release, the corresponding source state shall remain traceable.

---

## 7.3 Required Release Engineering Inputs

A release-ready project shall provide the engineering inputs required to construct its Application Release.

Depending on the application architecture, these may include:

### Application Components

- Backend source and build definition.
- Frontend source and build definition.
- Worker or supporting-service definitions.
- Required static and offline runtime assets.

### Container Resources

- Dockerfiles.
- Docker Compose source.
- Reverse-proxy configuration where applicable.
- Network and persistent-storage definitions.
- Health or readiness definitions where applicable.

### Configuration Resources

- Configuration contract.
- `.env.example` or equivalent reference.
- Required variable definitions.
- Service endpoint requirements.
- Port requirements.
- Persistent configuration requirements.

### Database Resources

- Initial database installation mechanism.
- Migration resources.
- Lookup and seed data.
- Database revision/version mechanism.
- Required users, roles, and permissions.
- Persistence requirements.

### External Infrastructure Requirements

- Shared database services.
- Shared AI or STT services.
- Authentication services.
- Storage services.
- Other required infrastructure dependencies.

### Verification Information

- Expected application startup behavior.
- Health endpoints or equivalent checks.
- Database readiness requirements.
- Required functional verification steps.

These inputs allow release engineering to construct deployment automation without reverse engineering the application.

---

## 7.4 Configuration Readiness

All deployment-specific configuration required by the application shall be externally configurable before release engineering begins.

The project shall identify:

- Mandatory configuration.
- Optional configuration.
- Safe defaults where applicable.
- Secrets.
- Database configuration.
- Service endpoints.
- Network ports.
- Persistent configuration.
- Environment-specific values.

Application source code and immutable images shall not contain production-specific infrastructure configuration.

The configuration contract shall be sufficiently explicit for release tooling to:

1. Determine what values are required.
2. Generate values where appropriate.
3. Preserve deployment-specific values across updates.
4. Validate mandatory configuration.
5. Supply configuration without modifying application source code.

Release engineering should not need to inspect arbitrary source-code locations to discover required production configuration.

---

## 7.5 Database Release Readiness

Applications using databases shall satisfy the Database Engineering Standard before release construction.

Release engineering shall be able to determine:

- Database engine.
- Database hosting model.
- Initial installation mechanism.
- Required seed or lookup data.
- Current migration mechanism.
- Required target migration/revision.
- Required database roles and permissions.
- Application connection requirements.
- Persistent-storage requirements.
- Backup and recovery considerations.

The database shall support both:

```text
Fresh Installation
        and
Existing Installation Update
```

where applicable.

Fresh installation shall establish the required initial database state.

Updates shall evolve existing production state through controlled migrations rather than database recreation.

The project shall provide sufficient information for release tooling to perform these operations deterministically.

---

## 7.6 Container Release Readiness

The Docker implementation shall satisfy the Docker Engineering Standard before release construction.

Release engineering shall be able to determine:

- Required images.
- Required services.
- Stable Compose project identity.
- Service relationships.
- Network requirements.
- Persistent volumes.
- Persistent configuration.
- Required ports.
- Startup dependencies.
- Health or verification mechanisms.
- Which services are replaceable.
- Which services contain or depend upon persistent state.

Application behavior shall not depend upon:

- Developer workstation paths.
- Temporary source directories.
- Incoming Release Package names.
- Version-specific Compose project names.
- Undocumented container-local modifications.

Application containers shall tolerate controlled recreation without destroying persistent production state.

---

## 7.7 Offline Runtime Readiness

Applications intended for the Offline Production Environment shall be validated for operation without public Internet connectivity before release publication.

Release engineering shall verify that required runtime dependencies are:

- Included in the application artifacts;
- Included in the required Docker images; or
- Supplied through approved internal infrastructure services.

Particular attention shall be given to frontend runtime assets such as:

- JavaScript libraries.
- CSS resources.
- Fonts.
- Icons.
- Images.
- Charting libraries.
- Document-generation assets.
- Other browser-side resources.

Release preparation shall include an offline asset audit appropriate to the application.

A project shall not be considered release-ready merely because it operates correctly while Internet access is available.

---

## 7.8 Browser Capability Readiness

Applications using browser capabilities that require secure contexts or explicit browser permission shall identify those requirements before release construction.

Examples include:

- Microphone access.
- Camera access.
- Other browser APIs restricted by browser security policy.

The application shall clearly identify:

- Which capability is required.
- Which user-facing route or origin requires the capability.
- Whether HTTPS is required.
- Whether browser permission must be established.
- Which supported browsers are expected to operate the capability.

Application engineering shall not assume that functionality verified on `localhost` will behave identically when accessed through a production hostname or IP address.

The **RAH Application Release & Deployment Standard** defines the operational guarantees that a release must establish for these capabilities.

The corresponding release-engineering implementation defines the browser-specific mechanisms used to establish them.

---

## 7.9 Release Verification Readiness

A release-ready project shall provide sufficient verification mechanisms to determine whether installation or update succeeded.

Depending on the application, verification may include:

- Container status.
- Health checks.
- Backend health endpoint.
- Frontend accessibility.
- Database connectivity.
- Database revision verification.
- Shared-service connectivity.
- Authentication verification.
- Application-specific functional checks.

Verification should distinguish between:

```text
Container is running
```

and

```text
Application is operational
```

where practical.

Release tooling shall be able to automate appropriate verification without requiring the operator to manually rediscover how application health is determined.

---

## 7.10 Release Compatibility Definition

The Application Release defines the compatible combination of artifacts required to operate a particular application version.

Internal components do not need to share identical numeric version strings.

For example:

```text
Application Release 2.4.0

Source Tag ............. v2.4.0
Backend Image .......... api-build-184
Frontend Image ......... web-build-73
Database Revision ...... rev_018
```

Release engineering shall explicitly record the artifact identities and database state included or required by the Application Release.

Compatibility shall therefore be established by the versioned Application Release rather than inferred from coincidentally matching component version numbers.

---

## 7.11 Release Construction Responsibility

Once the application satisfies the engineering requirements of this standard, release engineering is responsible for constructing the deployable Application Release.

The release-engineering process may generate or assemble resources such as:

- Versioned Docker image archives.
- Production Docker Compose configuration.
- Installation automation.
- Update automation.
- Shared script helpers.
- Configuration-generation logic.
- Database initialization and migration invocation.
- Credential generation.
- DBeaver provisioning.
- HTTPS and certificate provisioning.
- Browser permission provisioning.
- Verification procedures.
- Release metadata.
- Release documentation.

These mechanisms are **consumers of the application engineering contracts defined by this document**.

Their detailed implementation is intentionally outside this chapter and is governed by the RAH Application Release & Deployment Standard and its engineering implementation guidance.

---

## 7.12 Release Engineering Readiness Criteria

Before release construction begins, RAH Lab should verify that the applicable requirements have been satisfied:

- An identifiable source state exists.
- Application functionality has been technically validated.
- Docker images can be built reproducibly.
- Docker Compose describes the intended architecture.
- Compose identity is stable.
- Required configuration is externalized and documented.
- Persistent configuration is identified.
- Persistent application state is identified.
- Database initialization is reproducible.
- Database migration is controlled and versioned.
- Database connection requirements are documented.
- Required external and shared services are documented.
- Offline runtime behavior has been validated.
- Browser capability requirements are identified.
- Health and verification mechanisms are available.
- Deployment behavior does not depend upon developer-specific paths or knowledge.
- Another RAH engineer can understand the information required to construct the release.

When these conditions are satisfied, the project is considered ready to enter the RAH Application Release engineering process.

# 8. Project Delivery & Engineering Handover

This chapter defines the engineering handover requirements that shall be satisfied when responsibility for a software project is transferred to RAH Lab.

Project delivery represents the transfer of sufficient technical ownership for RAH Lab to understand, build, modify, validate, release, deploy, update, troubleshoot, and maintain the application independently of its original development team.

Project delivery is distinct from an **Application Release**.

An Application Release is a versioned deployable artifact governed by the RAH Application Release & Deployment Standard.

Project delivery is the transfer of the **engineering assets and knowledge from which present and future Application Releases can be constructed**.

---

## 8.1 Handover Philosophy

A software project shall not be considered successfully handed over merely because its source code has been copied to RAH Lab.

The handover should provide sufficient engineering ownership for RAH Lab to continue the software lifecycle.

Following a successful handover, RAH Lab should be capable of:

- Understanding the application architecture.
- Building the application.
- Modifying the source code.
- Building Docker images.
- Reproducing the deployment architecture.
- Configuring the application.
- Initializing a new database.
- Migrating an existing database.
- Identifying persistent application state.
- Understanding external infrastructure dependencies.
- Testing the application.
- Constructing future Application Releases.
- Troubleshooting technical and operational problems.
- Continuing future development.

Long-term maintenance shall not depend upon undocumented knowledge or the continued availability of the original development team.

---

## 8.2 Authoritative Source Repository

Every delivered project shall establish an authoritative RAH-controlled source repository.

The repository should contain, where applicable:

- Complete application source code.
- Relevant Git history.
- Stable source branches.
- Existing release tags.
- Dependency declarations.
- Build configuration.
- Docker engineering resources.
- Database engineering resources.
- Configuration templates.
- Tests.
- Technical documentation.

Where software originates from an external developer, available history should be preserved whenever practical.

The RAH-managed repository becomes the authoritative source for future:

- Engineering.
- Bug fixing.
- Feature development.
- Release construction.
- Database evolution.
- Deployment engineering.
- Long-term maintenance.

External repositories may remain upstream sources, but RAH production ownership shall not depend upon uncontrolled external repository state.

---

## 8.3 Application Architecture Handover

The delivered project shall provide enough information for another engineer to understand how the application is structured.

Documentation should identify, where applicable:

- Major application components.
- Backend architecture.
- Frontend architecture.
- Database architecture.
- Internal service relationships.
- External service dependencies.
- Shared infrastructure dependencies.
- Authentication model.
- Persistent storage.
- Important architectural decisions.
- Known architectural limitations.

The objective is not to document every implementation detail.

The objective is to prevent future engineers from having to reverse engineer fundamental system boundaries before they can safely modify or release the application.

---

## 8.4 Build and Dependency Handover

RAH Lab shall receive the information and resources required to reproduce application builds.

The handover shall identify where applicable:

- Required programming-language versions.
- Backend dependencies.
- Frontend dependencies.
- Native dependencies.
- Package-management files.
- Build commands.
- Build-time environment requirements.
- Docker build requirements.
- Required static assets.
- Offline runtime dependencies.

Dependencies that exist only on a developer's workstation and are not declared by the project represent an incomplete handover.

RAH Lab should be able to reproduce the application artifacts from the authoritative project source using the documented engineering environment.

---

## 8.5 Docker and Deployment Engineering Handover

Every project intended for Docker deployment shall provide the engineering resources required to reproduce its container architecture.

These should include where applicable:

- Backend Dockerfile.
- Frontend Dockerfile or equivalent.
- Dockerfiles for additional project-specific services.
- Docker Compose source.
- Reverse-proxy configuration.
- Environment configuration template.
- Network definitions.
- Persistent-volume definitions.
- Health-check definitions.
- Required service relationships.
- Port requirements.

The handover shall identify which services are:

- Application-specific.
- Persistent.
- Replaceable.
- Provided by shared RAH infrastructure.

The delivered Docker architecture shall satisfy the Docker Engineering Standard before the project is considered release-ready.

The handover does not need to contain a manually assembled production Application Release if RAH Lab is assuming engineering ownership before release construction. It must, however, contain everything required to construct one.

---

## 8.6 Database Handover

Every project using a database shall provide sufficient resources and documentation for RAH Lab to maintain the database independently.

The handover should identify:

- Database engine.
- Database architecture.
- Database hosting model.
- Schema or entity model.
- Initial installation mechanism.
- Lookup and seed data.
- Migration mechanism.
- Current migration/revision state.
- Required roles and permissions.
- Application connection requirements.
- Persistent-storage requirements.
- Backup and recovery considerations.

The database handover shall distinguish between:

```text
Initial Database Installation
```

and

```text
Existing Database Migration
```

where both apply.

RAH Lab shall not depend upon the original developer manually modifying production database schemas during future updates.

Production data itself is not part of the software-project handover unless an explicitly approved operational procedure requires otherwise.

---

## 8.7 Configuration Handover

The project shall document the complete application configuration contract.

This includes where applicable:

- Required environment variables.
- Optional environment variables.
- Safe defaults.
- Network ports.
- Database parameters.
- Shared-service endpoints.
- Authentication settings.
- Storage locations.
- Application secrets.
- Hardware requirements.
- Operating-system requirements.
- Browser capability requirements.

Production credentials and machine-specific operational values are not required to exist in the source repository.

Instead, the project shall define **what configuration is required and how the application consumes it**.

Application Release tooling is responsible for establishing and preserving deployment-specific operational values according to the RAH Application Release & Deployment Standard.

---

## 8.8 Testing and Verification Handover

The project shall provide enough information for RAH Lab to determine whether the software continues to operate correctly after modification or release.

Where applicable, the handover should include:

- Automated tests.
- Test execution instructions.
- Manual functional verification procedures.
- Health endpoints.
- Container health checks.
- Database verification procedures.
- Integration verification.
- Shared-service verification.
- Important regression scenarios.
- Known testing limitations.

Critical application behaviors that cannot be reasonably inferred from the software should be documented.

The objective is to allow RAH Lab to distinguish a successfully built application from a correctly functioning application.

---

## 8.9 Technical Documentation Handover

Every delivered project shall contain sufficient engineering documentation to support independent maintenance.

Documentation should include where applicable:

- Project overview.
- Business purpose.
- Technology stack.
- Architecture overview.
- Development setup.
- Project structure.
- Build procedure.
- Configuration contract.
- Database engineering guide.
- Docker architecture.
- External and shared-service dependencies.
- Testing procedures.
- Release-engineering considerations.
- Known technical limitations.
- Important maintenance considerations.

Repository documentation shall focus on durable **engineering knowledge**.

Machine-specific production information such as:

- Generated credentials.
- Current deployed version.
- Production database connection details.
- DBeaver registrations.
- Installation dates.
- Deployment history.
- Production certificate information.

belongs to the protected operational documentation system rather than the engineering repository.

---

## 8.10 Existing Release Information

When an existing application is transferred to RAH Lab, available release history should be preserved whenever practical.

Relevant information may include:

- Existing application versions.
- Git release tags.
- Existing Docker image identifiers.
- Database revisions.
- Release notes.
- Previous deployment documentation.
- Known compatibility constraints.
- Known production versions.

Historical information does not need to be artificially rewritten to match current RAH conventions.

Instead, RAH Lab should establish a clear controlled baseline from which future releases follow the current standards.

This prevents loss of useful engineering history while avoiding unnecessary reconstruction of legacy release processes.

---

## 8.11 Knowledge Transfer

Where practical, the original development team should provide structured technical knowledge transfer before final project acceptance.

Knowledge transfer should concentrate on information that is difficult to recover from source code alone, including:

- Architectural reasoning.
- Important design decisions.
- Non-obvious dependencies.
- Operational constraints.
- Known technical debt.
- Known failure modes.
- Sensitive migration areas.
- Difficult maintenance areas.
- Important customer or workflow assumptions.
- Future improvement recommendations.

Knowledge transfer complements documentation; it does not replace it.

Important information required for future maintenance should be incorporated into durable project documentation rather than remaining solely in conversations or individual memory.

---

## 8.12 Handover Deficiencies

RAH Lab may receive software that does not initially satisfy every requirement of this standard.

This is particularly likely for:

- Legacy software.
- Externally developed applications.
- Projects already operating in production.
- Projects with incomplete documentation.
- Applications not originally designed for RAH infrastructure.

Such projects should not automatically be rejected when RAH has an operational reason to assume responsibility for them.

Instead, identified deficiencies shall be documented and classified according to their effect on:

- Build reproducibility.
- Maintainability.
- Database safety.
- Deployment reproducibility.
- Offline compatibility.
- Security.
- Release readiness.
- Operational support.

Required remediation shall be completed before the project enters stages for which the missing capability is necessary.

This allows RAH Lab to assume controlled ownership of imperfect existing software without falsely declaring it compliant.

---

## 8.13 Project Acceptance Criteria

A project is considered successfully handed over when RAH Lab has sufficient engineering ownership to maintain it independently.

Applicable acceptance criteria include:

- Authoritative source repository established.
- Source code is complete.
- Application build process is reproducible.
- Dependencies are declared.
- Application architecture is understood.
- Docker architecture is reproducible.
- Configuration contract is documented.
- Persistent state is identified.
- Database initialization is reproducible.
- Database migration mechanism is understood and controlled.
- Required external and shared services are documented.
- Offline runtime dependencies are understood.
- Testing and verification mechanisms are available.
- Engineering documentation is sufficient for future maintenance.
- Existing release history has been preserved where practical.
- Significant handover deficiencies have been identified and documented.
- RAH Lab can construct future Application Releases without dependence upon undocumented original-developer knowledge.

Project acceptance does not necessarily mean that the application is immediately ready for production deployment.

Where deficiencies remain, acceptance establishes engineering ownership while the project continues through the required remediation, validation, and release-readiness activities.

---

## 8.14 Long-Term Ownership

Acceptance by RAH Lab marks the beginning of institutional software ownership.

After acceptance, the authoritative project source, engineering knowledge, release history, and future development are maintained according to RAH Lab standards.

Future changes shall follow the established engineering lifecycle:

```text
Engineering
        │
        ▼
Validation
        │
        ▼
Release Readiness
        │
        ▼
Application Release Engineering
        │
        ▼
Deployment
        │
        ▼
Operational Maintenance
```

The objective is that the software remains maintainable even as developers, infrastructure, application versions, and operational requirements change.

A successfully handed-over application becomes a sustainable RAH engineering asset rather than software whose continued operation depends upon the individuals who originally created it.
