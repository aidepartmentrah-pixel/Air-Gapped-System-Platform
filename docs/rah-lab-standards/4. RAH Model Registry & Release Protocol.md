# Purpose

Machine learning models are versioned engineering artifacts that evolve independently from application source code. Due to their size, binary format, and independent release lifecycle, they are not stored within the source code repository.

This standard defines how RAH Lab stores, versions, retrieves, and integrates machine learning model artifacts throughout the software development lifecycle. Its objectives are to:

- Establish a single canonical online registry for approved model artifacts.
- Standardize how models are organized and versioned.
- Ensure developers can retrieve the correct model versions required by an application.
- Support both online installations and offline (air-gapped) deployment workflows.
- Keep model management consistent across all AI software projects.

This document defines the engineering standard for model artifact management. It does not define model training procedures, dataset management, experiment tracking, or machine learning development methodologies.

# Scope

This standard applies to all machine learning model artifacts developed, maintained, or distributed by RAH Lab software projects.

Model artifacts include, but are not limited to:

- Model weight files (PyTorch, TensorFlow, scikit-learn, ONNX, GGUF, etc.).
- Tokenizers and vocabulary files.
- Model configuration files.
- Label mappings and class definition files.
- Model-specific metadata required for inference.
- Evaluation reports accompanying approved model releases.
- Documentation required to understand and consume a model artifact.

This standard does **not** cover:

- Training datasets.
- Raw hospital or patient data.
- Experiment notebooks.
- Training pipelines.
- Feature engineering code.
- Experiment tracking systems.
- Continuous training infrastructure.

# Registry

Every approved machine learning model shall have one canonical online copy maintained within the RAH Lab model registry. This registry serves as the authoritative source for storing, versioning, and distributing model artifacts throughout the software development lifecycle.

The current registry implementation is a private Hugging Face Organization. All approved model artifacts intended for software development or deployment shall be published to this registry.

The model registry is intended for engineering artifacts only. It is used to retrieve approved model versions during software development, online installation, and release preparation. Offline production systems shall never communicate directly with the online registry.

The registry provides the following engineering capabilities:

- Centralized storage of approved model artifacts.
- Version-controlled model repositories.
- Consistent model retrieval across development environments.
- Reproducible application installations using approved model versions.
- Preparation of model artifacts for offline deployment.

# Registry Management

The RAH Lab Hugging Face Organization is the centralized registry for all approved machine learning model artifacts.

Each model repository shall represent a single independently versioned model or a closely related group of models that are developed, versioned, and released together.

The registry is maintained as the canonical engineering source for model artifacts. Source code remains managed through Git repositories, while machine learning models are managed through the model registry.

Developers shall retrieve model artifacts from the registry during software development and online installation. Offline deployments shall consume model artifacts prepared from the registry as part of the application release package.

The registry is intended exclusively for model artifact management and shall not be used to store application source code, datasets, or operational system data.

# Repository Organization

The model registry is organized into independent repositories. Each repository shall contain either:

- A single machine learning model that is versioned independently, or
- A closely related group of model artifacts that are always developed, versioned, and released together.

Repositories should represent logical engineering units rather than complete software applications. Models that have independent release cycles, different consumers, or separate maintenance lifecycles should be stored in separate repositories.

Repository names shall follow a consistent naming convention that clearly identifies the project and model purpose. A recommended naming format is:

```
department-project-model-purpose
```

Examples:

```
rah-pfms-feedback-domain-classifier

rah-pfms-feedback-stage-classifier

rah-shared-whisper-small
```

The repository organization should support independent versioning, straightforward model discovery, and future reuse across multiple software projects.

# Visibility & Access

Machine learning model repositories shall be private by default.

Public repositories may be used only for models that are intentionally released for public consumption and contain no proprietary, confidential, or organization-specific artifacts.

Developers requiring model artifacts for software development or online installation shall be granted read access to the appropriate repositories.

Only authorized developers responsible for maintaining a model should publish or update model artifacts within the registry.

Offline production systems shall never require direct access to the online model registry.

# Repository Contents

Each model repository shall contain all artifacts required to successfully execute the published model during inference.

Depending on the model architecture, a repository may contain:

- Model weight files.
- Tokenizers and vocabulary files.
- Model configuration files.
- Label mappings and class definition files.
- Model-specific metadata.
- Documentation describing the model.
- Evaluation reports accompanying the published model.

Each repository should include a `README.md` describing:

- The purpose of the model.
- The machine learning framework used.
- Required runtime libraries.
- Expected model inputs and outputs.
- The intended application(s) consuming the model.

The following artifacts shall **not** be stored within the model registry:

- Training datasets.
- Raw hospital or patient data.
- Database exports.
- Application source code.
- Credentials, API keys, or secrets.
- Experiment notebooks.
- Temporary checkpoints or intermediate training artifacts.
- Logs or runtime-generated files.

The registry is intended exclusively for approved model artifacts required for software development, deployment, and inference.

# Versioning

Every published model shall be uniquely identifiable through an explicit version or immutable repository revision.

A published model version shall represent a fixed engineering artifact. Once referenced by a software application, its contents shall not be modified without publishing a new identifiable version or repository revision.

Applications should reference the exact model version or repository revision they were developed and tested against. This ensures that software installations retrieve the same model artifacts used during development and validation.

Model repositories may evolve over time through successive published versions. Previous versions should remain available whenever practical to support reproducibility, rollback, and maintenance of existing application releases.

# Upload Process

Machine learning model artifacts shall be uploaded to the model registry only after they have been prepared for software consumption.

Before publishing a model, developers should verify that:

- All required model artifacts are present.
- Repository documentation has been updated.
- The published model can be successfully loaded for inference.
- The model repository contains only approved engineering artifacts.

Each publication shall create a new identifiable model version or repository revision. Previously published versions shall not be silently modified.

After publication, developers should verify that the uploaded model artifacts can be successfully retrieved from the registry and loaded within a clean development environment.

The upload process concludes only after the published model has been validated for downstream software development and deployment.

# Download Process

Applications shall retrieve model artifacts exclusively from the canonical model registry during software development and online installation.

Developers shall retrieve the exact model version or repository revision required by the application being developed or maintained.

Downloaded model artifacts shall be stored in the application's designated local model directory and shall remain separate from the application's source code repository.

Before executing an application, developers should verify that:

- All required model artifacts have been successfully downloaded.
- The downloaded model version matches the version expected by the application.
- The model can be successfully loaded by the application runtime.

Offline production systems shall not retrieve models directly from the online registry. Required model artifacts shall instead be distributed as part of the prepared offline application release.

# Offline Deployment

Offline (air-gapped) production systems shall never communicate directly with the online model registry.

During release preparation, the exact model artifacts required by the application shall be retrieved from the canonical model registry and incorporated into the offline application release package.

The offline release package shall contain all model artifacts required for application execution, eliminating any dependency on external network resources after deployment.

Model artifacts included in an offline release shall correspond to the exact model version or repository revision validated during software testing.

Any model updates to an offline deployment shall be performed by preparing and distributing a new application release package containing the updated model artifacts.

# Security

The model registry shall contain only engineering artifacts required for model execution and software deployment.

The following artifacts shall **never** be stored within the model registry:

- Patient information.
- Hospital databases or database exports.
- Training datasets containing sensitive information.
- Credentials, API keys, access tokens, or secrets.
- Application configuration containing confidential operational data.
- Runtime logs or generated output files.
- Any information subject to organizational confidentiality or regulatory protection.

All repositories shall be reviewed to ensure that only approved model artifacts are published to the registry.

Sensitive operational or clinical data shall remain within approved development or deployment environments and shall never be distributed through the model registry.
