# 1. Purpose, Scope, and Relationship to Other Standards

## 1.1 Purpose

The **RAH Application Release & Deployment Standard** defines the requirements that every application maintained by RAH Lab must satisfy when it is packaged, installed, updated, and maintained within the hospital's production environment.

Its purpose is to establish a consistent Application Release model that allows software engineered within RAH Lab to be transformed into a predictable, self-contained, and maintainable production deployment.

The standard defines the guarantees that an Application Release must provide, including:

- Versioned and reproducible release packaging.
- Separation between release media and the live application deployment.
- Stable application deployment locations and identities.
- Persistent application configuration.
- Repeatable initial installation.
- Repeatable software updates.
- Preservation of production data and operational state.
- Automated generation and preservation of required operational information.
- Offline runtime independence.
- Database deployment and migration support.
- Operational database accessibility through approved administration tools.
- Support for secure browser capabilities when required by the application.
- Deployment verification and recovery readiness.

The objective is that an approved Application Release can be delivered to the Offline Production Environment and operated without depending on undocumented knowledge, the original developer, the location of a previous release package, or repeated assistance from an engineering agent.

An Application Release is therefore treated as a formal engineering product rather than simply a collection of Docker images or deployment scripts.

---

## 1.2 Scope

This standard applies to all RAH Lab applications intended for deployment within the hospital's Offline Production Environment.

It governs the release and deployment requirements associated with:

- Application Docker images.
- Docker Compose deployment definitions.
- Environment configuration.
- Initial database installation.
- Database migrations.
- Application installation.
- Application updates.
- Persistent deployment state.
- Application and service credentials.
- Operational documentation.
- Deployment history.
- Database administration integration.
- Offline frontend and runtime dependencies.
- HTTPS and certificate requirements.
- Client workstation preparation when required by application functionality.
- Deployment verification.
- Rollback and recovery readiness.

The requirements apply regardless of whether the application was developed internally by RAH Lab or received from an external developer.

Project-specific implementation details may differ, but the resulting Application Release shall provide the operational guarantees defined by this standard.

---

## 1.3 What This Standard Does Not Define

This standard defines **what an Application Release and its deployment must guarantee**. It does not prescribe every implementation mechanism used to achieve those guarantees.

Detailed engineering mechanisms such as shell-script architecture, reusable deployment functions, exact Docker commands, browser-specific configuration mechanisms, and automation techniques belong to the **RAH Application Engineering Playbook**.

Similarly, this standard does not define:

- General software architecture and development requirements.
- The physical or virtual infrastructure architecture of RAH Lab.
- The engineering and publication of the RAH Offline Infrastructure Platform.
- Machine-specific laboratory configuration.
- Detailed human operating procedures.

Those responsibilities belong to the corresponding RAH standards and references.

---

## 1.4 Relationship to Other RAH Documentation

The Application Release & Deployment Standard operates between software engineering and production operations.

The relationship is:

```text
RAH Software Engineering Standard
        │
        │  defines how applications must be engineered
        ▼
Application Source
        │
        │
        ▼
RAH Application Engineering Playbook
        │
        │  provides implementation methods
        ▼
RAH Application Release & Deployment Standard
        │
        │  defines the guarantees the resulting release must satisfy
        ▼

        │
        ▼

        │

        ▼

```

The supporting documents have the following responsibilities:

- **RAH Software Engineering Standard** — Defines the engineering requirements applications must satisfy before release.
- **RAH Application Engineering Playbook** — Defines practical engineering patterns and mechanisms used to produce compliant Application Releases.
- **RAH Infrastructure Architecture** — Defines the infrastructure environment within which applications are deployed and operated.
- **RAH Offline Infrastructure Platform Standard** — Defines how the underlying air-gapped Debian platform and Infrastructure Releases are engineered and maintained.
- **RAH Model Registry & Release Protocol** — Governs approved machine-learning model artifacts that may be incorporated into Application Releases.
- **RAH Lab Operator Manual** — Defines the human procedures used to install, update, verify, recover, and maintain approved releases.
- **RAH-OIP Lab Environment Reference** — Records the current implementation-specific machines, addresses, versions, paths, and laboratory configuration.

This separation prevents release requirements, implementation mechanisms, infrastructure architecture, and operational procedures from being redefined independently across multiple documents.

# 2. Application Release Model

## 2.1 Definition of an Application Release

An **Application Release** is the versioned, self-contained delivery artifact used to install or update one specific RAH application.

Depending on the application, an Application Release may contain:

- Backend Docker images.
- Frontend Docker images.
- Supporting application Docker images.
- Docker Compose definitions.
- Environment configuration templates.
- Database initialization resources.
- Database migration resources.
- Installation and update automation.
- Verification resources.
- Required offline application assets.
- Approved machine-learning model artifacts when applicable.
- Client workstation resources when required.
- Release documentation.
- Version and integrity information.

An Application Release shall contain, or provide through approved dependencies, everything required to perform its intended deployment without retrieving required runtime resources from the public Internet.

The release represents a **deployable application version**. It is not itself the running production application.

---

## 2.2 Release Package and Live Deployment

RAH Lab distinguishes strictly between the **Application Release package** and the **live application deployment**.

The Application Release package is versioned delivery and staging material.

The live deployment is the persistent operational installation created and maintained on the production system.

The canonical application runtime hierarchy is:

```text
/opt/rah/apps/<app-slug>/
```

For example:

```text
/opt/rah/apps/stt-schedule/
/opt/rah/apps/patient-complaints/
/opt/rah/apps/blood-bank/
```

The live deployment location shall remain stable across application versions.

A release may therefore arrive as:

```text
HCAT_Release_2.3.0/
HCAT_Release_2.3.1/
HCAT_Release_2.4.0/
```

while all versions operate against the same persistent deployment location:

```text
/opt/rah/apps/hcat/
```

The versioned release directory from which an installation or update is executed shall never become the application's permanent runtime identity.

---

## 2.3 Persistent Deployment State

Operational state that must survive application updates shall belong to the live deployment or another explicitly defined persistent service, not to the incoming release package.

This includes, as applicable:

- Production environment configuration.
- Generated service credentials.
- Persistent application secrets.
- Docker volumes.
- Application-generated files.
- Database data.
- Backup locations.
- Certificates and private keys.
- Other deployment-specific state.

In particular, the production environment configuration shall persist independently from individual Application Release versions.

An update shall therefore be capable of applying a newly delivered release without requiring the operator to manually copy configuration or persistent state from the previous release directory.

---

## 2.4 Disposable Release Staging

An incoming Application Release is treated as **disposable staging material** after successful deployment.

The production application shall not depend on the continued presence of the directory from which the release was installed.

After installation or update has completed successfully and required release artifacts have been archived according to RAH policy, removing the staging copy shall not affect the running application.

Likewise, a future release shall be deployable from a new directory or approved transfer medium without manually carrying files forward from the previous release package.

This principle ensures that:

```text
Release 2.3.0
      │
      ├────────► /opt/rah/apps/<app-slug>/

Release 2.3.1
      │
      ├────────► /opt/rah/apps/<app-slug>/

Release 2.4.0
      │
      ├────────► /opt/rah/apps/<app-slug>/
```

The **release changes**.

The **application's operational home remains stable**.

---

## 2.5 Versioning and Immutability

Every published Application Release shall have a unique version.

Published releases are immutable engineering artifacts. Once a release has been approved and published, its contents shall not be silently modified.

Any correction to a published release requires a new release version.

Application Release versions shall provide sufficient traceability to determine:

- Which application version was deployed.
- Which Docker images were deployed.
- Which database migrations were associated with the release.
- Which configuration model was expected.
- Which release was previously installed.
- Which release is currently operating.

Historical Application Releases shall be retained according to RAH release archival policy to support traceability, recovery, and rollback.

The mutable production deployment and the immutable release artifact therefore serve different purposes:

```text
Application Release
Versioned
Immutable
Archived
Delivery Artifact
        │
        │ install / update
        ▼
Live Deployment
Stable Location
Persistent State
Operational
Updated Over Time
```

---

## 2.6 Application Releases and Infrastructure Releases

RAH Lab maintains two independent release categories:

### Application Release

An Application Release delivers or updates an individual software system.

It contains application-specific components such as:

- Application Docker images.
- Application configuration definitions.
- Database installation or migration resources.
- Application deployment automation.
- Application documentation.
- Application-specific supporting assets.

### Infrastructure Release

An Infrastructure Release is produced through the **RAH Offline Infrastructure Platform (RAH-OIP)** and provides or updates the underlying platform required to operate applications.

It may contain:

- Debian packages.
- Docker Engine and Docker Compose resources.
- Infrastructure utilities.
- Platform-level Docker images.
- Infrastructure installation resources.
- Infrastructure verification resources.

Application Releases and Infrastructure Releases are versioned independently.

An Application Release shall not unnecessarily include infrastructure components already provided and maintained by RAH-OIP.

Likewise, an Infrastructure Release shall not become the release mechanism for individual business applications.

The relationship is:

```text
RAH-OIP
   │
   ▼
Infrastructure Release
   │
   ▼
Offline Debian Platform
   │
   ├───────────────────────────────┐
   ▼                               ▼
Application Release A        Application Release B
   │                               │
   ▼                               ▼
Application A                 Application B
```

An application deployment may require a minimum compatible RAH-OIP version, but the application and infrastructure release histories remain independent.

This separation allows RAH Lab to update applications without unnecessarily modifying the underlying infrastructure and to maintain the offline platform without rebuilding unrelated applications.

# 3. Canonical Deployment Architecture

Every RAH application shall have a stable deployment identity and a persistent operational home independent of the Application Release from which it was installed.

The canonical deployment architecture separates:

1. **Versioned release artifacts**, which deliver software into the environment.
2. **Persistent live deployment state**, which represents the installed application.
3. **External persistent services**, such as production databases, where applicable.

This separation allows an application to move through multiple releases without rebuilding its operational identity or depending upon previous release directories.

---

## 3.1 Canonical Application Root

The standard root for deployed RAH applications is:

```text
/opt/rah/apps/
```

Each application shall have a unique stable application identifier, referred to as the **application slug**, and a corresponding deployment directory:

```text
/opt/rah/apps/<app-slug>/
```

Examples:

```text
/opt/rah/apps/hcat/
/opt/rah/apps/stt-schedule/
/opt/rah/apps/blood-bank/
```

The application slug represents the deployed application's persistent identity.

It shall remain stable across normal application releases.

For example:

```text
HCAT Release 2.3.0 ────┐
HCAT Release 2.3.1 ────┼───► /opt/rah/apps/hcat/
HCAT Release 2.4.0 ────┘
```

Release versions shall therefore not be incorporated into the canonical live deployment path.

---

## 3.2 Live Deployment State

The live deployment directory contains the machine-specific state required to operate the currently deployed application.

Depending on the application's architecture, this may include:

- The active Docker Compose definition.
- Persistent production environment configuration.
- Deployment-specific configuration.
- Certificates and keys required by the deployment.
- Application-specific persistent files.
- References to persistent Docker volumes.
- Other machine-specific operational state.

The exact directory layout may differ when justified by the application architecture, but the distinction between **release material** and **persistent deployment state** shall remain.

Application containers themselves should remain replaceable.

Operational state that must survive an update shall not depend upon the lifecycle of an individual application container or incoming release directory.

---

## 3.3 Persistent Environment Configuration

Production environment configuration shall persist across Application Releases.

Where `.env` is used, the active production `.env` shall belong to the stable live deployment rather than to an individual versioned release directory.

Conceptually:

```text
Incoming Release
    │
    │ provides expected configuration definition/template
    ▼
/opt/rah/apps/<app-slug>/
    │
    └── persistent production configuration
```

Initial installation may create or derive the production configuration from resources supplied by the Application Release.

Subsequent updates shall preserve existing production values unless a release explicitly introduces a controlled configuration change.

This prevents application updates from unintentionally replacing:

- Database credentials.
- Generated secrets.
- Service endpoints.
- Deployment-specific ports.
- Application configuration.
- Other environment-specific values.

An update shall not require the operator to rediscover or manually reconstruct existing production configuration.

---

## 3.4 Stable Docker Compose Identity

Every deployed application shall use an explicit and stable Docker Compose project identity.

The identity of the deployed application shall not be derived solely from:

- The incoming release directory name.
- The release version.
- The location from which deployment scripts were executed.

For example:

```text
HCAT_Release_2.3.0/
HCAT_Release_2.3.1/
HCAT_Release_2.4.0/
```

shall not unintentionally create three independent Docker Compose projects for the same application.

All releases targeting the same deployed application shall resolve to the same intended Compose project identity.

This requirement ensures that installation, update, verification, stopping, starting, and recovery operations consistently target the existing application deployment.

The exact mechanism used to establish and enforce the Compose project identity is defined by the **RAH Application Engineering Playbook**.

---

## 3.5 Release Independence

A live application deployment shall remain operational independently from the release package used to create it.

After successful installation or update:

- The application shall not execute required runtime files directly from the incoming release directory.
- Persistent configuration shall not remain dependent upon the release directory.
- Application identity shall not depend upon the release directory name.
- Required operational state shall reside in approved persistent locations.
- Removal of disposable staging material shall not break the deployed application.

Likewise, a new Application Release shall be capable of updating the application without depending upon the physical presence of the previous incoming release directory.

This requirement enables releases to be delivered through different staging locations or approved physical media while preserving one continuous production deployment.

---

## 3.6 Deployment Continuity

Application updates modify the deployed software version while preserving the identity and required persistent state of the application.

Conceptually:

```text
Release 1.0.0
     │
     ▼
┌─────────────────────────────┐
│ /opt/rah/apps/<app-slug>/   │
│                             │
│ Persistent configuration    │
│ Stable deployment identity  │
│ Persistent operational state│
└─────────────────────────────┘
     ▲
     │
Release 1.1.0
     ▲
     │
Release 1.2.0
```

The deployment therefore has a lifecycle that is longer than the lifecycle of any individual Application Release.

This continuity is fundamental to reliable updates, rollback, troubleshooting, and long-term maintenance.

---

# 4. Application Release Contents

An Application Release shall contain the application-specific artifacts required to perform its intended installation or update within the Offline Production Environment.

Release contents vary according to application architecture. Not every release requires every artifact listed in this chapter.

However, any component required for successful offline deployment or operation shall either:

- be included in the Application Release;
- already exist as an approved persistent deployment dependency;
- or be provided by an explicitly identified compatible RAH infrastructure service.

The release shall not silently depend upon resources that are unavailable within the air-gapped environment.

---

## 4.1 Release Manifest and Version Information

Every Application Release shall clearly identify:

- Application name.
- Application slug.
- Application Release version.
- Release date.
- Included deployable components.
- Required database changes.
- Required infrastructure dependencies.
- Minimum compatible infrastructure version when applicable.
- Required external or shared services.
- Relevant release notes.

The release shall provide sufficient information to determine what is being deployed before installation or update begins.

Where integrity information such as checksums is used, it shall accompany the corresponding release artifacts.

---

## 4.2 Docker Images

All application Docker images required by the release shall be provided in a form that can be loaded without access to an external container registry.

Typical images may include:

- Backend.
- Frontend.
- Reverse proxy.
- Background workers.
- Application-specific supporting services.

Images shall correspond to the published Application Release and shall not be rebuilt within the Offline Production Environment.

The exact images included depend upon the architecture of the application.

Shared infrastructure images already governed and supplied through RAH-OIP or another approved infrastructure mechanism should not be unnecessarily duplicated within every Application Release.

---

## 4.3 Docker Compose Definition

The release shall provide the Docker Compose definition required to deploy the application version.

The Compose definition shall identify the application services and their relationships, including as applicable:

- Docker images.
- Networks.
- Persistent volumes.
- Environment configuration.
- Published ports.
- Service dependencies.
- Restart behavior.
- Health checks.

The release-provided definition represents the deployment definition expected by that application version.

During installation or update, the appropriate deployment definition is applied to the application's canonical live deployment according to the deployment mechanisms defined by the Engineering Playbook.

---

## 4.4 Environment Configuration Template

The Application Release shall define the environment configuration expected by the software.

Where `.env` configuration is used, the release shall provide a template or equivalent configuration definition identifying the required variables without embedding production-specific secrets.

This resource establishes:

- Which configuration values exist.
- Which values are required.
- Which values may be generated during installation.
- Which values require environment-specific configuration.
- Which new configuration requirements have been introduced by an update.

The template belongs to the release.

The resulting production configuration belongs to the persistent live deployment.

An Application Release shall not overwrite valid persistent production configuration merely because a new template is delivered.

---

## 4.5 Database Resources

When an application owns or evolves database state, the Application Release shall provide the resources required for the corresponding database operation.

For an initial installation, these may include:

- Database creation resources.
- Initial schema.
- Lookup or seed data.
- Required database roles.
- Initial application administrator resources where applicable.

For an update, these may include:

- Versioned schema migrations.
- Lookup-data migrations.
- Data transformations.
- Stored procedure or view changes.
- Other controlled database changes.

Database resources shall distinguish between **initial installation** and **migration of an existing production database**.

An application update shall not recreate an existing production database as a substitute for performing the required migration.

---

## 4.6 Deployment Automation

Every Application Release shall provide the automation required to perform its supported deployment operations.

At minimum, releases intended to support both initial installation and future maintenance shall provide standardized entry points for:

- Initial installation.
- Application update.
- Deployment verification.

Additional automation may be supplied for:

- Backup.
- Rollback.
- Recovery.
- Diagnostics.
- Client workstation preparation.

The release standard defines the required behavior of these operations.

The exact script structure, helper functions, commands, and implementation mechanisms are defined by the **RAH Application Engineering Playbook**.

---

## 4.7 Offline Application Assets

All application resources required during normal production operation shall be available without public Internet access.

An Application Release shall therefore account for runtime dependencies such as:

- Frontend JavaScript libraries.
- CSS frameworks.
- Fonts.
- Icons.
- Images.
- Static resources.
- Application-specific binaries.
- Other resources otherwise retrieved from public CDNs or external services.

Required frontend assets shall be bundled or otherwise made available through approved local infrastructure.

A production application shall not lose functionality, layout, styling, or required runtime behavior merely because public Internet access is unavailable.

Development-time Internet dependencies are permitted when they are resolved during engineering and do not become production runtime dependencies.

---

## 4.8 Model and Application Artifacts

Applications requiring machine-learning models or other large application-specific artifacts shall identify the exact artifacts required by the release.

Approved model artifacts shall be obtained according to the **RAH Model Registry & Release Protocol**.

The required production artifact shall then be included in the Application Release or provided through another explicitly approved offline delivery mechanism.

Production operation shall not depend upon downloading required model artifacts from an online model registry.

Model versions used by the application shall remain traceable to the corresponding Application Release.

---

## 4.9 Release Documentation

Every Application Release shall contain sufficient documentation to understand the release before deployment.

Release-level documentation may include:

- Release notes.
- Version information.
- Installation prerequisites.
- Update notes.
- Database migration information.
- Known issues.
- Compatibility requirements.
- Rollback considerations.
- Changes requiring operator attention.

Release documentation is distinct from the persistent operational documentation maintained under:

```text
/opt/rah/documentation/
```

The Application Release describes **the delivered version**.

The operational documentation describes **the deployed system and its history**.

Installation and update procedures shall maintain the relationship between these two forms of documentation.

---

## 4.10 Client-Side Resources

Some applications require configuration outside the application server in order to provide their intended functionality to hospital users.

Examples may include:

- Certificate trust resources.
- Browser configuration resources.
- Secure-origin configuration.
- Permission configuration.
- Workstation preparation scripts.
- Other application-specific client resources.

When such preparation is required, the Application Release shall contain the resources necessary to establish the supported client environment without public Internet access.

Client-side requirements shall be documented and versioned with the Application Release.

The deployment shall minimize manual workstation configuration whenever the required behavior can be established safely and reproducibly through deployment automation.

The detailed browser-specific or operating-system-specific implementation belongs to the **RAH Application Engineering Playbook**.

---

## 4.11 Release Self-Containment

An Application Release is considered self-contained when it contains or explicitly identifies every dependency required to perform its intended deployment within the approved RAH environment.

Self-containment does not mean duplicating the entire RAH infrastructure inside every application package.

A release may rely upon approved existing capabilities such as:

- Docker provided by RAH-OIP.
- A supported production database platform.
- Shared AI services.
- Shared infrastructure services.
- Existing persistent application state.

Those dependencies shall be explicit.

The release shall not rely upon:

- Undocumented files from a developer workstation.
- Files left behind in an older release directory.
- Public package repositories during deployment.
- Public container registries during deployment.
- Public CDNs during normal operation.
- Unrecorded manual configuration.
- Knowledge available only to the original developer.

This requirement establishes the boundary between a reproducible Application Release and an application that merely happens to work on an engineer's machine.

# 5. Installation Standard

Initial installation establishes the first persistent production deployment of an application.

An installation is not considered complete merely because Docker containers are running. It shall establish the complete operational state required to use, administer, understand, and maintain the application after the installation process has finished.

The standard installation process shall therefore create the live deployment, initialize required persistent state, establish credentials, prepare the database, register required operator tooling, generate operational documentation, start the application, and verify the resulting deployment.

---

## 5.1 One-Command Installation

Every Application Release intended for initial deployment shall provide a standardized installation entry point.

Under normal conditions, the operator should be able to initiate installation through a single command without manually performing intermediate configuration steps.

Conceptually:

```text
Application Release
        │
        ▼
Standard Installation Entry Point
        │
        ├──► Validate prerequisites
        ├──► Establish live deployment
        ├──► Generate required credentials
        ├──► Prepare configuration
        ├──► Initialize database
        ├──► Load application images
        ├──► Start application services
        ├──► Configure operator integrations
        ├──► Generate operational documentation
        └──► Verify deployment
```

The installation process may internally execute multiple scripts, tools, migrations, or configuration operations.

Those internal mechanisms shall not require the operator to repeatedly stop the installation in order to discover paths, passwords, ports, database names, or other information that can be determined or generated automatically.

If information genuinely requires an operator decision, the requirement shall be explicit and limited to information that cannot reasonably be derived by the release.

---

## 5.2 Installation Prerequisite Validation

Before modifying the target system, installation shall verify the prerequisites required by the Application Release.

Depending on the application, validation may include:

- Required RAH-OIP or platform compatibility.
- Docker availability.
- Required shared infrastructure services.
- Required network ports.
- Required filesystem locations and permissions.
- Database service availability.
- Required deployment resources.
- Required Docker images.
- Sufficient storage.
- Other application-specific dependencies.

Installation should fail clearly when a mandatory prerequisite is unavailable rather than proceeding into an incomplete or ambiguous deployment.

Failure messages shall provide sufficient information to identify the unmet requirement.

---

## 5.3 Persistent Deployment Creation

Initial installation shall establish the application's canonical live deployment under:

```text
/opt/rah/apps/<app-slug>/
```

The installation process shall create the persistent deployment resources required by the application and establish its stable Docker Compose identity.

Release resources required for live operation shall be installed into their appropriate persistent locations.

The resulting deployment shall not depend upon continued execution from the incoming Application Release directory.

After successful installation, the canonical application location becomes the operational home of the application.

---

## 5.4 Production Configuration Creation

Initial installation shall create the production configuration required by the application.

Where `.env` configuration is used, the production `.env` shall be established within the persistent deployment rather than remaining tied to the incoming release.

The installation process shall:

- Start from the configuration definition supplied by the release.
- Generate values that can safely be generated automatically.
- Populate known deployment-specific values.
- Preserve a clear distinction between templates and active production configuration.
- Prevent required configuration from remaining accidentally dependent upon development values.

The completed production configuration becomes persistent deployment state and shall survive future Application Releases.

---

## 5.5 Machine and Service Credentials

Credentials required for internal machine-to-machine or service operation should be generated automatically during initial installation whenever practical.

Examples include:

- Database passwords.
- Application secret keys.
- Internal service credentials.
- Generated tokens.
- Other machine-oriented secrets.

Generated values shall be compatible with the actual software stack in which they are used.

RAH Lab does not require a universal password character policy for automatically generated service credentials. The implementation shall generate values that are sufficiently suitable for their purpose while avoiding characters or formats known to cause compatibility problems with the corresponding application, database, shell, configuration format, or deployment tooling.

Generated credentials become part of the persistent deployment state and shall not be regenerated during a routine application update.

---

## 5.6 Application Administrator Credentials

Where an application requires an initial human-facing administrator account, installation shall ensure that a usable administrator account exists.

RAH Lab permits predictable initial operator-facing credentials, such as:

```text
Username: admin
Password: admin123
```

where this model is appropriate for the application and accepted within the controlled hospital environment.

If the required administrator already exists, installation shall handle the condition deterministically rather than failing because initialization is being executed against an existing valid state.

Application administrator credentials are conceptually distinct from automatically generated machine and service credentials.

The operator shall be able to discover the active administrator credentials through the application's approved operational documentation.

---

## 5.7 Database Initialization

For an application's first production installation, the deployment process shall establish the required database state.

Depending on the architecture, this may include:

- Creating the application database.
- Applying the initial schema or migration baseline.
- Creating lookup and seed data.
- Establishing database users and permissions.
- Creating the initial application administrator.
- Recording the initial database or migration version.

Database initialization shall be safe for the expected installation state and shall fail clearly if it encounters an incompatible pre-existing database rather than silently destroying or replacing operational data.

Production data shall never be included as part of an Application Release.

---

## 5.8 DBeaver Registration

Where the application's database is intended to be administered through DBeaver, initial installation is not operationally complete until the required database connection is available to the operator through the approved DBeaver environment.

The connection shall expose the information necessary for administration, including as applicable:

- Application/database identity.
- Database type.
- Host.
- Port.
- Database name.
- Required username.
- Required credential.

The objective is that an operator shall not need to inspect Docker containers, search configuration files, rediscover ports, or ask the original developer or an AI engineering agent how to connect to the application's database after deployment.

The exact mechanism used to provision the DBeaver connection belongs to the **RAH Application Engineering Playbook**.

---

## 5.9 Operational Documentation Generation

Initial installation shall automatically create or update the application's persistent operational documentation under the RAH documentation hierarchy:

```text
/opt/rah/documentation/
```

The generated documentation shall contain sufficient information for a future operator to understand the installed deployment without reconstructing its configuration manually.

Depending on the application, this shall include:

- Application name.
- Application slug.
- Installed Application Release version.
- Installation date.
- Canonical deployment path.
- Application access information.
- Relevant service ports.
- Database platform.
- Database connection information.
- Required operational credentials.
- Application administrator credentials where applicable.
- DBeaver connection information.
- Infrastructure or shared-service dependencies.
- Certificate information where applicable.
- Relevant operational notes.

Because this documentation may contain credentials and other sensitive operational information, the documentation Vault shall be treated as protected internal operational material.

---

## 5.10 Installation History

The initial installation shall establish the beginning of the application's deployment history.

The history shall identify at minimum:

- Application Release installed.
- Installation date.
- Installation result.
- Relevant database version or migration state.
- Deployment location.
- Other information required to understand the resulting operational state.

Subsequent updates shall extend this history rather than replacing it.

---

## 5.11 Installation Verification

Installation shall conclude with verification of the resulting deployment.

Verification shall confirm, as applicable:

- Required Docker services are running.
- Expected application services are reachable.
- Database initialization completed successfully.
- Database connectivity is functional.
- Persistent production configuration exists.
- Stable deployment identity has been established.
- Required shared services are reachable.
- DBeaver registration is available when required.
- Operational documentation has been generated.
- Required application credentials are discoverable.
- HTTPS and client-side requirements operate when applicable.
- Core application functionality is available.

A successful command execution alone does not constitute successful installation.

The resulting system shall satisfy the operational requirements of the Application Release.

If mandatory verification fails, the installation shall be reported as unsuccessful or incomplete and shall not be recorded as a successfully deployed production release.

---

# 6. Update Standard

An application update replaces or evolves the software components of an existing deployment while preserving the operational state that must survive between versions.

An update shall operate against the existing canonical deployment rather than creating a new application identity for every release.

The fundamental update principle is:

> **Replace what belongs to the software version. Preserve what belongs to the deployment.**

An update is complete only when the new application version is running against the intended persistent state, required database changes have been applied, operator integrations remain functional, operational history has been updated, and the resulting deployment has passed verification.

---

## 6.1 One-Command Update

Every Application Release intended to update an existing deployment shall provide a standardized update entry point.

Under normal conditions, the operator should initiate the complete update through a single command.

Conceptually:

```text
New Application Release
        │
        ▼
Standard Update Entry Point
        │
        ├──► Validate existing deployment
        ├──► Validate release compatibility
        ├──► Preserve persistent state
        ├──► Backup where required
        ├──► Load new application images
        ├──► Apply database migrations
        ├──► Apply deployment definition
        ├──► Reconcile application services
        ├──► Ensure operator integrations
        ├──► Update operational documentation
        ├──► Record deployment history
        └──► Verify updated deployment
```

The operator shall not be required to manually move `.env` files, rediscover credentials, reconstruct DBeaver connections, identify old container instances, or copy operational state between release folders as part of a normal update.

---

## 6.2 Existing Deployment Validation

Before modifying the application, the update process shall identify and validate the existing canonical deployment.

Validation shall confirm, as applicable:

- Expected application deployment exists.
- Stable application identity matches the intended release.
- Existing production configuration is available.
- Required persistent resources are available.
- Existing database state is identifiable.
- Current application/database version is compatible with the intended update path.
- Required infrastructure services are available.

An update shall fail clearly rather than accidentally behaving as a fresh installation when the expected production deployment cannot be safely identified.

---

## 6.3 Preservation of Persistent State

Routine application updates shall preserve all persistent operational state that is not explicitly intended to change.

This includes, as applicable:

- Production `.env`.
- Generated machine and service credentials.
- Application administrator state.
- Production database data.
- Docker volumes.
- Certificates and private keys.
- Persistent application files.
- Operational documentation.
- Deployment history.
- Other deployment-specific state.

A new Application Release shall not replace persistent state merely because equivalent files or defaults exist inside the incoming release package.

If an update genuinely requires a change to persistent configuration, that change shall be handled as an explicit controlled migration rather than an accidental overwrite.

---

## 6.4 Credential Preservation

Automatically generated machine and service credentials shall normally remain stable throughout routine application updates.

An update shall not regenerate credentials simply because a new Application Release is being installed.

Credential rotation, when required, is a separate controlled operational action and shall account for every dependent service before replacing active values.

Likewise, existing application administrator accounts shall normally be preserved.

The purpose of an application update is to evolve the software—not to silently reset the operational identity of the deployed system.

---

## 6.5 Database Migration

Database schema evolution shall occur through controlled migrations.

Before applying database changes, the update process shall determine the existing migration state and apply only the changes required to reach the target version.

An update shall not recreate a production database as a substitute for migration.

Where the migration carries meaningful risk to production information, an appropriate database backup shall be created before modification.

Migration failure shall prevent the deployment from being reported as successfully updated.

The resulting database version shall remain compatible with the deployed application version.

---

## 6.6 Deployment Definition Update

When the new Application Release introduces changes to the Docker Compose definition or other version-controlled deployment resources, the required resources shall be applied to the canonical live deployment.

This process shall preserve machine-specific persistent configuration while updating the version-specific deployment definition.

The incoming release directory itself shall not become the new permanent operational home.

The update therefore modifies:

```text
Software Definition
Docker Images
Migration State
Version-Specific Deployment Resources
```

while preserving:

```text
Application Identity
Canonical Deployment Path
Production Configuration
Credentials
Production Data
Persistent Operational State
```

---

## 6.7 Deterministic Service Reconciliation

After new Docker images and deployment definitions are applied, application services shall be reconciled deterministically with the target release.

The update process shall ensure that:

- Services intended to run the new version actually use the new release artifacts.
- Stale application containers do not survive unintentionally.
- Failed containers from previous deployment attempts do not prevent correct replacement.
- Removed application services do not remain active unintentionally.
- Required application services are recreated when necessary.
- Persistent infrastructure is not treated as disposable merely because application containers require recreation.

The exact Docker Compose commands and recreation strategy are implementation mechanisms defined by the **RAH Application Engineering Playbook**.

The requirement of this Standard is the resulting state: the running application services shall accurately represent the intended Application Release.

---

## 6.8 DBeaver Reconciliation

Every update shall ensure that the application's required DBeaver connection remains available and correct.

This requirement also allows an update to bring an older application deployment into compliance when it was originally installed without automated DBeaver registration.

The update process shall therefore ensure or repair the DBeaver connection rather than assuming that a previous installation configured it correctly.

Where connection information has not changed, the existing usable registration should remain valid.

Where relevant database connection information has changed, the DBeaver registration shall be reconciled with the resulting deployment.

The exact technical mechanism remains an Engineering Playbook concern.

---

## 6.9 Operational Documentation Update

Every successful application update shall update the application's persistent operational documentation.

Documentation shall reflect the resulting deployment rather than merely preserving information from the initial installation.

As applicable, it shall update:

- Current Application Release version.
- Update date.
- Database/migration version.
- Deployment configuration changes.
- Relevant endpoint or port changes.
- Database connection changes.
- Certificate changes.
- Operational notes.
- Other information necessary to administer the current deployment.

Stable information such as persistent credentials shall remain available rather than disappearing when documentation is regenerated.

---

## 6.10 Deployment History

Application updates shall append to the existing deployment history.

A deployment history entry shall identify, at minimum:

- Previous Application Release version.
- Target Application Release version.
- Update date.
- Database migration applied.
- Update result.
- Relevant operational observations.
- Rollback or recovery information when applicable.

The deployment history shall allow a future operator to determine how the currently installed system reached its present state.

An update shall not erase the history established by previous installations and releases.

---

## 6.11 Update Verification

Every update shall conclude with verification of the resulting production state.

Verification shall confirm, as applicable:

- Expected Application Release is running.
- Required Docker services are healthy.
- Stale application containers have not survived unintentionally.
- Persistent configuration has been preserved.
- Existing credentials remain valid.
- Database migrations completed successfully.
- Production data remains available.
- Database connectivity is functional.
- DBeaver registration remains usable.
- Required shared infrastructure services are reachable.
- Operational documentation reflects the new version.
- Deployment history contains the update.
- HTTPS and client-side functionality continue to operate when applicable.
- Core application functionality remains available.

Where practical, verification should confirm both **the new software version** and **the preservation of the previous deployment's required operational state**.

---

## 6.12 Update Failure

An update shall not be considered successful merely because some new containers were created.

If mandatory migration, deployment, service startup, persistence, integration, or verification requirements fail, the update shall be treated as unsuccessful or incomplete.

The deployment shall then follow the applicable recovery or rollback procedure rather than leaving an ambiguous partially updated system in production.

Failure information shall be recorded sufficiently to support diagnosis and corrective engineering.

---

## 6.13 Installation and Update Consistency

Initial installation and application update are different lifecycle operations, but they shall produce the same canonical form of operational deployment.

After either operation, the operator should encounter the same predictable structure:

```text
/opt/rah/apps/<app-slug>/
        │
        └── Live Application Deployment

/opt/rah/documentation/
        │
        └── Application Operational Documentation

DBeaver
        │
        └── Application Database Connection

Production Database
        │
        └── Current Persistent Data and Schema

Docker
        │
        └── Current Application Services
```

This consistency is intentional.

The operator should not need to understand whether an application's current state resulted from its first installation or its tenth update in order to locate, administer, or maintain it.

# 7. Operational Documentation Standard

Every deployed RAH application shall maintain persistent operational documentation describing the application as it actually exists within the production environment.

Operational documentation is part of the deployment itself. An application shall not be considered fully operationally maintainable if a future RAH Lab engineer cannot determine how it is deployed, how to access its administrative resources, which version is running, how its database is reached, and how the deployment has evolved over time.

The purpose of this documentation is to eliminate dependence on personal memory, undocumented configuration, inspection of running containers, or repeated consultation with the original developer or an AI engineering agent.

---

## 7.1 Canonical Documentation Root

The canonical root for RAH operational documentation is:

```text
/opt/rah/documentation/
```

This directory exists parallel to the canonical application deployment root:

```text
/opt/rah/
│
├── apps/
│   ├── <app-a>/
│   ├── <app-b>/
│   └── <app-c>/
│
└── documentation/
    ├── <app-a>/
    ├── <app-b>/
    └── <app-c>/
```

The two hierarchies serve different purposes:

```text
/opt/rah/apps/
        │
        └── Machine-operational deployment state

/opt/rah/documentation/
        │
        └── Human-operational knowledge
```

Application runtime resources shall not be placed in the documentation hierarchy merely for convenience.

Likewise, documentation required for human operation shall not exist only inside application runtime directories where it becomes difficult to discover or review.

---

## 7.2 Obsidian Operational Vault

The directory:

```text
/opt/rah/documentation/
```

shall serve as the standard **RAH operational Obsidian Vault**.

This allows the operator to browse the deployed environment as structured human-readable documentation rather than manually searching application directories, environment files, Docker configuration, or release media.

Obsidian acts as the human interface to the documentation hierarchy.

The underlying documentation shall remain based on ordinary files and directories, preferably using portable human-readable formats such as Markdown, so that operational knowledge does not depend exclusively upon Obsidian itself.

The documentation hierarchy therefore remains usable even if another approved viewer or editor is used in the future.

---

## 7.3 Per-Application Documentation

Every deployed application shall have a dedicated documentation area associated with its stable application identity.

Conceptually:

```text
/opt/rah/documentation/<app-slug>/
```

For example:

```text
/opt/rah/documentation/hcat/
/opt/rah/documentation/stt-schedule/
/opt/rah/documentation/blood-bank/
```

The documentation area shall describe the persistent deployment rather than merely reproducing the contents of the latest Application Release.

It should provide a clear operational view of:

- What the application is.
- Where it is deployed.
- Which version is currently running.
- When it was installed.
- How it is accessed.
- Which database it uses.
- Which credentials are required for administration.
- Which shared services it depends upon.
- How the deployment has changed over time.
- Any application-specific operational information required for maintenance.

The exact internal Markdown filenames and generated document structure may be standardized by the **RAH Application Engineering Playbook**.

---

## 7.4 Current Deployment Information

The documentation for every application shall clearly identify its current operational state.

At minimum, the operator should be able to determine:

- Application name.
- Application slug.
- Canonical deployment path.
- Current Application Release version.
- Initial installation date.
- Most recent update date, when applicable.
- Application access URL or endpoint.
- Relevant service ports.
- Database platform and database identity.
- Required shared infrastructure dependencies.
- Current certificate information when applicable.
- Other application-specific operational information.

The documentation shall describe the deployment that currently exists, not merely the configuration expected by a historical release package.

---

## 7.5 Credential Discoverability

Credentials required for legitimate operation and administration shall be discoverable through the approved operational documentation.

This may include:

- Application administrator credentials.
- Database administration credentials.
- Service credentials required for maintenance.
- Other deployment-specific credentials that an authorized operator must know.

An operator shall not be expected to obtain required credentials by:

- Inspecting running containers.
- Searching application source code.
- Reading arbitrary Docker internals.
- Guessing passwords.
- Recovering values from old release media.
- Asking the original developer.
- Asking an AI engineering agent to reconstruct the deployment.

Automatically generated credentials shall therefore be recorded in the appropriate protected operational documentation when they are required for future human administration.

Machine-only secrets that provide no legitimate operational value to a human operator need not be unnecessarily exposed merely to make the documentation exhaustive.

---

## 7.6 Sensitive Operational Information

The RAH operational Obsidian Vault is not public documentation.

Because it may contain:

- Database credentials.
- Application administrator credentials.
- Internal URLs.
- Hostnames.
- IP addresses.
- Service ports.
- Certificate information.
- Infrastructure relationships.
- Other sensitive deployment information,

the entire Vault shall be treated as **sensitive internal operational information**.

Access shall be limited according to the hospital's applicable operational and security controls.

The acceptance of operational credentials within the Vault is intentional: the objective is to ensure that authorized RAH operators can maintain the deployment without undocumented knowledge.

This does not permit credentials to be placed in:

- Public documentation.
- Public source repositories.
- Docker images.
- Application source code.
- Externally shared release notes.

The operational Vault and public/project engineering documentation have different security boundaries.

---

## 7.7 Installation Record

Initial installation shall create the first permanent operational record for the application.

The record shall identify, at minimum:

- Application installed.
- Application Release version.
- Installation date.
- Result of the installation.
- Database initialization state or version.
- Canonical deployment location.
- Relevant deployment information.
- Any important installation observations.

This record establishes the beginning of the application's production deployment history.

---

## 7.8 Deployment and Update History

Operational documentation shall preserve the history of significant deployment events.

Updates shall append to the application's history rather than replacing previous records.

A typical history may conceptually appear as:

```text
Application: HCAT

Initial Installation
2026-07-10
Application Release: 1.0.0
Result: Successful

Update
2026-07-18
1.0.0 → 1.1.0
Database Migration: Applied
Result: Successful

Update
2026-07-30
1.1.0 → 1.2.0
Database Migration: Applied
Result: Successful
```

The history should allow a future operator to determine:

- What was installed.
- When it was installed.
- Which updates occurred.
- Which versions were involved.
- Which database migrations were applied.
- Whether deployment succeeded.
- Whether rollback or recovery occurred.
- Relevant observations associated with the event.

Operational history is cumulative and shall survive routine Application Releases.

---

## 7.9 Generated and Maintained Documentation

Installation and update automation shall create or update operational documentation whenever the deployment state changes.

Documentation generation shall not depend solely upon an engineer remembering to manually edit a separate notebook after deployment.

Automation should populate information that can be determined reliably by the deployment process, including:

- Version.
- Date.
- Paths.
- Database identity.
- Generated credentials.
- Ports.
- Deployment result.
- Migration information.

Human-written operational notes may supplement the generated information when judgment or explanation is required.

Automation shall preserve historical information rather than regenerating the documentation in a manner that destroys previous deployment records.

---

## 7.10 Release Documentation and Operational Documentation

RAH distinguishes between **release documentation** and **operational documentation**.

Release documentation belongs to a particular immutable Application Release and explains that delivered software version.

Operational documentation belongs to the persistent deployed application and evolves throughout its production lifecycle.

```text
Application Release 1.0.0
    └── Release Documentation

Application Release 1.1.0
    └── Release Documentation

Application Release 1.2.0
    └── Release Documentation


             │ deployment/update
             ▼

/opt/rah/documentation/<app-slug>/
    │
    ├── Current Operational State
    ├── Required Administrative Information
    └── Complete Deployment History
```

Release documentation answers:

> **What does this release deliver?**

Operational documentation answers:

> **What is actually deployed here, and what has happened to it?**

Both are required, but they shall not be treated as interchangeable.

# 8. Database Operational Requirements

Production databases represent persistent operational state whose lifecycle normally extends across many Application Releases.

For this reason, database operations shall be treated differently from replaceable application containers and version-specific software artifacts.

The governing principle is:

> **Application software may be replaced. Production data shall be preserved.**

Application installation, update, rollback, and recovery procedures shall respect this distinction.

---

## 8.1 Database Ownership and Identity

Every application using a database shall have a clearly documented database architecture.

Operational documentation shall identify, as applicable:

- Database platform.
- Database host.
- Database port.
- Database name.
- Application database user.
- Administrative database user when applicable.
- Database deployment model.
- Current migration or schema version.

The database may be provided through:

- A shared approved database platform.
- A dedicated application database service.
- Another architecture explicitly approved for the application.

Regardless of the physical architecture, the application's production database shall have a stable operational identity that can be understood and maintained independently from individual Application Release directories.

---

## 8.2 Initial Installation and Migration Are Different Operations

RAH distinguishes strictly between:

1. **Initial database installation**, and
2. **Migration of an existing production database**.

Initial installation establishes a new database for an application that does not yet possess production operational state.

It may include:

- Database creation.
- Initial schema creation.
- Migration baseline.
- Lookup and seed data.
- Required database users and permissions.
- Initial application administrator data where applicable.

A migration modifies an existing production database while preserving its operational information.

It may include:

- New tables.
- New columns.
- Schema modifications.
- Index changes.
- Constraint changes.
- Lookup-data changes.
- Stored procedure or view changes.
- Controlled data transformations.

An update shall never treat an existing production database as though it were a new installation merely because recreating it is easier.

---

## 8.3 Production Data Preservation

Production data shall survive normal application updates.

Application Releases shall not contain procedures that routinely destroy and recreate production databases as part of software deployment.

Update procedures shall preserve:

- Existing clinical and administrative records.
- Existing application users where appropriate.
- Existing operational configuration stored in the database.
- Existing historical information.
- Other production state required by the application.

Destructive database operations require explicit engineering justification and an approved recovery strategy.

The absence of a convenient migration mechanism is not sufficient justification for destroying production state.

---

## 8.4 Database Migration State

The production database shall have an identifiable migration or schema state sufficient to determine whether it is compatible with the deployed Application Release.

An update shall determine the existing database state before applying migrations.

Only the changes required to reach the target release shall be applied.

Conceptually:

```text
Application Release 1.0.0
Database State 1.0.0
        │
        ▼
Migration
        │
        ▼
Application Release 1.1.0
Database State 1.1.0
        │
        ▼
Migration
        │
        ▼
Application Release 1.2.0
Database State 1.2.0
```

The exact migration technology may vary between projects.

The requirement is that database evolution remains controlled, versioned, traceable, and compatible with the corresponding application deployment.

---

## 8.5 Database Credentials

Database credentials required for application operation shall be established during initial deployment.

Machine-oriented database credentials should be generated automatically when practical and shall persist across routine Application Releases.

Updates shall not regenerate database passwords merely because application software has changed.

Where authorized human administration requires database credentials, the required connection information shall be discoverable through the protected operational documentation.

Database credentials shall not be hardcoded into:

- Application source code.
- Docker images.
- Public repositories.
- Public documentation.

The active application configuration and protected operational documentation shall remain the authoritative operational locations for the relevant credential information.

---

## 8.6 DBeaver Operational Availability

Where DBeaver is the approved database administration interface for the deployment, the application's database shall be available through DBeaver as part of the completed operational state.

Initial installation shall establish the required connection.

Subsequent updates shall ensure that the connection remains available and correct.

Updates may also repair or create DBeaver registration for applications deployed before this requirement was introduced.

The operator should be able to open DBeaver and identify the application database without reconstructing the connection manually from:

- Docker configuration.
- Environment files.
- Port mappings.
- Source code.
- Previous engineering conversations.

DBeaver registration is therefore treated as an **operational deployment requirement**, not as an optional convenience performed after installation.

The exact technical provisioning mechanism belongs to the **RAH Application Engineering Playbook**.

---

## 8.7 Database Backup Before Change

Database changes capable of affecting production information shall be preceded by an appropriate recovery measure.

Before applying significant production migrations or other potentially destructive database operations, the deployment process shall create or verify an appropriate database backup whenever required by the risk of the operation.

The backup shall correspond to the state immediately preceding the change closely enough to support meaningful recovery.

The deployment process shall not assume that a successful backup command automatically guarantees recoverability when verification can reasonably be performed.

The required level of backup and verification may depend upon:

- Migration complexity.
- Amount and importance of affected data.
- Database platform.
- Existing hospital backup infrastructure.
- Expected rollback procedure.

---

## 8.8 Database Recovery and Application Rollback

Application rollback and database recovery are related but not identical operations.

Restoring an older Docker image does not automatically restore an older database schema.

Likewise, restoring a database may affect compatibility with the currently running application version.

Every release involving database changes shall therefore consider the compatibility relationship between:

```text
Application Version
        │
Database Schema / Migration State
```

A rollback strategy shall determine whether failure can be recovered through:

- Application rollback only.
- Reverse database migration.
- Database restoration.
- Forward corrective migration.
- A combination of these operations.

No universal rollback mechanism shall be assumed safe for every database migration.

The appropriate recovery strategy shall be determined during release engineering according to the nature of the database change.

---

## 8.9 Database Changes and Deployment History

Successful database migrations shall be reflected in the application's operational deployment history.

The record shall identify, as applicable:

- Previous database state.
- Target database state.
- Migration applied.
- Application Release associated with the migration.
- Date.
- Result.
- Backup or recovery information when relevant.

This creates traceability between application evolution and database evolution.

A future operator should be able to determine not only which application version is running, but also how the production database reached its current state.

---

## 8.10 Database Operational Completion

A deployment involving a database is not operationally complete merely because the application can establish one successful database connection.

The resulting database environment shall satisfy the relevant operational requirements, including:

- Required database exists.
- Required schema or migrations have been applied.
- Production data has been preserved.
- Required application credentials function.
- Migration state is identifiable.
- DBeaver access is available where required.
- Required administrative information is documented.
- Backup or recovery requirements have been satisfied.
- Application and database versions are compatible.
- Database connectivity passes deployment verification.

These requirements ensure that the database remains both **usable by the application** and **maintainable by future RAH Lab operators**.

# 9. Offline Runtime Independence

Every application deployed within the RAH Offline Production Environment shall remain fully operational without access to the public Internet.

Offline compatibility is not limited to successful installation. The complete production runtime—including frontend behavior, backend services, application assets, required models, and other runtime dependencies—shall continue to operate after Internet access is unavailable.

An application that installs successfully but later requires an external Internet resource for normal operation is not considered compliant with this standard.

---

## 9.1 No Public Internet Runtime Dependency

Production applications shall not require access to public Internet services for functionality that forms part of their intended hospital operation.

Required runtime resources shall not depend upon:

- Public package repositories.
- Public Docker registries.
- Public JavaScript or CSS CDNs.
- Public font services.
- Public model registries.
- External asset servers.
- Internet-hosted application resources.
- Other public services required for normal application startup or operation.

Internet-connected resources may be used during engineering and release preparation.

The resulting Application Release, however, shall resolve those dependencies before entering the Offline Production Environment.

The governing principle is:

> **Internet access may assist engineering. It shall not be a hidden production dependency.**

---

## 9.2 Offline Frontend Assets

All frontend resources required during normal application operation shall be available locally or through approved offline infrastructure.

This includes, as applicable:

- JavaScript libraries.
- CSS frameworks.
- Fonts.
- Icons.
- Images.
- UI component resources.
- Visualization libraries.
- Static application resources.
- Other browser-loaded assets.

For example, production frontend code shall not rely upon runtime references such as:

```text
Public CDN
    │
    ▼
JavaScript / CSS / Fonts
    │
    ▼
Hospital Browser
```

when the corresponding public service cannot be reached from the production environment.

Instead:

```text
Application Release
    │
    ▼
Locally Available Assets
    │
    ▼
Application Deployment
    │
    ▼
Hospital Browser
```

Required assets may be incorporated during the application build process, bundled into the frontend image, or supplied through another approved offline mechanism.

The exact engineering mechanism belongs to the **RAH Application Engineering Playbook**.

---

## 9.3 Offline Backend Dependencies

Backend services shall likewise remain independent from public Internet resources required for normal operation.

Required:

- Python packages.
- System libraries.
- Runtime binaries.
- Application dependencies.
- Supporting resources.

shall be resolved during application engineering, Docker image construction, or approved offline infrastructure preparation.

Application containers shall not require public package repositories during normal production startup.

Docker images deployed into production shall be the previously built and validated images supplied through the Application Release or another approved RAH release mechanism.

---

## 9.4 External Services

An application may legitimately depend upon services outside its own Docker Compose project when those services exist within the approved hospital infrastructure.

Examples include:

- Shared database platforms.
- Shared Speech-to-Text services.
- Shared AI services.
- Authentication infrastructure.
- Other approved RAH internal services.

These are **infrastructure dependencies**, not public Internet dependencies.

Such dependencies shall be explicitly identified in the Application Release and operational documentation.

An application shall not silently substitute an Internet-hosted service for an unavailable internal dependency.

---

## 9.5 Machine-Learning Models and Large Artifacts

Applications requiring machine-learning models or other external artifacts shall ensure that the exact required production artifacts are available within the Offline Production Environment.

Approved ML models are governed by the **RAH Model Registry & Release Protocol** during engineering.

The production deployment shall not contact the online model registry directly.

The expected flow is:

```text
Online Model Registry
        │
        │ approved artifact retrieval
        ▼
Application Release Preparation
        │
        ▼
Approved Offline Release
        │
        ▼
Offline Production Environment
        │
        ▼
Application / AI Service
```

Where a model belongs directly to an application, the required artifact may be incorporated into the Application Release.

Where a model belongs to a shared AI service, it may instead be delivered and maintained through the approved release mechanism for that service.

In either case, the production runtime shall not require Internet retrieval of the model.

---

## 9.6 Release Self-Sufficiency

Before an Application Release is approved, its required runtime dependencies shall be identifiable and available within the target offline architecture.

A compliant deployment shall not require the operator to respond to missing runtime resources by:

- Temporarily connecting the production server to the Internet.
- Downloading packages manually from another computer.
- Searching online for missing frontend files.
- Pulling missing Docker images from a public registry.
- Downloading missing models after installation.
- Reconstructing undocumented external dependencies.

If a required resource is known during engineering, it shall be addressed during release preparation rather than deferred to production deployment.

---

## 9.7 Offline Validation

Offline runtime independence shall be verified under conditions representative of the actual air-gapped production environment.

Validation should confirm, as applicable:

- Application startup without Internet access.
- Backend functionality.
- Frontend rendering.
- Required fonts and icons.
- JavaScript and CSS behavior.
- Database communication.
- Shared internal service communication.
- Model availability.
- AI functionality.
- Browser functionality.
- Application restart without Internet access.

A successful online engineering test does not prove offline runtime independence.

An application shall be validated without public Internet connectivity before being considered ready for air-gapped production deployment.

---

## 9.8 Offline Independence Principle

The final production dependency model shall be explicit:

```text
                  Public Internet
                       │
                       │
              No runtime dependency
                       │

Offline Production Environment
          │
          ├── Application Containers
          ├── Local Application Assets
          ├── Production Database
          ├── Approved Shared Services
          ├── Required Models / Artifacts
          └── Hospital Client Workstations
```

The absence of Internet connectivity shall be treated as a normal operating condition—not as an exceptional failure mode.

# 10. Secure Browser Capability Standard

Some browser capabilities are restricted to **secure contexts** and cannot be relied upon when an application is served through an ordinary insecure HTTP origin.

Where an RAH application requires such browser functionality, its production deployment shall provide the secure origin and client configuration necessary for that functionality to operate over the real hospital LAN access path.

The purpose of this standard is not merely to remove browser warnings. It is to ensure that required application functionality works predictably on approved hospital workstations with minimal manual intervention.

---

## 10.1 Secure-Context Requirement

When an application requires browser capabilities that depend upon a secure context, the production deployment shall provide HTTPS over the actual application origin used by hospital workstations.

This may include capabilities such as:

- Microphone access.
- Other browser media-device APIs.
- Browser features restricted to trusted origins.

A feature working through:

```text
localhost
```

during development does not demonstrate that it will work when users access the application through:

```text
https://<hospital-server>:<port>
```

over the hospital LAN.

Validation shall therefore use the same class of network origin through which production users will access the application.

---

## 10.2 HTTPS Deployment

Applications requiring secure-context browser functionality shall be served through HTTPS in production.

The deployment shall establish:

- A server certificate.
- The corresponding private key.
- A certificate identity compatible with the intended application access path.
- HTTPS configuration for the relevant application service.
- Required client trust.

HTTPS resources required by the application shall be available entirely within the Offline Production Environment.

No public certificate service shall be required during normal installation, update, or operation.

---

## 10.3 Current Certificate Architecture

The current RAH application deployment model uses a **per-deployment self-signed certificate** where HTTPS is required.

The certificate is generated for the specific deployed application environment and shall account for the actual production identity through which clients access the service.

This may include the relevant:

- Hostname.
- IP address.
- Other required subject identities.

Certificate generation shall occur as part of the controlled deployment process rather than through undocumented manual preparation.

The exact certificate-generation mechanism belongs to the **RAH Application Engineering Playbook**.

---

## 10.4 Certificate Persistence

A deployment certificate and its corresponding private key form part of the persistent deployment state.

Once established, they shall normally survive routine Application Releases.

An application update shall not generate a new certificate merely because a new software version is being deployed.

Conceptually:

```text
Application 1.0.0 ────┐
Application 1.1.0 ────┼───► Same Deployment Certificate
Application 1.2.0 ────┘
```

This prevents routine application updates from repeatedly invalidating workstation trust.

Certificate replacement shall occur only when required by an explicit certificate-management event, such as:

- Certificate expiration.
- Host identity change.
- Certificate compromise.
- Intentional certificate rotation.
- Change in certificate architecture.

---

## 10.5 Workstation Certificate Trust

Serving an application through HTTPS is not sufficient if approved hospital workstations do not trust the deployment certificate.

Where a self-signed deployment certificate is used, the deployment process shall provide a reproducible mechanism for establishing the required trust on supported client workstations.

The target state is:

```text
Application Server
      │
      │ HTTPS
      ▼
Hospital Workstation
      │
      ├── Certificate trusted
      └── Application origin accepted
```

The operator shall not be expected to manually rediscover certificate files or repeatedly bypass browser security warnings on each use.

Client trust configuration shall be treated as part of application deployment readiness when the application requires it.

The exact operating-system and browser-specific trust mechanism belongs to the **RAH Application Engineering Playbook**.

---

## 10.6 Microphone Permission

Where microphone access is a required application capability, deployment shall establish both conditions necessary for reliable operation:

1. The application origin is trusted and satisfies the browser's secure-context requirements.
2. Microphone access is permitted for the approved application origin.

The intended operational result is:

```text
Trusted HTTPS Origin
        +
Approved Microphone Permission
        │
        ▼
Microphone Feature Works
```

RAH deployment engineering should minimize repeated browser prompts and manual permission configuration where supported, predictable, and appropriate for the approved hospital workstation environment.

The requirement is the resulting functionality, not one permanently mandated browser configuration technique.

---

## 10.7 Minimum Operator Intervention

Secure browser functionality shall be designed according to the same automation principle as the rest of the Application Release.

Where deployment automation can reproducibly establish:

- Certificate generation.
- Server HTTPS configuration.
- Workstation certificate trust.
- Approved browser-origin configuration.
- Required microphone permission.

these steps should not be left as repetitive manual work for the operator.

The desired deployment experience is:

```text
Deploy Application
        │
        ├──► HTTPS established
        ├──► Certificate available
        ├──► Workstation trust prepared
        ├──► Required browser permission prepared
        ▼
Application Feature Works
```

rather than:

```text
Deploy Application
        │
        ▼
Discover browser failure
        │
        ▼
Search for certificate
        │
        ▼
Manually configure trust
        │
        ▼
Search browser settings
        │
        ▼
Configure microphone
        │
        ▼
Repeat on another workstation
```

Some client-side actions may still require administrative privileges or interaction imposed by the operating system or browser.

Where unavoidable, those actions shall be minimized, documented, and supported by the Application Release.

---

## 10.8 Supported Browser Differences

Browsers may differ in how they implement certificate handling, managed policies, permissions, and secure-context behavior.

The Application Release shall support the browser environment approved for the corresponding hospital application.

The Standard does not mandate that Chrome, Edge, Firefox, or future browsers be configured through identical mechanisms.

Instead, the required outcome is that supported browsers provide the required application functionality under the approved workstation configuration.

Browser-specific registry settings, policy files, preference files, certificate stores, and automation mechanisms belong to the **RAH Application Engineering Playbook**.

---

## 10.9 Installation and Update Behavior

During initial installation, the deployment shall establish the secure-browser resources required by the application.

This may include:

- Certificate generation.
- HTTPS configuration.
- Client certificate resources.
- Workstation trust preparation.
- Required browser permission preparation.

During a routine update, the deployment shall preserve existing valid certificate state and avoid unnecessary client reconfiguration.

An update shall modify client-side security configuration only when the new release genuinely requires a change.

This preserves a stable relationship between:

```text
Persistent Application Origin
        │
        ├── Persistent Certificate
        ├── Persistent Workstation Trust
        └── Persistent Approved Permissions
```

while application software versions continue to evolve independently.

---

## 10.10 Verification

Applications requiring secure browser capabilities shall be verified using the intended production access path.

Verification shall confirm, as applicable:

- Application is reachable through HTTPS.
- Presented certificate corresponds to the intended deployment.
- Approved workstation trusts the certificate.
- Browser does not require an unsafe certificate bypass.
- Required secure-context capability is available.
- Microphone access works when required.
- Required permission is associated with the correct application origin.
- Functionality survives application restart.
- Functionality survives a normal application update without unnecessary certificate replacement.

Testing only on the application server or through `localhost` is insufficient when production users access the application remotely over the hospital LAN.

---

## 10.11 Future Internal Certificate Authority

RAH may eventually introduce an internal Certificate Authority to provide centrally managed certificates and trust across multiple hospital applications.

Such an architecture could replace the current per-deployment self-signed certificate model in the future.

However, an internal RAH CA is **not part of the current Application Release architecture** and shall not be treated as a prerequisite for present deployments.

The current standard remains:

> **Per-deployment self-signed certificates, with the required workstation trust established as part of deployment.**

If an internal CA is introduced later, the certificate architecture shall be updated through a deliberate infrastructure and release-standard revision rather than through application-specific ad hoc changes.

---

## 10.12 Secure Browser Capability Principle

The final requirement is functional rather than ceremonial.

A deployment is not compliant merely because:

- a certificate file exists;
- HTTPS starts successfully;
- a browser can technically reach the page;
- or microphone code works during development.

Where secure browser capabilities form part of the application, the complete production path shall work:

```text
Application Server
       │
       │ HTTPS
       ▼
Trusted Hospital Workstation
       │
       ▼
Approved Browser Origin
       │
       ▼
Required Permission
       │
       ▼
Application Capability
       │
       ▼
Works for the User
```

That complete path is the deployment requirement.

# 11. Deployment Verification

An Application Release shall not be considered production-ready solely because its Docker images build successfully or because the application operates within the Online Engineering Environment.

Deployment verification shall demonstrate that the release can establish and maintain the intended application deployment under conditions representative of the hospital's Offline Production Environment.

Verification shall test both:

1. **Initial installation from a clean deployment state.**
2. **Update of an existing deployment from a separate Application Release.**

This distinction is mandatory because a release may install correctly while failing to preserve configuration, credentials, database state, deployment identity, certificates, or other persistent resources during an update.

The purpose of deployment verification is therefore to validate the **complete application lifecycle**, not merely application startup.

---

## 11.1 Verification Environment

Application Releases shall be verified in an environment sufficiently representative of the intended production architecture.

Verification shall account for the characteristics relevant to the application, including:

- Debian-based deployment environment.
- Docker and Docker Compose.
- Offline operation.
- Intended database architecture.
- Application network configuration.
- Shared infrastructure services.
- Hospital LAN-style client access.
- Supported browser environment where applicable.
- Persistent deployment and documentation paths.

Where a production capability cannot reasonably be reproduced exactly during engineering validation, the difference shall be understood and documented rather than silently ignored.

---

## 11.2 Clean Installation Test

The Application Release shall first be tested as an initial installation against a clean application deployment state.

The test shall begin without an existing live deployment for the application.

Conceptually:

```text
Application Release 1.0.0
        │
        ▼
Clean Target Environment
        │
        ▼
Installation
        │
        ▼
/opt/rah/apps/<app-slug>/
        │
        ├── Persistent configuration
        ├── Stable deployment identity
        ├── Required credentials
        ├── Application services
        └── Required persistent state
```

The clean installation test shall verify, as applicable:

- Prerequisites are detected correctly.
- Installation can be initiated through the standard installation entry point.
- Canonical deployment directory is created.
- Stable Docker Compose identity is established.
- Production configuration is created.
- Machine and service credentials are generated where required.
- Application administrator is available where applicable.
- Database initialization completes successfully.
- Required Docker images are loaded.
- Application services start successfully.
- DBeaver registration is established where required.
- Operational documentation is generated.
- Required certificate and client resources are established where applicable.
- Application functionality is available.

A release that requires undocumented manual intervention to complete these expected operations shall not pass clean-installation verification.

---

## 11.3 Real Update Test

A release intended to support updates shall be tested against a genuine previously installed application deployment.

The update test shall not simulate an update by reinstalling the application from scratch.

The expected sequence is:

```text
Release 1.0.0
        │
        ▼
Install
        │
        ▼
Existing Operational Deployment
        │
        │ create representative persistent state
        ▼
Release 1.1.0
        │
        ▼
Update Existing Deployment
        │
        ▼
Same Operational Deployment
Running 1.1.0
```

The update shall be initiated from a **different release directory or staging location** from the original installation.

For example:

```text
/media/release-1.0.0/
        │
        ├──► Initial Installation

/media/release-1.1.0/
        │
        └──► Update
```

Both releases shall target the same canonical deployment:

```text
/opt/rah/apps/<app-slug>/
```

This test proves that application identity and persistent state are not accidentally coupled to the original release directory.

---

## 11.4 Release Independence Test

After successful deployment, verification shall confirm that the application does not depend upon the continued presence of disposable release staging material.

Where safe within the validation environment, the incoming release directory may be moved, unmounted, or otherwise made unavailable after deployment.

The application shall continue to operate using its canonical persistent deployment and approved infrastructure dependencies.

This test shall detect dependencies such as:

- `.env` remaining inside the release directory.
- Compose execution depending upon the release directory name.
- Certificates being read from staging media.
- Runtime assets remaining only in the incoming package.
- Application configuration referring to temporary release paths.
- Other operational dependencies on disposable release material.

A release shall fail verification if removal of staging material breaks normal production operation.

---

## 11.5 Persistence Test

Before performing the update test, representative persistent state shall be created within the installed deployment.

Depending on the application, this may include:

- Database records.
- Generated service credentials.
- Application administrator state.
- Persistent `.env` values.
- Docker volume content.
- Certificates and private keys.
- Application-generated files.
- Operational documentation.
- Deployment history.

After the update, verification shall confirm that state intended to persist remains intact.

The test should specifically detect accidental:

- Credential regeneration.
- Database recreation.
- Configuration replacement.
- Certificate replacement.
- Volume loss.
- Operational-history loss.
- Application identity changes.

The update is successful only when both conditions are true:

```text
New Software Version
        +
Required Previous Operational State
        │
        ▼
Valid Updated Deployment
```

---

## 11.6 Database Verification

Where the application uses a database, verification shall confirm the appropriate database behavior for both lifecycle operations.

### Initial Installation

Verify:

- Required database is created or initialized correctly.
- Initial schema or migration baseline is established.
- Required seed or lookup data exists.
- Required database credentials function.
- Initial database state is identifiable.

### Update

Verify:

- Existing production-style data remains present.
- Required migrations are applied.
- Database is not unnecessarily recreated.
- Migration state reaches the expected target.
- Application remains compatible with the resulting schema.
- Existing credentials remain valid unless intentionally changed.

Where the release requires backup or recovery preparation before migration, that behavior shall also be verified.

---

## 11.7 DBeaver Verification

Where DBeaver administration is required, verification shall confirm that the application database is discoverable and accessible through the approved DBeaver environment.

For initial installation, verify that the required connection is established.

For update, verify that the connection:

- Remains valid when database information is unchanged.
- Is corrected when deployment information legitimately changes.
- Can be created for an older deployment that did not previously satisfy the DBeaver requirement.

Verification shall confirm the actual operator experience rather than merely confirming that connection information exists somewhere in configuration files.

---

## 11.8 Operational Documentation Verification

Verification shall inspect the persistent documentation under:

```text
/opt/rah/documentation/
```

After initial installation, documentation shall contain the expected current deployment information and initial installation record.

After update, verification shall confirm that:

- Current Application Release version changed correctly.
- Previous deployment history remains available.
- New update history was appended.
- Database/migration information is current.
- Required credentials remain discoverable.
- Relevant operational endpoints remain documented.
- DBeaver information remains available.
- Certificate information remains correct where applicable.
- Sensitive operational information remains within the intended protected documentation boundary.

Documentation verification is part of deployment verification.

A deployment that operates technically but leaves the future operator unable to understand or administer it is incomplete.

---

## 11.9 Offline Runtime Verification

The application shall be tested without public Internet connectivity.

Verification shall confirm that required functionality does not depend upon:

- Public CDNs.
- Public package repositories.
- Public Docker registries.
- Public model registries.
- Public font or asset services.
- Other undocumented Internet-hosted resources.

Testing shall include the application functions most likely to reveal external dependencies, including frontend rendering and model-dependent functionality where applicable.

Offline operation shall represent the expected production condition.

---

## 11.10 LAN and Browser Verification

Where users access the application through hospital workstations, verification shall test the application through the intended LAN access path rather than exclusively through `localhost`.

Where secure browser capabilities are required, verification shall include, as applicable:

- HTTPS access.
- Certificate validity for the intended deployment identity.
- Workstation certificate trust.
- Supported browser behavior.
- Required microphone permission.
- Actual microphone functionality.
- Other secure-context browser capabilities used by the application.

The test shall represent the real path:

```text
Application Server
        │
        │ Hospital LAN
        ▼
Approved Workstation
        │
        ▼
Supported Browser
        │
        ▼
Actual Application Feature
```

A browser capability demonstrated only on the server through `localhost` shall not be considered sufficient validation for LAN users.

---

## 11.11 Application Functional Verification

Deployment verification shall include representative functional checks of the application itself.

The objective is not necessarily to repeat the complete software testing process performed during application engineering.

Instead, deployment verification shall confirm that the deployed environment has not broken essential application behavior.

Checks should include, as applicable:

- Application startup.
- User login.
- Frontend/backend communication.
- Database operations.
- Critical application workflow.
- Shared-service communication.
- AI or STT functionality.
- Required file or persistent-storage operations.
- Client browser functionality.

Application-specific verification requirements should be defined according to the operational importance and architecture of the software.

---

## 11.12 Restart Verification

Where practical, the deployed application shall be restarted after installation and update verification.

The restart test helps detect deployments that function only because temporary installation state remains available.

After restart, verify:

- Required services return successfully.
- Persistent configuration remains available.
- Database connectivity remains functional.
- Persistent volumes remain intact.
- Required certificates remain available.
- Application functionality returns without reconstruction.
- No Internet access is required to recover normal operation.

A production deployment shall be capable of surviving normal service and server restart conditions.

---

## 11.13 Failure Criteria

Deployment verification shall fail when a mandatory requirement of the Application Release cannot be demonstrated.

Examples include:

- Installation requires undocumented manual repair.
- Update creates a second unintended application deployment.
- Application identity depends upon the release folder.
- Persistent `.env` is lost or replaced unintentionally.
- Generated credentials change unexpectedly.
- Production-style database data is lost.
- Required migration fails.
- Stale containers prevent the intended release from operating.
- Application requires public Internet resources.
- Required DBeaver connection is unavailable.
- Operational documentation is missing or incorrect.
- Deployment history is lost.
- Required HTTPS trust is not established.
- Required microphone or secure-browser functionality does not operate.
- Application fails representative functional verification.

A failed mandatory verification shall prevent the release from being classified as production-ready.

The failure shall be corrected within the Engineering Environment and the affected verification shall be repeated before publication.

---

## 11.14 Verification Evidence

Verification results should be recorded sufficiently to establish that the release completed the required lifecycle tests.

The evidence may include:

- Release version tested.
- Environment used.
- Installation result.
- Update path tested.
- Database migration result.
- Persistence result.
- Offline runtime result.
- DBeaver result.
- Browser/client result where applicable.
- Functional verification result.
- Known limitations.
- Final release disposition.

The objective is not excessive paperwork.

The objective is to ensure that production approval represents a demonstrated engineering result rather than an assumption that deployment will probably work.

---

# 12. Release Compliance

An Application Release is considered **RAH-compliant** when it satisfies the applicable requirements of this standard and has successfully demonstrated those requirements through deployment verification.

Compliance describes the complete deployability and maintainability of the release.

It does not mean merely that:

- Source code is complete.
- Docker images build.
- Docker Compose starts.
- The application works on the developer's machine.
- The application works while connected to the Internet.

A compliant Application Release shall be capable of becoming a predictable and maintainable RAH production deployment.

---

## 12.1 Core Compliance Requirements

Where applicable to the architecture of the application, an RAH-compliant Application Release shall provide or guarantee:

### Release Identity

- A unique Application Release version.
- Clearly identified application and application slug.
- Immutable published release artifacts.
- Traceability of deployed components.

### Deployment Architecture

- Stable canonical deployment under:

```text
/opt/rah/apps/<app-slug>/
```

- Separation between incoming release material and live deployment.
- Persistent production configuration.
- Stable Docker Compose identity.
- Independence from previous release directories.

### Installation

- Standard one-command installation.
- Automatic establishment of required persistent deployment state.
- Generation of suitable machine/service credentials where applicable.
- Usable application administrator initialization where applicable.
- Initial database installation.
- Required operator integration.
- Operational documentation generation.
- Installation verification.

### Update

- Standard one-command update.
- Preservation of production configuration.
- Preservation of persistent credentials.
- Preservation of production data.
- Controlled database migration.
- Deterministic reconciliation of application services.
- Preservation or repair of required operator integrations.
- Operational documentation update.
- Deployment-history update.
- Update verification.

### Operational Documentation

- Persistent documentation under:

```text
/opt/rah/documentation/
```

- Per-application operational documentation.
- Current deployment information.
- Discoverable administrative information and credentials where required.
- Installation date.
- Current version.
- Deployment and update history.
- Appropriate protection of sensitive operational information.

### Database Operations

- Clear distinction between initial installation and migration.
- Preservation of production data.
- Versioned or identifiable migration state.
- Persistent database credentials.
- DBeaver availability where required.
- Appropriate backup and recovery consideration.

### Offline Operation

- No required public Internet runtime dependency.
- No required public CDN dependency.
- Required application assets available offline.
- Required Docker images available offline.
- Required models and large artifacts available through approved offline mechanisms.
- Explicit use of approved internal shared services.

### Secure Browser Capabilities

Where applicable:

- HTTPS over the real hospital LAN access path.
- Per-deployment self-signed certificate under the current architecture.
- Certificate persistence across normal updates.
- Required workstation trust.
- Required browser permission.
- Functional microphone or other secure-context capability.
- Minimum reasonable operator intervention.

### Verification

- Successful clean installation test.
- Successful real update test from a separate release location.
- Successful persistence verification.
- Successful database verification.
- Successful offline runtime verification.
- Successful DBeaver verification where applicable.
- Successful operational-documentation verification.
- Successful LAN/browser verification where applicable.
- Successful representative application functional verification.

---

## 12.2 Applicable Requirements

Not every application requires every optional capability described by this standard.

For example:

- An application without microphone functionality does not require microphone permission configuration.
- An application without ML models does not require model artifacts.
- An application without a database does not require DBeaver registration.
- An application that does not require secure-context browser capabilities may not require application-specific HTTPS under this standard.
- An application without client-side preparation does not require workstation configuration resources.

A requirement may therefore be classified as:

```text
Applicable
Not Applicable
```

but it shall not be silently ignored.

When a significant requirement is considered not applicable, that conclusion should be evident from the application architecture or release documentation.

---

## 12.3 Compliance Does Not Mandate One Implementation

This standard primarily defines required **behavior and outcomes**.

Compliance shall not depend unnecessarily upon one specific implementation mechanism.

For example, the standard requires:

> Stable Docker Compose identity.

It does not require one permanently fixed shell command for establishing that identity.

The standard requires:

> Deterministic reconciliation of application services.

It does not permanently mandate `--force-recreate` as the only valid implementation.

The standard requires:

> DBeaver availability.

It does not define one permanent DBeaver provisioning mechanism.

The standard requires:

> Supported browser functionality.

It does not require Chrome, Edge, and Firefox to be configured through identical mechanisms.

Implementation mechanisms are defined and evolved through the **RAH Application Engineering Playbook**, provided they continue to satisfy the behavioral guarantees established by this Standard.

---

## 12.4 Compliance Exceptions

If an application cannot satisfy an applicable requirement because of a justified technical or operational constraint, the deviation shall be explicit.

An exception should identify:

- Requirement not satisfied.
- Reason.
- Operational consequence.
- Risk introduced.
- Compensating measure where applicable.
- Whether the exception is temporary or permanent.

An undocumented deviation shall not be treated as an approved exception.

Exceptions should remain limited. They shall not become a mechanism for bypassing deployment engineering because implementing the standard is inconvenient.

---

## 12.5 Production-Ready Release

A release may be classified as **Production Ready** when:

```text
Application Engineering Complete
        +
Application Release Complete
        +
Applicable RAH Requirements Satisfied
        +
Deployment Verification Passed
        +
Known Exceptions Documented
        │
        ▼
RAH-Compliant Production-Ready
Application Release
```

Only then should the release proceed through the approved transfer procedure into the Offline Production Environment.

---

## 12.6 Final Release Contract

The practical meaning of an **RAH-compliant Application Release** is:

> A versioned and reproducible application package that can establish or update a stable production deployment within the hospital's air-gapped environment, preserve required operational state and production data, operate without undocumented Internet dependencies, provide the information and administrative access required for future maintenance, and demonstrate those guarantees through representative installation and update verification.

The release shall not depend upon the future operator remembering how the original engineer made it work.

It shall carry enough engineering structure that the deployment can be installed, understood, updated, verified, recovered, and maintained as a controlled RAH system.

That is the acceptance boundary of this Standard.
