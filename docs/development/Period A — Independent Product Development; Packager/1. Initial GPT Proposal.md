# Period A — Independent Product Development: Packager

## Period Goal

Build and validate the Packaging Engine independently from the Offline Platform.

The Packager shall be considered independently trustworthy when it can:

```
Known Application Repository
        ↓
Packager
        ↓
Contract-Compliant Release
        ↓
Independent Validator
        ↓
PASS
        ↓
Manual Offline Installation Test
        ↓
PASS
```

The Platform shall not be required to prove Packager correctness during this period.

---

# Development Strategy

The Packager shall be developed through **vertical slices**, not by building all CLI commands first and filling them later.

Each slice must include:

```
Behavior
+
Input model
+
Result model
+
Errors
+
State effects
+
Automated tests
+
Failure tests
```

A slice is complete only when its observable behavior is proven.

---

# Proposed Slice Map

I would use **8 primary slices**.

```
P0 — Packager Runtime & Test Foundation
        ↓
P1 — Project Initialization & State
        ↓
P2 — Repository Inspection
        ↓
P3 — Engineering Knowledge / Claude Bridge
        ↓
P4 — Release Planning
        ↓
P5 — Docker Build & Artifact Preparation
        ↓
P6 — Release Construction
        ↓
P7 — Validation, Finalization & Real Offline Proof
```

The ordering is deliberate.

Each slice creates something the next one can trust.

---

# P0 — Packager Runtime and Test Foundation

## Objective

Create the smallest working Packager runtime and test environment.

This slice does **not package an application yet**.

Its purpose is to prove that the Packager itself can reliably run on the Windows engineering workstation.

## Development Tasks

Build:

- Dockerized Packager development environment;
- CLI entry point;
- configuration loading;
- source repository bind mount;
- output-directory bind mount;
- access to the host Docker Engine;
- common result envelope;
- common error envelope;
- logging;
- test runner.

Initial CLI may expose:

```
rah --version
rah health
```

or equivalent minimal commands.

## Required Tests

### Runtime Test

Packager container starts successfully.

### Mounted Repository Test

Packager can read a known Windows repository mounted into the container.

### Output Test

Packager can create a test artifact in the configured output directory.

### Docker Connectivity Test

Packager can communicate with the host Docker Engine.

### Structured Result Test

CLI returns a valid JSON result object.

### Failure Test

If Docker is unavailable, Packager returns a deterministic Packager error instead of crashing.

## Completion Gate

P0 is complete when:

```
Packager runs
+
reads host repository
+
writes output
+
talks to Docker
+
returns structured results
+
tests pass
```

This slice eliminates infrastructure uncertainty before adding business logic.

# P1 — Project Initialization and Project Version State

## Objective

Allow an ordinary repository to become a Packager-managed project.

This slice establishes the Packager's first persistent state.

## Development Tasks

Implement:

```
rah init
```

Responsibilities:

- validate repository path;
- detect Git repository;
- create `.rah/`;
- create Project Version State;
- assign application identity;
- validate initial state against schema;
- refuse unsafe reinitialization.

The Project Version State should initially contain the already-designed fields such as:

- application identity;
- current version;
- next proposed version;
- release history;
- schema version.

## Required Tests

### Valid Initialization

Known clean repository → successful initialization.

### Existing State

Second initialization → safe refusal.

### Invalid Path

Missing directory → structured input error.

### Non-Git Repository

**Resolved:** for Version 1 the Packager requires a Git repository. If the
selected project is not a Git repository, `rah init` shall fail
immediately with a clear, structured error — not a silent partial
initialization. Non-Git support may be revisited in a future version if a
real use case arises; none of the five candidate applications need it
today.

### Atomicity

Failed initialization must not leave malformed partial state.

### Schema Test

Generated Project Version State validates against its schema.

## Completion Gate

A known repository can be initialized repeatedly and predictably without corrupting source files.

---

# P2 — Repository Inspection

## Objective

Make the Packager capable of determining everything that can be learned **deterministically** from the application repository.

This is one of the most important slices because it defines the boundary between software discovery and Claude assistance.

## Development Tasks

Implement:

```
rah inspect
```

Inspection shall detect where applicable:

### Git

- branch;
- commit;
- tag;
- clean/dirty state.

### Docker

- Dockerfiles;
- Compose files;
- services;
- image names;
- build contexts.

### Application Resources

- lifecycle scripts;
- database migration directories;
- configuration templates;
- environment-variable names;
- documentation;
- candidate verification resources.

### Packager State

- application identity;
- current version;
- previous Releases.

Produce:

```
ProjectInspectionResult
```

## Required Fixtures

Create known repositories such as:

```
fixtures/projects/
    valid-simple-app/
    dirty-repository/
    compose-multi-service/
    missing-dockerfile/
    malformed-compose/
```

## Required Tests

Each discovered fact must have a test.

Examples:

- clean Git state detected;
- dirty Git state detected;
- Compose services parsed correctly;
- Dockerfiles mapped correctly;
- missing optional resource reported as missing, not crash;
- malformed Compose produces stable error.

## Completion Gate

The Packager can produce a deterministic repository-inspection report whose fields are trusted by later slices.

---

# P3 — Engineering Knowledge and Claude Bridge

## Objective

Solve the information that repository inspection cannot determine reliably.

This is the hybrid portion of the Packager.

The slice should **not allow Claude to construct Releases**.

Claude only fills structured engineering knowledge.

## Development Tasks

Implement:

```
rah prepare-answers
rah validate-answers
```

### `prepare-answers`

Consumes:

```
ProjectInspectionResult
+
Release Contract
+
application repository context
```

Produces:

```
claude-packaging-request.md
engineering-answers.schema.json
```

### Claude Interaction

For V1:

```
Engineer
    ↓
Claude Code
    ↓
engineering-answers.json
```

### `validate-answers`

Checks:

- JSON Schema validity;
- required fields;
- allowed values;
- consistency with inspection result;
- stale-answer conditions.

## Important design requirement

This slice must explicitly solve **staleness**.

The engineering answers should be tied to repository evidence such as:

```
Git commit
or
inspection fingerprint
```

If the repository changes after Claude answered, the Packager should detect that the answers may no longer be valid.

That was one of the weaker areas identified during architecture review, so I would make it explicit during implementation.

## Required Tests

- valid answers accepted;
- malformed answers rejected;
- missing required answer rejected;
- conflicting deterministic fact rejected;
- answers generated against old Git commit detected as stale;
- second `prepare-answers` invocation behaves predictably.

## Completion Gate

The Packager can reliably distinguish:

```
Automatically discovered facts
```

from:

```
Human/Claude engineering knowledge
```

and merge them only after validation.

# P4 — Release Planning

## Objective

Produce a complete Release plan **without performing expensive build or finalization work**.

This becomes the preview and safety boundary before packaging begins.

## Development Tasks

Implement:

```
rah plan
```

The plan shall determine:

- current version;
- proposed version;
- version increment;
- output path;
- Contract version;
- expected Docker images;
- expected artifacts;
- required lifecycle scripts;
- required configuration resources;
- whether Packaging may proceed.

Produce:

```
ReleasePlan
```

## Required Tests

### Patch Increment

Correct next version.

### Minor Increment

Correct next version.

### Major Increment

Correct next version.

### Duplicate Version

Rejected.

### Dirty Git State

Rejected according to policy.

### Missing Engineering Answers

Plan blocked.

### Invalid Project State

Plan blocked.

## Completion Gate

The Packager can answer:

> "Exactly what Release am I about to build?"

without changing Release history or generating a finalized Release.

# P5 — Docker Build and Artifact Preparation

## Objective

Prove that the Packager can build and export the application artifacts required by the Release.

This is the first expensive external-operation slice.

## Development Tasks

Implement internal capabilities for:

- Docker image build;
- Docker Compose validation;
- image inspection;
- image tagging;
- image export to `.tar`;
- artifact inventory;
- build logs;
- build failure mapping.

Do **not yet finalize the full Release**.

Output should be a temporary build workspace.

Conceptually:

```
Repository
    ↓
Docker Build
    ↓
Built Images
    ↓
Image Inspection
    ↓
Exported Artifacts
```

## Required Fixtures

At least:

- trivial one-container application;
- simple frontend/backend application;
- deliberately broken Dockerfile;
- malformed Compose project.

Then, per the settled acceptance sequence: HCopilot first, Indicator
second (required — proves the P2/P3 inspect/ask-gap mechanism generalizes
across a structurally different app, not an optional stretch fixture).
HCAT is deliberately deferred past both — see
`docs/development/CURRENT.md`, "Acceptance decision (settled)".

## Required Tests

- valid image builds;
- expected image name/tag detected;
- Compose validates;
- image export exists;
- exported image can be loaded again;
- broken Dockerfile returns a structured error in the Packager's own
  operational error-code namespace (e.g. `PKG-DOCKER-*` — this namespace
  is a real future design task, deliberately not designed yet; distinct
  from the Contract's `RC-*` validation-rule namespace; see
  `docs/development/CURRENT.md`, "Future Design Tasks");
- failed build does not update Project Version State;
- partial build workspace does not become finalized Release.

## Completion Gate

The Packager can reliably transform source into the binary/container artifacts required for offline delivery.

# P6 — Release Construction

## Objective

Construct the complete candidate Release according to the machine-readable Release Contract.

This is where previous pieces finally combine.

## Development Tasks

Create temporary candidate Release containing:

```
Manifest
Docker artifacts
Lifecycle scripts
Configuration resources
Database resources
Verification resources
Documentation
Compliance resources
```

Implement deterministic generation of:

```
release.yaml
```

using:

```
Project Version State
+
Inspection Result
+
Validated Engineering Answers
+
Build Artifact Metadata
+
Release Plan
```

The Release directory structure must be generated from the canonical Release layout definition.

## Required Tests

### Directory Contract

Exact required structure generated.

### Manifest Schema

Generated Manifest validates.

### Artifact Contract

Declared artifacts actually exist.

### Script Contract

Declared lifecycle scripts exist.

### Identity Consistency

Application slug/version match across:

- project state;
- Manifest;
- Release directory.

### Reproducibility

Reproducibility is a Contract-level property, not a P6-specific idea —
promoted into `contracts/1.0/validation-rules.json` as `RC-REPRO-001`
("given the same application, target version, source Git commit,
validated engineering answers, and Packaging Software version, two
independently generated candidate Releases shall be structurally
equivalent," excluding fields inherently unique per build such as
`release.created_at`). This test verifies `RC-REPRO-001` holds: build a
candidate Release twice from the same P2–P5 fixture chain and diff the
outputs, rather than defining what "equivalent" means here from scratch.
Known limitation, not asserted by this test: byte-for-byte Docker image
archive content equality, since that depends on whether `docker build`
itself is reproducible.

## Completion Gate

A candidate Release exists that appears complete but has not yet been declared final.

# P7 — Validation, Finalization and Independent Offline Proof

## Objective

Turn a candidate Release into a finalized immutable Release and prove the Packager output independently.

This is the Period A Packager finish line.

## Development Tasks

Implement:

```
rah validate
rah package
```

or the final combined orchestration where `package` invokes internal validation/finalization.

Validation shall perform:

- directory validation;
- Manifest schema validation;
- semantic validation;
- artifact validation;
- checksum generation/verification;
- image validation;
- compliance-rule execution.

Generate:

```
Compliance Report
Checksums
Release fingerprint
PackagingResult
```

Then finalize:

```
temporary candidate
        ↓
validation PASS
        ↓
fingerprint/checksum closure
        ↓
final immutable Release
        ↓
Project Version State update
```

Project state must update **only after** finalization succeeds.

## Automated Tests

### Valid Release

PASS.

### Invalid Manifest

FAIL.

### Missing Artifact

FAIL.

### Checksum Mismatch

FAIL.

### Duplicate Release

FAIL.

### Finalization Atomicity

Failure before finalization does not modify project release history.

### Existing Final Release

Never overwritten silently.

## Real Manual Acceptance Test

Now use one real application.

The settled Period A acceptance app: **HCopilot** — see
`docs/development/CURRENT.md`, "Acceptance decision (settled)". Indicator
follows as the required second app; HCAT is deliberately deferred past
both.

Procedure:

```
Real repository
        ↓
Real Packager
        ↓
Generated Release
        ↓
Independent Validator PASS
        ↓
Copy manually to Offline Debian VM
        ↓
Run existing install_offline.sh
        ↓
Application starts
        ↓
Manual verification PASS
```

Then test one update Release similarly using the current manual procedure.

No Platform involvement.

## Period-A Packager Exit Gate

The Packager track is complete only when:

- a real application can be initialized;
- inspected;
- assisted through Claude;
- planned;
- built;
- packaged;
- validated;
- finalized;
- manually installed offline;
- and a second Release can be produced without corrupting version history.

# Important Integration Rule Within Packager Period A

Even inside the Packager, we should avoid one giant final test.

Each slice must produce an artifact that the next slice can test independently.

For example:

```
P2
→ ProjectInspectionResult fixture

P3
→ Valid EngineeringAnswers fixture

P4
→ ReleasePlan fixture

P5
→ BuiltArtifact fixture

P6
→ Candidate Release fixture
```

That means if P6 fails, Claude can run P6 against known P5 fixtures rather than rebuilding HCAT every time.

This will save a huge amount of debugging time.

## My assessment of this initial slicing

The important thing here is that the slices are **not just the CLI commands**.

They follow dependency and uncertainty boundaries:

```
Can the tool run?
↓
Can it own project state?
↓
Can it understand deterministic repository facts?
↓
Can it acquire missing engineering knowledge?
↓
Can it plan a Release?
↓
Can it build real artifacts?
↓
Can it construct the Contract?
↓
Can it prove and finalize the result?
```

That is the part I would most want Claude to challenge.

When you show this plan to Claude, ask him specifically to review whether
each slice's dependency and uncertainty boundary is actually where this
document draws it — that review happened; its accepted outcomes are
applied directly throughout this document (reproducibility promoted to
the Contract, the acceptance sequence corrected, the Master Development
Matrix consolidated to one owner, Non-Git behavior resolved, the
operational error namespace flagged as deferred future work).
