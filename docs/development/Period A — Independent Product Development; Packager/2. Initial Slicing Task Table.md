## P0 — Done

Built in `packager/` (Python, `click` CLI, `docker` SDK): `rah version`,
`rah health`, a common JSON result/error envelope, Docker connectivity
check, config loading (`RAH_REPO_PATH`/`RAH_OUTPUT_PATH`/`RAH_LOG_LEVEL`
env vars), logging to stderr only, and a Dockerfile.

All 6 required P0 tests verified — 14/14 pytest passing, and every one of
them re-proven live against the actual built container (`docker build` +
`docker run`), not just mocked:

- **Runtime Test** — container builds and starts.
- **Mounted Repository Test** — `docker run -v <repo>:/repo:ro
  -e RAH_REPO_PATH=/repo`, correctly read 12 top-level entries from the
  real repo.
- **Output Test** — `-v <dir>:/output -e RAH_OUTPUT_PATH=/output`, wrote
  and read back a marker file, cleaned up after itself.
- **Docker Connectivity Test** — `-v /var/run/docker.sock:/var/run/docker.sock`
  (Docker-outside-of-Docker), reached the real host Engine, reported
  `server_version: 29.6.1`.
- **Structured Result Test** — every invocation, success or failure,
  printed exactly one valid JSON envelope on stdout.
- **Failure Test** — same container run *without* the socket mounted:
  clean `PKG-RUNTIME-DOCKER-UNAVAILABLE` structured error, exit code 1, no
  crash, no traceback.

One real-environment finding worth keeping in mind for later slices:
`docker-py`'s `from_env()` cannot reach modern Docker Desktop's
`desktop-linux` context (`npipe:////./pipe/dockerDesktopLinuxEngine`) when
run directly against the Windows host from a bare Python process — it
only works from inside the container, via the standard Unix-socket bind
mount. Not a bug; just means "run the CLI directly on Windows outside
Docker" was never actually a supported path, only "run it containerized,"
which matches the plan's own framing throughout.

## P2 — Done

Built `rah inspect` (`inspection.py` orchestrating four category modules,
plus a new shared `repository.py` extracted from P1's path/Git-repo
checks). All four required categories from the spec:

- **Git** (`git_inspection.py`) — shells out to the real `git` binary
  (now installed in the Dockerfile, P1 didn't need it) for branch,
  commit, tag (`null` if untagged), and clean/dirty state. New error
  `PKG-GIT-INSPECTION-FAILED` for a confirmed-Git repo whose plumbing
  still fails (e.g. no commits yet, so `HEAD` doesn't resolve).
- **Docker** (`docker_inspection.py`) — finds Dockerfiles (pruning
  `node_modules`/`.venv`/etc. before descending, not after), finds the
  Compose file by convention, parses it (new `pyyaml` dependency),
  extracts services with `image`/`build.context`/`build.dockerfile`.
  Two failure modes handled differently: missing Dockerfile/Compose is
  not an error (empty/`null`); a Compose file that exists but doesn't
  parse as valid YAML is a real error (`PKG-DOCKER-MALFORMED-COMPOSE`).
- **Packager State** (`packager_state_inspection.py`) — reads
  `.rah/project-state.json` back via P1's own `project_state_path()`/
  `validate_state()`, no new schema. `null` if never `rah init`-ed
  (not an error); a corrupted file is (`PKG-PROJECT-STATE-READ-FAILED`
  for bad JSON, P1's existing `PKG-PROJECT-STATE-SCHEMA-INVALID` for
  schema violations).
- **Application Resources** (`application_resources_inspection.py`) —
  the one category with no universal filename convention (unlike
  `.git`/`Dockerfile`). The conventions used (`.env*example*`/`*template*`
  configuration templates, `scripts/`-named directories, `migrations`/
  `alembic`-named directories, root and `documentation/`-style `*.md`
  docs, `*verify*`/`*valid*`-named verification candidates,
  environment-variable names parsed out of the config templates) were
  not invented speculatively — they were checked against and confirmed
  by the real, consistent structure of **both** P2 acceptance apps
  (HCopilot and Indicator) before being implemented, not guessed and
  then tested.

26 new tests added (52/52 total passing). Fixtures added under
`packager/tests/fixtures/projects/`: `compose-multi-service/`,
`missing-dockerfile/`, `malformed-compose/`, and `valid-simple-app/`
(the last one filling a gap — see below). `dirty-repository/` was
deliberately **not** added as a static fixture: a "dirty repo" fixture
would need to be a nested Git repository with its own uncommitted
changes baked in, which isn't practically maintainable inside a
Git-tracked fixtures directory. Dirty-state coverage instead uses real,
disposable `git init` repos created on the fly in `test_git_inspection.py`
— a deliberate substitute, not an oversight.

Every category was also re-proven live against the real built container,
including against both real acceptance apps:

- Real disposable Git repos: clean+tagged, dirty via edit, dirty via
  untracked file, non-Git directory, Git repo with no commits yet — all
  produced the correct real `git` stderr surfaced in structured errors.
- A real clone of HCopilot: all 4 categories returned correctly,
  including its actual 4-service Compose stack (`sqlserver`, `db-init`,
  `backend`, `frontend`), its real `alembic` migrations, its real
  `.env.example`/`.env.offline.template` files, and (once initialized)
  its real Packager State.
- The **real Indicator repository directly** (read-only bind mount, no
  clone needed since `inspect` never writes) — structurally different
  from HCopilot (no database, `python-service` instead of `backend`,
  no explicit `image:` names) but produced the identical
  `ProjectInspectionResult` shape with no per-app branching anywhere in
  the code. This is the first real evidence that the `P2`→`P3`
  discovery mechanism actually generalizes, not just runs once.

## P3 — Done

P3's spec (`rah prepare-answers` + `rah validate-answers`) is the one
slice where the frozen architecture never pre-drafted a schema — the
proposal itself flags staleness as "one of the weaker areas identified
during architecture review." That design gap has been closed and both
commands are now built, tested, and live-proven end to end.

**Design decision written**: `docs/decisions/engineering-answers-and-staleness.md`
— the engineering-answers schema is derived field-by-field from the real,
frozen `contracts/1.0/release-manifest.schema.json` (not invented in
parallel), and the staleness mechanism uses two anchors (`git_commit` +
a sha256 fingerprint of the full `ProjectInspectionResult`) rather than
commit hash alone, so an uncommitted change still gets caught.

**Built and live-proven, no Claude API call needed for any of this**:

- `packager/src/rah_packager/engineering_answers.py` — `ENGINEERING_ANSWERS_SCHEMA`,
  `compute_inspection_fingerprint()`, structural schema validation.
- `packager/src/rah_packager/validate_answers.py` — `rah validate-answers`:
  schema check → cross-field consistency against the *current*
  `ProjectInspectionResult` (catches an answer claiming a script/doc path
  P2 never found) → staleness check (both anchors recomputed against the
  current repo).
- Live-proven against a real disposable Git repo, real container: valid
  matching answers accepted; a fabricated entrypoint script path rejected
  with the exact conflict named; staleness correctly detected after a
  **real** new commit, with real before/after commit hashes in the error
  message.
- **Real bug found and fixed along the way**: `git_inspection.py`'s dirty
  check counted untracked/modified content *inside* `.rah/` itself. Left
  unfixed, this would have broken staleness fingerprints the moment
  `rah prepare-answers` wrote its own output file (freshly-written,
  untracked `.rah/engineering-answers.json` would flip the repo dirty a
  moment after the fingerprint was computed against the clean state) —
  and retroactively explains the "immediately dirty after `rah init`"
  quirk noted during P1. Fixed by excluding `.rah/` via a Git pathspec
  (`git status --porcelain -- . ':!.rah'`), confirmed with real `git`.

**Also built, as a necessary prerequisite rather than part of the spec's
own 4 pieces**: real Claude API credential handling —
`Config.anthropic_api_key` (env var → mounted `~/.rah/credentials.env`
file, source-tracked; a real PowerShell/`Out-File` BOM bug was found and
fixed here too), `claude_client.py`'s `validate_api_key()`, 5 new
`PKG-CLAUDE-*` structured errors, and `rah health` reporting credential
status. Live-proven against the real Anthropic API: no key configured,
a real bogus key (real 401, no real secret needed), and finally the
engineer's real key (real 200, `valid: true`).

**`rah prepare-answers` — built and live-proven with real API spend**:
`packager/src/rah_packager/prepare_answers.py`. Three-tier suggestion
building (`build_suggestions()` — entrypoint/documentation guesses from
P2's discovered filenames, database platform guessed from Compose image
names, Contract defaults for `offline_requirements`/`models`/`client`;
all three keyword sets checked against HCopilot's and Indicator's real
filenames before being written, not invented then tested), context
bundling (`build_context_bundle()` — discovered facts + suggestions +
actual file contents of every script/doc/config template/Compose file
P2 found), a forced tool-use call to `claude-opus-5`
(`tool_choice={"type": "tool", "name": "submit_engineering_answers"}`,
schema derived from `ENGINEERING_ANSWERS_SCHEMA` minus `based_on`/
`schema_version` — those two are always computed deterministically by
the Packager, never asked of Claude, and always win over anything Claude
returns even if it echoed them back), `stop_reason: "refusal"` handling
(new `ClaudeRefusalError`/`PKG-CLAUDE-REFUSED`), and the same
tmp-write→validate→atomic-replace write pattern as P1. Confirmed
re-run behavior: unconditional overwrite, no "already initialized"
refusal.

18 new tests (108/108 total passing), all mocked at the `anthropic.Anthropic`
SDK boundary (same pattern as `test_claude_client.py`) so the suite costs
nothing to run.

Live-proven against a real disposable Git repo, real container, real
Anthropic API spend (`HTTP/1.1 200 OK` from `api.anthropic.com`):
- No API key configured → real `PKG-CLAUDE-API-KEY-MISSING`, no call made.
- Real key, real repo with one script + one doc → Claude returned a
  genuinely sensible answer (correctly confirmed the `install_offline.sh`
  suggestion, correctly inferred `database.required: false` and
  `models.required: false` from the absence of any DB/model evidence,
  confirmed all five documentation guesses) — schema-valid on write.
- Immediately re-validated with `rah validate-answers` → fresh, valid.
- A real new commit → `rah validate-answers` → real `PKG-ENGINEERING-ANSWERS-STALE`,
  correct before/after commit hashes in the message — closes the same
  staleness loop already proven deterministically for `validate-answers`
  alone, now proven through a real generation too.
- Ran `prepare-answers` again on the same (now-answered) repo → silently
  overwrote with a fresh answer keyed to the new commit, no refusal —
  confirmed re-validated as fresh immediately after.

Note: the real Indicator repository (this session's other live acceptance
app) had substantial unrelated uncommitted work in its working tree at
the time, so the live proof used a disposable scratch repo instead of
Indicator directly, specifically to avoid the new-commit step touching
unrelated WIP. `prepare-answers`/`validate-answers` don't need their own
polymorphism proof — P2 already proved the underlying
`ProjectInspectionResult` shape generalizes across HCopilot and Indicator;
P3 only needed to prove its own new logic (the Claude call, the schema
merge, the staleness loop) works for real, which it does.

## P4 — Done

`rah plan` (`release_plan.py`) previews exactly what Release would be
built, without building or finalizing anything — a pure read-only
combination of what P1–P3 already produce, not a new persisted artifact.
Unlike P1 (`project-state.json`) and P3 (`engineering-answers.json`),
`ReleasePlan` has no frozen JSON Schema and needed none: it's never
written to disk, so it gets the same ephemeral-result treatment as P2's
`ProjectInspectionResult`.

Four blocking conditions, each a real structured error, confirmed by the
user to have **no override policy in V1** (dirty source is always a hard
rejection — the Contract's own stated norm: `source_dirty: false`,
rejected "unless an explicit exceptional policy permits it", and V1
simply doesn't define one):

- **Project not initialized** (new `PKG-PLAN-PROJECT-NOT-INITIALIZED`) —
  distinct from P2's `packager_state: null`, which is a valid inspection
  result, not an error.
- **Dirty Git state** (new `PKG-PLAN-DIRTY-SOURCE-REJECTED`) — no
  `--allow-dirty` escape hatch.
- **Duplicate version** (new `PKG-PLAN-VERSION-ALREADY-RELEASED`) — the
  proposed version already exists in `release_history`.
- **Missing/invalid/stale engineering answers** — no new error at all;
  `prepare_plan()` calls P3's `validate_answers()` directly and lets its
  existing errors (`NOT-FOUND`/`SCHEMA-INVALID`/`CONFLICT`/`STALE`)
  propagate, rather than re-implementing any of that logic.

Version increment: before the first Release, the proposed version is
simply the `next_version` already chosen at `rah init` time (no
`--increment` semantics apply yet — nothing to bump from). After a first
Release, `--increment patch|minor|major` bumps semantically off
`current_release`. A fifth new error, `PKG-INPUT-INVALID-INCREMENT`,
covers a malformed `--increment` value (`click.Choice` also constrains
this at the CLI layer, but `release_plan.py` validates it independently
since `prepare_plan()` is a public function, not CLI-only).

`expected_release_directories` is computed by filtering
`release-layout.yaml`'s `required_structure` against the engineering
answers' `database.required` flag (the one genuinely conditional
directory in the frozen layout) — reusing the Contract's own directory
list rather than inventing a parallel one.

14 new tests (122/122 total passing): patch/minor/major increment,
first-release-uses-stored-next-version, invalid increment, duplicate
version, dirty state rejected, missing/stale engineering answers block
the plan, uninitialized project blocked, full plan shape (including the
conditional `database/` directory), plus 2 CLI-level tests. All use real
disposable `git init` repos, no mocks.

Live-proven against the real built container, using the same disposable
scratch repo already `rah init`-ed and answered during P3's live proof:
- Before `rah init` → real `PKG-PLAN-PROJECT-NOT-INITIALIZED`.
- After `rah init`, with a dirtied working tree → real
  `PKG-PLAN-DIRTY-SOURCE-REJECTED`, confirming the user's just-made "no
  override" decision holds in the real container, not just in tests.
- Clean, initialized, freshly-answered repo, `--increment minor` → a
  correct, complete `ReleasePlan` (proposed version, release directory
  name, required scripts, expected release directories with no
  `database/` since this app declares none required).

**Real finding during this live proof, not a bug**: computing the
staleness fingerprint via the host Python venv and via the container
produced two *different* fingerprints for the identical bind-mounted
repo at the identical commit — almost certainly a host-vs-container `git`
behavioral difference (e.g. Windows `core.autocrlf` affecting `git
status`'s clean/dirty read, which is itself hashed into the fingerprint).
This isn't new: P0 already established that running the Packager outside
its container was never a supported path, only documented there as a
Docker-connectivity issue rather than a `git`-behavior one. Fixed for the
live proof by computing the fingerprint and writing matching answers
*inside* the container exclusively, which is also the only way `rah
prepare-answers` ever actually runs in practice.

## P5 — Done

`rah build` (`docker_build.py`) builds every Compose service that
declares its own `build:` context, tags it, exports it to a `.tar`
archive, and reports a per-service inventory — the first slice to
perform real, expensive external operations (`docker build`, not just
reading/parsing).

Deliberately scoped down from the full P5 spec text, and documented as
such in the module docstring rather than left implicit: "internal
capabilities," not a full pipeline command — `application_slug` and
`version` are caller-supplied, not derived from Project Version State, so
`rah build` has no dependency on `rah init` having run and no "project
not initialized" gate (unlike P4). And "Docker image build" is read
literally — a service with only a prebuilt `image:` reference (no
`build:` key, e.g. a base database image) is reported in the inventory
but not built, tagged, or exported; the Packager doesn't attempt to
pull/re-export images it didn't produce in this slice.

Naming convention taken verbatim from the one concrete example in the
architecture's `docker` manifest section (`4. Stage 4 — Choose
Implementation Mechanisms.md` §18), not invented in parallel:
repository `rah-{application_slug}-{service}`, tag = the target version,
archive = `docker-images/{repository}_{tag}.tar`.

Compose validation is not reimplemented — `build_release_images()` calls
P2's `inspect_docker()` first, which already raises `MalformedComposeError`
for a structurally broken Compose file before any Docker interaction is
attempted at all.

Two new errors: `PKG-DOCKER-BUILD-FAILED` (carries the failing service
name and a real build-log tail — the "build failure mapping" and "build
logs" deliverables) and `PKG-DOCKER-IMAGE-EXPORT-FAILED`. Fails fast: the
first failing service build raises immediately, and whatever was already
built/exported before that point is left on disk in the output
workspace — a real, partial build workspace, never treated as finalized
(this module has no concept of a finalized Release at all; that's
entirely P6's job).

7 new tests (129/129 total passing), all against the **real** Docker
Engine — no mocks, consistent with this project's proof discipline. Two
new fixtures: `trivial-one-container/` (`FROM scratch` + `COPY`, no
network pull) and `broken-dockerfile/` (an unknown Dockerfile instruction —
fails during parsing, fast and deterministic, no network needed either).
Reused `compose-multi-service/` for the "simple frontend/backend
application" fixture (adjusted its backend Dockerfile from
`python:3.11-slim` to `python:3.12-slim`, already cached locally — a
pure test-fixture change with zero effect on any real app, confirmed
with the user) and `malformed-compose/` for the Compose-validation gate.
Covers: trivial build+export+reload-back, multi-service build (built vs.
prebuilt-image-reported-not-built), broken Dockerfile → structured error,
malformed Compose rejected before any Docker call, and a dynamically
constructed mixed-fixture proving a partial workspace survives a later
failure.

**Real bug found while writing the "partial workspace" test, not in
production code**: a Dockerfile containing only `FROM scratch` with no
further instruction produces no image ID at all ("No image was
generated") — a real Docker/BuildKit quirk, not a Packager bug. Fixed by
giving the test's own ad-hoc "good" fixture a `LABEL` instruction; the
real `trivial-one-container/` fixture was never affected since it always
had a `COPY`.

Live-proven against the real built container:
- The trivial fixture, end to end (build → tag → export → real
  `docker images load` round-trip on the exported `.tar`).
- **Real HCopilot** (the settled first acceptance app) — a real,
  substantial multi-service Compose stack: `sqlserver` (prebuilt image,
  correctly reported but not built), `db-init` (references the backend
  image directly, no `build:` key, correctly reported but not built),
  `backend` (real Python/FastAPI image — apt package installs including
  the MS ODBC driver, full `pip install` of `requirements.txt`, ~496 MB
  exported archive) and `frontend` (real `nginx:1.27-alpine`-based image,
  ~21 MB exported archive). Both builds and exports succeeded for real
  against the genuine HCopilot Dockerfiles, full real build logs captured
  in the structured result.
- **Real Indicator** (the required second, structurally different
  acceptance app — no database at all, shorthand `build: ./service`
  Compose syntax rather than the explicit `context`/`dockerfile` mapping
  form, unlike HCopilot's explicit form) — both `backend`
  (`python:3.12-slim`-based, ~144 MB exported archive) and `frontend`
  (nginx-based, ~23 MB exported archive) built and exported successfully
  for real, proving the shorthand-form handling P2 already covers extends
  correctly into an actual build, not just parsing. `ok: true`, full real
  build logs captured for both services.
- Both acceptance apps' proof images (4 total: HCopilot backend/frontend,
  Indicator backend/frontend) were removed from the local Docker image
  cache after their proofs, and the large exported `.tar` workspaces were
  deleted from the scratch directory — these were proof runs, not
  something to leave behind.

## P6 — Done

`rah construct` (`construct_release.py` + `release_manifest.py`) — "where
previous pieces finally combine": assembles a temporary *candidate*
Release directory (`release-layout.yaml`'s structure), generating
`release.yaml` from all five inputs the architecture's own P6 spec lists —
Project Version State (P1) + Inspection Result (P2) + validated
Engineering Answers (P3) + Build Artifact Metadata (P5) + Release Plan
(P4) — combined for the first time in one command. Produces a candidate,
not a finalized Release: no checksums, no Compliance Report, no Project

## P7 — Automated Portion Done

`rah package` and `rah validate` — the Period A Packager finish line's
automated half. `rah package` turns a P6 candidate into a finalized
Release: every RC-* rule from `validation-rules.json` (56 of the 57
total — everything except `RC-REPRO-001`, which the Contract itself
excludes from `validation_order` since it compares *two* independently
generated candidates, not one already-built Release; P6's own
`test_construct_release_is_reproducible` covers it instead), checksums,
a Compliance Report, and a Project Version State update that happens
*only* after everything else succeeds. `rah validate` independently
re-validates any Release directory afterward — no source project
required, matching the "Independent Validator" step in the Real Manual
Acceptance Test procedure.

**New modules**: `checksums.py` (SHA256SUMS generation/verification,
sha256sum-CLI-compatible format, plus the Release fingerprint —
COMPLETED as sha256 of `release.yaml`'s own bytes, deliberately *not*
derived from SHA256SUMS, which would create a circular dependency against
RC-INT-004's mandated closure order: Compliance Report generates before
the final checksum file that has to cover it); `compliance_report.py`
(`COMPLIANCE_REPORT_SCHEMA` embedded verbatim from the real, frozen
Contract file, same drift-test pattern as P6's manifest schema);
`compliance_rules.py` (the 56-rule engine, one function per rule, driven
by `validation_order`'s fatal-failure short-circuit: Release root
inaccessible / release.yaml missing / unparseable / Contract version
unresolved stops everything downstream as `NOT_EXECUTED`, everything else
is non-fatal and always runs so one pass surfaces every discoverable
violation); `finalize_release.py` (`package_release()` orchestration);
`validate_release.py` (`validate_release()`, standalone).

**Stage-A vs. RC-INT split**: RC-INT-004 explicitly excludes "final
SHA256SUMS and the Compliance Report" from stage-A validation — they're
*generated after* stage-A passes, so `compliance_rules.py` separates
`run_stage_a_rules()` (RC-CON through RC-SEC, 52 rules — what
`rah package`'s own Compliance Report contains) from `run_integrity_rules()`
(RC-INT, 4 rules — only meaningful once closure has happened, so only
`rah validate` runs them). `rah validate` also runs a full
`verify_checksums()` re-hash of every file, stricter than RC-INT-003
alone (which only re-checks `release.yaml` itself) — the real detector
for the "Checksum Mismatch" test scenario.

**Four real bugs found and fixed via live-proofing, not synthetic
tests**:
- **P6 itself was missing directories.** `configuration/` (unconditionally
  required by the layout Contract) was only created when a template
  existed; `checksums/`/`compliance/` were never created at all (they're
  P7's job, but the *directories* should exist from construction time
  onward). Fixed in `construct_release.py` — now creates every
  layout-required directory unconditionally, even empty ones P6 itself
  never populates.
- **RC-DIR-004/006 checked for `checksums/SHA256SUMS`'s existence during
  stage-A**, before it's generated — a direct contradiction of RC-INT-004's
  own closure ordering. Fixed to check only what should genuinely exist
  pre-closure (the directory, and `compose/docker-compose.yml`).
- **RC-ART-008 assumed the classic Docker `manifest.json` format
  (`RepoTags` populated).** This Docker installation's `image.save()`
  produces OCI-format archives (`index.json` + content-addressed blobs)
  where `RepoTags` is `null` and no tag is recoverable anywhere —
  observed directly, not assumed. Fixed to verify tag identity when the
  format carries it, and fall back to structural validity (every blob
  `manifest.json` references actually exists in the tar) when it
  doesn't — documented as a real, environment-dependent limitation, not
  silently ignored.
- **A placeholder-detection false positive in RC-CFG-001/RC-SEC-003**:
  the original heuristic only recognized `changeme`/`replace_me` as
  placeholder text; HCopilot's real `.env.offline.template` uses
  `REPLACE_WITH_STRONG_PASSWORD`, which didn't match. Rewritten from an
  exact-word whitelist to a substring-marker approach
  (`change|replace|your|todo|sample|example|placeholder|xxx|dummy|<…>|${…}`),
  since placeholder phrasing genuinely varies across teams and an exact
  whitelist can never be complete.

**Two real environment findings, not Packager bugs** (both specific to
this Windows + Docker Desktop bind-mount setup, not the containerized
execution path itself):
- **Executable bits don't propagate through `git checkout` on a
  Windows-bind-mounted repo** when `core.fileMode=false` (Git for
  Windows' default) — `chmod`ing a *freshly created* file inside the
  container works fine, but files git materializes from its index at
  `core.fileMode=false` never get the exec bit applied, regardless of
  what the index itself records. Root cause, not just a symptom
  workaround: `git config core.fileMode true && git checkout -- <path>`
  inside the container. `RC-SCR-005` also gained a live probe
  (`_exec_bit_propagates()`) that writes a throwaway file into the
  Release directory and checks whether `chmod` sticks at all — a genuine
  environment-capability check, not an assumption based on `os.name`;
  correctly degrades to a syntax-only check when the Release directory
  is mounted read-only (proven live during the standalone `rah validate`
  re-check).
- **`core.autocrlf=true` (this session's earlier CRLF fix from P4/P6)
  solves `git status` false-dirty detection but does not produce LF
  content** — it converts checked-out files *to* CRLF (its actual,
  Windows-oriented purpose), which is exactly wrong for a script `bash
  -n` needs to parse. The correct fix for genuinely LF working-tree
  content is `core.autocrlf=input` (normalize CRLF→LF on commit, no
  conversion on checkout) — discovered when `bash -n` failed on HCopilot's
  real scripts with visible `\r` bytes in the syntax error output despite
  `git status` already reporting clean. This refines, not reverses, the
  earlier P4/P6 finding: that fix was correct for what it was solving
  (status cleanliness); this session's RC-SCR-005 live proof is the first
  time anything in this codebase needed to actually *execute* checked-out
  script content, which is what exposed the gap.

## P8 — Model Artifacts & Offline-Completeness Closure

Not part of the original P0–P7 proposal — it only became a well-defined,
buildable problem once a real declared model artifact (HCopilot's
`Flow_prediction.pkl`) was pushed all the way through `rah package` for
the first time. `P6`'s own text had already flagged this as unimplemented;
this slice is the actual design and build.

**Two real gaps closed, both discovered by testing against real apps, not
designed up front:**

- **Model-artifact resolution.** The engineering-answers schema gained two
  new required fields per declared artifact — `source_path` (where the
  model file or directory actually lives in the source repo) and
  `service` (which Compose service it's baked into) — neither existed
  before, and without them there was no way to know *what* to checksum.
  New module `model_artifacts.py`: `verify_and_checksum_model_artifacts()`
  runs before the Docker build (fail fast on a bad path, matches the
  Contract's own "computed before the build" wording for `checksum`);
  `resolve_baked_into_image()` runs after, once the real `docker.images[]`
  list exists, to cross-check `service` against it. Directory artifacts
  (HCAT's `models_directory/`, 100+ files) get a deterministic tree
  checksum, not just a single-file hash — same code path as a single file,
  not a special case. This did **not** require touching the frozen
  Release Contract — only the Packager-owned engineering-answers schema.
- **`RC-OFF-002` sibling-image gap.** Found live, against real HCopilot:
  its `db-init` service has no `build:` key but declares the *same* image
  tag `backend` builds — not an external image to pull (which failed with
  a real 404), but a build another service in the same file already
  produces. Fixed by cross-referencing every build-having service's own
  image tag before deciding to pull anything; the compose-rewrite step
  now resolves the shared service's `image:` to whatever tag the sibling
  actually got.

**Two more real, previously-unknown bugs surfaced and fixed along the
way** (neither related to models specifically):
- A placeholder-detection gap — HCopilot's own `.env.offline.template`
  correctly used `__GENERATE_ME__` as its placeholder convention, but the
  detection regex only recognized `change`/`your`/`todo`/`sample`-style
  markers. Extended, not worked around.
- A staleness-loop bug — the Packager's own `--output` directory,
  conventionally nested inside the project it's packaging, wasn't
  excluded from the project's own inspection walk, so every `rah package`
  run silently changed the very fingerprint used to detect whether
  engineering answers had gone stale.

previous session's live-proof got past every model/image gate for the
