## P0 — Done

Built in `packager/` (Python, `click` CLI, `docker` SDK): `rah version`,
`rah health`, a common JSON result/error envelope, Docker connectivity
check, config loading (`RAH_REPO_PATH`/`RAH_OUTPUT_PATH`/`RAH_LOG_LEVEL`
env vars), logging to stderr only, and a Dockerfile.

All 6 required P0 tests verified — 14/14 pytest passing, and every one of
them re-proven live against the actual built container (`docker build` +
`docker run`), not just mocked:

- **Runtime Test** — container builds and starts.
- **Mounted Repository Test** — `docker run -v <repo>:/repo:ro
  -e RAH_REPO_PATH=/repo`, correctly read 12 top-level entries from the
  real repo.
- **Output Test** — `-v <dir>:/output -e RAH_OUTPUT_PATH=/output`, wrote
  and read back a marker file, cleaned up after itself.
- **Docker Connectivity Test** — `-v /var/run/docker.sock:/var/run/docker.sock`
  (Docker-outside-of-Docker), reached the real host Engine, reported
  `server_version: 29.6.1`.
- **Structured Result Test** — every invocation, success or failure,
  printed exactly one valid JSON envelope on stdout.
- **Failure Test** — same container run *without* the socket mounted:
  clean `PKG-RUNTIME-DOCKER-UNAVAILABLE` structured error, exit code 1, no
  crash, no traceback.

One real-environment finding worth keeping in mind for later slices:
`docker-py`'s `from_env()` cannot reach modern Docker Desktop's
`desktop-linux` context (`npipe:////./pipe/dockerDesktopLinuxEngine`) when
run directly against the Windows host from a bare Python process — it
only works from inside the container, via the standard Unix-socket bind
mount. Not a bug; just means "run the CLI directly on Windows outside
Docker" was never actually a supported path, only "run it containerized,"
which matches the plan's own framing throughout.

## P1 — Done

Built `rah init` (`project_state.py`, plus new `PackagerError` subclasses in
`errors.py`, plus the CLI wiring in `cli.py`):

- `--project`, `--name`, `--slug`, `--initial-version` (default `1.0.0`).
- Validates the project path exists, detects a Git repository (presence of
  `.git` at the project root — no `git` binary needed for this; real commit/
  branch/tag extraction is P2's job, not P1's), refuses reinitialization if
  `.rah/project-state.json` already exists, validates `name`/`slug`/
  `initial_version`, then builds and atomically writes the initial Project
  Version State.
- The JSON Schema (`PROJECT_STATE_SCHEMA` in `project_state.py`) is copied
  verbatim from architecture §12; application-level rules and the write-safety
  recipe (write `.tmp` → validate → `os.replace`) follow §13–14 exactly.
- New error codes: `PKG-INPUT-PROJECT-PATH-NOT-FOUND`,
  `PKG-GIT-NOT-A-REPOSITORY`, `PKG-PROJECT-ALREADY-INITIALIZED`,
  `PKG-INPUT-INVALID-APPLICATION-IDENTITY`, `PKG-PROJECT-STATE-SCHEMA-INVALID`,
  `PKG-FILESYSTEM-PROJECT-STATE-WRITE-FAILED` — all within the category
  namespace already given in `docs/architecture/4.6. Stage 4 — Packaging
  Engine Specification.md` §9 (`PKG-INPUT`, `PKG-GIT`, `PKG-PROJECT`,
  `PKG-FILESYSTEM`), not the still-deferred full sub-code taxonomy.

12 new tests added (26/26 total passing), covering all 6 required P1 tests
from the spec: Valid Initialization, Existing State (safe refusal, original
file untouched), Invalid Path, Non-Git Repository, Atomicity (schema-validation
failure and atomic-replace failure both verified to leave no `project-state.json`
and no leftover `.tmp` file — using `subprocess`-driven real `git init` repos,
not mocks), and Schema Test.

Every required test was also re-proven live against the real built container,
not just pytest:

- Built `rah-packager` image with the new `jsonschema` dependency.
- Ran `rah init` against a real disposable Git repository (`git init` +
  a real commit) bind-mounted into the container — produced a valid
  `.rah/project-state.json` on the host filesystem, exactly matching the
  architecture §9 "before first release" shape.
- Ran it again against the same repo — got the real, structured
  `PKG-PROJECT-ALREADY-INITIALIZED` refusal, original file untouched.
- Ran it against a bind-mounted directory with no `.git` — got the real,
  structured `PKG-GIT-NOT-A-REPOSITORY` failure.
- Ran it against a real clone of HCopilot (Period A's designated P1
  acceptance app; a disposable local clone was used rather than the
  engineer's live working copy, to avoid writing into it) — succeeded,
  produced a valid `.rah/project-state.json` inside the real HCopilot
  source tree.

## P2 — Done

Built `rah inspect` (`inspection.py` orchestrating four category modules,
plus a new shared `repository.py` extracted from P1's path/Git-repo
checks). All four required categories from the spec:

- **Git** (`git_inspection.py`) — shells out to the real `git` binary
  (now installed in the Dockerfile, P1 didn't need it) for branch,
  commit, tag (`null` if untagged), and clean/dirty state. New error
  `PKG-GIT-INSPECTION-FAILED` for a confirmed-Git repo whose plumbing
  still fails (e.g. no commits yet, so `HEAD` doesn't resolve).
- **Docker** (`docker_inspection.py`) — finds Dockerfiles (pruning
  `node_modules`/`.venv`/etc. before descending, not after), finds the
  Compose file by convention, parses it (new `pyyaml` dependency),
  extracts services with `image`/`build.context`/`build.dockerfile`.
  Two failure modes handled differently: missing Dockerfile/Compose is
  not an error (empty/`null`); a Compose file that exists but doesn't
  parse as valid YAML is a real error (`PKG-DOCKER-MALFORMED-COMPOSE`).
- **Packager State** (`packager_state_inspection.py`) — reads
  `.rah/project-state.json` back via P1's own `project_state_path()`/
  `validate_state()`, no new schema. `null` if never `rah init`-ed
  (not an error); a corrupted file is (`PKG-PROJECT-STATE-READ-FAILED`
  for bad JSON, P1's existing `PKG-PROJECT-STATE-SCHEMA-INVALID` for
  schema violations).
- **Application Resources** (`application_resources_inspection.py`) —
  the one category with no universal filename convention (unlike
  `.git`/`Dockerfile`). The conventions used (`.env*example*`/`*template*`
  configuration templates, `scripts/`-named directories, `migrations`/
  `alembic`-named directories, root and `documentation/`-style `*.md`
  docs, `*verify*`/`*valid*`-named verification candidates,
  environment-variable names parsed out of the config templates) were
  not invented speculatively — they were checked against and confirmed
  by the real, consistent structure of **both** P2 acceptance apps
  (HCopilot and Indicator) before being implemented, not guessed and
  then tested.

26 new tests added (52/52 total passing). Fixtures added under
`packager/tests/fixtures/projects/`: `compose-multi-service/`,
`missing-dockerfile/`, `malformed-compose/`, and `valid-simple-app/`
(the last one filling a gap — see below). `dirty-repository/` was
deliberately **not** added as a static fixture: a "dirty repo" fixture
would need to be a nested Git repository with its own uncommitted
changes baked in, which isn't practically maintainable inside a
Git-tracked fixtures directory. Dirty-state coverage instead uses real,
disposable `git init` repos created on the fly in `test_git_inspection.py`
— a deliberate substitute, not an oversight.

Every category was also re-proven live against the real built container,
including against both real acceptance apps:

- Real disposable Git repos: clean+tagged, dirty via edit, dirty via
  untracked file, non-Git directory, Git repo with no commits yet — all
  produced the correct real `git` stderr surfaced in structured errors.
- A real clone of HCopilot: all 4 categories returned correctly,
  including its actual 4-service Compose stack (`sqlserver`, `db-init`,
  `backend`, `frontend`), its real `alembic` migrations, its real
  `.env.example`/`.env.offline.template` files, and (once initialized)
  its real Packager State.
- The **real Indicator repository directly** (read-only bind mount, no
  clone needed since `inspect` never writes) — structurally different
  from HCopilot (no database, `python-service` instead of `backend`,
  no explicit `image:` names) but produced the identical
  `ProjectInspectionResult` shape with no per-app branching anywhere in
  the code. This is the first real evidence that the `P2`→`P3`
  discovery mechanism actually generalizes, not just runs once.

## What's Actually Been Done So Far

Three things, all at the planning/contract layer — none of it code yet:

1. **Release Contract V1 materialized.** All four files this table's `P2`,
   `P4`, and `P6` rows depend on now exist as real, tested files:
   `contracts/1.0/release-layout.yaml`,
   `contracts/1.0/release-manifest.schema.json`,
   `contracts/1.0/validation-rules.json`,
   `contracts/1.0/compliance-report.schema.json` (plus
   `contracts/1.0/README.md`). Both JSON Schemas were tested against
   realistic valid and invalid instances, not just written and assumed
   correct. **Not yet frozen** — see
   `docs/development/contract-v1-completion-log.md` for the 8 completed
   decisions still needing review before this table's "blocked on Contract
   V1 Freeze" rows can clear.

2. **Packager responsibility boundaries decided**
   (`docs/decisions/packager-responsibility-boundaries.md`). Directly
   narrows scope for `P2`, `P5`, and `P6`:
   - No separate `assets/`/`models/` Release directory exists. All
     app-specific binary content (ML models included) bakes into a Docker
     image via ordinary `COPY`. `P2`'s inspector does not need a
     "does this app declare a separate large asset" heuristic; `P5`'s
     fixture list does not need a large-asset-extraction case; `P6`'s
     Release Construction does not need an assets category, checksum
     handling, or extraction logic.
   - Confirmed: if a future session ever needs `if project == "HCAT"`
     inside the Packager's own code, that's a sign the Contract or the
     `P3` engineering-answers schema is incomplete — never a legitimate
     per-app branch. Worth keeping in mind while implementing `P2`/`P3`.
   - Confirmed with real evidence: Release output is additive — every
     `rah package` run produces a new, immutable, versioned directory,
     never overwriting a prior one. Relevant to `P4`'s duplicate-version
     rejection tests and `P6`'s Release Construction.

3. **Acceptance app sequence decided** (`docs/development/CURRENT.md`,
   memory `packager-acceptance-app-sequence`). `P5`'s "Later add HCAT"
   fixture note is superseded: **HCopilot first, Indicator second** —
   Indicator is a required proof that the `P2`→`P3` inspect/ask-gap
   mechanism actually generalizes across a structurally different app
   (no database at all), not an optional stretch fixture. HCAT is
   deliberately deferred past both.
