**Problems Discovered:**

The root cause of the `RC-SCR-005` failure is in the Indicator application
repository, not the Packager: all ten scripts under `release/scripts/`
(including the five declared as lifecycle entrypoints) are committed to
Git as mode `100644`, confirmed directly via `git ls-files -s
release/scripts/` on the freshly cloned commit — this is a real gap at the
Git object level, not a checkout-time artifact like the CRLF/exec-bit
findings already documented for HCopilot in P6/P7. Same underlying cause
as those — the repo was authored and committed from Windows, where
`core.fileMode` is typically off and the executable bit was never recorded
— but a distinct instance of it, since these are Packager-generated
Release *scripts* the Indicator engineer wrote by hand, not source checked
out by the Packager itself. `rah package` did exactly what it's supposed
to: it built real Docker images, assembled a full candidate Release, then
correctly refused to finalize a non-compliant Release rather than
producing one silently missing a required property — the Compliance
Report did its job.

Worth a design note for whoever picks this up next (not fixed in this
session — the procedure is explicit that a `PKG-*` error means record and
stop, not hand-patch and retry): `rah construct`'s resource-copy step
(`construct_release.py:127`, `_copy_resources_and_rewrite_answers`) copies
each declared script via `shutil.copy2`, which preserves the source file's
permission bits verbatim and includes no `chmod` call anywhere in that
write path (confirmed absent from `construct_release.py`,
`docker_build.py`, `release_manifest.py`, and `finalize_release.py`). That
means the Packager currently has no independent enforcement of the
executable bit on the scripts it places into a Release — it relies
entirely on `RC-SCR-005` at the `package` gate to catch a source-repo
defect after a full, real Docker build has already run. Functionally
correct (nothing non-compliant escaped), but expensive: a genuine build of
both images (161 MB total) ran to completion before the failure surfaced,
when a `chmod`-on-copy (or a pre-build permission check) could have caught
the same problem before spending the Docker build time at all.

**Problems Discovered — three real, previously-unknown bugs, all found by
genuine execution failure, not inspection:**

1. **Packager: sibling-script copy gap** (`construct_release.py`).
   `_copy_resources_and_rewrite_answers` copied only the individually
   declared entrypoint file per manifest field, never any sibling file it
   might `source`. Indicator's real `install_offline.sh` sources a shared
   `_common.sh` that no manifest field names — `RC-SCR-005` had already
   passed (syntactically valid, executable) but real execution failed
   immediately with "No such file or directory." Root cause: real
   lifecycle scripts routinely depend on a shared helper library; no
   single declared entrypoint field can name every file such a script
   needs. **Fix**: copy every file in a script-like entrypoint's own
   source directory (not just the one named file) into whichever Release
   subdirectory(s) draw from it, deduplicated per (destination subdir,
   source directory) pair — verified correct for the case where the same
   source file is copied to two different destinations
   (`deployment.entrypoints.verify` and `verification.entrypoint` both
   point at `verify_installation.sh`). One new regression test
   (`test_construct_release_copies_sibling_scripts`).
2. **Indicator repo: two real script bugs, not Packager bugs.** The
   scripts under `release/scripts/` were written for the old, pre-Packager
   manual RAH-OIP deployment convention (a self-contained `release/`
   folder toolkit) and never adapted to what `rah package` actually
   produces: `COMPOSE_FILE` referenced `docker-compose.offline.yml` in 8
   places across `_common.sh` and 7 other scripts (Packager always
   generates `compose/docker-compose.yml`, fixed by the layout Contract);
   `load_images.sh` hardcoded `docker-images/backend.tar` and
   `frontend.tar` (Packager names archives
   `rah-{slug}-{service}_{version}.tar`, version embedded on purpose so
   Release versions never collide — rewritten to `docker load` every
   `*.tar` found under `docker-images/` instead of assuming fixed names);
   `install_offline.sh`'s config-template copy referenced
   `compose/.env.offline.template` instead of the real
   `configuration/.env.offline.template`. All fixed, syntax-checked
   (`bash -n`), and committed locally to Indicator's own repo
   (`ab170e9`, `6013394`) — not yet pushed.
3. **Packager: image-tag export bug, serious — affects every Release
   ever produced** (`docker_build.py`). `_export_one_image` called
   `image.save()` with no arguments. `docker-py`'s own docstring says
   plainly: the default (`named=False`) "will not retain repository and
   tag information for this image." Every prior live-proof — including
   P6's and P7's own automated-portion proofs, and P8's HCopilot proof —
   only ever reloaded an export back into the *same* Docker Desktop
   installation that built it, which never surfaced this. A genuinely
   separate Docker Engine (Debian Docker CE on the offline VM) loaded
   every archive as **completely untagged**, so `docker compose up`
   couldn't find the image locally and fell back to a registry pull —
   which fails offline, the exact failure mode the whole Contract exists
   to prevent. This also retroactively explains an already-documented,
   only partially-understood P7 finding from the automated-portion proof
   (RC-ART-008's "OCI-format archive, `RepoTags: null`" observation) —
   that was already live evidence of this exact bug, treated at the time
   as a merely cosmetic Docker-format quirk the Validator needed to
   tolerate, not root-caused at the export layer. **First fix attempt
   (`named=True`) was itself insufficient** — caught immediately on the
   very next install attempt: it silently picks `image.tags[0]`, and a
   content-addressed image ID accumulates every tag it was ever
   built/pulled with across repeated runs in this Engine's history
   (nothing untags the previous version automatically) — a stale prior
   version's tag (`1.0.0`) got embedded into the `1.0.2` archive instead
   of the current Release's own tag, caught by `RC-ART-008` itself
   refusing to finalize the mismatch rather than silently shipping it.
   **Final fix**: pass the exact, already-known tag reference explicitly
   (`image.save(named=image_ref)`) instead of relying on list order — both
   call sites (built images, pulled images) already have that exact
   string in scope. Two regression tests strengthen the existing
   same-installation round-trip tests in `test_docker_build.py` (which
   never asserted `.tags` at all — the actual gap that let this ship
   undetected for every prior Release), plus one new test
   (`test_export_uses_the_correct_tag_when_image_has_prior_versions`)
   that reproduces the multi-tag scenario directly by building the same
   Dockerfile content twice under different versions. 186/186 tests pass.
