**Problems Discovered:**

The root cause of the `RC-SCR-005` failure is in the Indicator application
repository, not the Packager: all ten scripts under `release/scripts/`
(including the five declared as lifecycle entrypoints) are committed to
Git as mode `100644`, confirmed directly via `git ls-files -s
release/scripts/` on the freshly cloned commit — this is a real gap at the
Git object level, not a checkout-time artifact like the CRLF/exec-bit
findings already documented for HCopilot in P6/P7. Same underlying cause
as those — the repo was authored and committed from Windows, where
`core.fileMode` is typically off and the executable bit was never recorded
— but a distinct instance of it, since these are Packager-generated
Release *scripts* the Indicator engineer wrote by hand, not source checked
out by the Packager itself. `rah package` did exactly what it's supposed
to: it built real Docker images, assembled a full candidate Release, then
correctly refused to finalize a non-compliant Release rather than
producing one silently missing a required property — the Compliance
Report did its job.

Worth a design note for whoever picks this up next (not fixed in this
session — the procedure is explicit that a `PKG-*` error means record and
stop, not hand-patch and retry): `rah construct`'s resource-copy step
(`construct_release.py:127`, `_copy_resources_and_rewrite_answers`) copies
each declared script via `shutil.copy2`, which preserves the source file's
permission bits verbatim and includes no `chmod` call anywhere in that
write path (confirmed absent from `construct_release.py`,
`docker_build.py`, `release_manifest.py`, and `finalize_release.py`). That
means the Packager currently has no independent enforcement of the
executable bit on the scripts it places into a Release — it relies
entirely on `RC-SCR-005` at the `package` gate to catch a source-repo
defect after a full, real Docker build has already run. Functionally
correct (nothing non-compliant escaped), but expensive: a genuine build of
both images (161 MB total) ran to completion before the failure surfaced,
when a `chmod`-on-copy (or a pre-build permission check) could have caught
the same problem before spending the Docker build time at all.

Separately, two environmental notes from getting to this point, for
whoever runs this test again: (1) the Indicator repo on the Legion had
real, substantive uncommitted work sitting in the working tree — not
noise — including a fix removing a `fonts.googleapis.com` CDN `@import`
in favor of locally bundled `@fontsource/cairo`/`@fontsource/inter`
packages (a genuine offline-readiness fix; a plain `git clone` of the
prior commit would have silently shipped a Release that still phones home
for fonts) and a `docker-compose.yml` rewrite fixing a real storage
mount-path inconsistency and adding healthchecks. These were committed by
the user (`98c83c6`) before packaging, at this session's request, rather
than packaged in a dirty state or silently dropped via a naive clone. (2)
`scp -r` from `or-stt` to the Legion's Windows OpenSSH failed on
`node_modules/.bin` entries (Windows reparse points/shims that Windows
OpenSSH's SFTP can't open); switched to `git bundle create - HEAD` over
SSH piped into a local `git clone`, which avoided both that and an
unrelated `git+ssh://` failure caused by the Legion's default remote shell
being `cmd.exe` rather than something `git-upload-pack` can run over
directly.
