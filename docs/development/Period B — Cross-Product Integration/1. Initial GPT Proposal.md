# Period B — Cross-Product Integration

This period is fundamentally different from Period A.

In Period A we ask:

> **Does each product work independently?**

In Period B we ask:

> **Does the exact Release produced by the real Packager behave correctly when consumed by the real Platform?**

That means Period B should be much smaller than Period A. We are not building a third product. We are proving the **boundary between the two products** and the complete manual workflow.

The main danger here is also different: if we add too many features during integration, we lose the clean signal we worked so hard to create in Period A.

---

# Period B — Cross-Product Integration

## Period Goal

Integrate the independently validated Packaging Engine and Offline Platform and prove that a Release generated by the Packager can pass unchanged through transfer, Platform discovery, import, installation, verification, update, and manual qualification.

The governing rule is:

```
Packager Output
        ↓
NO MANUAL REPAIR
NO REPACKAGING
NO MANIFEST EDITING
        ↓
Platform Input
```

If the Platform cannot consume the Package exactly as produced, the integration test fails.

The Release Package itself shall remain immutable throughout Period B.

---

# Entry Gate

Period B shall **not start merely because development has progressed far enough**.

It begins only when the relevant Period-A gates have passed.

## Packager Minimum Gate

The Packager must already prove independently that it can:

- initialize a real repository;
- inspect it;
- validate engineering answers;
- plan a Release;
- build Docker artifacts;
- construct the Release;
- validate it against the Contract;
- finalize it;
- produce a stable Release fingerprint;
- produce a Release that can be manually installed offline.

## Platform Minimum Gate

The Platform must already prove independently that it can:

- scan known Golden Releases;
- import them;
- represent Applications and Releases correctly;
- plan installations;
- install a known Golden Release;
- verify it;
- update between known compatible Golden Releases;
- preserve backup/history;
- detect failures and drift;
- expose operation results through the API.

Period B starts only after both sides can be trusted independently.

---

# Integration Principle

Period B shall introduce **one new uncertainty at a time**.

We should not immediately do:

```
Real HCAT
↓
Packager
↓
Network Transfer
↓
Platform
↓
Install
↓
Update
↓
Verification
↓
Recovery
```

in one giant first test.

Instead, we progressively extend the boundary.

The integration slices should answer increasingly stronger questions.

---

# Proposed Slice Map

I recommend **7 Period-B slices**:

```
B0 — Integration Harness & Traceability
        ↓
B1 — Packager Release → Platform Discovery
        ↓
B2 — Packager Release → Platform Import
        ↓
B3 — Real Generated Release → Fresh Installation
        ↓
B4 — Real Generated Release → Verification & State Consistency
        ↓
B5 — Real Release Pair → Update Path
        ↓
B6 — Full Manual Qualification & Failure Proof
```

The important characteristic is that every slice uses **real Packager output**.

Golden Releases remain useful as diagnostic controls, but they are no longer the primary input.

---

## Objective

Prepare a controlled integration environment before connecting product behavior.

This slice proves that we can identify, move, and trace one exact Release across both environments.

No installation yet.

## Required Tests

### Fingerprint Before Transfer

Record Packager-produced fingerprint.

### Transfer

Copy exact Release.

### Fingerprint After Transfer

Must match.

### No Mutation

No files may be modified to make the Platform accept the Release.

### Repeatability

The same Package can be transferred again and produces the same fingerprint.

---

## Completion Gate

We can prove:

> **The Release being tested by the Platform is exactly the Release finalized by the Packager.**

This becomes the foundation of all later qualification evidence.

# B1 — Packager Release → Platform Discovery

## Objective

Test the smallest real Packager/Platform boundary:

> Can the Platform discover an actual Release generated by the Packager?

No import yet.

---

## Workflow

```
Real Application Repository
        ↓
Packager
        ↓
Finalized Release
        ↓
Transfer
        ↓
Platform incoming/
        ↓
Scan
```

---

## Required Tests

### Valid Generated Release

Platform classifies candidate:

```
READY_FOR_IMPORT
```

### Identity Agreement

Platform discovers exactly the same:

- application slug;
- version;
- Contract version;

as the Packager declared.

### Repeated Scan

Does not create duplicate candidate confusion.

### Incomplete Transfer Simulation

A partially copied Packager Release must not be treated as ready.

### Fingerprint Integrity

Candidate corresponds to the same Release artifact.

---

## Failure Signal

If this slice fails, the problem is limited mainly to:

```
Packager directory/layout output
or
Platform discovery interpretation
```

We do not yet involve Registry import, Docker, installation, or verification.

That is exactly why this deserves its own slice.

---

## Completion Gate

Real Packager Release is discoverable by the Platform without modifications.

# B2 — Packager Release → Platform Import

## Objective

Prove full compatibility between:

```
Packager-produced Release Contract
```

and:

```
Platform Release consumer
```

This is the most important **contract integration test**.

---

## Workflow

```
Packager-generated Release
        ↓
Platform Scan
        ↓
Platform Import
        ↓
Application + Release Registry
```

---

## Required Comparisons

After import, compare Packager and Platform interpretation of:

- application slug;
- application name;
- Release version;
- Release fingerprint;
- Contract version;
- Manifest schema version;
- supported operations;
- Docker artifacts;
- configuration inputs;
- lifecycle scripts;
- verification declarations;
- compatibility rules.

There must be no semantic reinterpretation.

---

## Required Tests

### Successful Import

Real generated Release imports.

### Registry Identity

Correct application created/reused.

### Fingerprint

Platform stored fingerprint equals Packager fingerprint.

### Manifest Interpretation

Key fields match exactly.

### Duplicate Import

Predictable behavior.

### Generated Bad Release Control

Take a copied test fixture and deliberately corrupt one checksum.

Platform rejects it.

Important: this corrupted copy is a test fixture, not a modification of the real candidate.

---

## Completion Gate

We prove:

> **The producer and consumer understand the Release Contract the same way.**

This is the real Packager/Platform compatibility gate.

---

# B3 — Real Generated Release → Fresh Installation

## Objective

Prove that a Release generated by the actual Packager is operationally usable by the actual Platform.

This is the first end-to-end deployment integration.

---

## Workflow

```
Real repository
        ↓
Packager
        ↓
Real Release 1.0.0
        ↓
Transfer
        ↓
Platform Import
        ↓
Installation Plan
        ↓
Configuration
        ↓
Install
```

---

## Important Rule

Do not manually run:

```
install_offline.sh
```

during the primary integration test.

Period A already proved manual installation.

Period B is specifically testing whether the **Platform can correctly invoke and manage** that same Release behavior.

Manual script execution may still be used diagnostically if the Platform test fails.

---

## Required Tests

### Installation Plan Agreement

Platform correctly discovers the configuration requirements Packager encoded.

### Lifecycle Entrypoint

Platform invokes the exact Packager-declared installation entrypoint.

### Docker Artifacts

Platform successfully consumes the exported images.

### Configuration

Deployment values are rendered correctly.

### Installation Result

Lifecycle execution succeeds.

### Registry

Deployment attempt recorded.

### Logs

Operation evidence is captured.

---

## Diagnostic Control

If Platform installation fails:

1. preserve Platform failure evidence;
2. run the same Release manually using the already-proven Period-A method;
3. compare.

This gives a powerful signal:

```
Manual install PASS
Platform install FAIL
→ Platform integration problem

Manual install FAIL
→ likely Release/Packager regression
```

This is one of the major benefits of the Period-A separation.

---

## Completion Gate

A real Packager-generated Release can be installed by the real Platform without Package modification.

---

# B4 — Real Release → Verification and State Consistency

## Objective

Prove that the Platform's three-authority model correctly understands the deployed result of a Packager-generated Release.

---

## Workflow

```
Manifest Expected State
        +
Platform Registry State
        +
Actual Host State
        ↓
Verification
        ↓
Reconciliation
```

---

## Required Tests

### Release Identity

Installed image/version matches generated Release.

### Docker State

Expected services and image tags match Manifest declarations.

### Port

Observed port matches deployment configuration.

### Database

Expected database/migration state reached.

### Health

Mandatory application checks pass.

### Registry Activation

Only after successful verification does Release become active.

### Traceability

Active deployment can be traced back to:

```
deployment
→ Platform Release ID
→ Release fingerprint
→ Packager Release
→ Git commit
```

### Controlled Drift

Manually stop one expected container.

Platform must detect drift.

Restart/restore the expected state and reverify.

---

## Completion Gate

The real generated Release is not merely installable; the Platform can **correctly understand and prove its resulting state**.

# B5 — Real Release Pair → Update Path

## Objective

Prove the complete version-transition contract using two actual Packager-generated Releases.

This is substantially stronger than a fresh-install test.

We need:

```
Release A
+
Release B
```

generated independently from real application revisions.

Example:

```
HCAT 1.0.0
HCAT 1.1.0
```

---

## Preparation

Both Releases must independently pass Packager validation.

Both fingerprints are recorded.

Release B must explicitly support:

```
UPDATE from 1.0.0
```

according to the chosen Manifest transition contract.

---

## Workflow

```
Import A
        ↓
Install A
        ↓
Verify A
        ↓
Import B
        ↓
Prepare Update
        ↓
Backup
        ↓
Update A → B
        ↓
Verify B
        ↓
B active
A historical
```

---

## Required Tests

### Transition Recognition

Platform correctly understands B accepts A as update source.

### Configuration Preservation

Deployment-specific values survive.

### Secret Preservation

Secrets survive without re-entry unless the Release requires change.

### Backup

Required backup completes before update.

### Image Replacement

B artifacts replace A's versioned artifacts correctly.

### Persistent State

Database/data survive according to Contract.

### Migration

Expected migration executes.

### Verification

B passes mandatory verification.

### Active State

B becomes active only after complete success.

### History

A remains historically visible.

---

## Controlled Failure Test

Create a deliberate **test Release B-fail** or controlled failure mode.

For example:

- verification endpoint fails;
- migration returns failure;
- one mandatory service remains unhealthy.

Then prove:

```
Update attempt FAILED
Target not active
Previous successful record preserved
Recovery requirement visible
```

Again, the intentionally broken artifact must be a test artifact, not a mutation of the real qualified Release.

---

## Completion Gate

The Packager and Platform agree not only on static Releases but on a real version transition.

This is the strongest technical integration gate before qualification.

# B6 — Full Manual Qualification and Failure Proof

## Objective

Execute the complete Release Qualification procedure manually using the two real products, without Jenkins.

This is Period B's final deliverable and directly defines what Period C will automate.

---

# Qualification Scenario

Start from a reproducible validation-machine baseline.

## Phase 1 — Candidate Creation

```
1. Select real application source state.

2. Package candidate Release B.

3. Validate candidate.

4. Finalize candidate.

5. Record:
   - Git commit
   - Package operation
   - Release version
   - Release fingerprint
```

---

## Phase 2 — Fresh Install Qualification

```
6. Transfer candidate B.

7. Verify destination fingerprint.

8. Platform scans B.

9. Platform imports B.

10. Prepare fresh installation.

11. Install B.

12. Verify B.

13. Record all operation/verification evidence.
```

---

## Phase 3 — Reset Validation Environment

The environment must be restored to the defined baseline.

The reset procedure itself must be documented and repeatable.

This may involve:

- application removal;
- database cleanup;
- Docker cleanup;
- Registry reset;
- VM snapshot restoration.

For V1, a **VM snapshot restore** may be the cleanest qualification reset mechanism if available.

This decision should be made explicitly during Period B.

---

## Phase 4 — Update Qualification

```
14. Import/install previous Release A.

15. Verify A.

16. Import candidate B.

17. Prepare update A → B.

18. Create mandatory backup.

19. Perform update.

20. Verify B.

21. Confirm B active.

22. Confirm A preserved in history.
```

---

## Phase 5 — Controlled Failure Qualification

Execute at least one intentionally failing test.

Examples:

- bad verification result;
- update failure;
- checksum corruption before import.

Confirm that:

- failure is recorded;
- target is not falsely activated;
- error code is correct;
- evidence is preserved.

---

## Phase 6 — Qualification Decision

Collect:

```
Packager result
Compliance Report
Release fingerprint
Transfer evidence
Import result
Fresh-install result
Fresh-install verification
Update result
Update verification
Backup evidence
Failure-path evidence
Relevant logs
```

Then record:

```
QUALIFICATION PASS
```

or:

```
QUALIFICATION FAIL
```

The exact Qualification Report schema may already be defined by the Release Engineering architecture; Period B should exercise it concretely.

# When an Integration Test Fails

This deserves an explicit debugging rule.

Do **not** immediately edit both products.

Use controlled isolation.

For example:

```
Packager Release fails Platform import
```

Run:

```
Packager Validator
```

Then compare against:

```
known Golden Release
```

Decision tree:

```
Generated Release fails independent Validator
        ↓
Packager problem

Generated Release passes Validator
but Platform rejects it
        ↓
Platform/Contract interpretation problem

Golden Release also fails Platform
        ↓
Platform regression
```

Likewise for installation:

```
Platform install fails
        ↓
Run same Release manually

Manual install succeeds
        ↓
Platform execution problem

Manual install fails
        ↓
Release/application packaging problem
```

This debugging discipline is one of the central reasons Period A existed.

---

# Contract Changes During Period B

Period B is probably where the first **real Contract deficiencies** may appear.

That's okay.

But use a strict rule:

> Integration failure does not automatically authorize a Contract change.

First classify the failure:

```
Implementation Bug
Contract Misinterpretation
Application-Specific Bug
Actual Contract Limitation
```

Only the fourth category may reopen Architecture V1.

If a Contract change is justified:

```
Evidence
    ↓
Architecture decision
    ↓
Contract version/change
    ↓
Packager update
    ↓
Platform update
    ↓
Independent regression tests
    ↓
Return to integration
```

This prevents integration from becoming uncontrolled architecture redesign.

---

# UI Role During Period B

The UI is useful, but it should not become the only integration test interface.

Every critical integration workflow must be provable through the Platform API.

For example:

```
API Qualification Test
→ authoritative automation-compatible evidence

UI Qualification Test
→ operator usability evidence
```

For B3–B6, I would run the important scenario both ways at least once:

- API/manual engineering flow;
- normal operator UI flow.

Both must reach the same Platform state.

---

# Why B6 matters so much

Period B's real output is not simply:

> "Packager and Platform connect."

It's actually:

> **A written, repeatable manual qualification procedure exists.**

That procedure becomes the specification for Period C.

So Period B produces something like:

```
Manual Qualification Procedure V1
```

Then Period C's job becomes almost boring:

```
Take this exact proven procedure
        ↓
replace human orchestration
        ↓
with Jenkins orchestration
```

That is exactly what we want.
