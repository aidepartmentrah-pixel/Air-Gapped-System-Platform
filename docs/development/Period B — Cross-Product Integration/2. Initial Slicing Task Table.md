## Why `B5` needed strengthening: one update hop can hide a bug the second one wouldn't

The proposal's own `B5` already uses real, independently-generated
Releases (not synthetic fixtures) and already tests real config/secret
preservation, backup, migration, and history — but only across a single
`A → B` transition. A single hop cannot catch failure modes that only
show up on the *second* transition: stale config drift accumulating
across updates, a second backup incorrectly overwriting or losing the
first, a migration that assumes it's always running against the
*original* schema rather than whatever the previous update already left
behind. Since the user identified update — specifically, updating
frontend + backend + database while keeping the data — as the genuinely
critical, unproven part of the Platform, testing it twice in the deep
single-app slice (not just once, and not deferring the second hop to the
fleet pass) is the right amount of rigor before declaring the mechanism
proven. `B5` now requires `A → B → C`: two real update hops, both
required to pass, before `B6`'s qualification procedure runs.

## Why `B7` exists: fleet confidence needs its own slice, not a footnote

`B0`–`B6` are deliberately scoped to **one** real app — correctly so; the
proposal's own governing principle ("introduce one new uncertainty at a
time") is exactly what made Period A's debugging tractable, and diluting
it here would lose the same clean signal. But proving the mechanism once
is not the same claim as "the Platform correctly installs and updates
real hospital software" — that requires the fleet. Packager solved the
identical tension with `P0`–`P8` (deep, one app) → `P9` (fleet, all 5
apps); `B7` is the direct Platform-side analogue. Recommended app for the
deep `B0`–`B6` pass: **HCopilot** — real SQL Server, real migrations via
`db-init`, the most-proven app across all of Period A, and the one app
among the five that actually exercises "keep the database data" in a way
Indicator (no database at all) structurally cannot. `B7` then repeats the
exact same proven 3-version install → update → update → data-check
procedure across the other four real apps (Indicator, STT-SCHEDULE,
Voice Project, HCAT), recording real pass/fail per app in a Testing
Record — this is what actually answers "for each app we try the install,
then update, and see if any data is lost," fleet-wide, not just once.

## The rule that keeps `B5`/`B7` from becoming a fake test: real divergent versions, not re-tagged identical code

The "3 versions" per app must be **real, meaningfully divergent points in
each app's own git history** — ideally spanning at least one real
database schema/migration change — not the same code re-packaged three
times under bumped version numbers. Re-tagging identical code as
`1.0.0`/`1.0.1`/`1.0.2` (which is what this session's own bug-fix
re-packaging runs did, for a different, legitimate reason — proving the
Packager's own export logic) would make an update test that *cannot*
fail, since nothing about the running application or its schema actually
changes between versions. That defeats the entire point of `B5`/`B7`.
Every one of the five real apps has substantial real commit history —
HCAT alone has well over a hundred real, dated completion-report
documents in its own repo attesting to genuine iterative development.
Picking the actual 3 commits per app (ideally: an early stable point, a
point with a real schema change, and current `HEAD` or close to it) is an
execution-time decision for whoever runs `B5`/`B7`, not something to pin
in this planning pass — but the rule itself belongs here, since it's easy
to get wrong by default (re-using an already-built Release is the path
of least resistance, and the wrong one).

## What this slice set deliberately does not cover during `B0`–`B7`

- **Genuinely air-gapped Platform+Packager integration, until `B8`.**
  `B0`–`B7` all run against Platform's real, current, *online*
  deployment on `or-stt` — correct for proving the Packager/Platform
  boundary itself (the proposal's own stated goal, "does the Platform
  correctly consume Packager output," doesn't require an air gap to
  answer), and a deliberate, practical choice: the offline VM is a
  shared lab resource that must be reverted between uses and has
  genuinely been disrupted mid-test before by other real, unrelated work
  landing on it (this happened during `PL9b` itself). Iterating on real
  failures — expected during `B3`–`B6` — is dramatically faster against
  an always-on, directly reachable machine than a resettable, shared,
  offline one. This mirrors exactly how Period A itself handled the same
  tradeoff: build and iterate mostly online/on-hardware, then run **one
  dedicated, final, genuinely air-gapped confirmation pass** at the end
  (the Packager's own Real Manual Acceptance Test; the Platform's own
  `PL9b`) — not throughout.
  Real evidence already exists for each product **alone**, genuinely
  offline (`PL9b` for Platform, using Golden Fixtures; the Real Manual
  Acceptance Test for the Packager, manually installed): what has never
  been proven is the two **together** — a real Packager-built Release,
  imported and installed by a genuinely air-gapped Platform, for the
  first time. `B8` is that missing pass, now a committed slice rather
  than an implicit footnote.
- **Jenkins itself.** Confirming no CLI is needed and that the REST API
  is the right integration point is Period B's job (settled above);
  actually building Jenkins pipelines is Period C's.
- **API authentication.** Explicitly out of scope for this testing stage,
