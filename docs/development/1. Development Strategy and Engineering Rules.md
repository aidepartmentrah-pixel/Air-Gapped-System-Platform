## 1. Independent Product Testability

The Packaging Engine and Offline Platform shall be developed so that each product can be tested independently before integration.

The correctness of one product shall not initially depend on trusting the correctness of the other.

Therefore:

```
Packager testing
→ known repository inputs
→ Release Contract
→ Validator
→ expected Release output
```

while:

```
Platform testing
→ known valid/invalid Release fixtures
→ Platform operation
→ expected operational result
```

Only after both products demonstrate reliable independent behavior shall Packager-generated Releases become the primary test input for the Platform.

This rule exists to preserve a clean failure signal.

If an integration test fails, we should already have evidence about whether:

- the Packager works independently;
- the Release is valid;
- the Platform works against known valid Releases.

---

## 2. Contract Before Integration

The Release Contract shall be the boundary between the two products.

The Packager shall be tested against the Contract.

The Platform shall be tested against the Contract.

Neither product shall initially be used as the authoritative validator of the other.

This means that machine-readable Contract artifacts and test fixtures must exist before meaningful cross-product integration begins.

Conceptually:

```
                Release Contract
                 /            \
                /              \
               ↓                ↓
          Packager          Platform
```

The Contract is the stable meeting point.

---

## 3. Vertical Slice Development

The products shall not be implemented by first creating every CLI command or HTTP endpoint as an empty placeholder and then filling the implementation afterward.

Instead, development shall proceed through **vertical slices**.

Each slice should implement one meaningful capability from interface to tested behavior:

```
Input
  ↓
Interface
  ↓
Engine behavior
  ↓
State / filesystem / Docker effect
  ↓
Result
  ↓
Error behavior
  ↓
Tests
```

A capability is not considered implemented merely because an endpoint exists.

The endpoint, engine behavior, result object, failure behavior, and tests must work together.

---

## 4. Smallest Testable Increment

Each development slice shall be small enough that its success or failure can be understood clearly.

Avoid combining several unknown mechanisms into one first implementation.

For example, do not make the first Platform feature simultaneously depend on:

```
Release scanning
+
Manifest parsing
+
PostgreSQL
+
Docker execution
+
installation
+
verification
+
frontend
```

unless all preceding dependencies have already earned sufficient confidence.

Every slice should introduce the smallest meaningful amount of new uncertainty.

---

## 5. Development Environment Separation

The products shall be developed in environments representative of where they will operate.

### Packaging Engine

Primary development environment:

```
Windows engineering workstation
```

because the Packager operates on application repositories maintained on the Windows engineering workstation and interacts with the local engineering Docker environment.

### Offline Platform

Primary development environment:

```
Online Debian development VM
```

because its runtime behavior depends on Debian, Docker, filesystem paths, permissions, lifecycle scripts, and host-level installation behavior.

### Offline Validation

The Offline Debian VM shall primarily be treated as a **validation environment**, not the main coding environment.

Therefore:

```
Online Debian
→ develop and debug

Offline Debian
→ validate and prove
```

This allows rapid iteration without weakening the requirement that the final behavior must succeed offline.

---

## 6. Representative-Environment Testing

A feature that succeeds only in a development environment is not yet considered complete if its intended execution environment is different.

Platform functionality involving:

- Docker;
- installation paths;
- permissions;
- lifecycle scripts;
- ports;
- application updates;
- backup;
- recovery;

must eventually be tested inside the Debian validation environment.

Likewise, Packager functionality depending on Windows-host repositories or Docker Desktop must be tested in the Windows engineering environment.

---

## 7. Golden Fixtures and Known Inputs

Testing shall use known inputs whose expected behavior is already defined.

For the Packager, examples may include:

```
valid simple repository
invalid repository
dirty Git repository
repository missing Compose configuration
```

For the Platform, examples may include:

```
valid Release 1.0.0
valid Release 1.1.0
invalid Manifest
invalid checksum
unsupported Contract
incomplete Release
```

These fixtures shall allow a developer to answer:

> Did the product fail because its implementation is wrong, or because the test input itself was unknown?

Fixtures should remain version-controlled and reusable.

---

## 8. Real Application Testing Comes After Controlled Fixtures

Real applications such as HCAT are essential acceptance tests, but they should not be the only development inputs.

The order should be:

```
Controlled fixture
        ↓
Known expected behavior
        ↓
Feature becomes stable
        ↓
Real application
```

This avoids having application-specific complexity hide bugs in the generic Packager or Platform.

---

## 9. One Git Repository, Multiple Working Environments

The use of Windows and Debian development machines shall not create independent source histories.

There shall remain one authoritative Git repository.

Conceptually:

```
                   Git Repository
                    /          \
                   /            \
                  ↓              ↓
            Windows clone    Debian clone
             Packager          Platform
```

The Windows environment may primarily modify Packager-related files.

The Debian environment may primarily modify Platform-related files.

Both shall synchronize through normal Git branches, commits, pushes, and pulls.

There are therefore **multiple working copies, not multiple authorities**.

---

## 10. Shared Contract Changes Require Coordination

Files that define the Packager/Platform boundary shall be treated differently from ordinary product-local code.

Examples:

```
release-manifest.schema.json
release-layout.yaml
validation-rules.json
compliance-report.schema.json
```

A Contract change shall be considered a cross-product change.

It shall require checking:

```
Packager compatibility
+
Validator compatibility
+
Platform compatibility
+
Contract tests
```

A Packager developer shall not casually change a shared Contract merely to make one local implementation easier.

---

## 11. Testing Is Part of the Slice

Testing shall not be postponed to a later project phase.

Every meaningful development slice shall define its tests as part of the slice itself.

A slice should normally contain:

```
Implementation
+
success-path test
+
expected-failure tests
+
state-safety test where relevant
```

For API or CLI operations, the test record should identify:

- operation being tested;
- input;
- expected result;
- expected state change;
- expected error behavior;
- environment tested;
- test status.

This will later support the larger development tracking tables you described.

---

## 12. Do Not Use Claude as the Correctness Oracle

Claude may assist with:

- implementation;
- code review;
- understanding repositories;
- generating test cases;
- debugging;
- explaining failures.

Claude shall not be the final authority on whether a feature works.

Correctness shall come from:

```
Schema validation
Automated tests
Contract tests
Integration tests
Real execution
Offline validation
```

Claude can help interpret the evidence.

It does not replace the evidence.

---

## 13. Integration Only After Minimum Independent Confidence

Packager ↔ Platform integration shall begin only after both sides reach a defined minimum confidence threshold.

This does not require either product to be completely finished.

It means only that the specific boundary being integrated is already independently proven.

For example:

```
Packager can generate a valid Release
+
Platform can import a known valid Release
=
Ready to test Packager → Platform import
```

Later:

```
Packager can generate installable Release
+
Platform can install Golden Release
=
Ready to test real Packager → Platform installation
```

Integration therefore proceeds progressively rather than waiting for two completely finished products.

---

## 14. Jenkins Comes After a Proven Manual Workflow

Jenkins shall not be used to discover how the system should work.

The required procedure shall first succeed manually.

The sequence is:

```
Manual capability works
        ↓
Manual cross-product workflow works
        ↓
Workflow becomes repeatable
        ↓
Jenkins automates it
```

Jenkins shall orchestrate established product interfaces.

It shall not contain business logic that compensates for missing Packager or Platform behavior.

---

## 15. Failure Signal Preservation

Development choices shall prioritize the ability to identify **which component failed**.

Avoid tests where several immature components can produce the same symptom.

The preferred progression is:

```
Unit signal
        ↓
Component signal
        ↓
Contract signal
        ↓
Integration signal
        ↓
End-to-end signal
```

A failing end-to-end test should be investigable using lower-level tests that already exist.

---

## 16. Evidence-Based Architecture Changes

After Architecture V1 Freeze, architectural changes should primarily arise from implementation evidence.

Examples:

- a Contract cannot represent a real application requirement;
- a Debian permission model makes the chosen execution approach impossible;
- the operation model cannot safely recover from interruption;
- the chosen Packager runtime cannot perform required Docker integration.

Minor implementation inconvenience alone should not reopen architecture.

The principle becomes:

```
Observed problem
        ↓
Evidence
        ↓
Architecture impact analysis
        ↓
Change if justified
```

rather than:

```
New idea
        ↓
Redesign everything
```

---

## 17. Definition of a Completed Development Slice

A development slice is complete only when:

```
Behavior implemented
+
defined input accepted
+
defined output produced
+
expected failures handled
+
state effects correct
+
tests passing
+
representative environment tested where required
+
documentation updated if behavior changed
```

A partially wired endpoint or UI button is not a completed slice.

---

# Final Development Principle

The development strategy shall optimize for **clear feedback, controlled uncertainty, and independent testability**.

The Packager and Platform shall grow separately against stable contracts and known fixtures, then integrate progressively once their individual behavior can be trusted.

The governing development model is:

```
Stable Contract
        ↓
Small Vertical Slice
        ↓
Independent Test
        ↓
Confidence
        ↓
Controlled Integration
        ↓
Manual End-to-End Proof
        ↓
Jenkins Automation
```
