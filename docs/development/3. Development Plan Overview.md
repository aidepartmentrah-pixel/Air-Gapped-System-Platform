## What the three periods actually mean

### Period A — Independent Product Development

Question:

> **Can each engine correctly perform its own job without trusting the other engine?**

Two parallel tracks:

```
PACKAGER                           PLATFORM

Repository                        Golden Release Fixture
    ↓                                   ↓
Packager                               Platform
    ↓                                   ↓
Release                           Install / Update / Verify
    ↓                                   ↓
Validator                         Known Expected Result
```

Period A finishes when each product earns enough independent confidence.

That means Part A needs the most serious slicing now.

---

### Period B — System Integration and Manual Qualification

This is what was still blurry.

Period B asks:

> **Now that Packager works and Platform works independently, does the actual output of one work correctly as the input of the other?**

This is where the two products finally meet.

Conceptually:

```
Real Application Repository
          ↓
     Real Packager
          ↓
   Generated Release
          ↓
       Transfer
          ↓
    Real Platform
          ↓
Install / Update / Verify
```

So Period B is **not another product**.

It is integration testing.

Its eventual slices will look something like:

```
B1 — Generated Release can be discovered

B2 — Generated Release can be imported

B3 — Generated Release can fresh-install

B4 — Generated Release can update previous Release

B5 — Verification evidence matches expectations

B6 — Full manual qualification procedure
```

But I would **not freeze those yet**. Part A implementation will teach us what the real integration boundaries are.

---

### Period C — Jenkins Automation

Period C asks:

> **Can Jenkins repeat the already-proven manual Period B procedure automatically?**

Jenkins should add almost no new engineering behavior.

It simply becomes the conductor:

```
Jenkins
   ↓
Call Packager
   ↓
Read Packaging Result
   ↓
Transfer Release
   ↓
Call Platform API
   ↓
Poll operation
   ↓
Collect verification
   ↓
PASS / FAIL pipeline
```

So Period C is primarily:

- orchestration;
- Jenkins agents;
- credentials/configuration;
- machine availability;
- transfer;
- retries;
- evidence collection;
- pipeline result reporting.

Again, we should write an initial vision for it, but detailed slicing should wait until Period B is manually proven.

# How we should slice the Packager

Before naming slices, make a **capability dependency map**.

For every Packager capability, ask:

|Question|Why|
|---|---|
|What does it receive?|Defines test input|
|What does it produce?|Defines observable success|
|What does it depend on?|Determines ordering|
|Does it modify state?|Determines safety tests|
|Does it require Docker?|Determines environment|
|Does it require Claude?|Determines external dependency|
|Can it be tested alone?|Determines fixture|
|What proves it works?|Determines acceptance test|
|What capability needs it later?|Determines dependency graph|

The capabilities we already know include roughly:

```
Project initialization
Project state reading
Git inspection
Docker/Compose inspection
Repository inspection
Engineering-question generation
Engineering-answer validation
Release planning
Docker image building
Artifact export
Release construction
Manifest generation
Contract validation
Compliance reporting
Fingerprint/checksum generation
Release finalization
Project Version State update
```

Then we draw dependencies.

For example:

```
Project Initialization
        ↓
Project State Reader
        ↓
Repository Inspection
   ┌────┴────┐
   ↓         ↓
Git       Docker/Compose
Inspection Inspection
   └────┬────┘
        ↓
Engineering Request
        ↓
Engineering Answers Validation
        ↓
Release Planning
        ↓
Artifact Build
        ↓
Release Construction
        ↓
Validation
        ↓
Finalization
```

**That graph should determine the slices.**

Not command names.
