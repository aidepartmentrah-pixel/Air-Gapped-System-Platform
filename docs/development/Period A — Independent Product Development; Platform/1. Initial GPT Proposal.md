# Period A — Independent Product Development: Platform

And I want to use exactly the same standard we used for the Packager: the slices should not merely follow endpoint names. They should follow **dependency boundaries, uncertainty boundaries, and clean testing signals**.

The independent Platform Period-A goal is:

> **Prove that the Platform can consume known-good Release fixtures and reliably discover, import, install, verify, update, recover, and represent them through its API/UI without depending on the Packager.**

The Packager is deliberately absent.

```
Known Golden Releases
        ↓
Offline Platform
        ↓
Scan / Import / Install / Update / Verify
        ↓
Known Expected Host + Registry State
        ↓
PASS
```

If this Period succeeds, then when we later feed it a real Packager-generated Release in Period B, we already know the Platform itself works.

---

# Period A — Independent Product Development: Platform

## Period Goal

Build and validate the RAH Offline Installation Platform independently from the Packaging Engine.

The Platform shall be considered independently trustworthy when it can take **known, manually controlled Release fixtures** and correctly:

- discover them;
- validate and import them;
- represent Applications and Releases;
- determine available actions;
- prepare deployment configuration;
- install a Release;
- verify the deployment;
- preserve operational state;
- update between two known compatible Releases;
- create the required backup;
- handle controlled failures;
- detect host drift;
- execute a supported recovery;
- expose the same behavior through its HTTP API and web UI.

The Packager shall not be required to prove any of these capabilities.

---

# Development Strategy

The Platform shall be developed primarily in the **Online Debian development VM**.

The Offline Debian VM shall be used as the representative acceptance environment.

```
Online Debian VM
→ Develop
→ Debug
→ Run fast automated/integration tests

        ↓ when slice is sufficiently stable

Offline Debian VM
→ Install actual Platform build
→ Run representative acceptance tests
→ Record evidence
```

The Platform shall be developed through vertical slices:

```
HTTP Input
    ↓
Request Model
    ↓
Platform Engine
    ↓
Registry / Filesystem / Docker Effect
    ↓
Result Model
    ↓
HTTP Response
    ↓
Tests
```

The UI shall consume those same HTTP operations rather than creating independent logic.

---

# The Key Test Dependency

Before discussing slices, we need one deliberate testing mechanism.

The Platform shall initially consume **Golden Release Fixtures**, not Packager-generated Releases.

For example:

```
tests/fixtures/releases/

├── hcat-1.0.0-valid/
├── hcat-1.1.0-valid/
│
├── invalid-manifest/
├── invalid-checksum/
├── unsupported-contract/
├── incomplete-transfer/
└── identity-conflict/
```

The two valid Releases must have behavior that we understand completely.

For example:

```
Golden HCAT 1.0.0
        ↓
Fresh Install supported

Golden HCAT 1.1.0
        ↓
Fresh Install supported
Update from 1.0.0 supported
Backup required
Verification required
```

This becomes the Platform's clean testing signal.

# Proposed Slice Map

I recommend **10 primary Platform slices**.

```
PL0 — Runtime, Database & Test Foundation
        ↓
PL1 — Generic Operation Framework
        ↓
PL2 — Release Discovery
        ↓
PL3 — Release Import & Registry
        ↓
PL4 — Application State & Action Intelligence
        ↓
PL5 — Deployment Planning & Configuration
        ↓
PL6 — Fresh Installation Execution
        ↓
PL7 — Verification & Host Reconciliation
        ↓
PL8 — Backup, Update & Recovery
        ↓
PL9 — Operator UI & Independent Offline Proof
```

There is a reason I put **Operation Framework before Scan/Import**, even though it feels abstract.

We just fixed the `operations` architecture precisely because almost every important future action relies on:

- `operation_id`;
- status;
- events;
- logs;
- locking;
- error correlation.

If we postpone that, every later slice will invent temporary execution tracking and we will have to rewrite it.

So PL0–PL1 establish the skeleton once.

Then the real vertical product behavior begins.

# Why I chose these boundaries

There are three very different kinds of Platform uncertainty.

### First: Platform infrastructure

```
Can the system itself run?
Can it remember operations?
```

That's:

```
PL0
PL1
```

### Second: Understanding Releases without touching the host

```
Can it find?
Can it trust?
Can it understand?
Can it plan?
```

That's:

```
PL2
PL3
PL4
PL5
```

### Third: Changing reality

```
Can it install?
Can it prove the installation?
Can it update and recover safely?
```

That's:

```
PL6
PL7
PL8
```

And only then:

```
Can a normal human operate the proven engine?
Can the whole thing survive the real offline environment?
```

That's:

```
PL9
```

That progression gives us increasingly expensive feedback only after cheaper feedback has earned confidence.

---

# A subtle but important dependency decision

I would **not** build the complete frontend alongside every backend endpoint at the beginning.

That would produce this:

```
Backend bug?
Frontend bug?
API mismatch?
State bug?
Docker bug?
```

all at the same time.

Instead:

```
Backend Engine
        ↓
API tests
        ↓
Proven behavior
        ↓
UI
```

You can absolutely create the shell/layout early because it is enjoyable and visually motivating.

But real buttons should only become functional when their underlying API slice has passed.

For example:

```
PL2 complete
→ Scan button becomes real

PL3 complete
→ Import button becomes real

PL6 complete
→ Install button becomes real

PL8 complete
→ Update button becomes real
```

This creates a beautiful alignment between development status and UI capability.

# What PL9 must NOT accidentally do

When the Platform finally works against Golden Releases, **do not immediately feed it Packager output and call that Platform Period A testing**.

That belongs to Period B.

The boundary should remain clean:

```
Period A Platform Final Proof

KNOWN GOLDEN RELEASE
        ↓
PLATFORM
        ↓
PASS
```

Then Period B starts with:

```
REAL PACKAGER
        ↓
UNKNOWN REAL OUTPUT
        ↓
REAL PLATFORM
```

That separation is what preserves the pure feedback signal you were concerned about from the beginning.

# Final Period A Platform Principle

The Platform shall earn trust in this order:

```
Can it exist?
        ↓
Can it remember work?
        ↓
Can it discover Releases?
        ↓
Can it trust Releases?
        ↓
Can it understand application state?
        ↓
Can it plan safely?
        ↓
Can it change the host?
        ↓
Can it prove the host is correct?
        ↓
Can it update and recover?
        ↓
Can a human operate it?
        ↓
Can all of this survive the real Offline VM?
```

That is the Platform slicing proposal I would now give Claude for architectural/development review.

The most useful question to ask Claude is the same stringent one we used for Packager:

> **Review these Platform slice boundaries specifically for dependency correctness, independent testability, feedback-signal purity, and implementation realism on Debian. Identify any slice that is too large, incorrectly ordered, circularly dependent, or impossible to test independently. Do not redesign the Platform or add new V1 capabilities.**

If Claude can attack this plan and we resolve the real weaknesses, then the two hardest Period-A plans will be in very strong shape before either machine starts accumulating implementation work.
