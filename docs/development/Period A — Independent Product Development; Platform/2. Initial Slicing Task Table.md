# Review — Platform Slicing Proposal (pre-PL0)

Performed before any Platform code was written, mirroring the review pass
the Packager plan received before its `P0` began. Framing used, taken
verbatim from the proposal's own closing section:

> "Review these Platform slice boundaries specifically for dependency
> correctness, independent testability, feedback-signal purity, and
> implementation realism on Debian. Identify any slice that is too large,
> incorrectly ordered, circularly dependent, or impossible to test
> independently. Do not redesign the Platform or add new V1 capabilities."

Cross-checked against the frozen architecture — specifically
`docs/architecture/4.7. Stage 4 — Offline Platform Specification.md`
(Platform Public Operations §2, Internal Workflows §3, Platform State
Rules §7, Error Contract §8, and the architecture's own recommended
`§11.19 Initial Implementation Slices`) and
`docs/architecture/4.5. Stage 4 — Packager and Platform Interface
Specification.md` — not against speculation, since the review's job was to
check the proposal against what was already decided, not to invent new
opinions.

## No circular dependencies found

Walking the Master Development Matrix's `Depends On` column end to end
(`PL0 → PL1 → PL2 → PL3 → PL4 → PL5 → PL6/PL7 → PL8 → PL9`) produces a
strict DAG. Nothing in a later slice's required behavior is needed by an
earlier one.

## No incorrectly-ordered slice found

The proposal's `PL0 → PL1` ordering (Operation Framework built before any
Release-facing capability) is a deliberate departure from the
architecture's own suggested order in `§11.19` (which places Scan/Import/
Queries — Slices 2–4 — before the Operation Framework, Slice 5). This is
not a defect: `§11.19` itself only requires that the `operations` table
*migration* exist before Release Import (Slice 3) needs it — not that the
full framework (polling, locking, stale-operation detection, event API)
be built first. The proposal's version builds the full framework before
any consumer exists, at the cost of one abstract-feeling slice, in
exchange for never having to retrofit ad hoc execution tracking into
`PL2`/`PL3` later. Given the Operation Attempt Rule (architecture §7.12)
requires an operation record before *any* irreversible action — including
import — this is a legitimate, better-justified alternative to the
architecture's own suggested sequencing, not an inconsistency with it.

## One slice too large: `PL8`

`PL8 — Backup, Update and Recovery` bundles three capability groups that
the architecture treats as distinct:

- the Packager/Platform Interface Specification's own capability-group
  table (`4.5`) lists **Update** and **Backup and recovery** as two
  separate rows;
- the architecture's own recommended implementation order (`4.7 §11.19`)
  implements them as two separate slices — **Slice 9 — Update** and
  **Slice 10 — Backup and Recovery**.

`PL8`'s own "Required Tests" section already shows the cost of the
bundling: ten distinct test scenarios spanning backup success/failure,
update success/failure, configuration preservation, migration failure,
post-update verification failure, restore, recovery, and cross-application
backup rejection, all reported under one slice status. That weakens
exactly the "clean testing signal" property the proposal sets as its own
bar for slicing (see "The Key Test Dependency" in the proposal). A
regression anywhere in that surface reports as "`PL8` broken" rather than
pointing at backup, update, or recovery specifically.

**Recommendation, applied in the Master Matrix above:** track and report
`PL8` as two sub-slices rather than splitting the underlying document:

- **`PL8a` — Backup + Update.** These two cannot be fully separated —
  the Backup Requirement Rule (architecture §7.22) makes a successful,
  verified backup a hard precondition of update — so they stay paired.
- **`PL8b` — Recovery.** Recovery only activates on a controlled failure
  path (a failed update, per §7.24 Recovery History Rule) and is testable
  independently via fault injection, without needing to re-run a full
  successful update cycle for every recovery test case.

The proposal's own narrative text, objective, and required tests for
`PL8` are unchanged — this is a testing/status-tracking split, not a
redesign.

## One slice recommended for the same treatment: `PL9`

`PL9 — Operator UI and Independent Offline Proof` bundles two disciplines
that are already named separately inside the slice itself — "Part A — UI
Integration" and "Part B — Offline VM Acceptance" — but reported under one
status. UI engineering and representative hardware acceptance testing are
different failure domains (a failed offline acceptance run says nothing
about whether the UI is broken, and vice versa). For the same reason as
`PL8`, this review recommends tracking `PL9` as `PL9a` (UI Integration)
and `PL9b` (Offline VM Acceptance) in status reporting, with the
document's Part A / Part B content unchanged.

## No slice found to be impossible to test independently

Every other slice's required tests can run using only what its declared
dependencies provide:

- `PL2` (Discovery) needs only a filesystem fixture tree — no database
  writes, no Docker.
- `PL3` (Import) is often assumed to need a completed `PL2` scan first,
  since that's the real product flow. It doesn't have to: the interface
  specification (`4.5 §4.3`) explicitly allows `import_release` to accept
  a validated `candidate_directory` directly, as "an initial simpler
  implementation," instead of requiring a `candidate_id` produced by a
  real scan. `PL3`'s own tests should use that path so they don't
  accidentally couple to `PL2`'s scan output — worth stating explicitly
  in `PL3`'s implementation notes so a future session doesn't assume the
  coupling is required.
- `PL1`'s "use a synthetic test operation" instruction is exactly the
  right way to avoid the circular "build install to test the operation
  framework, build the operation framework to track install" trap.

## One clarification needed: `PL4`'s test fixtures

`PL4`'s required tests ("Installed Application," "Compatible Target,"
"Release From Different Application") all presuppose Registry state — an
existing deployment, an active Release — that in the real product is only
ever produced by `PL6`/`PL8` (Install/Update), both of which come later.
The Master Matrix correctly lists `PL4`'s only dependency as `PL3`, which
only holds if `PL4`'s tests seed that Registry state directly (test
fixtures written straight into PostgreSQL) rather than through a real
install/update operation. The proposal doesn't say this explicitly.
**Recommendation:** state directly in `PL4`'s Development Tasks that
"installed"/"active deployment" test fixtures are created via direct
Registry seeding, not through a real Platform operation — otherwise a
future implementer could reasonably (and incorrectly) conclude `PL4`
needs to wait for `PL6`.

## Two affirmative findings (no action needed, worth recording)

1. **The Platform has no open error-namespace design gap analogous to the
   Packager's deferred `PKG-*` codes.** The Packager's operational
   error-code namespace was explicitly left undesigned going into `P0`
   (see `CURRENT.md`'s Future Design Tasks). The Platform's equivalent —
   the full `PLT-*` error catalog, categories, HTTP mapping rule, and
   retryable rule — is already written into the frozen architecture
   (`4.7 §8`, categories `8.4`–`8.23`). `PL0`/`PL1` can implement the
   Platform error object directly against that catalog; no separate
   decision document is needed first, unlike the Packager's P3 staleness
   gap.
2. **`PL0`'s "Docker Failure" readiness test reuses a pattern already
   proven in this repository.** The Packager's `P0` already established
   Docker-outside-of-Docker (bind-mounting the host's
   `/var/run/docker.sock`) as the way a containerized RAH component
   reaches the host Engine on Debian, and proved the failure path by
   omitting that mount. `PL0` should reuse this directly rather than
   re-deriving it — see `packager/Dockerfile` and Packager `P0`'s
   Testing Record.

## Review conclusion

The Platform slice boundaries are sound. No slice is circularly
dependent, incorrectly ordered in a way that creates a hidden blocking
dependency, or untestable on its own declared dependencies. `PL8` and
`PL9` are recommended for paired-sub-slice status tracking due to size;
`PL3` and `PL4` get one clarifying implementation note each. None of this
redesigns the Platform or adds V1 capability — it is a review of
boundaries and sequencing only, exactly as scoped. `PL0` may begin.

  respectively, matching both the proposal's own task split and the
  architecture's `§11.19` note that Foundation only needs the migration
  *mechanism*, not every table, to exist yet.

## PL1 — Done

Built `operations.py` (the Generic Operation Framework), `models.py`
(SQLAlchemy Core table definitions), and migration `0002` on top of
`PL0`'s foundation. Per the proposal's own instruction, no real deployment
operation exists yet — every test uses a synthetic `TEST_OPERATION`
`operation_type` against a randomly generated `application_id`, since
`applications` doesn't exist until `PL3`.

**Schema** (`operations`, `operation_events`, `operation_logs`):
`operations.application_id` intentionally has no foreign key yet — see
"Decisions Made" below. The per-application operation lock (§7.13) is
enforced by a **partial unique index** —
`UNIQUE (application_id) WHERE status IN ('PENDING', 'RUNNING')` — rather
than application-level locking logic. This makes lock acquisition and
release atomic and race-free for free: acquiring the lock is just "the
`INSERT` succeeded," releasing it is just "the status `UPDATE` moved the
row to a terminal state." A concurrent conflicting `INSERT` fails with a
real Postgres `IntegrityError`, caught and translated to the structured
`PLT-LOCK-001` (423).

**Built**: `create_operation` / `start_operation` / `update_stage` /
`succeed_operation` / `fail_operation` / `get_operation` /
`get_operation_events` / `get_operation_logs` / `mark_stale_operations`,
plus correlation-aware `log()` — every log line is persisted against its
`operation_id` (retrievable via `get_operation_logs`) *and* emitted
through standard Python logging with the `operation_id` bound, so it's
correlatable in container/stdout logs too. Three endpoints wired into
`app.py`: `GET /api/v1/operations/{operation_id}`, `.../events`,
`.../logs`. The per-`PlatformError`-class `http_status` attribute added
to `errors.py` (PL0's generic handler always returned `500`; PL1 needed
real per-code HTTP mapping per §8.25 — `404` for not-found, `409` for an
invalid state transition, `423` for a lock conflict).

**21 new tests added (42/42 total passing)** — `test_operations.py` (the
framework functions directly, against a real disposable PostgreSQL
container migrated to head) and `test_operations_api.py` (the same

11 required `PL1` tests covered, including two extra lock-boundary cases
beyond the minimum list (`test_lock_is_per_application`,
`test_stale_detection_frees_the_lock`) since the lock/staleness

None. `operations` needed no foreign key to `applications` since that

## Decisions Made

- **`operations.application_id` has no foreign key yet.** `applications`
  is `PL3`'s table. The column is a plain UUID for now; the constraint
  gets added in whichever `PL3` migration creates `applications`. Tests
  use freshly generated random UUIDs as stand-in application identities,
  which is exactly what "synthetic test operation" implies.
- **The lock is a database constraint, not application logic.** Considered
  a `SELECT ... FOR UPDATE` / check-then-insert pattern first; rejected
  it because it's vulnerable to a TOCTOU race under real concurrent
  requests. The partial unique index makes the database itself the
  single source of truth for "is this application locked," which is
  simpler and provably race-free.
- **No background worker for stale-operation detection.** The
  architecture's own recommended Slice 5 mentions a "Worker" component,
  but `PL1` has no real long-running work yet for anything to interrupt.
  `mark_stale_operations()` is exposed as a plain callable; wiring it
  into a periodic check is deferred to whichever slice first has a
  process that can actually crash mid-operation — `PL6` (Fresh
  Installation), realistically.
- **`operation_logs` is a separate table from `operation_events`.**
  Matches the architecture's own split between `GET .../events`
  (structured lifecycle timeline, §5.20) and `GET .../logs` (sanitized
  diagnostic log lines, §2.8) as two distinct endpoints/concepts, rather
  than overloading one table for both purposes.

Built `release_discovery.py`, the `release_candidates` table (migration
`0003`), and the first four real Golden Release fixtures under
`tests/fixtures/releases/` — `valid-release-1.0.0/`,
`incomplete-release.partial/`, `missing-manifest/`, `malformed-manifest/`

full Manifest schema/Compliance Report/checksum validation stays `PL3`'s

**Classification heuristic** (engineering judgment, not the full
`release-layout.yaml` structural validation, which is out of PL2's
scope): `release.yaml` present + parses + has `application.slug`/
`application.name`/`release.version` + `checksums/SHA256SUMS` present →
`READY_FOR_IMPORT`; manifest present and valid but `checksums/SHA256SUMS`
absent → `INCOMPLETE` (the Contract itself generates `SHA256SUMS` last
during finalization, so its absence is a reasonable "transfer isn't
finished" signal); `release.yaml` missing but other Contract-reserved
structure present → `INVALID_MANIFEST`; `release.yaml` missing with
nothing else recognizable present → `INCOMPLETE`; `release.yaml` present
but fails to parse or is missing required identity fields →
`INVALID_MANIFEST`. `ALREADY_IMPORTED`/`PREVIOUSLY_REJECTED`/
`IDENTITY_CONFLICT` are part of the full architecture-level enum but
aren't reachable from PL2 alone (no Release Registry exists until `PL3`)
— confirmed the plan's own required fixtures/tests don't exercise them
for exactly that reason.

**Built**: `scan_releases` / `list_candidates` / `get_candidate` in
`release_discovery.py`; `release_candidates` upserted by `directory_name`
so a repeat scan of the same physical directory updates the existing row

## Decisions Made

- **`contracts/1.0/*.json` are mounted read-only into the container
  (`RAH_CONTRACTS_PATH`), not embedded as Python copies.** The Packager's
  own precedent (`P6`) embeds a verbatim Python-dict copy of the
  manifest schema plus a dedicated drift test against the real file.
  Mounting the real file directly is strictly better here — zero drift
  risk by construction, no duplicate to keep in sync, and it costs
  nothing extra since the Platform already mounts Release Storage the
  same way. `Config.contracts_path` defaults to `/contracts/1.0` (the
  Compose mount path) with an env var override for tests.
- **Release fingerprint = `sha256` of `release.yaml`'s raw bytes.**
  Architecture §7.3 requires a fingerprint but never specifies an exact
  algorithm (a COMPLETED-style gap, like several others in this
  Contract). Cheap, deterministic, and sufficient for §7.3's actual
  purpose — detecting whether two candidates claiming the same
  application+version declare the same content. Defined once in
  `release_discovery.py` (`compute_fingerprint`) and reused by
  `release_import.py`, not duplicated.
- **`_find_or_create_application` is select-then-insert, not
  concurrency-hardened against a true race.** `applications.slug` is
  `UNIQUE` at the database level, so a genuine race would surface as a
  real `IntegrityError` rather than silently corrupting anything, but
  the code doesn't currently catch and retry that case. Matches §7.13's
  own allowance ("initial Platform may serialize... if that
  substantially simplifies Version 1") — not exercised by any required
  test, flagged rather than silently assumed away.
- **`_check_shared_services` has no real service inventory to check
  against**, so any manifest that declares a *required* shared service is
  honestly rejected (`PLT-COMPATIBILITY-004`) rather than silently
  accepted. None of the Golden Fixtures declare one. A real check is
  Period B/infrastructure-inventory territory, not Period A Platform.
- **`CandidateNotFoundError`'s `PLT-STORAGE-004` reuse (from `PL2`)
  turned out to double as the "unknown candidate_id passed to import"
  case too** — confirmed live (`404` on an unknown `candidate_id` at the
  import endpoint), no new code needed.

## Decisions Made

- **`application_query.py`'s lookup helpers made shared/public rather
  than duplicated.** The alternative — writing `deployment_planning.py`'s
  own copies of "look up an application/release row" — would have
  created two implementations of the same lookup that could silently
  drift (e.g. a future error-message change applied to only one copy).
  Renamed instead of duplicated, no behavior change, full suite green
  before and after.
- **`prepare_update` calls `application_query.get_available_actions()`
  directly for transition validity** rather than re-deriving
  accepted-source-version/unsupported-update logic. Same reasoning as
  above, applied at the function level instead of the helper level.
- **Port checks are real `socket.bind()` calls, not simulated.** Matches
  this project's established discipline (real Docker, real Postgres,
  real checksums throughout `PL0`-`PL4`) — a fake/mocked port-availability
  check would not actually prove §7.17's "provisional, not a
  reservation" property, which is the entire point of the required Port
  Race Revalidation test.
- **`deployment_configuration.value` stays `NULL` for every
  `secret=true` row**, with only a `secret_reference` stand-in stored —
  no real secret ever touches the database in plaintext, consistent with
  §7.16 and with how the Packager already treats real secrets in its own
  test suite (mocked/never-persisted-plaintext).
