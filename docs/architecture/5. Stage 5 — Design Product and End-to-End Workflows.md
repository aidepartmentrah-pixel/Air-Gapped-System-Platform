# Consolidation

## 1. Purpose and Scope

Stage 5 defines the ordered workflows through which engineers, operators, Jenkins, the Packaging Engine, and the Offline Platform cooperate.

It answers:

> **Who initiates the work, which product operation is called, in what order operations occur, what state changes, what evidence is produced, and what happens after success or failure?**

Stage 5 shall not redefine:

- Packager internal business logic;
- Platform internal business logic;
- CLI request and result objects;
- Platform HTTP endpoints;
- database schemas;
- Release Contract rules;
- UI layout and visual behavior.

Those matters are already defined in Stages 3, 4, and 4.5.

Stage 5 uses those established operations to define complete procedures.

---

## 2. Workflow Levels

The system shall use three workflow levels.

### 2.1 Product Workflow

A sequence performed primarily inside one product.

Examples:

```
Packager:
Initialize → Inspect → Prepare Answers → Package → Validate

Platform:
Scan → Import → Plan Installation → Install → Verify
```

Stage 5 shall describe only the externally meaningful sequence.

The detailed internal stages of each operation remain authoritative in the Packager and Platform specifications.

### 2.2 Cross-Product Workflow

A sequence in which the Packager output becomes Platform input.

Example:

```
Package Release
        ↓
Transfer Release
        ↓
Scan Release Storage
        ↓
Import Release
        ↓
Install or Update
        ↓
Verify
```

### 2.3 End-to-End Qualification Workflow

A complete engineering procedure coordinated manually or by Jenkins.

Example:

```
Source change
        ↓
Package candidate Release
        ↓
Validate Release
        ↓
Transfer exact artifact
        ↓
Fresh-install test
        ↓
Update-path test
        ↓
Verification
        ↓
Qualification decision
```

---

## 3. Actors and Execution Environments

The Stage 5 workflows shall distinguish these actors:

|Actor|Responsibility|
|---|---|
|Engineer|Completes application changes and provides engineering input|
|Claude Code|Assists with repository-specific engineering knowledge|
|Packaging Engine|Constructs and validates the Application Release|
|Transfer mechanism|Moves the immutable Release between environments|
|Platform Backend|Executes offline operational workflows|
|Platform Web UI|Allows a human operator to call Platform operations|
|Jenkins|Automates proven Packager and Platform workflows|
|Operator|Approves or performs production deployment and recovery|

The workflows shall distinguish these environments:

```
Online Engineering Workstation
- Application repository
- Claude Code
- Packaging Engine
- Docker Desktop
- Jenkins agent

Offline Validation VM
- Offline Platform
- PostgreSQL Operational Registry
- Docker Engine
- Candidate application deployments

Production Air-Gapped System
- Offline Platform
- Approved Releases transferred by physical media
```

The same Release artifact shall be used across qualification and production. It shall not be rebuilt after qualification.

## 5. End-to-End Release Qualification Workflow

The primary Stage 5 workflow shall qualify one new Application Release.

```
1. Engineer completes application changes.

2. Packaging Engine inspects the repository.

3. Claude-assisted engineering answers are prepared and validated.

4. Packaging Engine generates the candidate Release.

5. Packaging Engine validates and finalizes the Release.

6. The exact finalized Release is transferred to the Offline Validation VM.

7. Platform scans and imports the Release.

8. Platform performs a fresh-install test of the new Release.

9. Platform verifies the fresh installation.

10. Validation environment is returned to the required baseline.

11. The previous supported Release is installed.

12. Platform updates from the previous Release to the new Release.

13. Platform verifies the updated deployment.

14. Jenkins or the engineer collects:
    - Packaging Result;
    - Compliance Report;
    - transfer fingerprint;
    - Platform import result;
    - installation result;
    - update result;
    - verification evidence;
    - operation logs.

15. A Qualification Report records PASS or FAIL.
```

The Release artifact tested during fresh installation and update testing shall have the same fingerprint as the finalized Packaging Engine output.

Your original Stage 5 notes already describe this intended sequence: generate the Release, validate it, transfer it, perform clean installation, restore the baseline, install the previous version, update to the candidate, verify, and make the qualification decision.

## 6. Jenkins Workflow

Jenkins shall automate only workflows that have already succeeded manually.

The Jenkins qualification pipeline shall perform:

```
Check required machines and services
        ↓
Invoke Packaging Engine
        ↓
Read PackagingResult
        ↓
Stop if Packaging failed
        ↓
Transfer finalized Release
        ↓
Verify destination fingerprint
        ↓
Call Platform scan/import API
        ↓
Run fresh-install qualification
        ↓
Reset validation environment
        ↓
Run previous-version-to-target update qualification
        ↓
Collect verification evidence
        ↓
Generate final pipeline result
```

Jenkins shall:

- invoke the Packager through its CLI;
- invoke the Platform through its HTTP API;
- poll long-running Platform operations;
- preserve operation IDs;
- stop the pipeline after mandatory failure;
- avoid duplicating Packager or Platform business logic.

The UI and Jenkins remain two callers of the same Platform backend operations.

## 7. Workflow Failure Model

Every workflow shall define:

```
Trigger
Inputs
Ordered steps
State changes
Success condition
Failure condition
Stop point
Retry rule
Recovery requirement
Recorded evidence
```

The general failure policy shall be:

### Before irreversible execution

Failure stops the workflow without changing active operational state.

Examples:

- invalid Release;
- unsupported transition;
- missing engineering answers;
- unavailable port;
- failed mandatory backup.

### During deployment execution

Failure creates and preserves a failed operation record.

The Platform shall determine whether:

```
Host unchanged
Host partially changed
Recovery required
State unknown
```

### After script success but verification failure

The deployment shall be considered failed.

The target Release shall not become active.

### After host success but Registry commit failure

The Platform shall require reconciliation because actual host state and recorded state may disagree.

### Pipeline failure

Jenkins shall stop remaining dependent steps and preserve:

- Packaging operation ID;
- Release fingerprint;
- Platform operation IDs;
- error codes;
- logs;
- verification results.
