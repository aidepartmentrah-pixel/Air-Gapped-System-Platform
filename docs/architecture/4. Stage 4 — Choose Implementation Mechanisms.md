# Part 1 — Project Version State

## 1. Purpose

The **Project Version State** is the persistent release-version record stored inside each application source-code repository.

It allows the Packaging Software to determine:

* the identity of the application;
* the latest release created from the project;
* the complete history of releases created from the repository;
* the next permitted version;
* whether a release version has already been used;
* which source-code state produced each release.

The Project Version State belongs to the **online engineering lifecycle**.

It describes releases created from the source repository. It does not describe what is currently installed in the offline production environment.

---

## 2. Canonical Location

Every application repository participating in the RAH release process shall contain:

  text
<application-repository>/
│
├── .rah/
│   └── project-state.json
│
├── backend/
├── frontend/
├── docker-compose.yml
└── other project resources
  

The canonical relative path is:

  text
.rah/project-state.json
  

The `.rah/` directory contains RAH-specific release-engineering information associated with the project.

---

## 3. Technology

The Project Version State shall use:

  text
JSON
  

JSON is selected because the file must be:

* machine-readable;
* deterministic;
* easy to validate;
* easy to inspect;
* easy to update from the Packaging Software;
* suitable for source control;
* independent of a database server;
* supported by common programming languages.

The file shall be encoded as UTF-8.

---

## 4. Authoritative Responsibility

The Project Version State is authoritative for:

* application release identity within the source repository;
* the sequence of Application Releases created from that repository;
* the latest release created;
* historical release creation dates;
* the source-code revision associated with each release;
* release-version uniqueness within the project.

It is not authoritative for:

* what version is installed offline;
* installation dates;
* update dates;
* deployment results;
* application ports;
* production paths;
* production configuration;
* database migration results;
* offline verification results;
* current Docker container state.

Those facts belong to the Platform Operational Database.

---

## 5. Concrete JSON Structure

The first Project Version State schema shall use the following structure:

  json
{
  "schema_version": "1.0",
  "application": {
    "name": "HCAT",
    "slug": "hcat"
  },
  "versioning": {
    "strategy": "semantic",
    "current_release": "1.0.9",
    "next_version": "1.1.0"
  },
  "release_history": [
    {
      "version": "1.0.0",
      "created_at": "2026-04-10T09:30:00+03:00",
      "source": {
        "git_commit": "81f4b726cf64dcae58b26f2b8c385642578b7615",
        "git_tag": "v1.0.0"
      },
      "summary": "Initial standardized offline Application Release."
    },
    {
      "version": "1.0.9",
      "created_at": "2026-07-31T11:15:00+03:00",
      "source": {
        "git_commit": "7c2a85b6a35d9e78324bf107a6a9708752de910c",
        "git_tag": "v1.0.9"
      },
      "summary": "Improved pagination and patient filtering."
    }
  ]
}
  

---

## 6. Field Definitions

### 6.1 `schema_version`

  json
"schema_version": "1.0"
  

Identifies the version of the Project Version State format.

This is not the application version.

It allows future Packaging Software versions to detect whether they understand the structure of the file.

Required rules:

* Must be present.
* Must use a supported Project Version State schema version.
* Initial value: `1.0`.

---

### 6.2 `application`

  json
"application": {
  "name": "HCAT",
  "slug": "hcat"
}
  

Identifies the application to which the repository belongs.

#### `name`

Human-readable application name.

Examples:

  text
HCAT
Patient Complaints
Blood Bank
Operating Room
  

#### `slug`

Stable machine-readable application identity.

Examples:

  text
hcat
patient-complaints
blood-bank
operating-room
  

The slug shall:

* use lowercase letters;
* use numbers when required;
* use hyphens between words;
* not contain spaces;
* not contain underscores;
* not contain the release version;
* remain stable across application releases.

The same slug will later connect:

  text
Project Version State
        ↓
Release Manifest
        ↓
Platform Operational Database
        ↓
Canonical deployment path
  

For HCAT:

  text
hcat
  

shall map to:

  text
/opt/rah/apps/hcat/
  

---

### 6.3 `versioning`

  json
"versioning": {
  "strategy": "semantic",
  "current_release": "1.0.9",
  "next_version": "1.1.0"
}
  

Contains the repository's current release-version state.

#### `strategy`

Initial supported value:

  text
semantic
  

This means versions use:

  text
MAJOR.MINOR.PATCH
  

Example:

  text
1.4.2
  

The initial Packaging Software shall support semantic versions only.

#### `current_release`

The most recent Application Release successfully created and finalized from the repository.

It must match the newest valid entry in `release_history`.

Before the first release, it may be:

  json
"current_release": null
  

#### `next_version`

The version currently proposed for the next Application Release.

This value may be selected or changed before packaging begins.

It shall not already exist in `release_history`.

The Packaging Software must not treat `next_version` as a completed release until release creation succeeds.

---

## 7. Versioning Rules

The Packaging Software shall support three explicit version increments:

  text
PATCH
MINOR
MAJOR
  

Given:

  text
1.0.9
  

the available increments are:

  text
PATCH → 1.0.10
MINOR → 1.1.0
MAJOR → 2.0.0
  

The software shall not use the earlier decimal-counter interpretation in which a patch moving from `9` automatically becomes a new minor version.

Therefore:

  text
1.0.9 → 1.0.10
  

is valid semantic versioning.

It does not automatically become:

  text
1.1.0
  

The engineer chooses whether a release represents a patch, minor, or major change.

The Packaging Software calculates the resulting version deterministically.

---

## 8. `release_history`

  json
"release_history": []
  

Contains append-only records for releases successfully created from the repository.

Each entry represents one immutable Application Release identity.

A release-history entry contains:

  json
{
  "version": "1.0.9",
  "created_at": "2026-07-31T11:15:00+03:00",
  "source": {
    "git_commit": "7c2a85b6a35d9e78324bf107a6a9708752de910c",
    "git_tag": "v1.0.9"
  },
  "summary": "Improved pagination and patient filtering."
}
  

### `version`

The unique Application Release version.

Rules:

* Required.
* Must follow semantic versioning.
* Must not occur more than once in the history.
* Must match the release version later written into the Release Manifest.

### `created_at`

The date and time at which the Application Release was finalized by the Packaging Software.

It shall use ISO 8601 with a timezone offset.

Example:

  text
2026-07-31T11:15:00+03:00
  

This is the **release creation time**, not the production installation time.

### `source.git_commit`

The complete Git commit hash representing the source state used to create the release.

This supports traceability from:

  text
Application Release
        ↓
Project Version State
        ↓
Git source state
  

The Packaging Software shall retrieve this automatically where Git is available.

### `source.git_tag`

The Git tag corresponding to the release.

Recommended format:

  text
v<version>
  

Example:

  text
v1.0.9
  

The field may initially be `null` if tag creation occurs after packaging, but a finalized release should normally be traceable to an immutable Git tag.

### `summary`

A concise human-readable description of the main change delivered by the release.

This value may be provided by:

* the engineer;
* Claude based on the actual project changes;
* a combination of generated and reviewed text.

It must not be silently invented by deterministic tooling.

The same summary will later be copied into the Release Manifest.

---

## 9. State Before the First Release

A newly initialized project shall begin with:

  json
{
  "schema_version": "1.0",
  "application": {
    "name": "HCAT",
    "slug": "hcat"
  },
  "versioning": {
    "strategy": "semantic",
    "current_release": null,
    "next_version": "1.0.0"
  },
  "release_history": []
}
  

This means:

  text
The application is registered for RAH packaging.
No Application Release has yet been created.
The proposed first release is 1.0.0.
  

---

## 10. State-Transition Behavior

Release creation must behave transactionally from the perspective of the Project Version State.

### Before packaging

  json
"current_release": "1.0.9",
"next_version": "1.1.0"
  

### While packaging is running

The Project Version State remains unchanged.

The Packaging Software may create temporary working files elsewhere, but it shall not append a release-history entry yet.

### If packaging fails

The Project Version State remains:

  json
"current_release": "1.0.9",
"next_version": "1.1.0"
  

No successful release record is written.

### After successful finalization

The Packaging Software:

1. Appends the new release to `release_history`.
2. Changes `current_release` to `1.1.0`.
3. Calculates or requests the next proposed version.
4. Writes the updated file atomically.
5. Commits or prepares the state for Git commit.

Example resulting state:

  json
{
  "versioning": {
    "strategy": "semantic",
    "current_release": "1.1.0",
    "next_version": "1.1.1"
  }
}

## 11. Relationship with the Release Manifest

During release creation, selected Project Version State values are copied into the immutable Release Manifest.

The mapping is:

  text
Project Version State                       Release Manifest
────────────────────────────────────────────────────────────
application.name                     →      application.name
application.slug                     →      application.slug
versioning.next_version              →      release.version
new history created_at               →      release.created_at
new history summary                  →      release.summary
source.git_commit                     →      source.git_commit
source.git_tag                        →      source.git_tag
  

After successful release finalization:

  text
Project State current_release
  

and:

  text
Release Manifest release.version
  

must contain the same version.

The Project Version State remains mutable for future releases.

The Release Manifest becomes immutable with the finalized release.

## 13. Application-Level Validation Rules

The Packaging Software shall enforce all of the following:

1. `application.slug` must remain unchanged after the first release unless an explicit project migration is performed.
2. Every `release_history.version` must be unique.
3. `versioning.next_version` must not already exist in `release_history`.
4. If history is empty, `current_release` must be `null`.
5. If history is not empty, `current_release` must equal the most recently finalized history entry.
6. `git_tag`, when present, must correspond to the release version.
7. The Git commit must exist in the current repository.
8. The source repository should be clean before final release packaging, unless an explicitly approved policy permits otherwise.
9. A failed packaging attempt must not append a history entry.
10. Historical entries shall not be edited or deleted during normal operation.
11. Release dates shall represent release creation, not offline deployment.
12. The new history version must equal the generated Release Manifest version.

## 14. Write Safety

The Packaging Software shall update the Project Version State atomically.

Recommended behavior:

  text
1. Read project-state.json.
2. Validate it.
3. Create the new in-memory state.
4. Write project-state.json.tmp.
5. Validate the temporary file.
6. Replace project-state.json atomically.
  

The Packaging Software should create a temporary backup before replacement:

  text
project-state.json.bak
  

The backup is a recovery convenience and shall not become a second authoritative state.

Git remains the long-term history and recovery mechanism.

# Part 2 — Release Manifest

## 1. Purpose

The **Release Manifest** is the canonical machine-readable description of one immutable RAH Application Release.

It allows the Packaging Software, Release Validator, Offline Qualification procedure, and Offline Installation Platform to determine:

* which application the Release belongs to;
* the exact Release version;
* which source-code state produced it;
* when and how it was created;
* what changed in the Release;
* which Docker images and other artifacts it contains;
* which deployment entry points it provides;
* which configuration values it requires;
* which database and migration state it expects;
* which infrastructure capabilities it depends upon;
* which transition operations the Release supports;
* how the Release must be verified.

The Release Manifest travels with the Application Release from the Online Engineering Environment into the Offline Environment.

---

## 2. Canonical Location

Every RAH Application Release shall contain the manifest at its root:

    text
<Application>_Release_<version>/
│
├── release.yaml
├── docker-images/
├── scripts/
├── database/
├── configuration/
├── documentation/
├── verification/
└── checksums/
    

The canonical filename is:

    text
release.yaml
    

There shall be only one authoritative Release Manifest inside the Release Package.

---

## 3. Technology

The Release Manifest shall use:

    text
YAML
    

The manifest shall:

* be encoded as UTF-8;
* use a stable documented schema;
* avoid YAML features that make parsing ambiguous;
* avoid custom YAML tags;
* avoid executable content;
* be readable by humans;
* be readable deterministically by software;
* validate against the canonical Release Manifest JSON Schema.

Although the manifest is written in YAML, its data structure shall remain compatible with JSON data types:

* object;
* array;
* string;
* number;
* boolean;
* null.

---

## 4. Authority and Lifecycle

The Release Manifest is authoritative for the identity and intended behavior of the Release Package in which it exists.

It is authoritative for:

* application identity;
* Release identity;
* packaged artifacts;
* application-specific dependencies;
* lifecycle entry points;
* configurable deployment inputs;
* database migration information;
* supported transition declarations;
* verification entry point;
* release-specific documentation references;
* source traceability.

It is not authoritative for:

* what is currently installed in production;
* whether installation actually succeeded;
* the production port selected during deployment;
* generated production credentials;
* current container health;
* production database contents;
* actual installation or update dates;
* deployment history;
* the final offline qualification decision.

Those facts belong to qualification evidence or the Platform Operational Database.

---

## 5. Relationship with the Project Version State

The Packaging Software shall copy selected values from:

    text
.rah/project-state.json
    

into:

    text
release.yaml
    

The mapping is:

| Project Version State        | Release Manifest                     |
| ---------------------------- | ------------------------------------ |
| `application.name`           | `application.name`                   |
| `application.slug`           | `application.slug`                   |
| selected next version        | `release.version`                    |
| release creation time        | `release.created_at`                 |
| release summary              | `release.summary`                    |
| Git commit                   | `source.git_commit`                  |
| Git tag                      | `source.git_tag`                     |
| Project state schema version | not copied; remains project-specific |

The Release Manifest becomes immutable when the Release is finalized.

The Project Version State remains mutable for future release creation.

The application uses an approved shared database service but still manages its own database/schema lifecycle.

### `external_existing`

This allows verification to prove that the application code and database state are aligned.

# 29. Validation Rules

The Packaging Software and Release Validator shall enforce at least the following rules.

## Identity consistency

1. `application.name` must match Project Version State.
2. `application.slug` must match Project Version State.
3. `release.version` must match the selected project version.
4. `source.git_tag` must correspond to `release.version`.
5. `deployment.canonical_path` must correspond to the application slug.
6. `deployment.compose_project_name` must be stable and version-independent.

## File consistency

7. Every declared entry point must exist.
8. Every declared Docker archive must exist.
9. Every declared documentation file must exist.
10. Every declared model artifact must exist unless provided by an approved shared service.
11. Every relative path must remain inside the Release root.
12. No path traversal such as `../` shall be allowed.
13. The checksum file must exist.
14. Manifest contents must match actual packaged files.

## Operation consistency

15. If fresh installation is supported, an install entry point is required.
16. If update is supported, an update entry point is required.
17. If database backup is required, the backup entry point must exist.
18. If downgrade is false, the Platform must not treat an older supplied version as automatically deployable.
19. Update compatibility declarations must not be empty when update is supported unless an explicit “any previous version” policy is declared.

## Offline consistency

20. Required Docker images must be available offline.
21. Required runtime assets must be included or supplied by approved RAH infrastructure.
22. Public Internet requirements must be false.
23. Public registry requirements must be false.
24. Required models must be packaged or supplied by an approved offline shared service.

## Security consistency

25. Secret configuration inputs must not contain real secret values in the manifest.
26. Password defaults must normally be null.
27. Private keys and production credentials shall not be embedded into the manifest.
28. Generated secrets belong to persistent operational state after deployment.

## Chapter 1 — Foundation

### 1.1 Purpose

The **RAH Application Release Contract** is the canonical engineering specification that defines what constitutes a valid RAH Application Release.

It establishes a common language shared by all components participating in the RAH release lifecycle.

The contract allows independently developed software to be packaged, validated, transferred, installed, updated, and verified through deterministic procedures rather than application-specific assumptions.

Every compliant Application Release shall satisfy the requirements defined by this contract.

 

### 1.2 Scope

This contract governs the engineering representation of an RAH Application Release.

It defines:

- the required directory structure of every Release;
    
- mandatory and optional Release artifacts;
    
- Release Manifest requirements;
    
- artifact organization;
    
- lifecycle script requirements;
    
- validation rules;
    
- Release compliance requirements;
    
- responsibilities of the Packaging Software;
    
- responsibilities of the Release Validator;
    
- assumptions the Offline Platform may safely make about every compliant Release.
    

This contract does **not** define:

- application source-code architecture;
    
- software design;
    
- frontend implementation;
    
- backend implementation;
    
- Docker image contents;
    
- business logic;
    
- deployment history;
    
- production operational state.
    

Those concerns belong to other components of the RAH ecosystem.

 

### 1.3 Authority

The RAH Application Release Contract is the authoritative specification describing what a valid Application Release is.

Every engineering component participating in the release lifecycle shall implement this contract rather than independently defining Release behavior.

The following components are governed by this specification:

- RAH Packaging Software
    
- Release Generator
    
- Release Validator
    
- Offline Qualification Procedure
    
- Offline Installation Platform
    

If any implementation conflicts with this specification, the specification takes precedence.

 

### 1.4 Fundamental Principle

The Release Contract defines the language of every Application Release.

The Release Manifest is one document written using that language.

Therefore:

- the Release Contract defines the rules;
    
- the Release Manifest follows those rules;
    
- the Packaging Software creates Releases according to those rules;
    
- the Release Validator verifies those rules;
    
- the Offline Platform consumes Releases assuming those rules have been satisfied.

#### Release Validator

The engineering component responsible for verifying that an Application Release satisfies every applicable rule defined by this contract.

It shall not modify the Release.

 

#### Offline Platform

### 1.7 Engineering Philosophy

No compliant Release shall require:

### 1.8 Compliance Levels

Engineering opinion shall not override failed validation.

# Chapter 2 — Release Directory Contract

## 2.1 Purpose

Every compliant Application Release shall use one deterministic directory structure.

- generated automatically;

  text

├── compose/

├── docker-images/

├── database/

├── documentation/
│
├── verification/
│
├── checksums/
│   └── SHA256SUMS
│
└── compliance/

|Path|Required|

  text

  text

- remain inside the Release root;

- never reference external locations;
    
- never contain path traversal (   ../   );
    
- use UTF-8 filenames.
    

Absolute filesystem paths are prohibited except where explicitly declared as deployment targets inside the Release Manifest.

 

## 2.7 Additional Files

Applications may include additional files and directories provided they do not conflict with reserved Release Contract paths.

Reserved names defined by this specification shall not be repurposed.

 

## 2.8 Structural Validation Rules

- root directory naming;
    
- mandatory directories;
    
- mandatory files;
    
- duplicate Release Manifests;
    
- duplicate lifecycle scripts;
    
- missing checksum resources;
    
- invalid relative paths;
    
- forbidden absolute paths;
    
- prohibited directory traversal;
    
- unknown reserved names.
    

Failure of any mandatory structural rule results in:

NON-COMPLIANT

- create mandatory directories;
    
- populate required artifacts;

## 2.10 Validator Obligations

- verify directory structure before artifact validation;
    
- stop validation if mandatory structural requirements fail;
    
- produce deterministic validation results;
    
- never modify the Release while validating it.
    

 

## 2.11 Platform Assumptions

Because every compliant Release follows the same directory contract, the Offline Platform may safely assume:

- lifecycle scripts are located in deterministic locations;
    
- Docker artifacts exist in deterministic locations;
    
- checksum resources exist in deterministic locations;
    
- documentation exists in deterministic locations;
    
- compliance information exists in deterministic locations.
    

The Platform shall not search the Release for alternative file locations.

 

## 2.12 Final Directory Principle

The Release Directory Contract transforms every Application Release into a deterministic engineering artifact.

Regardless of the application being packaged, every compliant Release presents the same external engineering structure, allowing the Packaging Software, Release Validator, Offline Qualification procedure, and Offline Platform to operate without application-specific knowledge.

# Chapter 9 — Validator Obligations

## 9.1 Purpose

This chapter defines the contractual responsibilities of the **RAH Release Validator**.

The Validator is responsible for determining whether an Application Release satisfies the applicable version of the RAH Application Release Contract.

Its responsibility is limited to deterministic contract validation.

The Validator does not construct, repair, qualify, install, update, or operate Application Releases.

---

## 9.2 Fundamental Responsibility

The Validator SHALL answer one question:

> **Does this Application Release satisfy every applicable mandatory requirement of the declared RAH Application Release Contract version?**

The result SHALL be one of:

       text
COMPLIANT
       

or:

       text
NON-COMPLIANT
       

The Validator SHALL NOT produce an ambiguous or partially successful overall compliance state.

---

## 9.3 Validator Inputs

The Validator SHALL receive:

1. The Application Release root directory.
    
2. The declared Release Contract version.
    
3. The applicable Release Contract schemas and validation rules.
    
4. The finalized Release contents, excluding the final Compliance Report that the Validator itself generates.
    
5. Optional validation context explicitly permitted by the Contract.
    

The Validator SHALL NOT depend on:

- application source code outside the Release;
    
- previous Claude conversations;
    
- undocumented developer knowledge;
    
- Internet access;
    
- files located on the original engineering workstation;
    
- previous Release folders;
    
- a running production deployment.
    

---

## 9.4 Contract Version Resolution

The Validator SHALL determine the applicable Contract version from:

       yaml
compatibility:
  release_contract_version: "1.0"
       

The Validator SHALL verify that:

- the declared Contract version exists;
    
- the Validator supports that Contract version;
    
- the Release Manifest schema is compatible with it;
    
- all rules belonging to that Contract version are available.
    

If the Contract version is unsupported or unavailable, validation SHALL fail.

Example result:

       text
RC-CON-001 — FAIL

Release Contract version 2.0 is not supported by Validator 1.3.0.
       

The Validator SHALL NOT silently apply a different Contract version.

---

## 9.5 Validation Order

The Validator SHALL evaluate the Release in a deterministic order.

The initial validation sequence SHALL be:

       text
1. Contract availability
2. Release-root accessibility
3. Directory structure
4. Release Manifest parsing
5. Manifest schema validation
6. Cross-field identity validation
7. Declared-path validation
8. Artifact validation
9. Script validation
10. Configuration validation
11. Database validation
12. Offline-dependency validation
13. Security validation
14. Integrity preparation
15. Compliance decision
16. Compliance Report generation
       

A Validator implementation MAY internally optimize execution, but the resulting rule outcomes SHALL be equivalent.

---

## 9.6 Fatal and Non-Fatal Validation Failures

A **fatal validation failure** prevents meaningful continuation.

Examples include:

- Release root cannot be accessed;
    
-         release.yaml         does not exist;
    
- YAML cannot be parsed;
    
- declared Contract version cannot be resolved.
    

When a fatal failure occurs, the Validator MAY stop further checks that depend on the failed component.

The Compliance Report SHALL explicitly identify:

- the fatal rule;
    
- the checks not executed;
    
- why they could not be executed.
    

A non-fatal validation failure SHALL NOT automatically stop unrelated checks.

Where practical, the Validator SHOULD continue and report every discoverable violation in one validation run.

---

## 9.7 Deterministic Rule Evaluation

Every validation rule SHALL have:

- a stable identifier;
    
- a category;
    
- a clear requirement;
    
- a deterministic evaluation procedure;
    
- an explicit result;
    
- an understandable result message.
    

The same Release, Contract version, Validator version, and validation context SHALL produce the same compliance result.

Validation SHALL NOT depend on:

- subjective engineering opinion;
    
- random decisions;
    
- undocumented heuristics;
    
- LLM interpretation;
    
- interactive human judgment.
    

An LLM MAY assist in producing Release inputs before validation, but SHALL NOT decide whether a mandatory Contract rule passed.

---

## 9.8 Rule Outcomes

Each executed mandatory rule SHALL produce:

       text
PASS
       

or:

       text
FAIL
       

A conditional rule whose triggering condition does not apply MAY produce:

       text
NOT_APPLICABLE
       

For example:

       text
RC-DB-004 — NOT_APPLICABLE

The Release does not require a database.
       

        NOT_APPLICABLE         SHALL NOT be used to hide missing mandatory information.

The Validator SHALL record why the rule was not applicable.

A rule that should have been evaluated but could not be evaluated because of an earlier failure SHALL produce:

       text
NOT_EXECUTED
       

Example:

       text
RC-ART-006 — NOT_EXECUTED

Docker artifact declarations could not be evaluated because release.yaml failed parsing.
       

The overall compliance result remains binary:

       text
COMPLIANT
NON-COMPLIANT
       

---

## 9.9 Validation Categories

The Validator SHALL support the categories defined by the Contract.

The initial categories are:

|Prefix|Category|
|---|---|
|        RC-CON        |Contract and schema resolution|
|        RC-DIR        |Directory structure|
|        RC-MAN        |Release Manifest|
|        RC-ART        |Packaged artifacts|
|        RC-SCR        |Lifecycle scripts|
|        RC-CFG        |Configuration|
|        RC-DB        |Database lifecycle|
|        RC-OFF        |Offline dependencies|
|        RC-SEC        |Security|
|        RC-INT        |Integrity and checksums|

Future Contract versions MAY introduce additional categories.

Existing rule identifiers SHALL NOT be reused for unrelated meanings.

---

## 9.10 Directory Validation Obligations

The Validator SHALL verify:

- Release root naming;
    
- required root files;
    
- required directories;
    
- conditional directories;
    
- prohibited duplicate authoritative files;
    
- reserved directory use;
    
- relative-path safety;
    
- case-sensitive path consistency where applicable.
    

The Validator SHALL NOT create missing directories.

The Validator SHALL NOT relocate misplaced artifacts.

---

## 9.11 Manifest Validation Obligations

The Validator SHALL:

1. Locate exactly one canonical         release.yaml        .
    
2. Parse it using a safe YAML parser.
    
3. Reject unsupported YAML tags or executable constructs.
    
4. Validate it against the applicable JSON Schema.
    
5. Evaluate semantic and cross-field rules.
    
6. Verify identity consistency.
    
7. Verify declared paths.
    
8. Verify conditional sections.
    

The Validator SHALL NOT:

- insert missing fields;
    
- replace invalid values;
    
- reinterpret malformed data;
    
- infer values from filenames when the Manifest is invalid.
    

---

## 9.12 Artifact Validation Obligations

For every declared artifact, the Validator SHALL verify:

- the artifact exists;
    
- its path matches the Manifest;
    
- its location satisfies the Directory Contract;
    
- its category is valid;
    
- required metadata is present;
    
- it is included in integrity coverage where required.
    

For Docker image archives, validation SHOULD also verify, where practical:

- the archive can be inspected;
    
- the declared image name exists in the archive;
    
- the declared tag matches;
    
- the archive is not empty or obviously malformed.
    

The Validator is not required to run the Docker image during Contract validation.

Operational image behavior belongs to Offline Qualification.

---

## 9.13 Script Validation Obligations

The Validator SHALL verify that every declared lifecycle script:

- exists;
    
- is located within the Release;
    
- resides in an allowed directory;
    
- uses an allowed filename or declared path;
    
- has suitable executable permissions for the target environment;
    
- is covered by integrity validation;
    
- corresponds to a supported operation declared in the Manifest.
    

The Validator SHOULD perform static checks where practical, including:

       bash
bash -n script
       

or an equivalent syntax check appropriate to the declared script interpreter.

Static validation SHALL NOT be treated as proof that the script works operationally.

The Validator SHALL NOT perform fresh installation, update, recovery, or production migration operations.

---

## 9.14 Configuration Validation Obligations

The Validator SHALL verify:

- the declared configuration template exists;
    
- every Platform-facing input is declared;
    
- required input fields have valid types;
    
- generated values do not include pre-generated production secrets;
    
- operator inputs are distinguishable from generated and fixed values;
    
- port inputs are declared using the appropriate type;
    
- defaults satisfy their declared types.
    

The Validator SHOULD detect obvious secret exposure patterns.

However, automated secret detection is supplementary and SHALL NOT replace explicit Contract rules.

---

## 9.15 Database Validation Obligations

When:

       yaml
database:
  required: true
       

the Validator SHALL verify:

- database platform is declared;
    
- deployment mode is declared;
    
- initialization resources exist where required;
    
- migration resources exist where required;
    
- target schema or migration state is declared;
    
- backup resources exist when backup is mandatory;
    
- recovery resources exist when recovery is declared;
    
- all referenced entry points exist.
    

The Validator SHALL NOT execute production migrations during Contract validation.

The Validator MAY run safe static or isolated checks when explicitly supported by the validation architecture.

---

## 9.16 Offline Dependency Validation Obligations

The Validator SHALL verify that the Release does not declare required public runtime dependencies.

It SHALL verify applicable declarations for:

- public Internet access;
    
- public Docker registries;
    
- public package repositories;
    
- public CDNs;
    
- online model registries;
    
- externally downloaded frontend assets.
    

Every required deployment or runtime dependency SHALL be:

1. included in the Application Release;
    
2. supplied by an approved RAH-OIP capability;
    
3. supplied through an explicitly declared approved shared service.
    

An undeclared required external dependency SHALL result in non-compliance.

---

## 9.17 Security Validation Obligations

The Validator SHALL check for violations including:

- production passwords inside the Release Manifest;
    
- real credentials inside configuration templates;
    
- embedded private keys without an approved reason;
    
- unsafe path traversal;
    
- lifecycle entry points outside the Release root;
    
- executable content in data-only fields;
    
- unsupported or dangerous manifest constructs.
    

The Validator SHALL avoid printing complete secret values in validation output.

Where a suspected secret is reported, the report SHOULD identify the file and field without reproducing the secret itself.

---

## 9.18 Integrity Validation and Report-Bootstrapping Rule

The Compliance Report creates a circularity problem:

       text
The report is generated after validation,
but finalized Release checksums must include the report.
       

The Validator and Generator SHALL resolve this using the following two-stage finalization procedure:

       text
Stage A — Pre-final validation
1. Validate all Release contents except:
   - final SHA256SUMS;
   - final Compliance Report.
2. Produce the provisional validation result.

Stage B — Final integrity closure
3. Generate the Compliance Report.
4. Generate final SHA256SUMS covering:
   - release.yaml;
   - packaged artifacts;
   - lifecycle scripts;
   - documentation;
   - verification resources;
   - Compliance Report.
5. Verify the final checksum file.
6. Perform a final closure check.
7. Freeze the Release.
       

The checksum file SHALL NOT list itself.

The final closure check SHALL confirm that no Release-critical artifact changed after checksum generation.

This rule supersedes any earlier simplified description in which checksums were generated before the Compliance Report without a closure step.

---

## 9.19 Non-Modification Rule

The Validator SHALL operate as a read-only evaluator, except for writing its own output into the designated compliance work area during the controlled finalization process.

It SHALL NOT modify:

-         release.yaml        ;
    
- Docker archives;
    
- scripts;
    
- configuration templates;
    
- database resources;
    
- documentation;
    
- verification resources.
    

If validation detects a defect, the Release SHALL return to generation or engineering.

The Validator SHALL NOT fix the defect.

---

## 9.20 Compliance Decision

The Validator SHALL classify a Release as:

       text
COMPLIANT
       

only when:

- every applicable mandatory rule passes;
    
- no mandatory rule fails;
    
- no required rule remains         NOT_EXECUTED        ;
    
- final integrity closure succeeds;
    
- the Compliance Report is generated successfully.
    

The Release SHALL be classified as:

       text
NON-COMPLIANT
       

when any mandatory requirement fails.

A warning SHALL NOT change compliance unless the Contract identifies that warning condition as mandatory failure.

---

## 9.21 Compliance Report Obligations

The Validator SHALL generate the Compliance Report defined in Chapter 7.

The report SHALL include:

- Release identity;
    
- Contract version;
    
- Generator version where available;
    
- Validator version;
    
- validation time;
    
- validation environment;
    
- overall result;
    
- every applicable rule result;
    
- failure messages;
    
- not-applicable explanations;
    
- not-executed explanations;
    
- summary counts.
    

A failed validation MAY generate its report outside the candidate Release work directory because the Release is not finalized.

Only a successful final Compliance Report becomes part of the immutable Release Package.

---

## 9.22 Validator Independence

The Generator and Validator MAY be distributed within the same Packaging Software repository or executable.

However, their logical responsibilities SHALL remain separate.

The Validator SHALL evaluate the generated artifact from disk rather than trusting the Generator's in-memory assumptions.

The Validator SHALL not treat successful generation as evidence of compliance.

The architecture SHOULD permit validation of a Release created by:

- another version of the Generator;
    
- another compatible implementation;
    
- an external developer;
    
- a manually prepared engineering process.
    

The Contract, not the Generator implementation, defines validity.

---

## 9.23 Validator Versioning

The Validator SHALL have its own identifiable version.

The Validator version SHALL be recorded in every Compliance Report.

A Validator update SHALL NOT silently change the meaning of existing Contract rules.

When validation behavior changes materially, one of the following SHALL occur:

- the Validator defect is documented and corrected while preserving Contract meaning;
    
- the Release Contract version is updated;
    
- a compatibility note explains the changed interpretation.
    

---

## 9.24 Failure Reporting

Failure messages SHALL be actionable.

A failure SHALL identify:

- rule identifier;
    
- affected path or field;
    
- expected condition;
    
- observed condition;
    
- concise correction direction.
    

Example:

       text
RC-SCR-004 — FAIL

Path:
scripts/update_offline.sh

Expected:
An executable update entry point because deployment.supported_operations.update is true.

Observed:
The declared file does not exist.
       

Failure messages SHALL NOT require the engineer to reverse-engineer the Validator source code.

---

## 9.25 Final Validator Principle

The Validator is the independent deterministic enforcement mechanism of the RAH Application Release Contract.

It proves Contract compliance by inspecting the generated Release as an external artifact.

It SHALL report defects precisely, SHALL NOT repair them, and SHALL NOT confuse structural compliance with offline operational qualification.

# Chapter 10 — Platform Obligations

## 10.1 Purpose

This chapter defines the contractual responsibilities of the **RAH Offline Installation Platform** when discovering, importing, presenting, installing, updating, verifying, and recording Application Releases.

The Platform consumes compliant Application Releases.

It does not define the Release Contract, create Application Releases, or perform engineering-side compliance validation.

---

## 10.2 Fundamental Responsibility

The Platform SHALL transform:

       text
Compliant Application Release
+
Existing Offline Operational State
       

into:

       text
Controlled Deployment Operation
+
Verified Resulting State
+
Persistent Operational Record
       

The Platform SHALL act as the orchestration and operational-visibility layer for RAH Application Releases.

---

## 10.3 Responsibility Boundary

The Platform is responsible for:

- discovering supplied Application Releases;
    
- reading Release Manifests;
    
- checking local compatibility;
    
- registering available Release metadata;
    
- presenting valid deployment actions;
    
- collecting permitted operator inputs;
    
- generating permitted values;
    
- invoking declared lifecycle operations;
    
- monitoring execution;
    
- invoking deployment verification;
    
- recording operational outcomes;
    
- presenting application and deployment history.
    

The Platform is not responsible for:

- modifying application source code;
    
- creating Release Packages;
    
- generating Release Manifests;
    
- repairing non-compliant Releases;
    
- moving Git tags;
    
- rebuilding Docker images;
    
- inventing missing deployment behavior;
    
- silently rewriting Release scripts.
    

---

## 10.4 Platform Inputs

The Platform SHALL consume:

1. A supplied Application Release.
    
2. Its         release.yaml        .
    
3. Its Compliance Report.
    
4. Its checksum information.
    
5. The current Platform Operational Database.
    
6. The current host and approved infrastructure state.
    
7. Operator inputs explicitly declared by the Release Manifest.
    

The Platform SHALL NOT require application source code.

---

## 10.5 Release Discovery

The Platform SHALL discover candidate Application Releases only within configured Release Storage locations.

An initial canonical Release Storage root MAY be:

       text
/opt/rah/releases/
       

The exact storage path SHALL be established by the infrastructure and Platform standards.

The Platform SHALL NOT treat arbitrary directories across the host as candidate Releases.

A discovered directory SHALL not become an available Application Release until import validation succeeds.

---

## 10.6 Import Validation

Before registering a candidate Release, the Platform SHALL:

1. Locate         release.yaml        .
    
2. Parse the Manifest safely.
    
3. verify that the Manifest schema version is supported;
    
4. verify that the declared Release Contract version is supported;
    
5. locate the Compliance Report;
    
6. verify that its overall result is         PASS        ;
    
7. verify final Release checksums;
    
8. confirm application and Release identity;
    
9. confirm target architecture compatibility;
    
10. confirm minimum RAH-OIP compatibility;
    
11. confirm required shared services are known or available.
    

Import validation is not full engineering-side Contract validation.

The Platform relies on the Compliance Report but independently verifies integrity and local compatibility.

If any mandatory import check fails, the Platform SHALL reject the Release.

---

## 10.7 Imported Release States

The Platform SHALL distinguish at least the following Release states:

       text
DISCOVERED
IMPORT_REJECTED
AVAILABLE
DEPLOYING
DEPLOYED
DEPLOYMENT_FAILED
SUPERSEDED
REMOVED_FROM_STORAGE
       

Definitions:

###         DISCOVERED        

A candidate Release directory has been found but not fully imported.

###         IMPORT_REJECTED        

The Release failed integrity, compatibility, compliance-evidence, or parsing checks.

###         AVAILABLE        

The Release is validly imported and may be considered for a supported operation.

###         DEPLOYING        

An installation, update, downgrade, reinstall, or recovery operation is currently executing.

###         DEPLOYED        

The Release is the currently verified active Release for the application.

###         DEPLOYMENT_FAILED        

The attempted operation failed or mandatory verification did not pass.

###         SUPERSEDED        

The Release was previously deployed but is no longer active.

###         REMOVED_FROM_STORAGE        

The Release metadata remains historically known, but its candidate Release Package is no longer present in Release Storage.

The exact database implementation will be defined by the Platform Operational Database schema.

---

## 10.8 Application Identity

The Platform SHALL identify applications using:

       yaml
application:
  slug: "hcat"
       

The slug is the stable machine identity across:

- Project Version State;
    
- Release Manifest;
    
- Platform database;
    
- canonical live deployment;
    
- operational history.
    

The Platform SHALL NOT identify an application solely by:

- display name;
    
- Release-folder name;
    
- Docker container name;
    
- port number.
    

---

## 10.9 Release Identity

A Release SHALL be identified at minimum by:

       text
application slug
+
Release version
       

For example:

       text
hcat@1.1.0
       

The Platform SHOULD also record:

- Manifest checksum;
    
- Git commit;
    
- Git tag;
    
- Release creation time;
    
- Contract version.
    

The Platform SHALL detect conflicting Releases that claim the same application slug and version but possess different manifest or artifact checksums.

Such a conflict SHALL require explicit rejection or controlled investigation.

It SHALL NOT be silently treated as the same Release.

---

## 10.10 Available and Installed Release Distinction

The Platform SHALL maintain a strict distinction between:

       text
Supplied/Available Release
       

and:

       text
Currently Deployed Release
       

Example:

       text
Available Release: HCAT 1.1.0
Deployed Release:  HCAT 1.0.9
       

Copying a Release into Release Storage SHALL NOT change the deployed version.

The deployed version changes only after:

- the declared lifecycle operation succeeds;
    
- mandatory verification succeeds;
    
- the Platform commits the successful operational record.
    

---

## 10.11 Action Determination

The Platform SHALL determine available actions from:

- whether an active deployment exists;
    
- the supplied Release version;
    
- the active Release version;
    
-         deployment.supported_operations        ;
    
- transition declarations;
    
- local infrastructure compatibility;
    
- current operation state.
    

Examples:

### No existing deployment

The Platform MAY offer:

       text
INSTALL
       

only when:

       yaml
fresh_install: true
       

### Existing compatible deployment with different supplied Release

The Platform MAY offer:

       text
UPDATE
       

only when:

- update is supported;
    
- the installed version satisfies the declared transition rules;
    
- local prerequisites are satisfied.
    

### Older supplied Release

The Platform SHALL NOT offer downgrade merely because the supplied semantic version is lower.

It MAY offer:

       text
DOWNGRADE
       

only when downgrade is explicitly supported and the transition from the active Release is permitted.

### Same supplied and installed Release

The Platform SHALL not label the action as an update.

It MAY offer reinstall or repair only when explicitly supported.

---

## 10.12 Configuration Input Handling

The Platform SHALL construct its deployment-input interface from:

       yaml
configuration:
  inputs:
       

It SHALL respect:

- field key;
    
- label;
    
- datatype;
    
- required status;
    
- source;
    
- default;
    
- secret classification;
    
- allowed values and constraints when defined.
    

The Platform SHALL NOT ask the operator to manually edit         .env         files during the normal supported workflow.

The Platform SHALL validate operator input before invoking lifecycle scripts.

---

## 10.13 Port Allocation

For configuration inputs declared as:

       yaml
type: "port"
       

the Platform SHALL:

- validate the permitted numeric range;
    
- inspect current host port usage;
    
- detect conflicts with known Platform deployments;
    
- allow selection of an available valid port;
    
- record the chosen port in persistent operational state.
    

The Platform MAY suggest available ports.

A suggested port SHALL be rechecked immediately before deployment because host state may have changed.

The Release Manifest defines that a port input exists.

The Platform determines the deployment-specific value.

---

## 10.14 Secret Handling

For inputs declared as secret, the Platform SHALL:

- mask values in the user interface;
    
- avoid writing values to ordinary logs;
    
- generate strong values when the source is         generated        ;
    
- store values only in approved persistent operational locations;
    
- avoid copying production secrets into the immutable Release Package;
    
- preserve persistent secrets across ordinary updates.
    

The Platform SHALL NOT record plaintext secrets in general deployment-history fields.

Authorized operational access mechanisms may expose required credentials through protected operational views.

---

## 10.15 Lifecycle Invocation

The Platform SHALL invoke lifecycle operations only through Manifest-declared entry points.

It SHALL NOT:

- scan for alternative scripts;
    
- construct undocumented Docker commands as a substitute for a missing entry point;
    
- infer application-specific migration commands;
    
- modify lifecycle scripts before execution.
    

The Platform SHALL invoke scripts using a controlled execution context containing only permitted inputs and environment values.

---

## 10.16 Privileged Execution Boundary

The Platform SHALL use a constrained execution mechanism for privileged host operations.

The web-facing application process SHOULD NOT possess unrestricted root-command execution capability.

The implementation SHALL restrict executable operations to approved lifecycle entry points and Platform-owned operational functions.

The Platform SHALL NOT expose an arbitrary shell-command interface through the user interface or API.

The exact mechanism belongs to the Platform engineering design and may include:

- a constrained privileged service;
    
- controlled         sudo         rules;
    
- a local execution agent;
    
- narrowly defined operating-system capabilities.
    

Regardless of implementation, the observable behavior SHALL satisfy this obligation.

---

## 10.17 Operation Locking and Concurrency

The Platform SHALL prevent conflicting operations.

At minimum:

- one application SHALL NOT undergo two lifecycle operations concurrently;
    
- the same Release SHALL NOT be installed twice concurrently;
    
- an application update SHALL NOT begin while backup, restore, or recovery for that application is active;
    
- Platform database updates SHALL be transactionally protected.
    

The Platform MAY permit independent applications to deploy concurrently only when the implementation safely supports it.

The initial implementation SHOULD serialize deployment operations to reduce complexity.

---

## 10.18 Installation Obligations

For fresh installation, the Platform SHALL:

1. verify the Release is         AVAILABLE        ;
    
2. verify no conflicting active deployment exists;
    
3. collect and validate required inputs;
    
4. create or prepare the controlled execution context;
    
5. record the deployment attempt;
    
6. invoke the declared installation entry point;
    
7. capture logs and exit status;
    
8. invoke mandatory verification;
    
9. record the result;
    
10. mark the Release active only after verification succeeds.
    

The Platform SHALL NOT mark an application installed merely because containers were created.

---

## 10.19 Update Obligations

For update, the Platform SHALL:

1. identify the active deployed Release;
    
2. verify transition compatibility;
    
3. preserve active deployment configuration;
    
4. preserve persistent credentials and required state;
    
5. create or verify required backup measures;
    
6. record the intended source and target Releases;
    
7. invoke the declared update entry point;
    
8. invoke mandatory verification;
    
9. record migration and verification results;
    
10. activate the target Release only after success;
    
11. preserve the previous operational history.
    

An unsuccessful update SHALL NOT overwrite the last known successful active-deployment record.

---

## 10.20 Downgrade and Recovery Obligations

The Platform SHALL distinguish:

       text
Downgrade
Application rollback
Database recovery
Full deployment recovery
       

These are not interchangeable.

The Platform SHALL execute downgrade only when explicitly supported.

The Platform SHALL not assume that deploying older Docker images safely reverses database migrations.

Recovery operations SHALL use declared Release behavior and recorded backup information.

---

## 10.21 Verification Obligations

Every installation or update SHALL conclude with the declared verification entry point.

The Platform SHALL treat mandatory verification failure as deployment failure.

Verification SHALL cover applicable outcomes declared in the Manifest, including:

- Release identity;
    
- service state;
    
- application health;
    
- database connectivity;
    
- migration state;
    
- persistent configuration;
    
- offline runtime;
    
- operational integration.
    

The Platform SHALL record each required check's result when structured output is available.

---

## 10.22 Script Result Handling

The Platform SHALL treat:

       text
exit code 0
       

as script-level success and a non-zero exit code as script-level failure.

However, script success SHALL NOT alone establish successful deployment.

The complete success condition is:

       text
Lifecycle Script Success
+
Mandatory Verification Success
+
Operational Record Commit Success
       

The Platform SHALL display understandable failure information without exposing secrets.

---

## 10.23 Platform Operational Database

The Platform SHALL maintain a persistent relational operational database.

The database SHALL record at minimum:

- applications;
    
- imported Releases;
    
- active deployments;
    
- historical deployment attempts;
    
- installation and update results;
    
- source and target versions;
    
- selected ports;
    
- canonical deployment paths;
    
- verification outcomes;
    
- failure information;
    
- backup and recovery references;
    
- important operational timestamps.
    

The concrete schema will be defined separately in **Part 4 — Platform Operational Database**.

The Platform database is authoritative for operations performed through the Platform.

It is not authoritative for the immutable contents of an Application Release.

---

## 10.24 Transactional Operational Recording

The Platform SHALL distinguish between:

       text
attempted state
       

and:

       text
successful active state
       

A deployment operation SHALL begin by creating an attempt record.

The active deployment reference SHALL change only after mandatory execution and verification succeed.

Example:

       text
Begin update attempt: 1.0.9 → 1.1.0
        ↓
Run backup
        ↓
Run update
        ↓
Run verification
        ↓
PASS
        ↓
Commit active deployment = 1.1.0
       

On failure:

       text
Record failed attempt
Preserve previous successful active deployment record
Initiate applicable recovery procedure
       

---

## 10.25 Reconciliation with Actual Host State

The Platform SHALL not rely exclusively on its database when determining whether a deployment is healthy.

It SHALL reconcile recorded state with applicable observable host state, including:

- canonical deployment path;
    
- Docker Compose project identity;
    
- expected containers;
    
- expected image tags;
    
- expected ports;
    
- required persistent configuration;
    
- verification results.
    

The Platform database answers:

> What operations were performed and what state was last successfully recorded?

Host inspection and verification answer:

> Does the actual machine still match that recorded state?

A detected mismatch SHALL be presented as operational drift or inconsistency.

The Platform SHALL NOT silently overwrite historical records to hide drift.

---

## 10.26 Release Storage Retention

The Platform SHALL separate:

- Release Package availability;
    
- Release metadata history;
    
- deployment history.
    

Removing an old candidate Release Package from storage SHALL NOT erase:

- its imported metadata;
    
- its past deployment records;
    
- its verification results;
    
- its role in application history.
    

The Platform MAY mark its storage state as:

       text
REMOVED_FROM_STORAGE
       

while retaining operational history.

---

## 10.27 Documentation Presentation

The Platform SHALL present human-readable operational information derived from its structured operational state.

It MAY generate Markdown for Obsidian or another approved documentation view.

When Markdown is generated from the Platform database:

- the Platform database remains the structured operational authority;
    
- generated Markdown is a human-readable projection;
    
- generated files SHALL identify their generated nature where appropriate;
    
- manual edits SHALL not silently create a conflicting operational truth.
    

Release-specific documentation inside the immutable Release remains separate from generated operational documentation.

---

## 10.28 Audit and Logging

The Platform SHALL maintain deployment-operation logs sufficient to diagnose failures.

Logs SHOULD record:

- operation identifier;
    
- application;
    
- source and target Releases;
    
- start and completion times;
    
- responsible operator where applicable;
    
- executed lifecycle entry point;
    
- exit status;
    
- verification result;
    
- recovery action.
    

Logs SHALL avoid exposing secret values.

Operational history SHALL not depend solely on unstructured logs; essential facts belong in the relational database.

---

## 10.29 Failure Handling

When a mandatory operation fails, the Platform SHALL:

1. stop subsequent unsafe stages;
    
2. capture failure information;
    
3. preserve the previous successful state record;
    
4. classify the operation as failed;
    
5. expose applicable recovery guidance;
    
6. avoid claiming success;
    
7. avoid silently improvising a repair.
    

The Platform MAY execute an explicitly supported recovery procedure.

It SHALL record the recovery attempt and result separately.

---

## 10.30 Platform Self-Deployment

The Offline Platform is itself software operating in the RAH environment.

It SHALL be installed, updated, backed up, and maintained through an approved deployment mechanism.

The Platform SHALL not rely on the candidate Application Releases it manages for its own continued operation.

Its operational database and configuration SHALL persist across normal Platform updates.

---

## 10.31 Compatibility Evolution

The Platform SHALL advertise the versions it supports for:

- Release Manifest schema;
    
- Release Contract;
    
- RAH-OIP compatibility;
    
- supported architectures.
    

A Platform update MAY add support for newer Contract versions.

It SHALL NOT silently reinterpret an older Contract version using incompatible rules.

Unsupported Releases SHALL be rejected with a clear compatibility explanation.

---

## 10.32 Platform SHALL NOT

The Platform SHALL NOT:

- accept a Release with failed compliance evidence;
    
- bypass checksum failures;
    
- edit immutable Release Packages;
    
- invent missing lifecycle operations;
    
- treat every version difference as a valid transition;
    
- regenerate engineering compliance reports;
    
- modify Git or source repositories;
    
- store Release Packages inside the live application deployment;
    
- treat the incoming Release directory as the permanent runtime identity;
    
- erase deployment history during updates;
    
- expose arbitrary privileged command execution;
    
- mark deployment successful before verification.
    

---

## 10.33 Platform MAY

The Platform MAY:

- provide a dashboard of installed and available applications;
    
- suggest free ports;
    
- generate deployment secrets;
    
- display Release summaries;
    
- show recent deployment history;
    
- link to Release documentation;
    
- generate operational Markdown views;
    
- provide controlled backup and recovery actions;
    
- inspect Docker and host state;
    
- warn about drift;
    
- present structured deployment progress.
    

These capabilities remain subordinate to the Release Contract and operational-state rules.

---

## 10.34 Final Platform Principle

The Offline Platform is the deterministic consumer and operational orchestrator of compliant RAH Application Releases.

It SHALL trust the Release Contract for representation, the Release Manifest for Release intent, the Compliance Report for engineering compliance, host verification for actual behavior, and its Operational Database for persistent deployment history.

It SHALL never replace these distinctions with one ambiguous Platform-owned interpretation.

# Chapter 11 — Evolution Rules

## 11.1 Purpose

This chapter defines how the **RAH Application Release Contract** may evolve without breaking existing Application Releases, Packaging Software versions, Validators, Offline Platforms, or deployed applications.

Its purpose is to ensure that the Release ecosystem can improve over time while preserving:

- compatibility;
    
- traceability;
    
- reproducibility;
    
- deterministic validation;
    
- long-term operability;
    
- historical understanding.
    

The Release Contract SHALL evolve deliberately.

It SHALL NOT change through undocumented implementation behavior.

---

## 11.2 Fundamental Evolution Principle

A Release is created under one explicit Release Contract version.

That relationship remains permanent.

For example:

         text
HCAT Release 1.4.0
        ↓
Release Contract 1.0
         

Future Contract versions SHALL NOT retroactively redefine whether that immutable Release was compliant under Contract 1.0.

The governing rule is:

> **A Release is interpreted and validated according to the Contract version it explicitly declares.**

---

## 11.3 Independent Version Domains

The following versions are independent and SHALL NOT be confused:

         text
Application Release Version
Release Manifest Schema Version
Release Contract Version
Packaging Software Version
Generator Version
Validator Version
Offline Platform Version
RAH-OIP Version
         

Example:

         yaml
release:
  version: "2.4.1"

manifest_schema_version: "1.1"

compatibility:
  release_contract_version: "2.0"
  minimum_rah_oip_version: "1.3.0"
         

A change in one version domain does not automatically require a change in every other domain.

---

## 11.4 Contract Version Format

The Release Contract SHALL use:

         text
MAJOR.MINOR
         

Examples:

         text
1.0
1.1
2.0
         

The Contract does not require a patch component because implementation bug fixes belong primarily to Generator and Validator versions, provided the meaning of the Contract remains unchanged.

---

## 11.5 Major Contract Changes

The Contract MAJOR version SHALL increase when a change may make an existing compliant Release incompatible with the new Contract.

Examples include:

- removing a previously valid field;
    
- changing the meaning of a field;
    
- changing required directory names;
    
- changing mandatory script interfaces;
    
- changing lifecycle semantics;
    
- making previously optional artifacts mandatory;
    
- changing compliance behavior incompatibly;
    
- changing the meaning of a validation rule;
    
- introducing a new required operational contract that older Releases cannot satisfy.
    

Example:

         text
1.1 → 2.0
         

A Contract 2.0 implementation SHALL NOT assume that Contract 1.x Releases satisfy Contract 2.0.

---

## 11.6 Minor Contract Changes

The Contract MINOR version MAY increase when the change is backward-compatible within the same major version.

Examples include:

- adding optional Manifest fields;
    
- adding optional artifact categories;
    
- adding new optional lifecycle capabilities;
    
- defining additional standard verification identifiers;
    
- clarifying an existing rule without changing its meaning;
    
- adding validation rules for newly introduced optional behavior;
    
- adding new metadata that older Releases may omit.
    

Example:

         text
1.0 → 1.1
         

A Contract 1.1 Platform SHOULD continue to support valid Contract 1.0 Releases unless support is explicitly discontinued according to policy.

---

## 11.7 Clarifications and Errata

A wording correction or implementation clarification that does not change normative meaning MAY be published as an erratum without changing the Contract version.

An erratum SHALL:

- identify the affected section or rule;
    
- explain the ambiguity or defect;
    
- preserve the original intended requirement;
    
- be recorded in Contract documentation;
    
- not silently change compliance meaning.
    

If the correction changes what Releases pass or fail, a Contract version change is required.

---

## 11.8 Manifest Schema Evolution

The Release Manifest Schema SHALL have its own version.

A new Manifest Schema version is required when the YAML data structure changes.

Backward-compatible changes MAY include:

- new optional properties;
    
- new permitted values that older consumers may safely ignore;
    
- additional optional metadata sections.
    

Breaking changes include:

- renamed required properties;
    
- changed datatypes;
    
- removed fields;
    
- changed field meaning;
    
- new mandatory fields without a compatibility mechanism.
    

The Release Contract SHALL declare which Manifest Schema versions it permits.

Conceptually:

         text
Release Contract 1.0
    supports Manifest Schema 1.0

Release Contract 1.1
    supports Manifest Schema 1.0 and 1.1

Release Contract 2.0
    supports Manifest Schema 2.0
         

---

## 11.9 Directory Contract Evolution

Reserved Release paths SHALL remain stable within one Contract major version.

A minor Contract release MAY add:

- a new optional directory;
    
- a new optional standard file;
    
- a new optional artifact category.
    

A minor Contract release SHALL NOT:

- rename an existing mandatory directory;
    
- change the meaning of an existing reserved path;
    
- move a required artifact to another location;
    
- make an existing optional directory mandatory without a compatibility rule.
    

Breaking directory changes require a new Contract major version.

---

## 11.10 Validation Rule Evolution

Every validation rule identifier SHALL remain stable.

An existing rule identifier SHALL NOT be reused for a different requirement.

For example:

         text
RC-MAN-004
         

must retain its original meaning across compatible Validator versions.

When a new rule is introduced:

- it SHALL receive a new identifier;
    
- its Contract version of introduction SHALL be recorded;
    
- its applicability SHALL be explicit;
    
- its mandatory or conditional status SHALL be explicit.
    

If the meaning of a rule changes incompatibly, the Contract major version SHALL increase and a new rule identifier SHOULD be assigned.

---

## 11.11 Generator Evolution

The Generator MAY evolve independently from the Contract.

A new Generator version may:

- improve automation;
    
- improve error messages;
    
- support more project types;
    
- add new input workflows;
    
- improve artifact discovery;
    
- integrate better LLM assistance;
    
- improve performance;
    
- correct implementation defects.
    

A Generator update SHALL NOT silently change the meaning of a Contract version.

The Generator SHALL record:

         text
Generator version
Contract version implemented
Manifest Schema version emitted
         

A Generator MAY support multiple Contract versions.

Example:

         text
rah-packager 2.3.0

Supported Contract versions:
- 1.0
- 1.1
- 2.0
         

---

## 11.12 Validator Evolution

The Validator MAY evolve independently to:

- fix validation defects;
    
- improve diagnostics;
    
- improve static inspection;
    
- add support for newer Contract versions;
    
- improve performance;
    
- improve evidence collection.
    

A Validator update SHALL NOT intentionally cause different results for the same valid Contract interpretation.

If a previous Validator contained a defect that incorrectly passed or failed Releases, the correction SHALL be documented.

The Validator SHALL record its own version in every Compliance Report.

---

## 11.13 Platform Evolution

The Offline Platform SHALL explicitly declare supported:

- Release Contract versions;
    
- Manifest Schema versions;
    
- architectures;
    
- relevant RAH-OIP versions.
    

A Platform update MAY add support for newer Contract versions.

It SHALL preserve support for existing deployed Releases when practical.

The Platform SHALL NOT reinterpret historical deployment records according to newer Contract semantics.

An application deployed from Contract 1.0 remains historically associated with Contract 1.0 even after the Platform supports Contract 2.0.

---

## 11.14 Backward Compatibility

Backward compatibility means that a newer compatible implementation can still correctly consume an older artifact.

Within the same Contract major version:

- newer Validators SHOULD validate older compatible Releases;
    
- newer Platforms SHOULD import and operate older compatible Releases;
    
- newer Generators MAY continue producing older minor Contract versions when required.
    

Backward compatibility SHALL be tested, not assumed.

---

## 11.15 Forward Compatibility

Forward compatibility is not guaranteed.

An older Platform or Validator may reject a Release declaring a newer unsupported Contract or Manifest Schema version.

This is valid behavior.

The rejection SHALL be explicit.

Example:

         text
Import Rejected

Release Contract version 1.2 is not supported.
Installed Platform supports:
- 1.0
- 1.1
         

The Platform SHALL NOT guess how to interpret a newer Contract.

---

## 11.16 Unknown Fields

Within a Contract version that explicitly permits extensible metadata, consumers MAY ignore unknown optional fields only when the Contract states that doing so is safe.

Consumers SHALL reject unknown fields when:

-           additionalProperties           is prohibited by schema;
    
- the field appears in a security-sensitive section;
    
- ignoring it may alter lifecycle behavior;
    
- ignoring it may hide a required artifact or transition rule.
    

Extensibility SHALL be deliberate, not accidental.

---

## 11.17 Deprecation

A field, directory, operation, rule, or capability MAY be deprecated before removal.

Deprecation SHALL include:

- the deprecated element;
    
- the Contract version in which deprecation begins;
    
- the recommended replacement;
    
- the earliest Contract version in which removal may occur.
    

A deprecated element remains valid until removed by a new major Contract version.

Example:

         text
Deprecated in Contract 1.2:
configuration.legacy_env_path

Replacement:
configuration.template

Removal planned:
Contract 2.0
         

---

## 11.18 Migration Between Contract Versions

An existing immutable Release SHALL NOT be edited merely to declare a newer Contract version.

To move an application to a newer Contract:

         text
Existing Application Release
Contract 1.0
        ↓
Return to Release Engineering
        ↓
Generate a new Application Release
under Contract 2.0
        ↓
Validate
        ↓
Qualify
        ↓
Deploy
         

Contract migration therefore creates a new Release artifact.

It does not rewrite history.

## 11.19 Contract Selection During Packaging

The Packaging Software SHALL explicitly select the target Contract version before Release generation.

The selected version determines:

- directory requirements;
    
- Manifest Schema;
    
- validation rules;
    
- artifact rules;
    
- script obligations;
    
- Compliance Report requirements.
    

The Generator SHALL NOT mix rules from multiple Contract versions unless the Contract explicitly defines such compatibility.

## 11.20 Historical Preservation

The following SHALL remain preserved for every finalized Release:

- declared Contract version;
    
- declared Manifest Schema version;
    
- Generator version;
    
- Validator version;
    
- Compliance Report;
    
- checksum set;
    
- source traceability.
    

This allows future engineers to reconstruct how the Release was represented and validated at the time it was created.

## 11.22 Contract Change Process

Every proposed Contract change SHOULD include:

1. The problem being solved.
    
2. The affected components.
    
3. Whether the change is backward-compatible.
    
4. Required Contract version increment.
    
5. Manifest Schema impact.
    
6. Directory impact.
    
7. Generator impact.
    
8. Validator impact.
    
9. Platform impact.
    
10. Migration considerations.
    
11. Test cases.
    
12. Documentation changes.
    

No Contract change should be accepted solely because one application requires a convenient exception.

The change must be evaluated as:

- application-specific behavior;
    
- reusable implementation pattern;
    
- optional Contract extension;
    
- mandatory general Contract requirement.

## 11.23 Extension Mechanism

Application-specific metadata MAY be supported through an explicitly defined extension area.

For example:

         yaml
extensions:
  hcat:
    classification_model: "2.1.0"
         

An extension SHALL NOT:

- override standard Contract fields;
    
- redefine lifecycle behavior;
    
- bypass required validation;
    
- change application identity;
    
- weaken security rules;
    
- create hidden mandatory behavior unknown to the Platform.
    

If multiple applications require the same extension, it SHOULD be evaluated for promotion into a standard Contract field.

---

## 11.24 Compatibility Testing

Before publishing a new Contract version, RAH engineering SHOULD test:

- generation of a representative Release;
    
- validation with the matching Validator;
    
- import by a compatible Platform;
    
- old Release compatibility where claimed;
    
- new optional-field handling;
    
- failure behavior on unsupported versions;
    
- Contract migration workflow.
    

A Contract version SHALL NOT be considered operationally usable merely because its schema files parse successfully.

---

## 11.25 Removal of Support

Support for an older Contract version MAY eventually be removed from newer tooling.

Removal SHALL be deliberate and documented.

Before removal, RAH engineering SHOULD identify:

- applications still deployed under that Contract;
    
- archived Releases requiring future recovery;
    
- rollback dependencies;
    
- qualification evidence;
    
- whether migration Releases exist.
    

The Platform SHALL not remove support in a way that makes currently deployed applications unmanageable without an approved migration plan.

---

## 11.26 Security Evolution

A security defect MAY require stronger treatment than ordinary compatibility rules.

When an older Contract permits unsafe behavior, RAH engineering MAY:

- reject newly imported Releases using that behavior;
    
- require migration to a safer Contract version;
    
- restrict dangerous operations;
    
- publish a security erratum;
    
- update Platform policy.
    

Such changes SHALL be documented clearly.

Historical records SHALL remain preserved even when an old Release is no longer permitted for new deployment.

---

## 11.27 No Silent Semantic Drift

No component SHALL silently change the meaning of:

- a Contract version;
    
- a Manifest field;
    
- a validation rule;
    
- a lifecycle operation;
    
- a compliance outcome.
    

If semantics change, the change SHALL be represented through:

- a version increment;
    
- a new rule;
    
- an erratum;
    
- explicit migration documentation.
    

Implementation convenience SHALL NOT justify hidden protocol changes.

---

## 11.28 Final Evolution Principle

The RAH Application Release Contract is designed to evolve, but not to drift.

Every Release remains permanently tied to the Contract under which it was created.

New Contract versions may extend or replace earlier rules, but they SHALL preserve explicit compatibility boundaries, historical traceability, and deterministic interpretation.

The governing principle is:

> **Evolve the protocol deliberately. Preserve every artifact historically. Never change meaning silently.**

## Part 4 — Platform Operational Registry

#### 1. Purpose

The **Platform Operational Registry** is the persistent relational database used by the RAH Offline Installation Platform.

It records:

- which applications are known to the Platform;

## 7.5 `operations`

#### 7.5.1 Purpose

Stores one record for every long-running Platform operation, of any type. This is the authoritative identity and lifecycle record introduced by Architecture V1 Gap 1 (Operation Identity Model, Solution A). It is the single source of `operation_id` used across the Platform API for polling, progress reporting, logging, event retrieval, and application-level locking.

Operation types include:

           text
INSTALL
UPDATE
DOWNGRADE
REINSTALL
RECOVERY
ROLLBACK
VERIFY
BACKUP
RESTORE
IMPORT
           

`VERIFY`, `BACKUP`, `RESTORE`, and `IMPORT` were added to the original `deployments.operation_type` value set because the Operation Attempt Rule (§15, Rule 5, and the Platform Specification's own Operation Attempt Rule) already requires import, backup, and restore to create an operation record, not only install/update/downgrade/reinstall/recovery/rollback.

#### 7.5.2 Fields

|Field|Type|Purpose|
|---|---|---|
|`id`|UUID|Operation identity — this is the `operation_id` used throughout the Platform API|
|`application_id`|UUID|Target application|
|`operation_type`|VARCHAR(30)|Install/update/verify/backup/restore/etc.|
|`status`|VARCHAR(30)|External operation state: PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED|
|`stage`|VARCHAR(80), nullable|Internal detail stage: PREPARING/BACKING_UP/EXECUTING_SCRIPT/VERIFYING/RECOVERING/etc.|
|`requested_by`|TEXT, nullable|Caller identity, e.g. `operator:admin`, `automation:jenkins`|
|`started_at`|TIMESTAMPTZ, nullable|Operation start|
|`completed_at`|TIMESTAMPTZ, nullable|Operation finish|
|`created_at`|TIMESTAMPTZ|Record creation|

#### 7.5.3 Status and Stage Split

The original `deployments.status` list (`PENDING, PREPARING, BACKING_UP, EXECUTING, VERIFYING, SUCCEEDED, FAILED, RECOVERY_REQUIRED, RECOVERING, RECOVERED, CANCELLED`) mixed external lifecycle state with internal progress detail. This table splits that list, matching the Platform Specification's own external-status/internal-stage distinction (§5.5/§5.6):

           text
status (external, polled by callers):
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED

stage (internal detail, optional):
PREPARING
BACKING_UP
EXECUTING_SCRIPT
VERIFYING
RECOVERY_REQUIRED
RECOVERING
RECOVERED
           

#### 7.5.4 Success Rule

An operation becomes `SUCCEEDED` only when:

           text
Lifecycle script succeeded
+
Mandatory verification succeeded
+
Operational database transaction committed
           

A container starting is not sufficient.

#### 7.5.5 Shared Operation for Sub-Steps

A backup taken as a mandatory step of an install or update (stage `BACKING_UP`) uses the **same** `operation_id` as the parent install/update — it is not a separate operation. A backup requested directly through the standalone backup capability is its own operation, with `operation_type = BACKUP` and its own `operation_id`. The same principle applies to a verification run executed as the `VERIFYING` stage of an install/update versus a standalone manual/reconciliation verification.

#### 7.5.6 Locking

Application-level operation locking (§15, Rule 5) is enforced against this table — application_id plus non-terminal status (`PENDING` or `RUNNING`) — covering every `operation_type`, not `deployments` alone. This is what allows a running backup or verification to correctly block a concurrent update.

## 8. `deployments`

Stores the deployment-specific detail record produced by an INSTALL, UPDATE, DOWNGRADE, REINSTALL, RECOVERY, or ROLLBACK operation. This is the central historical table for what was actually deployed.

|Field|Type|Purpose|
|---|---|---|

|`operation_id`|UUID|Owning operation — see §7.5|

|`target_release_id`|UUID|Release being deployed|

|`script_exit_code`|INTEGER, nullable|Main lifecycle script result|
|`verification_status`|VARCHAR(30), nullable|Verification summary|

`operation_type`, `status`, `started_at`, `completed_at`, and `requested_by` are no longer columns on this table — they are owned exclusively by the linked `operations` row (§7.5.3) to avoid two tables independently tracking the same process lifecycle.

#### 8.3 Success Rule

A deployment becomes eligible to activate only when its linked operation reaches `SUCCEEDED` (see §7.5.4). This table does not carry its own status field.

#### 8.4 Active Deployment

           text
applications.active_deployment_id = deployments.id

|`summary`|TEXT, nullable|Human-readable result|

`started_at` and `completed_at` are no longer columns on this table — that timing is owned by the linked `operations` row. `status` is narrowed to the resolved verdict only (`PASS`/`FAIL`); pending/running state is tracked by `operations.status`, since a verification *process* can succeed while its *verdict* is FAIL — those are genuinely different concepts, not a duplication.

#### 11.3 Allowed Statuses

           text
PASS
FAIL
           

(`NULL` while the owning operation has not yet resolved a verdict.)

This allows the Platform UI to show:

           text

NOT_APPLICABLE
NOT_EXECUTED

## 13. `backups`

#### 13.1 Purpose

Stores backup and recovery references associated with deployment operations. Every row is linked to the `operations` row that created it (`operation_type = BACKUP`, or the `BACKING_UP` stage of an install/update — see §7.5.5).

The database does not necessarily contain backup data.

It records where backup data exists and what happened.

`status` here is deliberately **not** removed or merged with `operations.status` the way it was for `deployments` and `verification_runs`: `CREATED`/`VERIFIED`/`RESTORED` describe the backup artifact's own lifecycle, which continues to change after the creating operation has already reached a terminal state (e.g., verified or restored much later, potentially by a different, later operation). This is genuinely different from the process lifecycle `operations.status` tracks, not a duplicate of it.

#### 13.2 Fields

|Field|Type|Purpose|
|---|---|---|
|`id`|UUID|Backup identity|
|`operation_id`|UUID|Operation that created this backup — see §7.5|
|`application_id`|UUID|Application|
|`deployment_id`|UUID, nullable|Related deployment|
|`backup_type`|VARCHAR(40)|Database/files/full deployment|
|`storage_path`|TEXT|Backup location|
|`created_at`|TIMESTAMPTZ|Creation time|
|`status`|VARCHAR(30)|Backup artifact lifecycle: PENDING/CREATED/FAILED/VERIFIED/RESTORED|
|`verified`|BOOLEAN|Whether recoverability was checked|
|`verified_at`|TIMESTAMPTZ, nullable|Verification time|
|`checksum`|VARCHAR(64), nullable|Integrity hash|
|`notes`|TEXT, nullable|Important information|

## 15. Required Application-Level Constraints

Some important rules cannot be enforced cleanly using simple SQL constraints alone.

The backend service must enforce them transactionally.

#### Rule 1 — Release belongs to application

For every deployment:

           text
target_release.application_id
=
deployment.application_id
           

The same applies to `source_release_id`.

#### Rule 2 — Active deployment must be successful

Before setting:

           text
applications.active_deployment_id
           

the referenced deployment must:

- belong to the same application;
    
- have a linked `operations` row with `status = SUCCEEDED`;
    
- have successful verification.
    

#### Rule 3 — Install has no source Release

For an `operations` row with:

           text
operation_type = INSTALL
           

normally, its linked `deployments` row has:

           text
source_release_id = null
           

#### Rule 4 — Update has a source Release

For an `operations` row with:

           text
UPDATE
DOWNGRADE
ROLLBACK
           

its linked `deployments` row requires `source_release_id`.

#### Rule 5 — No concurrent application operation

Only one non-terminal operation may exist per application, across **all** operation types (`INSTALL`, `UPDATE`, `DOWNGRADE`, `REINSTALL`, `RECOVERY`, `ROLLBACK`, `VERIFY`, `BACKUP`, `RESTORE`, `IMPORT`) — not only deployment-producing types. This is the mechanism behind the Platform Specification's Operation Lock Rule: a running backup or verification must also block a concurrent update.

Non-terminal statuses are:

           text
PENDING
RUNNING
           

(the finer-grained progress previously listed here — PREPARING, BACKING_UP, EXECUTING, VERIFYING, RECOVERY_REQUIRED, RECOVERING — is now `operations.stage`, a detail within the `RUNNING` status, not a separate status value.)

The backend must lock the application by checking for an existing non-terminal row in `platform.operations` before creating a new one.

#### Rule 6 — Active Release changes only on success

The Platform shall update the active deployment reference in the same database transaction that sets the linked operation's `status` to `SUCCEEDED`.

## 16. Initial Import Workflow

When the Platform discovers a Release:

           text
1. Create operation: operation_type = IMPORT, status = PENDING.
2. Read release.yaml.
3. Validate supported schema and Contract version.
4. Verify Compliance Report.
5. Verify checksums.
6. Find application by slug.
7. Create application if it is new.
8. Find Release by application + version.
9. Detect fingerprint conflicts.
10. Insert immutable Release metadata if new.
11. Insert or update Release Storage record.
12. Mark storage state AVAILABLE.
13. operation.status = SUCCEEDED.
           

Step 1 was added under Architecture V1 Gap 1: the Operation Attempt Rule already requires import to create an operation record before performing irreversible work, but this workflow previously did not reflect that.

The Platform shall not create a deployment record during import.

Available Release
        ↓

## 18. Update Workflow

           text
Current active deployment
        +
Available target Release
        ↓
Validate transition
        ↓
Create operation:
operation_type = UPDATE
status = PENDING
        ↓
Create deployment record linked to operation_id:
source_release_id = current Release
target_release_id = supplied Release
        ↓
If backup is mandatory:
operation.stage = BACKING_UP
create backup record linked to the SAME operation_id
        ↓
operation.stage = EXECUTING
invoke update script
        ↓
operation.stage = VERIFYING
create verification run linked to the SAME operation_id
        ↓
On success:
operation.status = SUCCEEDED
mark new deployment active
preserve old deployment in history
           

A standalone backup requested outside an install/update (not as a mandatory pre-update step) is its own operation, with its own `operation_id` and `operation_type = BACKUP` — see §7.5.5.

On failure:

           text
operation.status = FAILED
active_deployment_id remains unchanged
           

A recovery operation may then receive its own operation and deployment record.

## 23. Final Registry Principle

#### Mechanism Consolidation

##### Part A — Packaging Software Mechanisms
###### 1. Packager Runtime

```
The RAH Packaging Software shall be implemented as a Dockerized command-line application.

During development and operation, the Packaging Software shall execute inside a dedicated Docker container rather than directly on the host operating system. This provides a consistent execution environment across development machines while simplifying iterative development and future portability.

The Packaging Software shall access the engineering workstation through controlled bind-mounted directories, allowing it to inspect application repositories, generate Release artifacts, and write output without duplicating project files.

The Packaging Software shall use the host Docker Engine to build, inspect, export, and validate application images. The Docker container itself shall not become an isolated execution environment disconnected from the engineering workstation.

The Packaging Software shall remain independent of the host operating system except for the minimal integration required to access project repositories, Release output locations, and the host Docker Engine.
```

###### 2. Packager User Interface

```
The initial Packaging Software shall expose a Command Line Interface (CLI).

The CLI shall become the primary interface used by engineers, automation systems, and future orchestration tools.

The CLI shall expose deterministic engineering operations such as project inspection, Release generation, Release validation, and Release qualification.

Graphical interfaces, desktop applications, or local web interfaces may be introduced later as convenience layers. Such interfaces shall invoke the same internal Packaging Software operations rather than implementing independent engineering logic.

The engineering capabilities of the Packaging Software shall therefore remain independent from its presentation layer.
```
###### 3. Project Input Mechanism
```
The Packaging Software shall operate directly on an existing local application repository.

The engineer shall provide the location of the application repository rather than copying the project into the Packaging Software.

The Packaging Software shall inspect the supplied repository, perform all engineering operations within temporary working directories when required, and generate the finalized Release Package inside a configurable Release output directory.

The Packaging Software shall not modify the application's source repository except where explicitly requested by the engineer.

Application source code and generated Release artifacts shall remain physically separated.
```
###### 4. Docker Integration
```
The Packaging Software shall interact with Docker through the standard Docker Command Line Interface and Docker Compose commands.

Docker operations shall include, where applicable:

- building application images;
- inspecting generated images;
- exporting Docker images;
- validating Docker Compose configurations;
- preparing Release artifacts for offline deployment.

All Docker operations shall be executed through deterministic commands whose execution results are captured by the Packaging Software.

Each Docker operation shall record:

- executed command;
- execution result;
- exit code;
- execution log;
- execution duration.

The Packaging Software shall not manipulate Docker images through undocumented or application-specific mechanisms.
```
##### 5. Claude Integration

```
Claude shall function as an engineering assistant within the Packaging Software workflow.

Its responsibility is to assist in extracting engineering knowledge that cannot be deterministically inferred from the application repository.

The Packaging Software shall first perform deterministic inspection of the application repository and automatically collect all information that can be reliably discovered without interpretation.

When additional engineering knowledge is required, the Packaging Software shall generate a structured engineering request describing the remaining unanswered questions.

Claude shall analyze the application repository together with the generated engineering request and produce structured engineering answers.

Those answers shall conform to predefined schemas and shall undergo validation before becoming part of the Release Engineering process.

Claude shall not directly generate Release artifacts, modify Release metadata, or construct Release Packages.

Final Release generation shall remain the exclusive responsibility of deterministic Packaging Software components.

During the initial implementation, Claude interaction may occur manually through Claude Code operating on the engineering workstation.

Future versions may automate this interaction provided the resulting engineering data continues to satisfy the same validation requirements.
```

##### Part B — Offline Platform Mechanisms
###### 6. Platform Application Stack

```
The RAH Offline Installation Platform shall be implemented as a normal web application deployed inside the offline Debian environment.

The initial Platform shall contain:

- a web frontend;
- a Python backend;
- a PostgreSQL Operational Registry;
- Docker Compose deployment resources.

The frontend shall provide the operator interface for discovering applications, reviewing available Releases, initiating installation and update operations, viewing progress, and examining operational history.

The backend shall implement the Platform’s operational logic, including:

- reading Release Manifests;
- importing Release metadata;
- validating deployment requests;
- executing lifecycle operations;
- maintaining operational state;
- recording deployment history;
- returning structured results to the frontend.

PostgreSQL shall store the Platform Operational Registry. It shall preserve applications, imported Releases, deployment attempts, verification outcomes, runtime configuration, and historical state.

The frontend technology may be selected according to implementation familiarity. The exact frontend framework shall not alter the Platform’s backend responsibilities, database model, or external API.
```
###### 7. Platform Command Execution

```
The initial Platform backend shall directly execute approved lifecycle scripts declared by the Release Manifest.

The execution flow shall be:

```
Platform Web Interface
        ↓
Platform Backend
        ↓
Manifest-declared lifecycle script
        ↓
Docker and operating-system operations
```

Examples include:

```
scripts/install_offline.sh
scripts/update_offline.sh
scripts/verify_deployment.sh
scripts/backup_database.sh
scripts/restore_database.sh
```

The backend shall not accept arbitrary shell commands from the frontend.

The frontend may request only supported Platform operations such as:

```
INSTALL
UPDATE
VERIFY
BACKUP
RECOVER
```

The backend shall map each permitted operation to the exact entry point declared in the immutable Release Manifest.

The Platform shall:

- validate the requested operation;
- confirm that the Release supports it;
- prepare the required configuration;
- execute the declared script;
- capture its output and exit code;
- record the operation result;
- initiate required verification.

The initial implementation shall favor this direct backend execution model because the Platform operates inside a controlled air-gapped environment and simplicity is important for the first working version.

A separate privileged execution service may be introduced later only if practical experience demonstrates a real need for a stronger execution boundary.
```

###### 9. Platform Release Discovery

```
The Platform shall discover candidate Application Releases through one configured Release Storage location.

The initial incoming directory should follow a stable convention such as:

 
/opt/rah/releases/incoming/
 

Copying a Release into this directory shall not automatically install or register it as deployed.

The Platform shall provide an explicit operation such as:

 
Scan Releases
 

or:

 
Import Release
 

When requested, the Platform shall:

1. scan the configured incoming directory;
2. identify candidate Release folders;
3. locate their Release Manifests;
4. verify their Compliance Reports;
5. verify checksums;
6. check supported Contract and Manifest versions;
7. register valid Release metadata;
8. report rejected candidates clearly.

The initial Platform shall not use a continuous filesystem watcher.

An explicit scan/import action is selected because it avoids:

- reading partially copied Releases;
- duplicate filesystem events;
- hidden automatic state changes;
- difficult debugging.

The same import operation may later be invoked through the Platform API by Jenkins.
```
###### 10. Results and Reporting

```
The Packager and Platform shall produce both machine-readable results and human-readable logs.

Machine-readable operational results shall use JSON.

Human-readable logs may use ordinary text.

JSON is selected for operation results because it is:

- directly consumable by the Platform frontend;
- directly consumable by Jenkins;
- structurally validatable;
- suitable for nested status and evidence;
- widely supported by programming languages.

YAML remains appropriate for the human-readable immutable Release Manifest. It shall not be used as the primary runtime operation-result format.

Every important operation shall return or generate an object containing at least:

 
operation identifier
operation type
current or final status
start time
completion time
application identity
target Release identity
result message
error code when applicable
generated artifact references
log location
 

Conceptual example:

 
{
  "operation_id": "95fd851d-fcf0-4abe-b920-b5e89470783a",
  "operation": "INSTALL",
  "status": "FAILED",
  "application_slug": "hcat",
  "target_version": "1.1.0",
  "started_at": "2026-08-06T14:10:00+03:00",
  "completed_at": "2026-08-06T14:13:25+03:00",
  "error_code": "PLT-INSTALL-004",
  "message": "The backend container failed its health check.",
  "log_path": "/var/log/rah/operations/95fd851d.log"
}
 

Lifecycle scripts may continue using ordinary shell exit codes:

 
0
→ Script-level success

Non-zero
→ Script-level failure
 

The Platform backend shall translate script execution into the shared structured result model.

A successful script exit shall not automatically mean successful deployment. Installation or update succeeds only after mandatory verification and operational-state recording also succeed.
```

##### Part C — Integration, Automation, and Environment
###### 11. Jenkins Integration

```
Jenkins shall function as an orchestration system.

It shall coordinate capabilities already implemented by the Packager and Platform.

Jenkins shall not contain:

- Release-generation logic;
- Release interpretation rules;
- application-specific installation behavior;
- migration logic;
- qualification rules;
- Platform database logic.

Its role shall be limited to invoking defined operations in an approved order.

The intended future orchestration model is:

 
Jenkins
   ↓
Invoke Packager CLI
   ↓
Receive packaging result
   ↓
Transfer finalized Release
   ↓
Invoke Platform import API
   ↓
Invoke installation/update test
   ↓
Invoke verification
   ↓
Collect Qualification evidence
 

Jenkins integration shall be added only after the complete procedure succeeds manually.

This order is required because the individual products must be testable independently before Jenkins is introduced as another failure source.

When automation begins, the recommended topology is:

- a Jenkins agent on the Windows engineering workstation;
- a Jenkins agent or authenticated Platform API access in the Offline Validation VM.

The Windows agent shall run the Packager CLI locally.

The validation-side integration shall invoke Platform operations and retrieve their structured results.

Claude shall not be controlled by Jenkins in the first implementation.

Initial Claude-assisted engineering shall occur before deterministic packaging. Jenkins automation of Claude Code may be considered only after the manual Claude workflow has proved stable and repeatable.
```
###### 12. Release Transfer

```
The same finalized immutable Release Package shall move between environments without being rebuilt or modified.

The laboratory qualification environment and real production environment may use different transport mechanisms.

#### Laboratory and Validation Transfer

During development and qualification, the Release may be transferred through SCP or SFTP across the controlled laboratory network.

The transfer operation shall:

1. accept the source Release path;
2. determine the configured destination machine;
3. copy the complete Release;
4. wait for transfer completion;
5. verify the Release checksum or fingerprint at the destination;
6. report success or failure structurally.

The Release-transfer script shall not depend permanently on an unstable manually entered Lenovo IP address.

Machine configuration should prefer:

1. stable hostnames where available;
2. reserved DHCP addresses or static laboratory addresses;
3. a configuration file containing the current address as a fallback.

The transfer mechanism should therefore refer to a logical machine identity:

 
machines:
  validation_vm:
    hostname: "rah-validation"
    address: "10.10.10.2"
 

rather than embedding IP addresses directly in scripts.

VPN behavior shall not silently change the selected network interface. The transfer script shall verify that the resolved destination is reachable before copying.

#### Production Transfer

For the real air-gapped environment, Release transfer shall occur through approved physical media such as USB or DVD.

After physical transfer, the Platform shall verify the same Release integrity information before import.

The transfer method does not change the Release’s identity or contents.
```
###### 13. Configuration and Credential Handling

```
The system shall distinguish between **configuration** and **credentials**.

#### Configuration

Configuration describes where and how the engineering environment operates.

Examples include:

 
machine hostnames
machine IP addresses
SSH usernames
Release output paths
incoming Release paths
default Contract version
Git branch names
Platform API address
 

Non-secret environment configuration shall be stored in a version-controlled template and a local environment-specific configuration file.

Example:

 
environment: "rah-validation-lab"

machines:
  engineering_workstation:
    hostname: "lenovo"
    address_mode: "dynamic"

  validation_vm:
    hostname: "rah-validation"
    address: "10.10.10.2"
    ssh_user: "rah"

paths:
  release_output: "C:\\RAH\\Releases"
  platform_incoming: "/opt/rah/releases/incoming"

platform:
  api_base_url: "http://10.10.10.2:8080"

contract:
  default_version: "1.0"
 

The monorepo may contain:

 
config/lab-config.example.yaml
 

The real local file should be:

 
config/lab-config.yaml
 

and may be excluded from Git when it contains machine-specific values.

#### Credentials

Credentials prove identity or grant permission.

Examples include:

 
SSH private keys
Platform service tokens
Claude authentication
Jenkins credentials
Passwords
 

Credentials shall not be stored inside:

- Application Releases;
- Release Manifests;
- ordinary configuration templates;
- source-controlled scripts;
- general logs.

Jenkins shall store the credentials it requires in its own credential store.

SSH authentication should use keys rather than repeatedly entered passwords.

Claude Code shall use its own supported local authentication on the engineering workstation.

The Packager may read references or paths to approved credentials when necessary, but it shall not become the canonical secret store.

A future Packager UI may edit ordinary configuration values. It shall not automatically become a password or private-key vault.
```

###### 15. Qualification Execution


```
### 15. Qualification Execution

Release Qualification shall remain an engineering responsibility, but its execution shall involve multiple components.

The qualification model shall be:

 
Packaging/Release Engineering side
→ Owns the qualification request and final decision

Offline Validation Platform
→ Executes installation, update, and verification operations

Manual controller initially
→ Coordinates the first complete qualification procedure

Jenkins later
→ Automates the proven procedure
 

The Packaging Software shall:

- finalize the immutable candidate Release;
- produce compliance evidence;
- identify the qualification procedure to perform;
- request qualification;
- collect or reference qualification results.

The Offline Platform inside the Validation VM shall:

- import the exact candidate Release;
- execute fresh-install testing;
- execute supported update testing;
- execute mandatory verification;
- produce structured deployment and verification results.

The frozen Release Manifest shall remain:

 
awaiting_offline_qualification
 

It shall not be edited after qualification.

The qualification outcome shall be recorded separately in a Qualification Report.

The initial qualification process shall be executed manually and repeatedly until stable.

Jenkins shall later orchestrate the same proven calls without taking ownership of the underlying engineering rules.

A Release shall be considered qualified only when:

- Release Contract compliance succeeds;
- required clean-install tests succeed;
- required update-path tests succeed;
- mandatory verification succeeds;
- the tested artifact fingerprint matches the finalized Release;
- the Qualification Report records a successful result.
```
