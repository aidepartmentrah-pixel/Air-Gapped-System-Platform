# Consolidation

## Part I — Packaging Engine Specification

## 1. Purpose

The RAH Packaging Engine transforms an initialized application repository into one finalized, immutable, contract-compliant Application Release.

The Packaging Engine shall:

- inspect the application repository;
- collect deterministic project information;
- request missing engineering knowledge through Claude-assisted input;
- build application Docker images;
- construct the Release directory;
- generate the Release Manifest;
- validate the Release against the Release Contract;
- generate integrity and compliance evidence;
- finalize the Release;
- update the Project Version State only after successful finalization.

The Packaging Engine shall not install or operate the application inside the offline environment.

---

## 2. Public Packaging Operations

The initial Packaging Engine shall expose the following public operations:

|Operation|Purpose|
|---|---|
|`init`|Initialize an ordinary repository for RAH packaging|
|`inspect`|Inspect the repository and produce deterministic project information|
|`prepare-answers`|Generate the structured engineering request for Claude or the engineer|
|`validate-answers`|Validate the returned engineering answers|
|`plan`|Calculate and preview the next Release without creating it|
|`package`|Execute the complete Release-generation process|
|`validate`|Validate an existing candidate or finalized Release|
|`status`|Read the result, progress, logs, or artifacts of a Packaging operation|

The ordinary user workflow shall primarily use:

```
init
inspect
prepare-answers
package
validate
```

The `package` operation shall coordinate the necessary internal stages.

Internal implementation stages such as image building, Manifest generation, checksum creation, and finalization shall not need to become separate public CLI commands unless debugging later demonstrates a real need.

---

## 3. Packaging Workflow

The `package` operation shall execute the following internal sequence:

```
1. Validate project path
2. Read Project Version State
3. Inspect Git state
4. Validate requested Release version
5. Read deterministic inspection information
6. Load and validate engineering answers
7. Create temporary Packaging workspace
8. Build required Docker images
9. Inspect and export Docker images
10. Construct Release directory
11. Generate Release Manifest
12. Copy scripts, configuration, database, documentation, and verification resources
13. Validate Release structure
14. Validate Manifest schema and semantic rules
15. Generate Compliance Report
16. Generate checksums
17. Perform final integrity closure
18. Move finalized Release to output storage
19. Update Project Version State atomically
20. Return Packaging Result
```

If any mandatory stage fails:

- the Release shall not be finalized;
- Project Version State shall remain unchanged;
- previously finalized Releases shall remain unchanged;
- a structured failure result and log shall be produced.

## 5. Packaging Result Objects

Every public operation shall return a structured JSON result.

The result shall use one common envelope:

```
{
  "operation_id": "uuid",
  "operation": "PACKAGE_APPLICATION",
  "status": "SUCCEEDED",
  "started_at": "2026-08-06T15:00:00+03:00",
  "completed_at": "2026-08-06T15:05:00+03:00",
  "data": {},
  "warnings": [],
  "errors": [],
  "artifacts": [],
  "logs": []
}
```

The allowed initial operation statuses shall be:

```
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED
```

For the initial synchronous CLI, the final visible status will normally be either:

```
SUCCEEDED
FAILED
```

## 6. Principal Result Types

### 6.1 `InitializeProjectResult`

Returns:

- application identity;
- Project Version State path;
- initial proposed version;
- schema validation result.

### 6.2 `ProjectInspectionResult`

Returns detected facts such as:

- application repository path;
- Git commit;
- Git branch;
- Git tag;
- clean or dirty source state;
- Dockerfiles;
- Compose file;
- Compose services;
- Docker image names;
- configuration-variable names;
- database migration resources;
- lifecycle scripts;
- documentation resources;
- information that could not be determined automatically.

### 6.3 `EngineeringRequestResult`

Returns:

- generated Claude request path;
- engineering-answer schema path;
- unresolved engineering questions.

### 6.4 `EngineeringAnswersValidationResult`

Returns:

- whether the answers are structurally valid;
- missing required answers;
- conflicting values;
- warnings requiring engineer review.

### 6.5 `ReleasePlan`

Returns:

- application identity;
- current Release;
- proposed next Release;
- version increment;
- Contract version;
- intended output path;
- Docker images to build;
- artifacts expected in the Release;
- whether Packaging may proceed.

### 6.6 `PackagingResult`

Returns:

- application identity;
- finalized Release identity;
- finalized Release path;
- Release fingerprint;
- Manifest path;
- Compliance Report path;
- checksum path;
- built Docker images;
- operation result;
- log references.

### 6.7 `ReleaseValidationResult`

Returns:

- overall compliance state;
- Contract version;
- Validator version;
- passed rules;
- failed rules;
- warnings;
- Compliance Report reference.

## 7. CLI Contract

The Packaging Engine shall be exposed through a Dockerized CLI.

Conceptual commands:

```
rah init --project /workspace/project \
         --name "HCAT" \
         --slug hcat

rah inspect --project /workspace/project

rah prepare-answers --project /workspace/project

rah validate-answers \
    --project /workspace/project \
    --answers /workspace/project/.rah/engineering-answers.json

rah plan \
    --project /workspace/project \
    --increment minor

rah package \
    --project /workspace/project \
    --output /workspace/output \
    --increment minor \
    --answers /workspace/project/.rah/engineering-answers.json

rah validate \
    --release /workspace/output/hcat/1.1.0
```

The CLI shall:

1. parse arguments;
2. create the appropriate request object;
3. invoke the Packaging Engine;
4. display understandable progress;
5. write the structured JSON result;
6. return the appropriate process exit code.

The CLI shall not contain core Packaging business logic.

## 8. CLI Exit Codes

The initial CLI shall use:

|Exit code|Meaning|
|---|---|
|`0`|Operation succeeded|
|`1`|General operation failure|
|`2`|Invalid command or input|
|`3`|Project-state failure|
|`4`|Git-state failure|
|`5`|Engineering-answer failure|
|`6`|Docker operation failure|
|`7`|Release Contract validation failure|
|`8`|Filesystem or artifact failure|
|`9`|Finalization failure|
|`10`|Unexpected internal failure|

The JSON result shall provide the more precise error code.

## 10. Claude-Assistance Contract

Claude Code shall run on the online engineering workstation from inside the application repository.

The Packaging Engine shall generate:

```
.rah/claude-packaging-request.md
.rah/engineering-answers.schema.json
```

Claude shall inspect the repository and create:

```
.rah/engineering-answers.json
```

The engineering-answer object may include:

- application description;
- Release summary;
- required operator inputs;
- secret classifications;
- persistent-state declarations;
- database lifecycle behavior;
- update compatibility information;
- application-specific verification requirements;
- documentation information;
- known limitations.

The Packaging Engine shall validate the returned file against its schema and cross-check it against deterministically discovered information.

Claude shall not directly create or modify:

- finalized `release.yaml`;
- Project Version State history;
- checksums;
- Compliance Report;
- finalized Release structure.

Those remain deterministic Packaging Engine responsibilities.

---

## 11. State-Safety Rules

The Packaging Engine shall follow these safety rules:

1. Project Version State shall not be updated before successful Release finalization.
2. A failed Packaging operation shall not create a successful release-history entry.
3. Existing finalized Releases shall never be overwritten silently.
4. A duplicate Release version shall be rejected.
5. A dirty Git repository shall normally be rejected before Packaging.
6. Generated work shall occur inside a temporary workspace.
7. Final output shall move into Release storage only after validation succeeds.
8. Project Version State shall be updated atomically.
9. Generated checksums shall cover finalized Release-critical contents.
10. Claude-produced values shall require schema validation before use.

---

## 12. Initial Acceptance Criteria

The Packaging Engine Version 1 is complete when it can demonstrate all of the following:

### Project Initialization

- Initialize an ordinary Git repository.
- Generate a valid `.rah/project-state.json`.
- Reject silent reinitialization of an existing project.

### Inspection

- Read Git information.
- Discover Docker and Compose resources.
- Detect configuration, scripts, database, and documentation resources.
- Produce a structured inspection result.

### Claude Assistance

- Generate a structured Claude request.
- Generate the engineering-answer JSON Schema.
- Accept valid engineering answers.
- Reject missing, malformed, or contradictory answers.

### Release Planning

- Calculate patch, minor, and major versions correctly.
- Reject a version already present in release history.
- Preview expected Release artifacts without modifying state.

### Packaging

- Build Docker images.
- Export the images into the Release.
- Generate the required Release directory structure.
- Generate a valid Release Manifest.
- Copy required scripts, configuration, database, documentation, and verification resources.
- Generate checksums.
- Generate the Compliance Report.
- Produce one finalized immutable Release.

### Failure Safety

- Preserve Project Version State after failure.
- Preserve previous finalized Releases.
- Return stable error codes.
- Produce useful logs.

### Finalization

- Move the Release into final output storage only after validation.
- Append the finalized version to Project Version State.
- Preserve Git traceability.
- Return a successful `PackagingResult`.

## 14. Final Packaging Engine Contract

The Packaging Engine shall expose a small deterministic CLI through which an engineer or Jenkins may initialize, inspect, plan, package, and validate an application repository.

Its main complete operation shall be:

```
package
```

The `package` operation shall coordinate all necessary internal work and return one structured `PackagingResult`.

The Packaging Engine shall be considered ready for implementation when:

- its public operations are fixed;
- its input and result objects are defined;
- its error model is defined;
- its state-safety rules are defined;
- its acceptance tests are defined.

At that point, implementation may proceed operation by operation without reopening the Packaging Engine’s fundamental behavior.
