# Part II — Offline Platform Specification

# 1. Purpose

The **RAH Offline Installation Platform** is the operational engine responsible for managing Application Releases inside the offline Debian environment.

Its purpose is to transform a compliant Application Release into a controlled, verified, and historically recorded deployment.

The Platform shall provide one shared backend engine used by two callers:

 
Web User Interface
        │
        ├──────────────┐
        ▼              ▼
Platform HTTP API   Jenkins
        │              │
        └──────┬───────┘
               ▼
       Platform Backend Engine
               ▼
      Lifecycle Scripts and Docker
 

The web interface and Jenkins shall not implement separate deployment logic.

They shall both invoke the same Platform backend operations through the Platform HTTP API.

The difference between them is only the caller:

- the **web UI** is used by a human operator;
- **Jenkins** is used for automated qualification and testing;
- both trigger the same underlying Platform engine;
- both receive the same structured operational results.

The Platform shall own the following responsibilities:

- discovering candidate Application Releases;
- validating whether a Release may be imported;
- registering Release metadata in the Platform Operational Registry;
- presenting known applications and Releases;
- determining which deployment operations are currently permitted;
- collecting and validating deployment configuration;
- installing an application;
- updating an existing deployment;
- verifying deployment correctness;
- creating and recording backups;
- performing supported recovery operations;
- inspecting actual Docker and host state;
- recording every operational attempt and result;
- maintaining the active deployment for each application;
- presenting deployment history and operational evidence.

The Platform shall consume the immutable Release Manifest, Compliance Report, checksum information, and lifecycle scripts supplied by the Application Release.

The Platform shall not:

- build application source code;
- build Docker images;
- create Application Releases;
- modify a Release Manifest;
- repair a malformed Release;
- generate engineering compliance evidence;
- invent application-specific installation commands;
- modify Git repositories;
- silently change lifecycle scripts;
- consider a Release installed merely because it was copied into Release Storage.

The Platform shall distinguish between:

 
Release discovered
Release imported
Release available
Deployment attempted
Deployment verified
Release active
 

These are separate operational states.

A Release becomes the active deployment only after:

1. the requested lifecycle script succeeds;
2. mandatory deployment verification succeeds;
3. the resulting operational state is successfully recorded.

The Platform database shall remember what the Platform attempted and what it last recorded as successful.

Actual host inspection and verification shall determine whether the machine still matches that recorded state.

The final responsibility of the Platform is therefore:

> **To provide one controlled operational engine through which a human operator or Jenkins may import, deploy, verify, inspect, and historically track compliant Application Releases inside the offline environment.**

The supporting Stage 4.5 document already establishes that the Platform specification must define its endpoint inventory, request and response objects, long-running-operation model, errors, Jenkins integration, and acceptance tests.

# 2. Platform Public Operations

The initial Platform shall expose the following public operations through its HTTP API.

The web frontend and Jenkins shall use these same operations.

 
Web UI button
        ↓
HTTP request
        ↓
Platform operation

Jenkins pipeline step
        ↓
HTTP request
        ↓
Same Platform operation
 

No public operation shall behave differently merely because it was triggered by the UI or Jenkins.

### 2.1 Operation Groups

The initial public operations are divided into seven groups:

 
1. Release Storage Operations
2. Application and Release Query Operations
3. Deployment Planning Operations
4. Deployment Execution Operations
5. Verification and Reconciliation Operations
6. Backup and Recovery Operations
7. Operation and History Query Operations
 

---

### 2.2 Release Storage Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`scan_releases`|Scan the configured incoming directory for candidate Releases|No permanent Release registration|No|
|`import_release`|Validate and register one candidate Release|Yes|Usually no|
|`list_rejected_releases`|Show candidates rejected during import|No|No|
|`refresh_release_storage`|Recheck whether known Release Packages still exist|Yes|No|
|`remove_release_from_storage`|Remove or mark a physical Release Package as unavailable while preserving history|Yes|No|

#### `scan_releases`

The operation shall:

- inspect the configured incoming Release directory;
- identify candidate Release folders;
- avoid treating incomplete copies as valid Releases;
- return discovered candidates;
- not install or activate anything.

#### `import_release`

The operation shall:

- parse the Release Manifest;
- verify the Compliance Report;
- verify Release checksums;
- verify supported Contract and Manifest versions;
- verify local architecture and infrastructure compatibility;
- detect conflicting Releases with the same application and version;
- register valid Release metadata;
- mark the Release as available.

Importing a Release shall not create a deployment record and shall not change the active Release.

---

### 2.3 Application and Release Query Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`list_applications`|List all applications known to the Platform|No|No|
|`get_application`|Return one application's identity and current operational state|No|No|
|`list_application_releases`|List imported Releases belonging to one application|No|No|
|`get_release`|Return one imported Release and its Manifest-derived metadata|No|No|
|`get_active_deployment`|Return the currently recorded active deployment|No|No|
|`get_available_actions`|Determine which actions are currently allowed|No|No|

#### `get_available_actions`

This operation shall determine whether the Platform may currently offer:

 
INSTALL
UPDATE
DOWNGRADE
REINSTALL
VERIFY
BACKUP
RECOVER
 

The decision shall use:

- whether an active deployment exists;
- the selected target Release;
- supported operations declared by the Release;
- transition rules;
- local compatibility;
- current operation locks;
- backup and recovery requirements.

A different version being available shall not automatically mean an update or downgrade is permitted.

---

### 2.4 Deployment Planning Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`prepare_installation`|Validate prerequisites and determine required inputs for fresh installation|No active-state change|No|
|`prepare_update`|Validate the transition from active Release to target Release|No active-state change|No|
|`validate_deployment_inputs`|Validate operator-supplied or generated configuration|No|No|
|`suggest_available_ports`|Suggest ports that appear free on the host|No|No|

#### `prepare_installation`

The result shall describe:

- selected Release;
- whether fresh installation is supported;
- required configuration inputs;
- generated values;
- operator-provided values;
- secret fields;
- port requirements;
- deployment path;
- expected services;
- backup requirements, where relevant;
- any blocking issue.

#### `prepare_update`

The result shall additionally describe:

- currently active Release;
- target Release;
- whether the transition is supported;
- state that must be preserved;
- database migration requirement;
- backup requirement;
- recovery capability;
- mandatory post-update checks.

Planning operations shall not execute lifecycle scripts.

---

### 2.5 Deployment Execution Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`install_application`|Perform a fresh installation|Yes|Yes|
|`update_application`|Transition an active application to another Release|Yes|Yes|
|`downgrade_application`|Perform an explicitly supported downgrade|Yes|Yes|
|`reinstall_application`|Recreate or repair the same Release when supported|Yes|Yes|
|`start_application`|Start a known deployed application|Operational state only|Usually no|
|`stop_application`|Stop a known deployed application|Operational state only|Usually no|
|`restart_application`|Restart a known deployed application|Operational state only|Usually no|

#### `install_application`

The operation shall:

1. create a deployment-attempt record;
2. validate the target Release;
3. validate deployment inputs;
4. prepare runtime configuration;
5. invoke the Manifest-declared installation entry point;
6. capture script output and exit status;
7. execute mandatory verification;
8. record the result;
9. mark the deployment active only after complete success.

#### `update_application`

The operation shall:

1. identify the current active deployment;
2. verify transition compatibility;
3. preserve existing deployment configuration and secrets;
4. create or verify the required backup;
5. invoke the Manifest-declared update entry point;
6. capture migration and execution results;
7. execute mandatory verification;
8. activate the target Release only after success;
9. preserve the previous deployment in history.

If update fails, the previous successful active-deployment record shall remain unchanged.

#### Downgrade and reinstall

These operations shall be available only when explicitly declared as supported by the target Release.

The Platform shall not infer downgrade safety from semantic-version ordering.

---

### 2.6 Verification and Reconciliation Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`verify_deployment`|Execute the Release-declared verification procedure|Records verification|Yes|
|`inspect_host_state`|Inspect actual Docker, port, path, and service state|No active-state change|Usually no|
|`reconcile_application_state`|Compare recorded state with actual host state|Records drift result|No/medium|
|`list_verification_runs`|Show previous verification executions|No|No|
|`get_verification_result`|Return one complete verification result|No|No|

#### `verify_deployment`

Verification may include:

- expected Release identity;
- expected Docker services;
- container health;
- backend health;
- frontend availability;
- database connectivity;
- migration state;
- persistent configuration;
- selected ports;
- offline runtime;
- required operational documentation.

Verification success shall not erase previous failed verification runs.

#### `reconcile_application_state`

This operation shall compare:

 
Platform Registry state
        ↕
Actual host state
 

It shall detect conditions such as:

- missing expected containers;
- wrong image tag;
- wrong Compose project;
- missing deployment path;
- unexpected port state;
- failed health check;
- configuration mismatch.

Detected drift shall be reported explicitly and shall not silently rewrite history.

### 2.7 Backup and Recovery Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`create_backup`|Create a declared application or database backup|Yes|Yes|
|`verify_backup`|Verify backup existence and integrity|Yes|Yes|
|`list_backups`|List known backups for an application|No|No|
|`restore_backup`|Restore a selected backup through a supported entry point|Yes|Yes|
|`recover_application`|Execute a declared recovery procedure|Yes|Yes|

#### `create_backup`

The operation shall record:

- application;
- active Release;
- backup type;
- related deployment operation;
- storage path;
- creation result;
- checksum where available;
- verification state.

#### `restore_backup`

The Platform shall not treat restoration as an ordinary update.

The operation shall:

- create a separate recovery-attempt record;
- invoke only the approved restore entry point;
- verify the resulting application and database state;
- record whether recovery succeeded;
- preserve the full previous history.

### 2.8 Operation and History Query Operations

|Operation|Purpose|Changes Platform state?|Long-running?|
|---|---|---|---|
|`get_operation`|Return current or final state of one operation|No|No|
|`list_operations`|List Platform operations using filters|No|No|
|`get_operation_events`|Return the ordered event timeline for an operation|No|No|
|`get_operation_logs`|Return or reference sanitized operation logs|No|No|
|`list_deployment_history`|Show all deployment attempts for an application|No|No|

Conceptually:

 
{
  "operation_id": "uuid",
  "operation_type": "INSTALL",
  "status": "PENDING"
}
 

The UI or Jenkins shall then call:

 
get_operation(operation_id)
 

until the operation reaches a terminal state.

Initial terminal states:

 
SUCCEEDED
FAILED
CANCELLED

# 3. Platform Internal Workflows

The Offline Platform shall implement each public operation through a defined internal workflow.

A public API call shall not directly execute an arbitrary shell command.

Instead, the backend shall:

 
Receive request
        ↓
Validate request
        ↓
Check current Platform state
        ↓
Create operation record
        ↓
Execute the approved workflow
        ↓
Verify the result
        ↓
Commit the resulting operational state
        ↓
Return structured result
 

The internal workflow is the authoritative implementation of the Platform operation.

The web UI and Jenkins shall both invoke this same workflow through the HTTP API.

---

### 3.1 Common Operation Lifecycle

Every state-changing Platform operation shall follow this common lifecycle:

 
1. Accept request
2. Authenticate caller
3. Validate request structure
4. Resolve application and Release identities
5. Check operation prerequisites
6. Check operation lock
7. Create operation record
8. Mark operation as PENDING
9. Begin execution
10. Record ordered operation events
11. Execute the operation-specific stages
12. Run mandatory verification where applicable
13. Record success or failure
14. Commit permitted state changes
15. Release operation lock
16. Return or persist the final result
 

The common lifecycle shall apply to operations such as:

- Release import;
- installation;
- update;
- verification;
- backup;
- restoration;
- recovery.

Read-only query operations do not require an operation record unless their execution is long-running or produces evidence that must be retained.

---

### 3.2 Common Operation States

The initial external operation-state model shall use:

 
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED
 

The Platform may use more detailed internal stages while retaining the simpler external state.

For example:

 
External state:
RUNNING

Internal stage:
BACKING_UP
 

or:

 
External state:
RUNNING

Internal stage:
VERIFYING
 

The initial internal stages may include:

 
REQUEST_ACCEPTED
VALIDATING
PREPARING
BACKING_UP
EXECUTING_SCRIPT
VERIFYING
RECORDING_RESULT
RECOVERING
COMPLETED
 

A completed operation shall end in one terminal external state:

 
SUCCEEDED
FAILED
CANCELLED
 

---

### 3.3 Operation Locking

*Revised under Architecture V1 Gap 1 (Operation Identity Model, Solution A): the lock described below is implemented against `platform.operations` — `application_id` plus non-terminal `status` (`PENDING` or `RUNNING`) — covering every `operation_type`, not against the `deployments` table alone. This is what makes it possible for a running backup or verification to correctly block a concurrent update; see the Platform Operational Registry, §7.5.6.*

The Platform shall initially permit only one active state-changing operation per application.

For example, HCAT shall not be updated while another HCAT operation is:

- installing;
- updating;
- backing up;
- restoring;
- recovering;
- verifying as part of deployment.

The initial implementation should serialize all deployment-changing operations across the Platform if that substantially simplifies Version 1.

The operation lock shall be acquired before execution begins and released after:

- successful completion;
- recorded failure;
- cancellation;
- recovery completion.

A crashed or interrupted operation shall not leave an invisible permanent lock.

The Platform shall be able to identify and report stale operation locks.

### 3.4 Release Scan Workflow

The `scan_releases` operation shall execute:

 
Configured incoming directory
        ↓
List candidate directories
        ↓
Check candidate completeness
        ↓
Locate release.yaml
        ↓
Read basic identity
        ↓
Compare with known Release Storage records
        ↓
Return candidate list
 

Detailed sequence:

1. Resolve the configured incoming Release directory.
2. Confirm that the directory exists and is readable.
3. Enumerate direct candidate Release directories.
4. Ignore temporary or incomplete-transfer directories.
5. Confirm that each candidate contains `release.yaml`.
6. Read only the minimum identity information required for discovery.
7. Determine whether each candidate is:
    - new;
    - already imported;
    - changed unexpectedly;
    - previously rejected;
    - incomplete.
8. Return a structured scan result.

Scanning shall not:

- register a Release permanently;
- execute scripts;
- install applications;
- modify the candidate Release.

---

### 3.5 Release Import Workflow

The `import_release` operation shall execute:

 
Candidate Release
        ↓
Parse Manifest
        ↓
Verify compliance evidence
        ↓
Verify checksums
        ↓
Check Platform compatibility
        ↓
Detect identity conflict
        ↓
Register application and Release
        ↓
Mark Release AVAILABLE
 

Detailed sequence:

1. Resolve the candidate Release path.
2. Confirm that the path belongs to configured Release Storage.
3. Locate and safely parse `release.yaml`.
4. Validate the Manifest schema version.
5. validate the Release Contract version;
6. locate and read the Compliance Report;
7. require a successful compliance result;
8. verify the Release checksum set;
9. calculate or verify the Release fingerprint;
10. verify architecture compatibility;
11. verify minimum Platform or RAH-OIP compatibility;
12. verify declared shared-service requirements;
13. find or create the application record by stable slug;
14. detect whether the same application and version already exist;
15. reject different artifacts claiming the same identity;
16. store immutable Release metadata;
17. create or update the Release Storage record;
18. mark the Release as `AVAILABLE`;
19. record the import result.

Import failure shall not create a partially valid Release record.

Rejected candidate information may be preserved separately for diagnosis.

---

### 3.6 Installation Preparation Workflow

The `prepare_installation` operation shall execute:

 
Available Release
        ↓
Check no active deployment
        ↓
Check fresh-install support
        ↓
Read configuration declarations
        ↓
Resolve generated and fixed values
        ↓
Request operator values
        ↓
Check ports and paths
        ↓
Return Installation Plan
 

Detailed sequence:

1. Resolve the target Release.
2. Confirm that the Release is `AVAILABLE`.
3. Confirm that it supports fresh installation.
4. confirm that the application has no conflicting active deployment;
5. inspect declared configuration inputs;
6. determine which values are:
    - fixed;
    - generated;
    - supplied by the operator;
    - supplied by Platform configuration;
7. inspect requested ports;
8. suggest valid available ports where applicable;
9. determine the canonical deployment path;
10. determine expected Docker services;
11. determine database initialization requirements;
12. determine mandatory verification checks;
13. return a complete installation plan.

Preparation shall not execute installation scripts.

---

### 3.7 Installation Workflow

The `install_application` operation shall execute:

 
Validated Installation Request
        ↓
Create deployment attempt
        ↓
Prepare configuration
        ↓
Invoke install script
        ↓
Capture execution result
        ↓
Run mandatory verification
        ↓
Commit active deployment
 

Detailed sequence:

1. Validate the installation request.
2. Recheck that the target Release remains available and intact.
3. Recheck ports immediately before execution.
4. Acquire the application operation lock.
5. Create a deployment-attempt record.
6. Set operation state to `RUNNING`.
7. store non-secret configuration values and secret references;
8. prepare production configuration files;
9. prepare the canonical deployment directory;
10. invoke the Manifest-declared installation script;
11. capture standard output, standard error, and exit code;
12. stop if the lifecycle script fails;
13. create a verification run;
14. invoke the Manifest-declared verification operation;
15. evaluate all mandatory verification checks;
16. if verification passes:
    - mark deployment `SUCCEEDED`;
    - set it as the application's active deployment;
    - record completion time;
17. if verification fails:
    - mark deployment `FAILED`;
    - do not mark it active;
    - retain diagnostic evidence;
18. release the operation lock;
19. return the final operation result.

The active deployment reference shall change only in the successful database transaction after verification.

---

### 3.8 Update Preparation Workflow

The `prepare_update` operation shall execute:

 
Active deployment
        +
Target Release
        ↓
Validate transition
        ↓
Determine preserved state
        ↓
Determine migration
        ↓
Determine backup
        ↓
Return Update Plan
 

Detailed sequence:

1. Resolve the active deployment.
2. Resolve the selected target Release.
3. confirm that update is supported;
4. compare current and target versions;
5. validate accepted source-version rules;
6. check infrastructure compatibility;
7. determine persistent state that must survive;
8. determine whether database migration is required;
9. determine whether backup is mandatory;
10. determine available recovery behavior;
11. load existing non-secret configuration and secret references;
12. identify any new required configuration inputs;
13. return a complete update plan.

Preparation shall not modify the active deployment.

---

### 3.9 Update Workflow

The `update_application` operation shall execute:

 
Validated Update Request
        ↓
Create update attempt
        ↓
Create required backup
        ↓
Preserve configuration
        ↓
Invoke update script
        ↓
Run verification
        ↓
Commit target as active
 

Detailed sequence:

1. Revalidate source and target Releases.
2. Revalidate the transition.
3. acquire the application lock;
4. create an update-attempt record containing source and target Releases;
5. create the required backup;
6. stop if mandatory backup fails;
7. preserve persistent configuration and secrets;
8. invoke the Manifest-declared update script;
9. capture script result and migration evidence;
10. stop normal progression if the update script fails;
11. run mandatory verification against the target Release;
12. if verification succeeds:
    - mark the update `SUCCEEDED`;
    - mark the target deployment active;
    - preserve the previous deployment record;
13. if execution or verification fails:
    - mark the attempt `FAILED`;
    - preserve the previous successful active-deployment record;
    - report whether recovery is required;
14. optionally initiate an explicitly supported recovery workflow;
15. release the lock;
16. return the result.

The Platform shall not treat loading older images as sufficient rollback of application or database state.

---

### 3.10 Verification Workflow

The `verify_deployment` operation shall execute:

 
Expected Release state
        +
Recorded Platform state
        +
Actual host state
        ↓
Execute declared verification
        ↓
Record individual checks
        ↓
Return Verification Result
 

Detailed sequence:

1. Resolve the application and expected Release.
2. create a verification-run record;
3. inspect the canonical deployment path;
4. inspect the expected Compose project;
5. inspect expected containers and image tags;
6. inspect configured ports;
7. invoke the Release-declared verification script;
8. parse structured verification output where available;
9. record each verification check separately;
10. classify the verification run as `PASS` or `FAIL`;
11. return the verification result.

A verification run shall not erase previous runs.

Manual verification failure shall report drift or operational failure but shall not automatically rewrite the active-deployment history.

---

### 3.11 Host Reconciliation Workflow

The `reconcile_application_state` operation shall execute:

 
Platform recorded state
        ↓
Inspect actual machine
        ↓
Compare expected and observed
        ↓
Record drift findings
 

The comparison shall include, where applicable:

- deployment path;
- active Release identity;
- Compose project name;
- expected container names;
- image names and tags;
- published ports;
- persistent configuration;
- service health;
- database migration state.

The result shall classify the application as, for example:

 
CONSISTENT
DRIFT_DETECTED
UNREACHABLE
PARTIALLY_RUNNING
UNKNOWN
 

Reconciliation shall not silently repair or normalize the host.

Repair or recovery shall require a separate explicit operation.

---

### 3.12 Backup Workflow

The `create_backup` operation shall execute:

 
Active deployment
        ↓
Resolve backup behavior
        ↓
Create backup record
        ↓
Invoke backup entry point
        ↓
Verify backup artifact
        ↓
Record result
 

Detailed sequence:

1. Resolve the active application deployment.
2. verify that backup behavior is available;
3. create a backup-attempt record;
4. invoke the Manifest-declared backup script;
5. capture the result;
6. locate the generated backup artifact;
7. calculate or verify its checksum where supported;
8. optionally run backup verification;
9. record the final backup state;
10. return a backup result.

---

### 3.13 Restore and Recovery Workflow

The `restore_backup` or `recover_application` operation shall execute:

 
Selected backup or recovery method
        ↓
Create recovery attempt
        ↓
Invoke approved restore/recovery script
        ↓
Verify resulting deployment
        ↓
Record recovery outcome
 

The Platform shall:

1. resolve the selected backup or recovery action;
2. validate that it belongs to the correct application;
3. acquire the application operation lock;
4. create a separate recovery operation record;
5. invoke only an approved declared entry point;
6. capture execution evidence;
7. run mandatory verification;
8. classify the recovery as successful or failed;
9. record the resulting operational state;
10. preserve all pre-recovery history.

Recovery shall never be hidden inside an ordinary update record.

---

### 3.14 Operation Event Recording

Each long-running operation shall create an ordered event timeline.

Example:

 
REQUEST_ACCEPTED
PREREQUISITES_VALIDATED
OPERATION_LOCK_ACQUIRED
BACKUP_STARTED
BACKUP_COMPLETED
SCRIPT_STARTED
SCRIPT_COMPLETED
VERIFICATION_STARTED
VERIFICATION_COMPLETED
ACTIVE_DEPLOYMENT_CHANGED
OPERATION_COMPLETED
 

Each event shall record:

- event type;
- event status;
- timestamp;
- sanitized message;
- structured details when useful.

The event timeline shall support:

- UI progress display;
- Jenkins polling;
- audit;
- failure diagnosis.

---

### 3.15 Common Failure Behavior

When a mandatory stage fails, the Platform shall:

1. stop subsequent unsafe stages;
2. record the failed stage;
3. capture sanitized error information;
4. preserve the previous successful active-deployment record;
5. avoid claiming success;
6. retain operation logs;
7. release locks safely;
8. expose whether retry or recovery is permitted;
9. return a structured failure result.

A failed operation shall not be deleted merely because a later retry succeeds.

# 4. Platform Request Objects

The Platform HTTP API shall use structured JSON request objects.

The web UI and Jenkins shall submit the same request structures.

The Platform API specification already identifies request and response schemas as a required deliverable of this layer.

---

## 4.1 Common Request Conventions

Every state-changing request may contain:

 
{
  "request_id": "optional-client-generated-uuid",
  "requested_by": "operator-or-automation-identity",
  "reason": "optional human-readable reason"
}
 

The backend shall generate the authoritative `operation_id`.

Requests shall use:

- JSON;
- UTF-8;
- ISO 8601 timestamps where dates are supplied;
- UUIDs for Platform database entities;
- stable application slugs;
- semantic application versions;
- boolean values rather than textual yes/no;
- explicit `null` only where allowed.

Requests shall not contain arbitrary shell commands.

Requests shall not contain raw Release Manifest replacements.

Secret values shall use dedicated protected fields and shall not be returned in ordinary responses.

---

## 4.2 `ScanReleasesRequest`

## 4.23 Caller Identity

Every state-changing request shall identify its caller.

Examples:

The backend shall derive the trusted caller identity from authentication where possible.

## 4.24 Request Idempotency

The Platform should support an optional client-generated request identifier for state-changing operations:

 
{
  "request_id": "uuid"
}
 

This allows Jenkins or the UI to safely retry a request after a network interruption without creating two deployments accidentally.

When the same authenticated caller repeats the same valid request identifier, the Platform should return the existing operation rather than start another one.

The initial implementation may support this first for:

- installation;
- update;
- backup;
- restore;
- recovery.

## 4.25 Request Validation Principle

Every request shall be validated at three levels:

 
1. Structural validation
   Is the JSON object correctly formed?

2. Referential validation
   Do the referenced application, Release, operation, and backup exist?

3. Operational validation
   Is this action permitted in the current state?
 

A structurally valid request may still be rejected operationally.

Example:

 
Valid JSON
+

# 5. Platform Result Objects

The Offline Platform shall return structured JSON results for every public operation.

The same result structures shall be used by:

- the Platform web frontend;
- Jenkins;
- future automation clients;
- integration tests.

The caller shall not need to inspect raw shell output to determine whether an operation succeeded.

The Platform backend shall translate internal workflow execution, lifecycle-script results, verification evidence, and Operational Registry state into stable result objects.

The Stage 4.5 specification requires the Platform to define both response schemas and a shared long-running-operation model.

---

## 5.1 Result Design Principles

Platform result objects shall follow these principles:

1. Every operation shall return a predictable structure.
2. Long-running requests shall return an operation reference immediately.
3. Final results shall distinguish execution success from deployment success.
4. Errors shall be structured rather than encoded only in text.
5. Secret values shall never be returned.
6. Historical results shall remain retrievable after completion.
7. The UI and Jenkins shall receive the same factual result.
8. Human-readable messages shall supplement, not replace, structured fields.
9. Result objects shall use stable identifiers.
10. Result schemas shall evolve through explicit interface versioning.

---

## 5.2 Shared API Response Envelope

Ordinary synchronous API responses shall use a common envelope:

  
{
  "success": true,
  "data": {},
  "warnings": [],
  "error": null,
  "request_id": "3d1fab06-b548-47e2-a841-569341c02e87",
  "timestamp": "2026-08-06T15:30:00+03:00"
}
  

Fields:

|Field|Type|Required|Meaning|
|---|---|---|---|
|  success  |Boolean|Yes|Whether the API request itself succeeded|
|  data  |Object, array, or null|Yes|Operation-specific response data|
|  warnings  |Array|Yes|Non-fatal warnings|
|  error  |Error object or null|Yes|Structured failure information|
|  request_id  |UUID|Yes|API request identity|
|  timestamp  |Date-time|Yes|Time the response was produced|

  success: true   means the immediate API request was accepted or completed successfully.

For long-running operations, it does not mean the deployment itself has already succeeded.

---

Operations such as installation, update, verification, backup, restore, and recovery shall normally run asynchronously.

When accepted, the API shall return:

## 5.5 Operation Statuses

The external operation status shall use:

  
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED
  

Meanings:

###   PENDING  

The request has been accepted but execution has not yet begun.

###   RUNNING  

The Platform is executing the operation.

###   SUCCEEDED  

All mandatory stages completed successfully.

For deployment operations, this means:

  
Lifecycle execution succeeded
+
Mandatory verification succeeded
+
Operational state was committed
  

###   FAILED  

A mandatory stage failed.

###   CANCELLED  

The operation was cancelled before successful completion.

The initial Platform may not permit cancellation of every operation.

PREPARING
BACKING_UP
EXECUTING_SCRIPT

RECORDING_RESULT

The Platform may add operation-specific stages later.

Unknown future stages shall not change the meaning of the main operation status.

# 6. Platform HTTP API Contract

## 6.1 Purpose

The Platform HTTP API is the single external invocation interface for the Platform backend engine.

It shall be used by:

  
Platform web frontend
Jenkins
Approved automation clients
Integration tests
  

The API shall not implement separate behavior for the UI and Jenkins.

Both shall call the same endpoints and receive the same object schemas.

  
Web UI button
        ↓
HTTP endpoint
        ↓
Platform backend operation

Jenkins pipeline command
        ↓
Same HTTP endpoint
        ↓
Same Platform backend operation
  

The difference between callers belongs to authentication, permissions, and presentation—not deployment logic.

---

## 6.2 API Base Path

The initial API base path shall be:

  
/api/v1
  

Example:

  
http://rah-platform.local/api/v1/applications
  

The   /v1   path identifies the Platform HTTP interface version.

It is not:

- the Platform product version;
- the Release Contract version;
- the Application Release version.

---

## 6.3 Transport

The initial air-gapped Platform may support HTTP inside the controlled local environment.

Where HTTPS is available through the internal infrastructure, it should be used.

The API contract itself shall not depend on whether transport is:

  
HTTP
or
HTTPS
  

Jenkins and the UI shall use the configured Platform API base URL.

# 7. Platform State Rules

The Offline Platform shall preserve a consistent operational state across Release import, installation, update, verification, backup, recovery, and host reconciliation.

These rules are **Platform invariants**.

They describe conditions that must remain true regardless of whether the operation was initiated by:

- the web UI;
- Jenkins;
- another approved API client;
- an internal Platform process.

The Platform database schema, backend logic, API behavior, and automated tests shall enforce these rules together.

---

## 7.1 State Authority Model

The Platform shall preserve the distinction between three kinds of truth:

 
Release Manifest
→ What the immutable Release declares

Platform Operational Registry
→ What the Platform attempted and last recorded successfully

Actual Host State
→ What is currently running on the Debian machine
 

No one layer shall silently replace another.

The Release Manifest shall not be modified to reflect deployment outcomes.

The Operational Registry shall not claim that the host is healthy without verification evidence.

Host inspection shall not erase or rewrite deployment history.

---

## 7.2 Application Identity Rule

Every application shall have one stable machine identity:

 
application.slug
 

The slug shall connect:

 
Project Version State
        ↓
Release Manifest
        ↓
Platform application record
        ↓
Canonical deployment path
        ↓
Docker Compose project identity
 

The Platform shall not identify applications only through:

- display name;
- port number;
- container name;
- Release-directory name;
- database name.

The application slug shall remain stable across Releases.

---

## 7.3 Release Identity Rule

An imported Release shall be identified by at least:

 
application identity
+
Release version
+
Release fingerprint
 

For example:

 
hcat@1.1.0
fingerprint: sha256...
 

The Platform shall reject a candidate when:

- the same application and version already exist;
- the existing and incoming Release fingerprints differ.

Two different artifacts shall not be accepted as the same Release merely because they claim the same version.

---

## 7.4 Release Immutability Rule

After successful import, the Platform shall treat the Release Package as immutable.

The Platform shall not modify:

-  release.yaml ;
- Docker image archives;
- lifecycle scripts;
- database resources;
- configuration templates;
- verification resources;
- documentation;
- checksums;
- Compliance Report.

If a Release is invalid, it shall be rejected.

If engineering content must change, a new Release shall be created through the Packaging Engine.

---

## 7.5 Discovery, Import, and Deployment Separation

The Platform shall treat these as distinct states:

 
DISCOVERED
        ↓
IMPORTED / AVAILABLE
        ↓
DEPLOYMENT ATTEMPTED
        ↓
VERIFIED
        ↓
ACTIVE
 

The following rules apply:

1. Discovering a Release does not import it.
2. Importing a Release does not install it.
3. Running a lifecycle script does not by itself make the Release active.
4. A Release becomes active only after mandatory verification succeeds.
5. Copying files into Release Storage does not alter application deployment state.

---

## 7.6 Imported Release State Rule

An imported Release may have a storage state such as:

 
AVAILABLE
INTEGRITY_FAILED
IMPORT_REJECTED
REMOVED_FROM_STORAGE
 

Removing a physical Release Package from storage shall not delete:

- Release metadata;
- previous deployment records;
- verification history;
- backup references;
- historical operation records.

The Platform shall preserve the difference between:

 
Release known historically
 

and:

 
Release Package currently available for use
 

---

## 7.7 One Active Deployment Rule

Each application shall have at most one active deployment.

Conceptually:

 
Application
        ↓
0 or 1 active deployment
 

The Platform shall not permit:

 
HCAT 1.0.9 active
+
HCAT 1.1.0 active
 

at the same time under the same application identity.

Previous successful deployments remain in history but are not active.

---

## 7.8 Active Deployment Eligibility Rule

A deployment may become active only when all mandatory success conditions are satisfied:

 
Lifecycle script succeeded
+
Mandatory verification passed
+
Operational state committed successfully
 

The Platform shall not mark a deployment active because:

- Docker images were loaded;
- containers were created;
- containers started;
- the lifecycle script returned exit code  0 ;
- some verification checks passed.

All required checks must pass.

---

## 7.9 Active-State Transaction Rule

Changing the active deployment shall occur transactionally.

The Platform shall perform the equivalent of:

 
1. Set the operation's status to SUCCEEDED
2. Set application.active_deployment_id to the deployment linked via that operation's operation_id
3. Record completion evidence
4. Commit transaction
 

*(Revised under Architecture V1 Gap 1: `deployments` no longer has its own `status` field — "mark deployment successful" now means setting the linked `operations` row's `status` to `SUCCEEDED`. See the Platform Operational Registry, §7.5 and §8.)*

If the database transaction fails, the Platform shall not expose the target Release as active.

The active deployment reference and successful deployment record shall not contradict one another.

---

## 7.10 Failed Operation Preservation Rule

A failed operation shall remain in history.

The Platform shall preserve:

- operation type;
- application;
- source Release;
- target Release;
- failed stage;
- error code;
- lifecycle exit code;
- verification result;
- timestamps;
- logs;
- related backup and recovery attempts.

A later successful retry shall create a new operation.

It shall not rewrite the earlier failed record as successful.

---

## 7.11 Previous Active Deployment Protection

An unsuccessful installation or update shall not overwrite the last successfully recorded active deployment.

For update:

 
Active Release: 1.0.9
Target Release: 1.1.0
Update fails
        ↓
Recorded active Release remains 1.0.9
 

This rule describes database authority.

The actual machine may still require reconciliation or recovery if the failed operation partially changed host state.

---

## 7.12 Operation Attempt Rule

Every state-changing action shall create an operation record before performing irreversible work.

Examples:

- import;
- install;
- update;
- backup;
- restore;
- recovery.

The operation record shall initially represent an attempt, not success.

 
Request accepted
        ↓
Attempt record created
        ↓
Execution begins
 

This ensures that interruption or failure remains visible.

---

## 7.13 Operation Lock Rule

*The lock described below is implemented against `operations.application_id` and `operations.status`, covering every `operation_type` — not only rows in `deployments` (Architecture V1 Gap 1; see Platform Operational Registry §7.5.6 and §15 Rule 5).*

Only one conflicting state-changing operation may run for an application at a time.

The Platform shall reject or delay operations such as:

 
Update HCAT
+
Restore HCAT backup
 

or:

 
Install HCAT
+
Second install HCAT
 

The initial Platform may serialize all deployment-changing operations globally to reduce complexity.

Read-only queries may continue while an operation is running.

---

## 7.14 Stale Operation Rule

If the Platform process, machine, or backend stops unexpectedly, an operation may remain recorded as:

 
RUNNING
 

The Platform shall be able to detect that the operation is no longer executing.

It shall not leave the application permanently locked without explanation.

The initial recovery behavior may mark such an operation as:

 
FAILED
 

with an error such as:

 
PLT-OPERATION-INTERRUPTED
 

after the operator confirms or the Platform proves the execution was interrupted.

---

## 7.15 Configuration Preservation Rule

Application deployment configuration shall belong to operational state, not the immutable Release.

The Platform shall preserve required deployment-specific values during ordinary updates, including:

- selected ports;
- generated credentials;
- operator configuration;
- deployment paths;
- approved persistent settings.

The Release Manifest declares which inputs exist.

The Platform records the values selected for a particular deployment.

---

## 7.16 Secret-State Rule

The Platform shall not store secret values in ordinary deployment-history fields or logs.

For a secret configuration input, the Operational Registry may store:

 
Secret exists
Secret reference
Secret source
Last rotation or creation time
 

It shall not return the secret through ordinary query endpoints.

An update shall preserve existing secrets unless:

- the operator explicitly changes them;
- the Release requires regeneration;
- recovery requires replacement.

---

## 7.17 Port-State Rule

A selected port shall be recorded as part of the deployment configuration.

Port availability shall be checked:

1. during planning;
2. immediately before execution.

A port suggestion is not a reservation.

If the port becomes unavailable before installation, the Platform shall reject execution or require a new value.

The Platform shall not silently assign a different port without reporting it.

---

## 7.18 Deployment Path Rule

Every application shall have one stable canonical deployment path.

Recommended form:

 ```
  /opt/rah/apps/<application.slug>
 ```

 

A normal update shall reuse the same canonical application path.

Release versions shall not create unrelated permanent deployment paths unless the deployment architecture explicitly requires them.

The incoming Release directory shall not become the live deployment path.

---

## 7.19 Compose Identity Rule

Each application shall use one stable Docker Compose project name.

Recommended form:
```
rah-<application.slug>
```
 

 

The Compose identity shall not include the Release version.

This allows updates to replace application components while preserving one operational application identity.

---

## 7.20 Transition Rule

An update or downgrade is permitted only when a supported transition exists.

The Platform shall evaluate:

- active Release;
- target Release;
- supported operation;
- accepted source versions;
- infrastructure compatibility;
- migration requirements;
- backup requirements.

The Platform shall not infer transition safety only from version ordering.

For example:

 
1.0.9 → 1.1.0
 

may be supported, while:

 
1.0.2 → 1.1.0
 

may be unsupported.

---

## 7.21 Downgrade Rule

Downgrade shall be disabled unless explicitly supported.

A lower semantic version does not prove that deploying it is safe.

The Platform shall not assume that restoring older Docker images reverses:

- database migrations;
- configuration changes;
- persistent data transformations;
- filesystem changes.

Downgrade and recovery shall remain distinct operations.

---

## 7.22 Backup Requirement Rule

When a Release declares that backup is mandatory before update, the Platform shall not execute the update until a successful backup is recorded.

The Platform shall verify:

- backup creation succeeded;
- the backup artifact exists;
- required integrity evidence is available.

The Platform may require backup verification when declared by policy.

---

## 7.23 Backup Ownership Rule

A backup shall be associated with:

- one application;
- the deployment state from which it was created;
- the operation that requested it, where applicable;
- its backup type;
- creation time;
- storage location;
- integrity state.

A backup from one application shall not be restored into another application through ordinary Platform operation.

---

## 7.24 Recovery History Rule

Recovery shall create a separate operation record.

The Platform shall preserve:

 
Failed update
        ↓
Recovery attempt
        ↓
Recovery result
 

It shall not collapse these into one rewritten deployment record.

The history must show both the failure and the attempted correction.

---

## 7.25 Verification History Rule

Every verification run shall be preserved independently.

The Platform shall record:

- expected Release;
- verification type;
- individual checks;
- check results;
- evidence;
- start and completion times;
- final verification result.

A later passing verification shall not erase an earlier failure.

---

## 7.26 Verification-to-Activation Rule

Verification executed as part of installation or update shall directly control whether activation is permitted.

A manual verification performed later may:

- confirm health;
- detect drift;
- record failure.

It shall not silently change which Release is recorded as active unless a distinct deployment or recovery operation justifies that change.

---

## 7.27 Host Drift Rule

The Platform shall distinguish between:

 
Recorded operational state
 

and:

 
Observed host state
 

If they differ, the Platform shall record or report drift.

Examples:

- wrong image tag;
- missing container;
- unexpected stopped service;
- changed port;
- missing deployment directory;
- unexpected database migration state.

The Platform shall not silently modify historical state to make the mismatch disappear.

---

## 7.28 Query Consistency Rule

Application, Release, deployment, operation, verification, and backup query results shall derive from consistent relationships.

For example:

- an active deployment must belong to its application;
- its target Release must belong to the same application;
- its verification run must refer to the expected Release;
- its backup must belong to the same application;
- an update source and target Release must belong to the same application.

The backend shall enforce these rules even when database foreign keys alone cannot express them fully.

---

## 7.29 UI and Jenkins Consistency Rule

The UI and Jenkins shall observe the same Platform state.

The Platform shall not maintain:

 
UI deployment state
 

and a separate:

 
Jenkins deployment state
 

Both clients shall read from the same Operational Registry and operation API.

The same operation identifier shall return the same factual status to both callers.

---

## 7.30 State Rule Acceptance Criteria

The Platform state model is acceptable when tests prove:

1. Import does not activate a Release.
2. Failed installation does not create an active deployment.
3. Successful installation activates exactly one deployment.
4. Failed update preserves the previous active record.
5. Successful update changes the active deployment transactionally.
6. Duplicate Release identity with a different fingerprint is rejected.
7. Deployment history survives removal of a Release Package.
8. Verification history is append-only.
9. Recovery is recorded separately from failure.
10. Conflicting operations are prevented.
11. Secrets are not returned through ordinary APIs.
12. Drift is reported without rewriting history.
13. UI and Jenkins receive the same operation state.

---

## 7.31 Final State Principle

The Platform shall preserve one coherent operational history.

It shall clearly distinguish:

 
What Release declared
What the Platform attempted
What the Platform recorded as successful
What the host currently shows
 

A state transition shall occur only through an explicit Platform operation and shall remain historically traceable.

---

- web UI messages;
- Jenkins execution;
- operation records;
- deployment history;
- logs;
- integration tests.

  "log_reference": null

|Field|Type|Required|Meaning|
|---|---|---|---|

# 9. Operational Safety Rules

## 9.1 Purpose

The Operational Safety Rules define how the Offline Platform shall prevent incomplete, contradictory, destructive, or falsely successful deployment operations.



These rules apply regardless of whether an operation is initiated through:

- the Platform web interface;
- Jenkins;
- another approved API client;
- an internal Platform procedure.

The Platform shall prioritize:

  
Correctness
    ↓
Recoverability
    ↓
Traceability
    ↓
Convenience
  

An operation shall fail visibly rather than claim success without sufficient evidence.

---

## 9.2 Controlled Operation Rule

The Platform backend shall execute only operations explicitly supported by the Platform and declared by the selected Release.

Permitted operation categories include:

  
IMPORT
INSTALL
UPDATE
VERIFY
BACKUP
RESTORE
RECOVER
  

Optional operations may include:

  
DOWNGRADE
REINSTALL
START
STOP
RESTART
  

The frontend and API shall not accept arbitrary shell commands.

The Platform shall map each approved operation to:

- a Platform-owned workflow;
- the appropriate Manifest-declared lifecycle entry point;
- the required validation and recording behavior.

---

## 9.3 Manifest-Declared Entrypoint Rule

The Platform shall invoke application-specific lifecycle behavior only through entry points declared by the immutable Release Manifest.

Examples:

  
scripts/install_offline.sh
scripts/update_offline.sh
scripts/verify_deployment.sh
scripts/backup_database.sh
scripts/restore_database.sh
  

The Platform shall not:

- search for substitute scripts;
- invent missing commands;
- modify lifecycle scripts;
- execute a similarly named undeclared script;
- construct application-specific deployment commands to compensate for an incomplete Release.

If a required entry point is absent or invalid, the operation shall fail.

---

## 9.4 Release Integrity Before Execution

Before any deployment-changing operation, the Platform shall recheck that the selected Release still matches its imported identity.

The Platform shall verify, where applicable:

- Release Package presence;
- Release fingerprint;
- Manifest checksum;
- lifecycle-script checksums;
- required Docker archives;
- required configuration and database resources.

A Release whose integrity changed after import shall not be executed.

The Platform shall return an integrity error and require re-import or engineering investigation.

---

## 9.5 Precondition Revalidation Rule

Planning results shall not be treated as permanent permission to execute.

Immediately before installation or update, the Platform shall revalidate:

- Release availability;
- Release integrity;
- application state;
- active deployment;
- supported transition;
- operation lock;
- selected ports;
- required paths;
- Docker availability;
- required backup capability;
- required configuration values.

This prevents stale plans from executing after machine state changes.

---

## 9.6 Attempt-Before-Execution Rule

The Platform shall create an operation or deployment-attempt record before beginning irreversible work.

The sequence shall be:

  
Validate request
        ↓
Create attempt record
        ↓
Acquire operation lock
        ↓
Begin execution
  

If the backend or machine stops during execution, the interrupted attempt remains visible in the Operational Registry.

The Platform shall never perform a deployment-changing action with no corresponding operation record.

---

## 9.7 Application Operation Lock

The Platform shall prevent conflicting operations against the same application.

While an application operation is active, conflicting requests shall be rejected or delayed.

Examples of prohibited concurrency:

  
UPDATE + UPDATE
INSTALL + INSTALL
UPDATE + RESTORE
BACKUP + RESTORE
RECOVERY + UPDATE
  

The initial implementation may use one global deployment lock across the entire Platform if this substantially reduces complexity. *The lock is implemented against `operations.application_id` and `operations.status` (Architecture V1 Gap 1) — this is what makes it possible to enforce `BACKUP + RESTORE` and `RECOVERY + UPDATE` conflicts above, which span operation types beyond `deployments`.*

The lock shall not block ordinary read-only queries.

---

## 9.8 Lock Recovery Rule

An operation lock shall have an identifiable owner and related operation ID.

The Platform shall record:

- locked application;
- operation ID;
- lock creation time;
- backend worker identity where applicable;
- last known operation state.

After interruption, the Platform shall detect stale locks.

A stale lock shall not be deleted silently. The related operation shall first be classified and recorded as interrupted, failed, or requiring investigation.

---

## 9.9 Temporary Workspace Rule

Deployment preparation shall use controlled temporary or staging locations.

The Platform shall not assemble an installation directly inside the final canonical deployment path before validation is complete unless the lifecycle design specifically requires it.

Temporary work shall be associated with the operation ID.

Example:

  ``` 
  /opt/rah/work/<operation-id>/
  ```

  

After completion:

- temporary resources may be removed;
- diagnostic resources may be retained when failure occurs;
- finalized operational state shall live only in approved paths.

Temporary work shall not become a second permanent deployment truth.

---

## 9.10 Canonical Deployment Path Protection

The Platform shall deploy an application only to its approved canonical path.

Recommended form:
```
 /opt/rah/apps/<application-slug>/
```
  

  

The Platform shall reject paths that:

- escape the approved application root;
- contain path traversal;
- point to Release Storage;
- overlap another application's deployment;
- target system-critical directories;
- contradict the imported Manifest without approved migration behavior.

The incoming Release directory shall remain separate from the live deployment directory.

---

## 9.11 Configuration Generation Safety

The Platform shall generate deployment configuration from:

- Manifest-declared fields;
- operator-provided values;
- generated values;
- preserved operational configuration;
- approved Platform-level configuration.

The Platform shall not silently invent required application-specific values.

Before execution, generated configuration shall be validated against the declared input types and constraints.

Configuration files shall be written atomically where practical.

A partially written configuration file shall not replace a previously valid production configuration.

---

## 9.12 Secret Handling Safety

Secret values shall be masked in:

- API responses;
- UI views;
- operation events;
- ordinary logs;
- database history;
- error details.

The Platform shall not pass secrets as visible command-line arguments when a safer mechanism is available.

Preferred mechanisms include:

- protected environment files;
- standard input;
- restricted temporary files;
- environment variables supplied to the controlled subprocess.

Temporary secret-bearing files shall use restrictive permissions and shall be removed when no longer needed.

The immutable Release Package shall not be modified to store production secrets.

---

## 9.13 Port Assignment Safety

The Platform shall validate port values structurally during planning and inspect actual availability before execution.

A suggested port is provisional.

The Platform shall not:

- silently replace an operator-selected port;
- reuse a port recorded for another active application;
- assume a previously available port is still free;
- declare success without verifying expected service availability.

If a conflict appears before execution, the operation shall stop before lifecycle scripts run.

---

## 9.14 Docker Command Safety

The backend may invoke Docker and Docker Compose commands required by approved Platform workflows.

Docker commands shall be constructed by Platform code from trusted internal values.

The API caller shall not provide raw Docker command fragments.

The Platform shall control:

- Compose project name;
- Compose file path;
- deployment directory;
- image archive paths;
- expected image names and tags;
- permitted lifecycle operation.

Every Docker invocation shall capture:

- command category;
- start time;
- completion time;
- exit code;
- sanitized output;
- related operation ID.

---

## 9.15 Lifecycle Script Execution Safety

Before running a lifecycle script, the Platform shall verify:

- the path is declared in the Manifest;
- the path remains inside the Release;
- the file exists;
- the file has appropriate permissions;
- the Release integrity check passed;
- the operation is supported;
- required inputs are available.

The Platform shall execute the script with:

- a known working directory;
- a controlled environment;
- a defined timeout;
- captured standard output;
- captured standard error;
- an operation-specific log.

A script timeout shall be treated as failure.

The Platform shall not assume that terminating the script automatically restores the previous host state.

---

## 9.16 Script Exit and Deployment Success Separation

A lifecycle script returning exit code   0   means only:

> The script reports that its execution completed successfully.

It does not by itself mean:

> The deployment is operationally successful.

The Platform shall require:

  
Script success
+
Mandatory verification success
+

Deployment success
  

A successful script followed by failed verification shall produce a failed deployment operation.

---

## 9.17 Mandatory Verification Rule

Fresh installation and update shall always execute mandatory verification.

The caller shall not be allowed to disable required verification merely by sending:

  
{
  "verify_after_install": false
}
  

or:

  
{
  "verify_after_update": false
}
  

If the Release Contract or Manifest declares verification mandatory, such a request shall be rejected.

The Platform shall not activate an unverified deployment.

---

## 9.18 Verification Evidence Rule

Verification shall produce structured evidence.

At minimum, the Platform shall preserve:

- verification-run ID;
- expected Release;
- verification type;
- individual check identifiers;
- PASS/FAIL status;
- human-readable explanation;
- structured evidence where available;
- start and completion times.

The Platform shall not rely exclusively on one unstructured log line such as:

  
Everything looks good.
  

---

## 9.19 Backup-Before-Update Rule

When backup is mandatory, the Platform shall create and record the backup before executing the update script.

The update shall not begin until the backup satisfies required conditions.

These may include:

- backup script succeeded;
- backup artifact exists;
- checksum was calculated;
- basic integrity verification passed.

If mandatory backup fails, the update shall stop.

---

## 9.20 Backup Isolation Rule

Backup artifacts shall be stored outside:

- the immutable Release Package;
- temporary deployment workspaces;
- replaceable application container filesystems.

Recommended conceptual location:

  ```
  /opt/rah/backups/<application-slug>/
  ```

  

A backup shall have an identity independent from the deployment operation that created it.

Removing an old Release Package shall not remove its related backup automatically.

---

## 9.21 Update Preservation Rule

Before update, the Platform shall identify state that must survive, including where applicable:

- production configuration;
- generated credentials;
- database data;
- Docker volumes;
- uploaded files;
- certificates;
- selected ports;
- operational documentation;
- deployment history.

The Platform shall not replace persistent state merely because a new Release contains new application artifacts.

Update behavior shall distinguish:

  
Replaceable application artifacts
  

from:

  
Persistent operational state
  

---

## 9.22 Failed Update Rule

If an update script or mandatory verification fails, the Platform shall:

1. mark the update attempt as failed;
2. preserve the previous successful active-deployment record;
3. record the actual failed stage;
4. retain logs and verification evidence;
5. determine whether host state may have changed;
6. report whether recovery is required;
7. prevent automatic activation of the target Release.

The Platform shall not falsely claim that the host remains unchanged.

The database record and actual host state may temporarily disagree, which shall trigger reconciliation or recovery.

---

## 9.23 No Automatic Destructive Rollback

The Platform shall not automatically perform a destructive rollback merely because an update failed.

Automatic recovery may occur only when:

- the recovery procedure is explicitly supported;
- required backup evidence exists;
- the procedure has been designed and tested;
- the resulting deployment will be verified;
- the action is recorded separately.

Otherwise, the Platform shall report:

  
RECOVERY_REQUIRED
  

and await an explicit recovery operation.

---

## 9.24 Recovery Safety

A recovery operation shall:

- reference the failed operation;
- reference the selected backup or previous state;
- validate application identity;
- use an approved recovery entry point;
- create its own operation record;
- acquire the application lock;
- run mandatory verification;
- preserve both failure and recovery history.

Recovery success shall not erase evidence of the incident that required it.

---

## 9.25 Database Transaction Safety

Operational Registry changes shall use database transactions where multiple records must remain consistent.

Examples include:

- importing Release metadata and storage state;
- completing deployment and changing active deployment;
- recording backup success;
- committing verification and deployment outcome.

If a transaction fails, the Platform shall not expose a partially committed operational truth.

The host may still require reconciliation if external execution succeeded before the database transaction failed.

---

## 9.26 Database Migration Safety

When application database migration is required, the Platform shall:

- verify that the update declares migration behavior;
- verify mandatory backup first;
- invoke only the declared migration mechanism;
- capture migration evidence;
- verify the target migration state;
- treat target-state mismatch as deployment failure.

The Platform shall not assume that restarting containers completes database migration.

---

## 9.27 Release Storage Safety

The Platform shall not import a candidate while it is still being transferred.

A transfer process should use a temporary name or staging marker such as:

  
HCAT_Release_1.1.0.partial
  

and rename or mark it complete only after transfer finishes.

The scanner shall ignore incomplete candidates.

The Platform shall verify integrity again after transfer and before import.

---

## 9.28 Logging Safety

Every state-changing operation shall produce a diagnostic log associated with its operation ID.

Logs shall record enough information to reconstruct:

- what operation was requested;
- what application and Release were involved;
- which stages ran;
- which entry point was executed;
- what result occurred;
- which verification checks passed or failed.

Logs shall not contain secrets.

Log-write failure shall be reported when it prevents required auditability.

---

## 9.29 API Safety

The API shall enforce:

- schema validation;
- authentication;
- authorization;
- operation-state validation;
- application and Release relationship validation;
- idempotency where supported;
- request-size limits;
- safe error serialization.

The UI shall not be trusted merely because it is the official frontend.

Jenkins and the UI shall pass through the same backend validations.

---

## 9.30 Idempotency Safety

For supported state-changing endpoints, an   Idempotency-Key   shall prevent accidental duplicate operations.

Example:

  
Jenkins sends install request
        ↓
Network response is lost
        ↓
Jenkins retries with same key
        ↓
Platform returns existing operation
  

The Platform shall not create two installation attempts for the same retried request.

Idempotency shall not allow a client to reuse the same key for a materially different request.

---

## 9.31 Cancellation Safety

The initial Platform may support limited cancellation.

Cancellation shall not be offered for an operation after it has entered a stage where interruption could produce undefined state unless a safe cancellation mechanism exists.

The Platform shall distinguish:

  
Cancellation requested
  

from:

  
Cancellation completed safely
  

A killed process shall not automatically be classified as a safely cancelled deployment.

---

## 9.32 Restart and Crash Safety

After backend or host restart, the Platform shall inspect operations previously marked:

  
PENDING
RUNNING
  

It shall determine whether:

- execution never began;
- execution was interrupted;
- the process is still active;
- host changes occurred;
- reconciliation is required.

The Platform shall not automatically mark every interrupted operation successful or failed without evidence.

Version 1 may require operator confirmation after presenting the known evidence.

---

## 9.33 Disk-Space Safety

Before copying, extracting, loading, backing up, or deploying large artifacts, the Platform should verify sufficient available disk space.

The check should consider:

- Release Package size;
- extracted deployment resources;
- Docker image load requirements;
- backup size;
- temporary workspace;
- operational safety margin.

Insufficient disk space shall stop the operation before destructive changes where possible.

---

## 9.34 Physical Media Safety

For production transfer through USB or DVD, the Platform shall treat the copied Release as untrusted until:

- it is fully copied into approved Release Storage;
- checksum validation succeeds;
- Release fingerprint is verified;
- compliance and compatibility checks pass.

The Platform shall not execute lifecycle scripts directly from removable media.

---

## 9.35 Safety Event Visibility

When safety rules prevent an operation, the Platform shall explain:

- which rule blocked execution;
- what state was observed;
- what condition was expected;
- whether the user can correct and retry;
- whether engineering work is required.

Example:

  
Update blocked.

Reason:
Mandatory database backup could not be verified.

Target Release:
HCAT 1.1.0

Active Release:
HCAT 1.0.9

Host state changed:
No

Retry permitted:
Yes
  

---

## 9.36 Operational Safety Principle

The Platform shall never trade correctness and traceability for apparent automation.

The governing safety rule is:

> **No deployment-changing action is considered complete until its prerequisites, execution, verification, and operational recording have all succeeded.**

---

# 10. Platform Acceptance Criteria

## 10.1 Purpose

The Acceptance Criteria define the concrete finish line for the first usable Offline Platform.

The Platform shall not be considered complete merely because:

- the UI loads;
- the API responds;
- the database exists;
- Docker commands can be executed;
- an application container starts.

The Platform Version 1 is complete when it demonstrates the required end-to-end operational behavior reliably and repeatedly.

---

## 10.2 Acceptance-Test Environment

Acceptance testing shall use the Offline Validation VM.

The environment shall contain:

- Debian;
- Docker Engine and Docker Compose;
- the Platform frontend;
- the Platform backend;
- PostgreSQL Operational Registry;
- configured Release Storage;
- at least two compatible HCAT Releases;
- a clean baseline or reproducible reset mechanism.

Recommended test Releases:

  
HCAT 1.0.0
HCAT 1.1.0
  

or another pair where:

  
1.0.0 → 1.1.0
  

is an explicitly supported update transition.

The same finalized Release artifacts used in testing shall remain identifiable by fingerprint.

---

## 10.3 Platform Startup Acceptance

The Platform shall:

1. start through its approved Docker Compose deployment;
2. connect to PostgreSQL;
3. access configured Release Storage;
4. confirm Docker Engine availability;
5. expose frontend and API;
6. return successful liveness;
7. return successful readiness when dependencies are available.

Required checks:

  
GET /api/v1/health/live
→ UP

GET /api/v1/health/ready
→ READY
  

If PostgreSQL or Docker is unavailable, readiness shall fail clearly.

---

## 10.4 Shared Backend Acceptance

The web UI and Jenkins/API client shall invoke the same backend operations.

The test shall prove:

1. an operation initiated from the UI creates a normal Platform operation record;
2. an equivalent API request creates the same type of record;
3. both expose the same operation statuses;
4. both use the same error model;
5. neither bypasses Platform validation;
6. neither executes lifecycle scripts independently.

There shall be no separate UI deployment engine and Jenkins deployment engine.

---

## 10.5 Release Scan Acceptance

Given a configured incoming directory containing:

- one complete valid Release;
- one incomplete Release copy;
- one invalid candidate;

the Platform shall:

1. detect the complete candidate;
2. classify it as ready for import;
3. ignore or classify the incomplete candidate safely;
4. identify the invalid candidate;
5. avoid importing anything automatically;
6. return structured scan results.

The scan shall not create an active deployment.

---

## 10.6 Release Import Acceptance

Given a valid compliant Release, the Platform shall:

1. parse its Manifest;
2. verify the Compliance Report;
3. verify checksums;
4. calculate or verify its fingerprint;
5. check Contract and Manifest versions;
6. check local architecture compatibility;
7. create or locate the application record;
8. register immutable Release metadata;
9. create the Release Storage record;
10. mark the Release as   AVAILABLE  .

The imported Release shall appear in:

  
GET /applications/{application_id}/releases
  

Import shall not create a deployment attempt.

---

## 10.7 Import Failure Acceptance

The Platform shall reject candidates where:

-   release.yaml   is missing;
- Manifest parsing fails;
- Compliance Report is missing or failed;
- checksum validation fails;
- Contract version is unsupported;
- architecture is incompatible;
- the same application/version exists with a different fingerprint.

For every rejection:

- a stable error code shall be returned;
- no partially valid Release record shall remain;
- the existing valid Release shall remain unchanged;
- diagnostic information shall be available.

---

## 10.8 Application Registration Acceptance

When the first Release for a new application is imported, the Platform shall create one application identity using the Manifest slug.

When later Releases of the same application are imported, they shall attach to the existing application.

The Platform shall not create:

  
HCAT 1.0.0
  

and:

  
HCAT 1.1.0
  

as two unrelated applications.

---

## 10.9 Available Actions Acceptance

For an application with no active deployment and a Release supporting fresh installation:

  
INSTALL
→ allowed
  

For an installed application with a compatible target Release:

  
UPDATE
→ allowed
  

For an unsupported downgrade:

  
DOWNGRADE
→ not allowed
  

The endpoint shall provide explicit blocking reasons.

The UI shall disable or hide prohibited actions based on this result.

Jenkins shall receive the same decision.

---

## 10.10 Installation Planning Acceptance

Given an available installable Release, the Platform shall return an installation plan containing:

- application and Release identity;
- canonical path;
- required configuration inputs;
- input types;
- secret classifications;
- generated values;
- operator values;
- port requirements;
- expected services;
- database initialization behavior;
- mandatory verification checks;
- blocking issues.

Planning shall not:

- invoke installation;
- create containers;
- change active state;
- write deployment history as success.

---

## 10.11 Configuration Validation Acceptance

The Platform shall accept valid deployment inputs and reject:

- missing required fields;
- unknown configuration keys;
- incorrect datatypes;
- invalid port ranges;
- unavailable ports;
- unsafe paths;
- malformed secret submissions.

Secret values shall not appear in:

- validation responses;
- logs;
- events;
- ordinary database query results.

---

## 10.12 Fresh Installation Acceptance

Given:

- a valid imported Release;
- no active deployment;
- valid configuration;
- available required ports;

when installation is requested, the Platform shall:

1. return   202 Accepted  ;
2. return an operation ID;
3. create an installation-attempt record;
4. expose operation progress;
5. prepare deployment configuration;
6. invoke the declared installation script;
7. capture exit status and logs;
8. run mandatory verification;
9. create a successful deployment record;
10. mark exactly that deployment active;
11. return a successful   DeploymentResult  .

The active version shown in the UI and API shall match the installed Release.

---

## 10.13 Installation Failure Acceptance

Tests shall deliberately cause failures at several stages.

### Invalid configuration

Expected:

- failure before script execution;
- no deployment activation;
- structured input error.

### Installation-script failure

Expected:

- failed operation record;
- script exit code retained;
- no active deployment;
- logs available.

### Verification failure

Expected:

- lifecycle script may report success;
- deployment operation reports failure;
- failed verification checks are visible;
- target Release does not become active.

### Operational Registry commit failure

Expected:

- operation reports registry failure;
- host reconciliation is required;
- Platform does not claim a normal successful active state.

---

## 10.14 Update Planning Acceptance

Given an active older Release and an available compatible target Release, the Platform shall produce an update plan showing:

- source Release;
- target Release;
- transition validity;
- preserved configuration;
- required backup;
- database migration;
- new required inputs;
- mandatory verification;
- available recovery behavior.

An unsupported source version shall produce a blocking transition error.

---

## 10.15 Successful Update Acceptance

Given:

  
Active Release: 1.0.0
Target Release: 1.1.0
Transition: supported
  

the Platform shall:

1. create an update-attempt record;
2. preserve existing configuration and secret references;
3. create mandatory backup;
4. invoke the declared update script;
5. capture migration evidence;
6. run mandatory verification;
7. mark the update successful;
8. activate Release   1.1.0  ;
9. retain the   1.0.0   deployment in history;
10. retain the backup record;
11. expose the complete operation timeline.

Only one active deployment shall remain.

---

## 10.16 Failed Update Acceptance

A deliberately failed update shall prove:

1. the failed attempt remains in history;
2. failure stage and error code are retained;
3. the previous successful active-deployment record remains unchanged;
4. the target Release does not become active;
5. host drift or partial state is reported where applicable;
6. recovery guidance is returned;
7. backup evidence remains available;
8. retry creates a new operation rather than rewriting the failed one.

---

## 10.17 Transition Protection Acceptance

The Platform shall reject:

- update when no active deployment exists;
- fresh install when an active deployment conflicts;
- update to the same active Release;
- unsupported downgrade;
- unsupported source-to-target transition;
- target Release belonging to another application;
- unavailable target Release Package.

Each rejection shall occur before lifecycle execution.

---

## 10.18 Mandatory Backup Acceptance

For an update requiring backup:

- the update script shall not begin before backup success;
- backup failure shall block update;
- backup record shall identify application and source deployment;
- backup artifact shall exist;
- checksum shall be stored where supported;
- backup result shall be queryable.

The test shall confirm no update execution occurred after backup failure.

---

## 10.19 Verification Acceptance

The Platform shall execute and record verification checks including, where applicable:

- Release identity;
- Docker services;
- expected image tags;
- backend health;
- frontend availability;
- database connectivity;
- migration state;
- persistent configuration;
- selected ports;
- offline runtime.

The result shall preserve each check independently.

One failed mandatory check shall cause the overall verification result to fail.

---

## 10.20 Host Inspection Acceptance

The Platform shall inspect actual host state and return:

- deployment path status;
- Compose project identity;
- expected containers;
- observed image tags;
- container states;
- health states;
- expected ports;
- listening ports.

Host inspection shall be read-only.

It shall not repair, restart, or rewrite application state.

---

## 10.21 Drift Detection Acceptance

After manually changing host state, such as:

- stopping a required container;
- changing a port;
- running an unexpected image tag;

the Platform shall:

1. detect the mismatch;
2. return   DRIFT_DETECTED   or another correct state;
3. identify expected and observed values;
4. preserve the recorded active deployment;
5. avoid silently correcting history;
6. offer or reference an explicit recovery or repair path where supported.

---

## 10.22 Backup and Restore Acceptance

The Platform shall successfully:

1. create a backup;
2. record its identity;
3. record storage location;
4. verify existence and checksum where supported;
5. list the backup;
6. restore it through an approved entry point;
7. run post-restore verification;
8. record restoration as a separate operation.

A backup belonging to another application shall be rejected.

---

## 10.23 Recovery Acceptance

Given a failed deployment-changing operation and a valid recovery mechanism, the Platform shall:

1. create a separate recovery operation;
2. reference the failed operation;
3. reference the backup or previous state;
4. execute the declared recovery procedure;
5. verify the resulting application;
6. record recovery success or failure;
7. preserve the original failed operation;
8. expose the resulting active Release.

Recovery shall not rewrite the failed update as successful.

---

## 10.24 Operation Polling Acceptance

For every long-running operation:

1. the initiating API returns an operation ID;
2.   GET /operations/{id}   returns current state;
3. progress or current stage is available;
4. terminal state is eventually returned;
5. events remain ordered;
6. logs remain available;
7. UI and Jenkins receive the same result.

The API shall not require one HTTP request to remain open for the entire installation.

---

## 10.25 Idempotency Acceptance

Given a state-changing request with an   Idempotency-Key  :

1. the first request creates one operation;
2. a retry with the same caller, key, and request returns the existing operation;
3. no duplicate deployment attempt is created;
4. reuse of the same key with materially different content is rejected.

This shall be tested at minimum for installation and update.

---

## 10.26 Operation Lock Acceptance

While an update is running for HCAT:

- a second HCAT update shall be rejected;
- HCAT restore shall be rejected;
- HCAT installation shall be rejected;
- ordinary HCAT status queries shall still work.

After the operation completes or fails, the lock shall be released.

Interrupted operations shall not leave an invisible permanent lock.

---

## 10.27 Restart and Interruption Acceptance

During a controlled test, interrupt the Platform backend or VM while an operation is running.

After restart, the Platform shall:

- identify the incomplete operation;
- preserve its record;
- report that execution was interrupted;
- inspect for possible host changes;
- release or resolve stale locks safely;
- require reconciliation or recovery where needed;
- avoid declaring success without evidence.

---

## 10.28 History Acceptance

The Platform shall preserve:

- imported Releases;
- successful deployments;
- failed deployments;
- verification runs;
- backups;
- recovery attempts;
- operation events;
- timestamps;
- source and target versions.

Removing an old Release Package from storage shall not erase its historical records.

The UI and API shall display at least the ten most recent deployment-related events or Releases for an application.

---

## 10.29 Error Contract Acceptance

Tests shall prove:

- expected failures return stable error codes;
- HTTP status mapping is consistent;
- operation ID appears when an operation exists;
- request ID appears in responses;
- retryable state is correctly represented;
- errors identify the failed stage;
- script exit codes are retained;
- secret values are absent;
- UI and Jenkins receive equivalent error facts.

---

## 10.30 Security and Secret Acceptance

The Platform shall prove that:

- arbitrary shell commands cannot be submitted through the API;
- unknown lifecycle scripts cannot be selected;
- secret values are masked;
- logs do not expose secrets;
- Release Packages are not modified with production credentials;
- ordinary GET endpoints do not return plaintext secrets;
- Jenkins authentication is distinct from ordinary operator access.

This Version 1 criterion focuses on controlled behavior, even within the air-gapped environment.

---

## 10.31 UI Acceptance Boundary

The Platform UI shall be considered functionally sufficient when an operator can:

1. view known applications;
2. scan and import Releases;
3. view installed and available versions;
4. view available actions;
5. prepare installation or update;
6. enter required configuration;
7. initiate operations;
8. observe progress;
9. view final results;
10. inspect history and errors.

## 11.6 Operation Worker

Long-running operations shall not require the initiating HTTP connection to remain open.

The Platform shall contain an operation worker or equivalent execution mechanism that can process:

```

The initial implementation may use:

- a database-backed work queue;

The selected implementation shall preserve:

- operation identity;
- ordered stages;
- database-backed status;
- restart visibility;
- operation locking;
- logs;
- terminal result.

## 11.9 Lifecycle Execution Service

The lifecycle execution component shall execute only approved Manifest-declared entry points.

It shall receive a structured internal request such as:

```
{
  "operation_id": "uuid",
  "operation_type": "INSTALL",
  "release_path": "/opt/rah/releases/incoming/HCAT_Release_1.1.0",
  "entrypoint": "scripts/install_offline.sh",
  "working_directory": "/opt/rah/work/uuid",
  "environment_reference": "/protected/path/production.env",
  "timeout_seconds": 1800
}
```

It shall return structured execution evidence:

```
{
  "status": "SUCCEEDED",
  "exit_code": 0,
  "started_at": "2026-08-06T16:00:00+03:00",
  "completed_at": "2026-08-06T16:04:00+03:00",
  "stdout_log": "/var/log/rah/operations/uuid.stdout.log",
  "stderr_log": "/var/log/rah/operations/uuid.stderr.log"
}
```

The lifecycle executor shall not determine final deployment success.

Its result becomes one input to the complete Platform workflow.

# 12. Final Platform Contract

## 12.1 Product Definition

The RAH Offline Installation Platform is a web-based operational engine deployed in the offline Debian environment.

It consumes standardized immutable Application Releases and provides controlled Release discovery, import, installation, update, verification, backup, recovery, operational visibility, and historical recording.

---

## 12.2 Client Model

The Platform has one backend engine and two principal clients:

```
Human operator
      ↓
Platform web UI
      ↓
Platform HTTP API
      ↓
Platform Backend Engine
```

and:

```
Jenkins
      ↓
Platform HTTP API
      ↓
Same Platform Backend Engine
```

The UI and Jenkins shall not implement separate operational logic.

---

## 12.3 External Interface

The Platform shall expose:

```
HTTP API base:
 /api/v1
```

The Platform frontend shall use that API.

Jenkins shall use that API.

State-changing operations shall normally return:

```
202 Accepted
+
operation_id
```

The caller shall retrieve progress and the final result through the operation API.

---

## 12.4 Operational Registry

The Platform shall use PostgreSQL as its persistent Operational Registry.

The Registry shall preserve:

- known applications;
- imported Releases;
- Release-storage state;
- deployment attempts;
- active deployment;
- deployment configuration;
- operation events;
- verification runs;
- backups;
- recovery attempts;
- failure history.

Historical operational records shall not be overwritten by later success.

---

## 12.5 Release Relationship

The Platform shall consume, but not modify:

- Release Manifest;
- Compliance Report;
- checksums;
- Docker image archives;
- lifecycle scripts;
- database resources;
- configuration templates;
- verification resources;
- documentation.

An invalid Release shall be rejected rather than repaired.

---

## 12.6 Deployment Relationship

The Platform shall execute application-specific lifecycle behavior only through Manifest-declared entry points.

The Platform backend shall own:

- request validation;
- operational planning;
- lifecycle invocation;
- Docker integration;
- verification;
- Registry updates;
- error handling;
- operation history.

The lifecycle script shall not independently decide Platform operational truth.

---

## 12.7 Deployment Success Definition

A deployment is successful only when:

```
Lifecycle script succeeds
+
Mandatory verification succeeds
+
Operational Registry commit succeeds
```

Only then may the target deployment become active.

---

## 12.8 Active-State Rule

Each application shall have no more than one active deployment.

A failed install or update shall not activate its target Release.

A successful update shall preserve the previous deployment in history while making the target deployment active.

---

## 12.9 Failure Rule

Every failed operation shall remain historically visible.

Failure evidence shall include:

- operation identity;
- failed stage;
- stable error code;
- related application and Releases;
- script exit code where applicable;
- verification evidence;
- logs;
- timestamps;
- recovery requirement.

A retry shall create a new operation.

---

## 12.10 Verification Rule

Installation and update shall require mandatory verification.

Verification shall record individual checks and structured evidence.

Script success without verification success shall not produce deployment success.

---

## 12.11 Safety Rule

The Platform shall not accept arbitrary shell commands.

API clients may request only approved Platform operations.

The backend shall map those operations to trusted workflows and Manifest-declared entry points.

The Platform shall revalidate prerequisites immediately before execution.

---

## 12.12 Concurrency Rule

The initial Platform shall serialize conflicting deployment-changing operations.

Only one conflicting operation may run against an application at a time.

The first implementation may use one global operation lock if that simplifies correctness.

---

## 12.13 Configuration Rule

The Release Manifest defines which deployment inputs exist.

The Platform records the actual values selected for a deployment.

Secret values shall not appear in ordinary API results, logs, or immutable Releases.

Existing deployment configuration shall normally be preserved during update.

---

## 12.14 Backup and Recovery Rule

Mandatory backup shall complete before update begins.

Recovery shall be represented as a separate operation.

The Platform shall not silently perform destructive rollback after failure.

Recovery success shall require verification and shall preserve the original failure record.

---

## 12.15 Host-State Rule

The Platform shall distinguish:

```
Recorded Platform state
```

from:

```
Observed host state
```

Reconciliation shall report drift without silently rewriting deployment history.

---

The Offline Platform answers one operational question:

> **Which compliant Application Releases are available on this offline system, what deployment operations are permitted, what was executed, what succeeded or failed, and what deployment is currently verified and active?**

Its canonical initial implementation is:

```
Runtime:
Docker Compose on offline Debian

Frontend:
Web interface

Backend:
Python HTTP API and operational engine

Database:
PostgreSQL Operational Registry
