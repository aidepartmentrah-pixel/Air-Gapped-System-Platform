# The two engines

## Engine 1 — Packaging Software

Its capability groups should probably be:

|Capability group|Purpose|
|---|---|
|Project initialization|Make an ordinary repository ready for RAH packaging|
|Project inspection|Discover deterministic facts from source, Git, Docker, configuration, and files|
|Engineering assistance|Generate Claude request and validate returned engineering answers|
|Release planning|Select version and preview what will be generated|
|Release construction|Build images and construct the candidate Release|
|Contract validation|Validate the candidate against the Release Contract|
|Release finalization|Generate checksums, compliance evidence, freeze Release, update project state|
|Qualification coordination|Prepare or request offline qualification and receive its evidence|
|Information retrieval|Show project state, Release details, validation outcomes, and logs|
Do not assume that every capability must become a separate CLI command. First map the capabilities; then choose the clean command surface.


## Engine 2 — Offline Platform

Its capability groups should probably be:

| Capability group       | Purpose                                                      |
| ---------------------- | ------------------------------------------------------------ |
| Release discovery      | Find candidate Releases in configured storage                |
| Release import         | Verify and register a supplied Release                       |
| Application querying   | Show known applications and active deployments               |
| Release querying       | Show available and historical Releases                       |
| Deployment preparation | Validate compatibility and collect inputs                    |
| Installation           | Execute fresh installation                                   |
| Update                 | Transition from active Release to target Release             |
| Verification           | Compare expected, recorded, and actual host state            |
| Backup and recovery    | Protect and restore operational state                        |
| Operation tracking     | Show progress and results of long-running work               |
| History and audit      | Show previous attempts, outcomes, and evidence               |
| Host reconciliation    | Detect drift between database state and actual machine state |


# Recommended order for completing Stage 4.5

## Phase A — Shared foundation

Write first:

1. Purpose and scope.
2. Interface architecture.
3. Shared naming conventions.
4. Shared IDs, timestamps, and version formats.
5. Shared operation-status model.
6. Shared error model.
7. Shared result envelope.

This gives both products one language.

## Phase B — Packager functionality and CLI

For every command:

```
init
inspect
prepare-engineering-request
validate-engineering-answers
plan
package
validate
finalize
qualify
show-status
```

We may later merge or remove commands. Do not freeze the inventory before discussing what each actually does.

For each command, specify:

- purpose;
- arguments;
- request object;
- result object;
- state changes;
- failures;
- exit codes;
- tests.

## Phase C — Platform functionality and HTTP API

Define resources and operations:

```
applications
releases
imports
deployments
verifications
backups
operations
```

Then define exact endpoints only after the resource model is clear.

For example:

```
POST /api/v1/releases/scan
POST /api/v1/releases/{release_id}/import
POST /api/v1/applications/{slug}/install
POST /api/v1/applications/{slug}/update
POST /api/v1/applications/{slug}/verify
GET  /api/v1/operations/{operation_id}
```

The current document’s separation between application endpoints, Release discovery/import, install, update, verification, recovery, and operation status is a sound starting structure.

## Phase D — Integration contract

Then define:

- how Jenkins invokes Packager;
- how it reads exit codes and JSON results;
- how it transfers a Release;
- how it calls Platform;
- how it polls an operation;
- how it gathers qualification evidence;
- how retries behave;
- what authentication it uses.

## Phase E — Acceptance tests

Stage 4.5 is not complete merely because an OpenAPI file or CLI table exists.

It is complete when the contracts are testable.

Examples:

```
Given a valid initialized repository,
when package is invoked,
then one finalized Release is returned.

Given Docker build failure,
when package is invoked,
then Project Version State remains unchanged.

Given an unsupported Release Contract,
when Platform import is invoked,
then import is rejected with a stable error code.

Given an installation request,
when the operation is accepted,
then the API immediately returns operation_id.

Given operation_id,
when status is requested,
then the current state and final result are returned.
```
